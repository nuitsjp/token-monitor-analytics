## 1. 利用許容量の推定

<a id="observation-validity"></a>
### 1.1 観測の組と採用条件

推定には、全Hubの端末・ツール報告から第1.5節の規則で選んだ論理利用額ソースと、そのソースに対応する全契約・利用枠の消費率を、比較点ごとに一組として使用します。provider の固定 allowlist や特定サービスの実契約を事前列挙することは共通要件にしません。各 provider について同じIDの `clientCosts[tool]` と `clientHealth.clients[tool]` を対応付け、利用枠の対応情報が得られる範囲で共通処理します。同一SSEイベントにすべての値が含まれることは要求しません。採用した論理利用額ソースと契約の正常で新しい観測が前回比較点より進んだ時だけ比較点を確定します。GET API で取得する日次・月次実績から現在値や過去の推定値を生成することはありません。累積額には端末報告の `periods.allTime.clientCosts[tool]` を使います。

同じ比較点に採用するソース間の測定時刻差による微小誤差は許容しますが、数値の許容幅は未指定です。取得失敗や帰属・継続性が不明な値を有効な観測として扱うことはありません。

[上流の更新状態と時刻の意味](interfaces.md#limit-fields) に基づき、以下のルールを適用します。

- 利用枠のみの更新では実績値が更新前のまま残る場合があるため、同一レコード内の値であっても同時測定とはみなしません。
- 利用枠の取得失敗時にも直前の成功値が残存する場合があるため、値の存在や端末更新日時、`stale: false` のみをもって取得成功や鮮度を判断しません。
- 更新状態と時刻から比較可能性を担保できない場合は「推定不可」とし、取得値の表示のみ継続します。

利用実績の収集日時には、対象クライアントの `clientHealth.clients[tool].collection.lastSuccessAt` があればそれを使い、未提供時だけ既存の収集時刻である `clientHealth.observedAt` を使います。対象クライアントの `overall` が `healthy` または `waiting`、`source.state` が `detected`、`collection.state` が `direct` または `ok` であることも必要です。最新通知にない端末、gap中の端末、`stale: true` の端末、利用額・有効な収集日時・正常な収集状態を確認できない端末は推定用の利用額ソースから除外し、残る有効なソースで推定を続けます。取得済みの数値0は有効ですが、欠落値を0で補完しません。

利用枠は `status: ok`、有効な `updatedAt`、非 stale を要求します。消費率は `usedPercent` を優先し、なければ `100 - remainingPercent`、最後に正の `limit` に対する `100 * used / limit` の順で導出します。導出結果は有限な 0〜100 の値だけを採用し、`used` と `limit` から導出した場合はその `limit` を `percentageLimit` として根拠へ保存します。除外後に残った利用額ソースが持つ契約集合の全契約について、利用枠の更新日時が前回比較点より進み、率を正常に取得できることが必要です。率の欠測・競合はその推定を停止します。値が同じでも測定日時が進んだことは観測として記録しますが、数値が同じ再観測による推定結果の追記は行いません。順序照合と比較再開は第1.6節、担当と保存境界は設計書第5.2〜5.3節に従います。

### 1.2 計算式と成立条件

**設定の適用範囲（2026-09-13 利用者指示）:** 通常は基準プラン・倍率の入力なしで推定します。同じツールの利用額に異なるプランの契約が混在し、まとめて推定する場合だけ、基準プランと利用上限倍率を設定します。ツールや端末を利用者に事前列挙させることを推定の共通前提にしません。

| 取得データの関係 | 推定方法 | 基準プラン・倍率の入力 |
| --- | --- | --- |
| 単一契約に対応する利用額を取得できる | 当該契約の利用額増分と消費率増分から算出する | 不要 |
| 同一プランの複数契約の利用額が混在する | 全契約に共通の利用許容量を算出する | 不要 |
| 異なるプランでも利用額を契約ごとに分離できる | 各契約を個別に算出する | 不要 |
| 異なるプランの複数契約の利用額が混在する | 基準プランの許容量と各プランの倍率を使って算出する | この場合だけ必要 |

単一契約では、比較可能な2つの観測のツール全体 API 換算額増分を ΔC（USD）、対象枠の消費率増分を Δp（パーセントポイント）とし、その枠の利用許容量を `100 × ΔC / Δp`（USD）として算出します。

共有利用額の場合は、対象契約 i の対象枠における消費率増分を Δpᵢ、基準プランに対する利用上限倍率を mᵢ、ツール全体の共有利用額の増分を ΔC とし、基準プランのその枠の利用許容量 B を次の式で算出します。

```text
B = 100 × ΔC / Σ(mᵢ × Δpᵢ)
各契約の推定利用許容量 = mᵢ × B
```

同一プランの契約だけをまとめる場合は、同じ枠キーの許容量を共通とし、すべての mᵢ を内部的に1として計算します。利用者による基準プランの登録は不要です。異なるプランをまとめる場合は、基準プランの倍率を1とし、同じ枠キーについて設定された正の倍率を用います。料金比やプラン名から倍率を推測しません。

ΔC はツール全体の API 換算額という一つの参考値であり、複数の利用枠へ課金額として按分しません。各枠キーの消費率から得た利用許容量は枠ごとの参考値として独立に扱い、枠別の推定値を合算してツール全体や契約の利用許容量とはしません。

以下の条件をすべて満たす場合のみ算出します。

1. 採用した論理利用額ソースの利用額増分と、そのソースに対応する契約集合の利用枠消費を用いること。除外端末がある場合は取得できた費用範囲だけの参考値として算出し、共有利用額を契約別の実績へ分離することは要求しません。
2. 同一契約を複数端末が報告しても同じ枠キーの消費率を一度だけ数え、利用額ソースも一度だけ加算すること。短時間枠と週次枠など異なる枠キーを一つの分母に混在させないこと。
3. 全契約の消費率を共通の比較区間の両端で取得でき、各契約について同一の対象期間内であること。リセット、欠測、契約集合・プラン・倍率の変更をまたぐ計算はしません。契約間でリセット予定日時そのものが一致する必要はありません。
4. ΔC と分母がともに正であり、各 Δpᵢ が取得済みの非負値であること。取得済みのゼロは含められますが、欠落・取得失敗をゼロで補完しません。
5. 定額制の割合メーターであり、`kind`・`metric` が `credits`・`balance` ではなく、`boundaryKind` が未指定または `reset` で、`showMeter` が `false` ではないこと。

共有利用額は観測された合計のまま保存・表示し、計算から導いた契約別の量を観測実績として扱いません。設定した倍率は利用許容量の関係を表すものであり、共有利用額を実績として按分する比率ではありません。

### 1.3 比較区間と対象期間

同一対象期間内において比較可能な最初と最新の観測を用い、最も広い区間の差分から計算します。新たな観測を受信した際も起点を維持して区間を延伸します。同一端末・同一対象期間の途中で累積額が減少しても、それのみを理由に起点をリセットせず、最初と最新の差分に第1.2節の成立条件を適用します。

共有利用額からの推定にも、各比較時点で採用された論理利用額ソースとその契約集合がそろった最初と最新の観測を用います。各契約の期間と継続性は個別に確認し、除外後に残った全契約と利用額ソースで第1.2節の条件を満たす区間だけを計算対象とします。

利用枠自体の同一性判定は [設計書 第5.1節](../../docs/architecture.md#identity) に従い、同一枠を特定した上でおのおの対象期間を判定します。

| 条件 | 扱い |
| --- | --- |
| 有効な `resetsAt` が同一 | 比較起点を維持し、最新観測との差分から算出する。 |
| 有効な `resetsAt` が更新 | 新期間へ移行したものとして起点を再設定する（期間をまたぐ差分計算は行わない）。 |
| `used` / `limit` から導出した `percentageLimit` が更新 | 同じ `resetsAt` でも上限変更前後を同じ比較区間に含めず、変更後の新しい観測から比較を再開する。 |
| `resetsAt` が欠落または不正 | 対象期間を特定できないため「推定不可」とする。 |
| 同一 `resetsAt` で消費率が減少 | データの継続性が不明となったため「推定不可」とし、不明区間をまたぐ計算は行わない。 |

`resetsAt` は次回リセットの予定時刻であり、リセット発生の通知ではありません。予定時刻を過ぎた枠は新しい枠の取得まで採用しません。日時は文字列表記でなく UTC の時点として比較します。欠測や過去データの再受信後の再開は第1.6節に従います。

### 1.4 結果の保存と表示

新たな共通推定結果は、算出日時・比較区間・算出根拠とともに、ツールと枠キーごとの系列として時系列で追記保存し、過去の結果を改変または遡及再計算することはありません。同一内容の再受信によって新しい実績や推定結果として二重計上することも防止します。枠ごとの結果を合算せず、ツール全体の API 換算額を枠別課金へ按分しません。旧Hub単位の推定結果は旧方式の履歴として保持し、共通推定とは別の履歴範囲で参照します。

推定条件を満たさない場合はその理由を表示し、過去に算出した結果が存在する場合は算出日時とともに併記します。なお、「機能未実装」の状態は「データ上の推定不可」と区別して表示します。「推定済み」「観測待ち」「推定不可」「設定が必要」を表示し、保存した共通推定と状態変更の履歴を新しい順に20件ずつ読み込めます。推定が止まった際の数値は「前回の推定」と明示します。除外端末がある推定は `partial: true` とし、「取得できた端末の利用額に基づく参考値」と除外端末・理由を表示します。除外端末の消費に対応する費用を含まないため、推定値が本来より低くなる可能性があります。根拠として起点・比較先の観測ID、採用した論理利用額ソース、利用額、消費率、各測定日時、リセット予定日時、契約集合、プラン、使用倍率を参照できます。Hub・端末の画面から関連契約・推定へ移動でき、Hub別の実績を確認できます。履歴照会は保存済み結果の読み出しだけを行います。

推定履歴は `/api/estimates/history` で取得します。`scope=global`（既定）は共通推定、`scope=legacy` は旧Hub単位方式の履歴を返します。`hubId` は任意の絞り込み、`seriesId`・`before`・`limit` は各scopeで指定でき、旧方式と共通推定の履歴IDはscopeをまたいで同一視しません。共通契約のカードと推定は `scope=global` の結果に対応し、旧方式は「旧方式の履歴」と明示します。集計方法または対象構成が変わった旧viewは前回結果を保持したまま非activeとし、既定で閉じた「以前の集計方法・対象構成の記録」に表示して現在値には使いません。

### 1.5 利用額・契約集合・利用枠の対応

上流の client と provider の共通IDでツールを対応付けます。表示名の類似で照合しません。特定サービスの allowlist や実契約の事前列挙は設けず、各 provider について同じIDの `clientCosts[tool]`、`clientHealth.clients[tool]`、利用枠行を共通規則で扱います。必要な対応情報が取得できない対象は取得値と理由を表示し、推定値を生成しません。Claude の組織識別不足は [Issue #34](https://github.com/nuitsjp/token-monitor-analytics/issues/34) に残しますが、共通実装の適用をブロックしません。

Grok も全 provider 共通の推定対象です。契約の対応付けには既合意の `accountEmail` trim・lowercase・SHA-256（`email:` 接頭辞）キーを使い、トークンの `accountKey` が変わっても同一契約へ束ねます。正規化後のメールアドレスが異なる場合は別契約です。`accountEmail` が欠落した行は契約を生成せず、端末の取得情報として保持します。

- 利用実績の収集範囲は、Cursorだけをアカウント全体（`usageScope: account`）、他ツールを端末単位（`usageScope: device`）として扱います。端末単位の論理利用額ソースはHub・端末ID・ツールの組です。Cursorの論理利用額ソースはツールと完全一致する契約ID集合の組であり、Hubや代表端末の違いを同一性に含めません。契約の観測上の識別には、全 provider で `provider` と `accountKey` の組を使い、Hubを識別子に含めません。これは公式契約IDではなく、上流が生成する識別子です。Grokだけは、既合意の `accountEmail` trim・lowercase・SHA-256（`email:` 接頭辞）キーを使い、トークンの `accountKey` 変更では契約を分けません。契約キーが欠落する対象は推定不可とし、端末の取得情報は表示します。
- Cursorの同じ論理利用額ソースを複数端末・Hubが報告した場合は、利用実績の収集日時が最新の一件だけを採用します。同時刻の利用額が異なる場合は `conflicting_usage` としてその論理ソースを不明扱いにします。契約ID集合が一部だけ重なる別集合は `overlapping_usage` とし、数値が同じでも統合しません。代表端末だけが交替しても同じ系列を維持し、採用する論理利用額ソース集合が変わった場合は新しい系列・比較基準を作ります。
- 同じ観測上の契約を報告したソースをHub横断で結び、その接続した集合を一つの推定対象にします。契約とソースの関係は多対多で保持します。別々の契約・別々のアカウントで分離できる集合は、プランが異なっても独立して推定します。プラン名は契約の属性であり、契約の同一性判定には使いません。
- 各論理利用額ソースの累積額を一度ずつ加算し、除外後に残った契約・枠の率を一度だけ使います。複数Hub・端末からの同一契約の報告は、正常かつ stale でない最新日時のものを選びます。同時刻で率、リセット予定日時、導出に使った `percentageLimit`、明示プラン、枠の採否条件が食い違う報告は `conflicting_rate` として採用しません。同じSSE通知に全ソースが含まれることは要求しません。
- 枠のキーは `[kind, windowMinutes, limitId, additionalがtrueか, metric]` です。未提供は `null` とし、配列位置・更新日時・リセット予定日時をキーにしません。`limitId` がない場合に限り、前後の空白を除いた `label` があればキーへ追加します。異なるラベルは別の枠として扱い、同じキーが同一provider行内で重複する場合は識別不能（`ambiguous_window`）です。異なる枠キーを共有式へ混ぜません。
- `kind`、`additional`、任意の `limitId`、`metric` の組合せは共通規則の対象とします。ただし、`kind` または `metric` が `credits`・`balance` の枠、明示された `boundaryKind` が `reset` 以外の枠、`showMeter` が `false` の枠は推定対象から除外します。残る枠について、消費率は `usedPercent`、`100 - remainingPercent`、`100 * used / limit`（正の `limit`）の順で導出し、有限な 0〜100 だけを採用します。最後の方法で導出した場合は `limit` を `percentageLimit` として根拠へ保存し、その変更を比較境界とします。
- プランは全 provider で明示された `planLabel` を契約の属性として使います。既知の Codex wire で `planLabel` が空の場合に限り、従来の `accountLabel` をプラン属性として読み取ります。`accountLabel` を一般的なプラン名とはみなさず、表示名や料金からプラン・倍率を推測しません。単一契約ではプラン名がなくても推定できますが、複数契約の共有利用額でプランを識別できない場合は `unknown_plan` として推定不可です。
- 推定用の利用額を採用できない端末は、その理由とともに対象から除外します。除外後に利用額ソースが一件も残らない場合は推定不可です。残る利用額ソースに対応する契約の消費率は必要であり、欠測・取得失敗・競合をゼロや対象外として扱わず停止します。未観測の契約利用や他の収集範囲外の消費が存在しないことを、APIだけで証明するものではありません。

以前の「既知の全端末・全利用額ソースがそろうまで停止し、残るソースだけでは部分計算しない」という規則は、最新の利用者指示により上記の除外・部分推定へ変更しました。契約・端末のn:n関連と元の観測は削除せず、推定対象からの一時的な除外と履歴保持を分けて扱います。

Grok の現在・過去の対応は次のとおりです。各端末の `status: ok` 行にあるメールアドレスの集合を現在の契約集合とし、正常行がない場合は全Grok行から最新 `updatedAt` の時刻を先に選び、その時刻の `notConfigured` と `disabled` の行を除外して失敗行のメールアドレスを保持します。同じメールアドレスの古いトークン行が `unavailable` でも同一契約へ束ね、別メールアドレスの古い `unavailable` 行は過去契約として保持します。複数メールアドレスの `ok` 行が同時に報告された場合は、契約と端末の n:n 関係を維持します。代表表示は正常かつ非 stale の報告から最新 `updatedAt` を選び、同時刻で利用枠の比較対象値（率、枠種別・ID、対象期間等）が異なる場合は `conflicting_rate` を表示します。`label`・`detail`・`source`・配列順だけの差は比較対象外とします。Hub内・端末内の同一Grok契約へのリンクは一件にまとめます。

### 1.6 比較の中断と再開

各共通推定対象で起点、直近の比較先、各論理利用額ソース・消費率の最大測定日時を保持します。古い測定日時、同時刻で異なる値、同一期間での率の減少を検出したら関係する起点と比較先を破棄し、過去の結果を残します。同時刻の複数報告で率、リセット予定日時、導出 `percentageLimit`、明示プラン、枠の採否条件（`showMeter`・`boundaryKind` 等）が異なる場合も競合として扱い、推定を停止します。リセット予定日時、`percentageLimit`、契約集合、プラン、倍率、採用する論理利用額ソース集合の変更も比較区間の境界です。端末単位ソースの端末構成が変わった場合は旧系列の履歴を残し、新しい構成の系列で開始します。Cursorでは同じ契約ID集合を報告する代表端末だけが交替しても同じ系列を維持します。

不正な通知、Hub切断、Hubの利用枠未取得、プロセス再起動では関係する推定対象の比較を直ちに中断します。次の正常なSSE通知で欠測・stale・取得不能な端末を除外し、採用可能な論理利用額ソースとその契約から対象を再構成します。新しい構成の最初の観測を起点とし、その後の比較可能な観測を待つため、境界前の値や再接続直後の古いスナップショットをまたいで計算しません。利用枠だけ先にリセットした通知でも、古い利用額を新期間の起点にしません。切断・不正・未取得Hubに関係しない推定対象は停止しません。

通常区間で累積額だけが減った場合は起点を維持します。起点からの利用額増分または重み付き消費率増分が正でない場合は算出せず、正になった後の観測で同じ起点から比較します。保存失敗・参照不能の境界は S6 に従い、停止中の値を後から架空の観測として取り込みません。

<a id="display"></a>
## 2. 取得情報と状態の表示

プロバイダーやプランを問わず、取得した利用枠・消費率・API 換算額を、推定可否にかかわらず画面に表示します。利用額には実際の集計単位（Hub、端末、ツール等）を明記し、特定できない契約への配分は行いません。推定結果もツール全体額と枠ごとの消費率から得た参考値であり、枠別課金への按分や枠別結果の合算は表示しません。また各項目には取得状態と更新日時を表示し、未取得の数値をゼロで補完することはありません。

**取得状態と利用枠の表示（2026-09-13 利用者指示）:** 取得状態が `notConfigured` のプロバイダー行は既定では画面から隠します。画面上部の「未設定の取得元も表示」トグルをオンにすると、同じ現在値と状態を再表示できます。保存値や API の内容はこの表示切替で変更しません。利用枠のラベルが空の場合、Codex の `kind: weekly` は `Weekly` と表示します。利用枠のパーセント表示とメーターは消費済み率ではなく残量率を使い、未使用時を100%として使用に応じて減少させます。`remainingPercent` がない場合は `100 - usedPercent` を表示に用い、推定計算で使う `usedPercent` の意味は変更しません。

**複数Hubの全体表示（2026-09-13 利用者指示、利用範囲の更新）:** 画面の最上段とHubごとに、`today`・`month`・`allTime` の `costUsd` と `totalTokens` を表示します。端末単位のツールはHubの保存済み集計を使います。Cursorは同じ契約ID集合を持つ端末報告がアカウント全体実績を重複して配信するため、各期間の `clientCosts.cursor` と `clients.cursor` を論理利用額ソースごとに一度だけ数えるよう補正します。補正値は、提供されたHub集計の完全な合計から、選ばなかった重複報告について当該期間に存在するCursor内訳だけを差し引いて求めます。選択した代表端末の当該期間内訳が未提供でも、Hub集計を未取得にせず、存在しない内訳を0として生成もしません。全体の `state.metrics` は全Hubを通じて補正し、Hubごとの `hubs[].metrics` はそのHub内で補正するため、全体値はHub表示値の単純和と異なる場合があります。元の `aggregate` と端末の生値は変更せず保持します。

メトリクス表示は保存済みの過去利用実績を示すため、端末のstaleや現在のHub未接続を理由に保存額を除外しません。これは推定用の端末除外とは別の規則です。Cursorの契約集合を同定できない、集合が部分重複する、または同じ収集日時の値が競合して合計を確定できない場合は、該当メトリクスを「未取得」とし理由を表示します。取得済みの0は有効ですが、欠落値を0で補完しません。利用枠の率や残量は合算しません。

**日時の区別（2026-09-13 利用者合意、ヒアリング1-1・1-2）:** 画面には「データ側の更新日時」と「最終保存成功データの受信日時」を区別して表示します。データ側の更新日時は Hub が報告する対象データの日時であり、Analytics が受信した時刻で上書きしません。受信日時は、保存に成功した通知を Analytics が受信完了した時刻を示します。正常な同一内容の通知を再受信して保存を完了した場合は、データ側の更新日時を維持し、受信日時を新たな受信時刻へ更新します。Hub の日時項目は [連携仕様 第3・4節](interfaces.md#observation-fields) の意味に従い、受信できたことだけをデータの鮮度や新たな測定の証拠にはしません。

日時の具体的な対応は次のとおりです。対象日時が欠落または `null` の場合は「未取得」と表示し、別の日時で代用しません。

| 表示対象 | 日時項目と表示上の意味 |
| --- | --- |
| 端末の利用実績 | `stats.devices[].updatedAt` をデータ側の更新日時とする。端末レコードの更新であり、利用発生時刻や実績測定の成功時刻とは表現しない |
| 端末の利用枠 | `stats.devices[].limits.providers[].updatedAt` をデータ側の更新日時とし、取得状態を併記する。取得失敗時に残っている数値を最新の取得成功値とは表現しない |
| Hub 全体の集計 | `stats.updatedAt` を「Hub 最終更新日時（データ側）」と表記し、端末・利用枠の更新日時とは区別する |
| 最終保存成功データの受信日時 | 当該通知を Analytics が受信完了したローカル時刻。通知に含まれる端末は同じ受信日時を持つ |
| 全体メトリクス | `state.metrics.periods` の `costUsd`・`totalTokens`。Cursorだけは同じ契約ID集合のアカウント全体実績を全Hubで一度だけ数え、他ツールはHub集計を使う。欠落値はゼロ補完しない |

Hub が返した元の全体集計、重複補正後のメトリクス、端末ごとの生値は、集計単位を区別して表示します。画面最上段は `state.metrics`、各Hubは `hubs[].metrics` を表示し、Cursor以外は保存済みHub集計、Cursorは契約ID集合単位で採用した一報を反映します。Hub 全体の利用枠は代表値の集約であり、端末の消費率を足した値として扱いません。端末の鮮度情報は正常な通知の保存成功後に更新します。直近の正常な通知に含まれなくなった端末の保存値を表示する場合は「最新通知に含まれない」と明示し、その端末の受信日時を進めません。

**共通契約の表示（2026-09-13 利用者合意）:** `/api/state` の全体 `contracts` と `estimates` を基に、Hubをまたいで同定された共通契約のカードと推定を全体で1件ずつ表示します。各Hubの `contractIds` と `estimateIds` は共通契約・推定への参照として表示し、Hub・端末の利用額ソース、利用枠、観測根拠はHub別に確認できるようにします。共有利用額を契約別実績へ按分した値は表示しません。旧Hub単位の推定履歴は全体の共通推定と混同しないよう、旧方式として分離して表示します。

状態JSONには、全体の `contracts`、`estimates`、`metrics`、`legacyEstimateCount` と、Hubごとの `contractIds`、`estimateIds`、`metrics` を含めます。共通契約のカードが複数Hubの利用額ソースを含む場合も、同じ契約を重複表示しません。契約・推定がまだ成立しない場合は、関係するHubや端末への参照と「観測待ち」「推定不可」等の理由を表示します。

Grok は同じ正規化済み `accountEmail` を一つの契約カードとしてHub横断で表示し、関係デバイスを n:n で参照します。カードの代表値は正常かつ非 stale の報告のうち最新 `updatedAt` とし、古いトークン行を別カードにしません。同時刻で利用枠の比較対象値（率、枠種別・ID、対象期間等）が食い違う場合は `conflicting_rate` と表示し、`label`・`detail`・`source`・配列順だけの差は無視します。メールアドレスがない行は契約カードを作らず、端末の取得情報として確認できるようにします。

Hub 接続状態、収集設定、データ保存状態、推定可否、ブラウザ接続状態は、それぞれ独立して管理します。同時に成立しうる状態（例: Hub 接続正常だが推定不可）を正確に表示し、過去の保存値を現在取得中の値と誤認させない表示を行います。状態の管理主体と永続化方針は [設計書 第5.5節](../../docs/architecture.md#state-management) に定めます。

## 3. 日次・月次実績

履歴データは推移の閲覧および比較専用です。端末別の保持履歴全体を照合し、停止中の欠落や遅れて報告された実績も再取得データで更新します。Hub 側の応答から過去の履歴が消失した場合でも、保存済みの履歴レコードを削除せず、推定結果も変更しません。履歴を同定するキーは [設計書 第5.1節](../../docs/architecture.md#identity) に従います。

| 対象 | 保存・表示規則 |
| --- | --- |
| 日次 | 各端末の現地日付に基づき、前日以前の確定分を保存する。当日分および SSE 現在値は日次履歴へ転記せず、当日の利用状況として表示する。 |
| 月次 | 返却された各月のデータを保存し、当月分は「途中集計」と明示する。 |
| 日付と数値 | 端末の現地日付および数値をそのまま保持し、タイムゾーン変換や按分は行わない。 |
| 複数端末の合算 | 同一日付の合算値を表示する場合は「現地日付の合計」と明記する。端末間でタイムゾーンが異なる場合は、同一時間帯の合算ではない旨を表示する。 |

定期取得スケジューラが参照する稼働マシン時刻と、保存対象の判定に用いる端末現地日付は独立しています。端末側のタイムゾーン情報が欠落または不正な場合は他のタイムゾーンで代用せず、判定ルールと継続範囲は [U6](../../PLAN.md#u6) で定めます。

## 4. 重要シナリオと検証条件

S1〜S9 は、仕様・設計・モック・テストで共通して使用するシナリオ ID です。本節では各シナリオの期待動作と検証条件を定めます（コンポーネント責務やトランザクション境界は [設計書 第6節](../../docs/architecture.md#runtime) 参照）。

<a id="s1"></a>
### S1. 通常の現在値受信と再受信

**動作:** 受信完了した現在値を検証・保存し、第1節の規則に従って関係する共通推定を更新します。不正入力時は既存の保存値を維持してエラー理由を通知し、後続の通知受付を継続します。欠測端末を除外した後に採用する論理利用額ソースとその契約の正常で新しい観測がそろった時だけ共通推定を確定し、保存成功後に画面表示を更新します。同一内容の再受信、およびCursorのアカウント全体実績の複数端末報告による二重計上を抑止します。

**データ側の日時の変化（2026-09-13 利用者合意、ヒアリング1-6）:** 利用額・消費率・取得状態が同じでも、端末または利用枠のデータ側の更新日時が進んだ場合は、その通知を新たな観測として保存します。Hub が報告した更新の記録を残すためであり、時刻の更新だけを取得成功や推定への採用根拠とはしません。Hub の集計・配信時刻や Analytics の受信時刻だけが変わった同一データの再配信は、観測を重複して追記しません。

**現在値観測の比較範囲:** 同じ Hub・端末の直前に保存した観測と比較します。実績、取得状態、利用枠、データ側の日時に変化がある場合は観測を追記します。一度別の内容へ変わった後に過去と同じ内容へ戻っても、その変化を残します。通知内の端末、プロバイダー、利用枠の配列順だけが変わった場合は同じ内容として扱い、同一要素の個数は区別します。通知内に同じ `deviceId` が複数含まれる場合は入力不正とします。具体的な比較項目と正規化の担当は [設計書 第5.3節](../../docs/architecture.md#53-保存モデルと確定点) に従います。

**不正入力の不採用範囲（2026-09-13 利用者合意）:** 一つの Hub から受信した SSE 通知に、数値欄に文字列が入るなど、入力検証で形式不正と判定した端末データが一件でも含まれる場合は、その通知全体を不採用とします。正常な端末分も部分的に保存・表示更新せず、当該 Hub の直前の保存値を維持してエラーを表示します。他 Hub の処理と後続通知の受付は継続し、次の正常な通知を保存できた時点で表示を更新します。

**検証条件:** 正常時の一括保存、同一内容の重複抑止、不正入力後の正常復帰、保存完了前の成功通知がないことを確認します。推定では、欠測・stale・費用欠落・収集状態不正の端末を除外して残る有効なソースで継続し、`partial` と除外理由を表示すること、残る契約の率欠測や競合では停止することを確認します。Cursorは同じ契約集合の複数報告から最新の収集成功日時を一件だけ採用し、代表端末の交替では系列を変えず、同時刻費用差を `conflicting_usage`、部分重複集合を `overlapping_usage` とすることも確認します。同時刻で率・リセット予定日時・`percentageLimit`・明示プラン・枠の採否条件が異なる報告は `conflicting_rate` として停止します。

推定の設定範囲と式は、単一契約の ΔC=10・Δp=10 から100 USD、同一プランの二契約の共有 ΔC=20・各 Δp=10 から共通100 USD、倍率1と5の二契約の共有 ΔC=60・各 Δp=10 から基準100 USDと別プラン500 USDを算出する例で検証します。さらに、異なるHubに分かれた同一 provider・accountKey の契約の利用額増分が10 USDと5 USD、契約の消費率増分が10ポイントの場合は、Hub別に分けず共通推定1件として150 USDを算出することを確認します。最初の二例では基準プラン・倍率の入力が不要であること、異なるプランでも利用額を個別に取得できれば倍率なしで計算できることを確認します。異なるプランの共有利用額で倍率が不足する場合だけ設定不足とし、消費率の欠落をゼロ扱いしないこと、同一契約の複数Hub・端末報告を重複加算しないことも確認します。各枠を独立に扱い、ツール全体の利用額を枠へ按分せず、枠別の推定値を合算しないことも確認します。共通 provider・枠の追加検証結果は [PLAN.md](../../PLAN.md) に記録します。

一つの通知に正常な二端末と形式不正な一端末を含め、通知全体が保存されず、直前の保存値とエラーが表示されることを確認します。他 Hub の処理が続くこと、および当該 Hub の次の正常な通知で保存・表示更新が再開することも確認します。

データ側の更新日時が10:00の通知を10:05に同一内容で再受信し、保存成功後に「データ側の更新日時 10:00」と「最終保存成功データの受信日時 10:05」が表示されること、同一内容の観測が重複して追記されないことを確認します。

利用額・消費率・取得状態を維持したまま、端末または利用枠のデータ側の更新日時を10:00から10:05へ進めた通知では観測が追記されることを確認します。集計・配信・Analytics 受信の時刻だけを進めた再配信では観測が追記されないことも確認します。

同じ Hub・端末で内容が A、B、A と変化した場合は3件の観測が残り、A、A の連続再受信だけが抑止されることを確認します。端末・プロバイダー・利用枠の配列順変更だけでは追記されず、同一要素の個数が変わった場合は変化を検出すること、通知内の端末 ID 重複は通知全体の不採用となることも確認します。

Hub 集計と端末の鮮度情報は再受信時にも保存・表示更新される一方、端末観測を不要に追記しないことを確認します。通知から消えた端末の観測と日時が保持され、未報告と表示されること、再び含まれた場合は直前観測との比較を再開することを確認します。日時または数値が未取得の場合に別項目やゼロで補完しないことも確認します。

**具体化:** 契約帰属・利用額範囲・枠識別・比較再開は第1.5〜1.6節、保存境界は設計書第5.3節に定義しています。全 provider 共通の契約・枠処理、Cursorのアカウント全体実績の重複除去、欠測端末を除外する推定はコードへ反映済みで、148件の自動テスト、schema 6の実DB・Mock移行、保全照合、実データ再起動、headless Edge表示を確認しました。詳細な検証結果と残件は [PLAN.md](../../PLAN.md#open-items) で追跡します。

<a id="s2"></a>
### S2. 補完中の新規受信と定期取得

**動作:** 初回接続および再接続時は SSE を直ちに開始し、履歴 GET の完了を待ちません。履歴取得の処理中も現在値の受信・保存・推定を継続します。取得した履歴には第3節の規則を適用します。

| 契機・結果 | 動作 |
| --- | --- |
| 初回接続 | Hub の保持履歴全体を取得・保存する。 |
| 定期取得 | 稼働マシンの現地時刻で毎日午前1時に Hub ごとに取得する。 |
| 再接続 | 当該 Hub の当日の定期取得が未完了の場合に取得する。 |
| 通信失敗 | 1時間間隔で再試行し、並行して SSE 受信・推定を継続する。 |
| 取得成功だが前日データなし | 該当なしの旨を表示し、ゼロ補完や短周期の再試行は行わず次回の定期取得を待つ。 |

※ 取得成功の判定はデータの永続化完了までを含みます。通信が成功しても保存に失敗した場合は成功扱いとせず、通信失敗の再試行ループには含めません（保存障害は S6 に従う）。収集停止中は履歴取得・再試行も停止します。

**検証条件:** GET 遅延・失敗時の SSE 継続、長時間稼働時の定期実行、通信失敗後の再試行と成功時の終了、保存失敗を成功や通信再試行の対象にしないこと、前日データ不在時の正常表示、第3節に基づく非破壊更新・日付表示、GET データが現在値や推定処理へ混入しないことを確認します。

**未決事項:** GET の競合制御・キャンセル処理、取得完了状態の永続化責務、タイムゾーン欠落時の判定は [U6](../../PLAN.md#u6)。

<a id="s3"></a>
### S3. 切断と再接続

**動作:** 収集有効なHubへの接続失敗・切断時は、理由を推測せず「未接続」と表示し、自動再接続を続けます。当該Hubを関係に含む共通推定対象は直ちに観測待ちへ移行し、比較基準を中断して最終保存値とその時刻を維持します。そのHubと関係しない推定対象、他Hubの通信、保存済みメトリクス、既存履歴の閲覧は維持します。別Hubからの通知を含む次の正常なSSE通知で欠測端末を除外した対象を再構成し、S1の新しい比較を開始します。履歴補完は S2 に従い、欠測値の架空生成は行いません。

**検証条件:** 未接続表示への切り替え、関係する共通推定だけが観測待ちになること、保存値・時刻の維持、再接続時の重複抑止、無関係な推定対象と他Hubの通信および閲覧継続を確認します。

**具体化・残る実機範囲:** 欠測後の共通推定再開は第1.6節に従います。共通設計のHub横断停止範囲はU2〜U5で検証します。実Hubでの通信切断・自動再接続の確認は [U1](../../PLAN.md#u1) に残っています。

<a id="s4"></a>
### S4. リセット・継続性不明・帰属不明

**動作:** 第1節の対象期間規則に従い、新期間への移行時は関係する共通推定の起点を再設定して過去の推定結果を保全します。帰属や継続性が不明な対象は「推定不可」として取得値と理由を表示し、条件を満たす他の対象の推定は継続します。Hub間の契約関係が変化した場合も関係する系列だけを境界で分離します。

**検証条件:** 期間をまたぐ差分計算を行わないこと、`percentageLimit` の変更前後を同じ比較区間に含めないこと、消費率減少と途中の累積額減少を正しく区別すること、累積額減少のみで起点を変更しないこと、不明区間をまたぐ計算を行わないこと、推定不可時にも過去の保存結果と算出日時を明確に区別して表示することを確認します。

**具体化:** 同一性と比較再開は第1.5〜1.6節、結果の保存境界は設計書第5.3節に従います。全 provider の観測上の共通契約をHubをまたいで同定し、キー不足・組織識別不足など対応できない場合は推定不可として系列を停止します。Claude の組織識別不足は [Issue #34](https://github.com/nuitsjp/token-monitor-analytics/issues/34) に残しますが、共通実装の利用を妨げません。

<a id="s5"></a>
### S5. Hub 個別の収集停止と再開

**動作:** 停止要求の受付を境界とし、当該 Hub の SSE 接続、再接続待機、履歴 GET、GET 再試行を停止します。一回の SSE 通知または GET 応答は、複数端末分を含んでいても一件の受信単位として扱います。

要求受付前に受信完了したデータは通常どおり処理・保存します。受信途中の通信は完了を待たずに中止し、受付後に届いた遅着応答は破棄します。受信済みデータの処理完了後に「収集停止」を表示します。保存処理で失敗した場合は安全に書き込みを停止し、「収集停止」と「保存失敗」を併記します。

収集の有効／停止設定は SQLite に保存し、明示的な再開操作まで通信を行いません。他 Hub の収集および保存済みデータの閲覧は維持します。

**検証条件:** 停止直前の受信完了処理、受信途中の中止、遅着応答の破棄、受信済み処理終了後の停止表示、保存失敗との併記、全通信の停止、他 Hub の収集・閲覧継続、再開および再起動後の設定維持を確認します。

**未決事項:** 通信停止・キュー処理・設定保存の順序と担当、設定保存失敗時や連続操作時の復元は [U6](../../PLAN.md#u6)・[U7](../../PLAN.md#u7)。

<a id="s6"></a>
### S6. データ保存失敗

**動作:** 保存失敗を成功として扱わず、原因をログ等で追跡可能にします。不整合を招く書き込みを停止し、参照可能な保存データの閲覧および安全な通信・状態通知を維持します。

**保存停止範囲（2026-09-13 利用者合意）:** 複数 Hub が共有する SQLite への保存に失敗し、原因や影響範囲が分からない場合は、全 Hub のデータ保存を停止します。復旧まで、正常な Hub も含めて新しい観測を記録できないことを許容します。画面には最後の保存値と保存障害を表示し、原因解消後の再起動で復旧します。

**保存失敗時の日時表示（2026-09-13 利用者合意、ヒアリング1-2）:** 保存に失敗した通知や保存停止中に受信した通知では、表示する数値と第2節の両方の日時を更新せず、最後に保存できた状態と「保存失敗」を表示します。保存停止中の通信状況は Hub 接続状態で示します。

**保存成功後の通知不達（2026-09-13 利用者合意）:** データ保存は成功したものの、ブラウザへの更新通知だけが届かなかった場合は、収集と保存を継続します。画面の数値が一時的に古いままであることを許容し、ブラウザの再接続時に最新の保存値を表示します。保存済みデータは維持し、通知不達を保存失敗やロールバックとして扱いません。

**稼働中の DB 参照不能（2026-09-13 利用者合意）:** 稼働中に SQLite を読み出せなくなった場合は、全 Hub のデータ保存を停止し、Web 画面は維持します。アプリ内に保持している保存済みの値に「更新停止・DB 参照不能」と表示し、更新中の値とは区別します。新たな DB 読み出しが必要な履歴閲覧は、取得できない旨を表示します。原因解消後の再起動で復旧します。コミット完了後の読み出しに失敗した場合も、そのコミットで保存されたデータは維持し、画面には最後に正常に読み出して保持した値を表示します。

**検証条件:** コミット前失敗時の部分保存の抑止、後続書き込みの安全な停止、誤った成功通知の不在、原因ログの出力を確認します。コミット完了後の失敗をロールバック扱いと誤認しないことも確認対象とします。

複数 Hub の収集中に、原因や影響範囲を特定できない保存失敗を発生させ、全 Hub の新しい観測が保存されないこと、最後の保存値と保存障害を表示すること、原因解消後の再起動で保存を再開することを確認します。

10:00時点で受信・保存できたデータを表示中に、10:05に受信した通知の保存を失敗させ、数値と両方の日時が直前の表示のまま維持されることを確認します。保存停止中に後続通知が届いても日時を更新せず、Hub 接続状態と「保存失敗」を併記することも確認します。

ブラウザへの更新通知が届かない状態でも新しい観測の収集・保存が続くこと、保存済みデータが維持されること、ブラウザの再接続後に通知不達中の更新を含む最新の保存値が表示されることを確認します。

稼働中の DB 読み出しを失敗させ、全 Hub の保存が停止し、Web 画面には保持済みの値と参照不能が表示されること、新たな履歴照会が取得不能として表示されることを確認します。コミット完了後の読み出し失敗では、画面の保持値は更新されず、コミット済みデータは残り、原因解消後の再起動でそのデータが復元されることも確認します。

**具体化状況:** 現在値の通知不達からの復帰担当・契機、および保存停止中の受信・通信・表示の境界は [設計書 第5.6節](../../docs/architecture.md#56-排他制御と通知シーケンス)・[S6](../../docs/architecture.md#s6) に具体化しています。履歴取得・管理操作への適用と実装・検証は [U9](../../PLAN.md#u9) で追跡します。

<a id="s7"></a>
### S7. 再起動とシャットダウン

**実データと Mock の排他運用（2026-09-13 利用者指示）:** `mise run real` は実 Hub の設定と実データ用 DB のみを使用し、`mise run mock` は内蔵 Mock Hub と Mock 用 DB のみを使用します。Mock モードは実 Hub の設定ファイルを読み込まず、不在・書式不正でも影響を受けません。待受アドレス・ポートの `.env` は共通とし、設定を編集せず同じURLで切り替えられます。画面とタブ名に起動モードを表示し、現在値・推定・履歴の全経路で他モードの保存値を使用しません。

同じ作業ディレクトリでは、モードや待受ポートにかかわらず一つだけ起動できます。二つ目は Hub 接続や DB 操作を始める前に起動を中止し、先に起動したターミナルで Ctrl+C により終了する手順をログに示します。既存プロセスの自動終了やモードの自動切り替えは行いません。Mock Hub は Analytics と同じプロセスで起動・終了します。起動途中の失敗や強制終了の後も排他状態が残らず、次回の起動を妨げません。

**動作:** 保存済みの現在値と Hub 収集設定を復元し、収集が有効で接続設定が正常な Hub のみに接続します。停止設定された Hub は停止状態を維持し、接続状態は起動後の実通信で判定します。保存済みの値を新規受信データとして扱わず、未コミットの観測データを架空生成することもありません。

**現在値機能の先行実装における設定入力（2026-09-13 利用者合意、ヒアリング1-3）:** Hub の接続先 URL 等は利用者がローカル設定ファイルへ記入し、アプリは起動時に読み込みます。設定変更はファイル編集後の再起動で反映します。Web 画面からの登録・変更は [PLAN.md 第2節の順序3](../../PLAN.md#2-作業の進め方と順序) で実装し、初期版の管理操作要件は S8 に従います。

**Web の利用範囲（2026-09-13 利用者合意、ヒアリング1-7）:** アプリ実行 PC に加え、利用者が管理する同じネットワークの別端末からも Web 画面を利用します。待受アドレスとポートは `.env` の `ANALYTICS_HOST`・`ANALYTICS_PORT` で指定し、変更後の再起動で反映します。設定例の既定値は `127.0.0.1`・`3000` とし、別端末から利用する環境では実行 PC の LAN 側 IP アドレスを明示します。Web の利用者認証なし・HTTP 利用という初期版の前提は設計方針に従います。

`.env` と Hub 設定ファイルを初期設定手順で作成します。待受アドレスは実行 PC の IP アドレス、ポートは1〜65535の整数として検証します。設定不正や指定したアドレス・ポートでの待受失敗は起動失敗とし、他のアドレス・ポートへ自動で切り替えません。

**先行実装の共有シークレット保存（2026-09-13 利用者合意、ヒアリング1-4）:** 共有シークレットは Git 管理対象外のローカル設定ファイルへ平文で保存し、Windows のファイルアクセス権で読み取りを制限します。ファイルを読む権限のある利用者がシークレットを読めることを許容します。画面・ログ・レスポンスへの非露出は S8 と設計方針に従います。

**設定ファイル全体の障害（2026-09-13 利用者合意、ヒアリング1-5）:** 設定ファイルの不在、読み出し不能、全体の書式不正により Hub ごとの設定を読み込めない場合は、起動を中止します。HTTP 待受および Hub への接続を開始せず、ターミナルとログに原因を出力します。設定ファイルの本文や共有シークレットは出力しません。利用者が設定を修正した後、手動で再起動します。設定を読み込めた後の一部 Hub の設定不正は、後述の Hub 単位の扱いに従います。

**設定入力の具体化（現在値機能の先行実装）:** Hub 設定は `.local/hubs.json` に UTF-8 の JSON として記入します。最上位は `hubs` 配列を持ち、任意で共通推定設定 `estimation` を持つオブジェクトとします。Hub要素は接続設定だけを持ち、倍率設定を含めません。

| 項目 | 意味・検証 |
| --- | --- |
| `id` | Analytics 内で Hub を識別する、空でない文字列。ファイル内で一意とし、画面にもこの ID を表示する。接続先を変更しても同じ登録として扱う場合は ID を維持する |
| `url` | Hub の絶対 URL。`http` または `https` を受け付ける。URL 内のユーザー名・パスワード、クエリ、フラグメントは受け付けない |
| `secret` | Hub 認証ヘッダーに使用する空でない文字列。ヘッダーに使用できない文字を含む値は設定不正とする |

最上位の `estimation.planMultipliers` は全Hubに共通の倍率設定です。通常は `estimation` ごと省略し、異なるプランの共有利用額をまとめる場合だけ指定します。

最上位の構造不正、Hub要素がオブジェクトでない場合、`id` の欠落・不正・重複は登録単位を特定できないためファイル全体の障害として扱います。Hub要素に `estimation` を置いた場合も設定場所の誤りとしてファイル全体の障害とし、`ConfigurationError('hub_estimation_must_be_top_level')` を記録して起動を中止します。トップレベルの `estimation` の形式不正はHub登録を特定できるため、共通推定だけを停止し、Hubの接続・観測保存を継続します。登録単位を特定できる `url`・`secret` の不正は当該 Hub の設定不正として扱います。エラー表示には項目名と理由を用い、入力値や JSON 解析例外に含まれる本文は出力しません。

設定ファイルは接続先と共有シークレットの正本とし、起動時に保存済みの旧接続設定で代用しません。新しい ID は新規 Hub として収集を有効にします。既存 ID の収集有効／停止設定は SQLite の保存値を維持します。設定から外した ID の保存データは保持し、通信を開始せず「接続設定なし」と表示します。ファイルの編集によって Hub の収集停止設定を解除しません。

**共有利用額の倍率設定:** トップレベルの `estimation.planMultipliers` は `{ tool, windowKey, basePlan, plans }` の配列です。`tool` はツールID、`windowKey` は画面に提示する対象枠のキー、`basePlan` は基準プラン名、`plans` はプラン名をキー、正の有限数の倍率を値に持つオブジェクトです。基準プランを `plans` に含め、その倍率を1にします。同じツール・枠の重複設定を受け付けません。対象契約のプランが設定に含まれなければ「設定が必要」とします。共通設定の不正は全体の推定を停止しますが、Hubの接続・現在値保存は継続します。入力本文をエラーへ含めません。変更は再起動で反映し、過去の推定結果や根拠の倍率は書き換えません。

**起動時の既存 DB 障害（2026-09-13 利用者合意）:** 起動時に既存の SQLite を開けない、または保存値・収集設定を読み出せない場合は、起動を中止します。Web 画面および Hub への接続を開始せず、ターミナルとログに原因を出力します。利用者が原因を確認・解消した後、手動で再起動して復旧します。

**一部 Hub の設定不正（2026-09-13 利用者合意）:** DB は正常に読み出せるものの、接続先 URL の形式不正など一部 Hub に接続設定の不正がある場合は、アプリ全体を起動します。設定不正な Hub には接続せず、Web 画面に「設定不正」と表示します。接続設定が正常で収集が有効な他 Hub の収集、および保存済みデータの閲覧は維持します。

**schema 6移行:** `migrateUsagePolicy` は、利用額の収集範囲と端末除外規則の変更に伴い、全サービスの旧checkpointから比較基準を破棄し、保存済み現在値を使って `methodVersion: 2` の状態をseedします。旧viewは `active: false`、`reason: method_changed` として `lastResult` を保持し、現在の比較や推定へ流用しません。既存の観測、Hub・端末の現在参照、旧方式・共通方式の推定events、契約、端末・契約関連は変更せず、過去の結果を遡及再計算しません。schema 3・4・5の移行・検証結果は歴史的事実として保持します。

**検証条件:** 保存値の復元、停止指定 Hub への接続抑止、未コミットデータの不採用、比較基準および推定結果の重複防止を確認します。トップレベルの共通倍率設定を不正にした場合は全体の推定だけが停止し、すべてのHubの接続・観測保存が継続することを確認します。`hubs[].estimation` を含む入力は黙って無視せず、`ConfigurationError('hub_estimation_must_be_top_level')` としてHTTP待受・Hub接続前に起動を中止することを確認します。

schema 6移行では、観測・現在値・旧方式と共通方式の推定events・契約関連を含む8表が不変であること、旧比較基準が新方式へ流用されないこと、旧viewの前回結果が非activeの記録として残ること、失敗時にschema 5へロールバックすることを確認します。148件の自動テスト、実DB・Mock移行、全行ハッシュと整合性の照合、実画面を確認済みです。詳細は [PLAN.md](../../PLAN.md) で追跡します。

両モードを個別に起動し、選択したモードだけの Hub・現在値・推定履歴を返すことと、他モードの DB を変更しないことを確認します。実 Hub 設定の不在・不正時にも Mock が動くこと、異なる待受ポートでも二重起動を拒否すること、通常終了・起動失敗・強制終了後にもう一方を起動できること、Mock Hub が終了することを確認します。既存の混在データを分離する際は、元の DB を保持し、全保存行の内容と件数が分離先で一致することを停止中に照合します。

既存 DB を開けない場合と、開いた後に保存値・収集設定を読み出せない場合のそれぞれで、HTTP 待受と Hub 接続が開始されず、原因がターミナルとログに出力されることを確認します。原因解消後の手動再起動で保存値と収集設定が復元されることも確認します。

DB を正常に読み出せる状態で、一つの Hub の接続先 URL を形式不正にし、HTTP 待受は開始され、該当 Hub への接続は開始されず「設定不正」と表示されることを確認します。他の有効な Hub の収集と、設定不正な Hub を含む保存済みデータの閲覧が維持されることも確認します。

現在値機能の先行実装では、設定ファイルに記入した正常な Hub へ接続できること、ファイルの接続先 URL を変更して再起動すると変更後の接続先へ接続することを確認します。

指定した待受アドレスとポートが使われ、不正設定や待受失敗時には Hub 接続を開始せず起動が失敗することを確認します。Windows では LAN 側アドレスで起動し、同じネットワークの別端末から画面・JSON API・ブラウザ向け SSE の表示更新と再接続を確認します。

共有シークレットを含む設定ファイルが Git 管理対象外であること、ファイルアクセス権を制限する手順が Windows で機能すること、設定不正や Hub の認証失敗を含め画面・ログ・レスポンスへシークレットを出力しないことを確認します。

設定ファイルの不在・読み出し不能・全体の書式不正のそれぞれで、HTTP 待受と Hub 接続が開始されず、本文や秘密情報を含めずに原因がターミナルとログへ出力されることを確認します。ファイルを修正して再起動すると、正常な設定で起動できることも確認します。

`id` の欠落・重複時は全体の起動を中止し、識別できる一つの Hub の `url`・`secret` が不正な場合は他 Hub を起動することを確認します。同じ ID の URL 変更時も保存済みデータと収集停止設定を維持すること、設定から ID を外しても既存データを削除せず接続しないこと、新しい ID を指定した場合は別 Hub として扱うことを確認します。

異なるHubへ分散した同一 provider・accountKey の契約について、端末範囲の有効な利用額増分10 USD・5 USDと共通の消費率増分10ポイントを別々の正常な通知で受信した場合、共通推定1件・150 USDを保存・表示することを確認します。一方の端末が欠測の場合はその端末を除外した新しい系列で比較し、`partial` と理由を表示します。Cursorでは同一契約集合の報告をHub横断で一件だけ採用します。旧Hub単位および旧集計方法の結果は共通推定へ流用せず、履歴または非activeの記録として区別します。

終了開始前に受信完了した通知は保存され、受信途中または終了開始後の通知は保存されないこと、再接続待機が解除されること、キュー処理後に DB を閉じることを確認します。保存停止中の終了でも未保存通知を採用せず、再起動時に収集有効／停止設定を維持することを確認します。

**具体化・残件:** 推定の保存値と境界の復元は第1.6節・設計書第5.2〜5.3節に従います。収集設定および日次・月次履歴完了状態の復元は [U6](../../PLAN.md#u6)、Webからの接続設定の更新操作は [U7](../../PLAN.md#u7) で追跡します。

<a id="s8"></a>
### S8. Hub 管理操作

**動作:** Web 画面から Hub の登録・一覧表示・個別停止・再開を行います。初期版は限定された安全な利用環境を前提とし、Web 経路の利用者認証は行いません（後続：[U12](../../PLAN.md#u12)）。管理操作には入力検証と CSRF 対策を施し、共有シークレット等の秘密情報を画面・ログ・レスポンスへ出力しません。Hub への接続認証は [連携仕様](interfaces.md#hub-api) に従います。

**検証条件:** 利用者認証なしでの画面・静的アセット・JSON API・ブラウザ向け SSE の利用、CSRF 検証失敗および不正入力の拒否、秘密情報の非露出、正常操作時および保存失敗時の適切な結果表示を確認します。

**未決事項:** 管理 API 契約、秘密情報の安全な永続化、CSRF 方式は [U7](../../PLAN.md#u7)。利用者認証の方式・適用時期は [U12](../../PLAN.md#u12)（初期版完了条件からは除外）。

<a id="s9"></a>
### S9. 手動更新と障害復旧

**動作:** ユーザーの明示操作による更新を行い、作業中の一時停止を許容します。自動更新や自動ロールバック、DB 初期化、履歴改変は行わず、更新結果、失敗原因、手動復旧に必要な情報を提示します。

**検証条件:** 正常更新と失敗時の区別、失敗時における既存 DB・履歴の保全、手動復旧情報の提示を確認します。

**未決事項:** 更新元・適用手順・互換性確認・復旧手順の具体化は [U8](../../PLAN.md#u8)。
