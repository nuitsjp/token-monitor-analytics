# 機能仕様

本書は、利用許容量の推定、取得情報の表示、履歴収集、Hub 管理、障害・更新時の動作と検証条件の正本です。製品の目標・制約・品質要求は [設計方針](../../docs/design-policy.md)、API の取得値と制約は [連携仕様](interfaces.md)、構造・責務・保存境界は [設計書](../../docs/architecture.md)、未決・未実装・未検証事項は [PLAN.md](../../PLAN.md) を参照します。

2026-09-13 に、現行設計書の動作仕様と [旧機能要件](../../old/docs/requirements.md)・[旧機能詳細設計](../../old/docs/functional-design.md) の合意済み条件を統合しました。旧 Analytics のコード・設定・画面の具体値は採用根拠に含めません。仕様の記載は実装・検証の完了を意味せず、未決事項に依存する設計は未完了のままです。

<a id="estimation"></a>
## 1. 利用許容量の推定

<a id="observation-validity"></a>
### 1.1 観測の組と採用条件

推定には、同一 SSE イベント（`snapshot` / `stats`）に含まれる利用額と `usedPercent` を一組として使用します。GET の日次・月次実績から現在値や過去の推定値を生成しません。採用する累積 API 換算額の項目と、契約・利用枠への帰属根拠は [U2](../../PLAN.md#u2) で確定します。

同一 SSE 内の測定時刻のずれによる微小誤差は許容します。数値の許容幅は指定されていません。この許容によって、取得失敗や帰属・継続性が不明な値を有効な観測として扱うことはしません。

[上流の更新状態と時刻の意味](interfaces.md#limit-fields)に基づき、次の条件を適用します。

- 利用枠のみの更新では実績が以前の値のまま残り得るため、同じレコード内の値が同時に測定されたとはみなしません。
- 利用枠の取得失敗後にも直前の成功値が残り得るため、値の存在、端末の更新日時、`stale: false` だけで取得成功や鮮度を判断しません。
- 更新状態と時刻を確認し、比較可能性を判断できない対象は推定不可とします。取得値の表示は継続します。

観測の順序・比較再開・複数端末の対応を判定する具体的な責務と規則は [U3](../../PLAN.md#u3) に残ります。独自の鮮度閾値を今回の統合で追加しません。

### 1.2 計算式と成立条件

同一契約・利用枠・対象期間の二観測について、API 換算額の増分を ΔC（USD）、消費率の増分を Δp（パーセントポイント）とすると、利用許容量は `100 × ΔC / Δp`（USD）です。次の全条件を満たす場合だけ算出します。

1. 利用額の増分が対象契約・利用枠の消費に対応し、契約の混在がなく帰属を特定できること。
2. 二観測が同じ対象期間に属し、リセットや欠測による対応不明な区間をまたがないこと。
3. ΔC と Δp がともに正であること。ゼロ・負値・不明値を代用して計算しないこと。
4. 定額制の利用枠であり、失効性クレジットや残高メーターではないこと。

帰属不明な利用額を仮の比率で配分したり、未知の利用許容量の比率を利用者に設定させたりして条件を補いません。複数契約でも、実績を分離できる契約・利用枠ごとに判定します。

### 1.3 比較区間と対象期間

同一対象期間内の比較可能な最初と最新の観測を使い、最も広い区間の差分から計算します。新規観測を受けても起点を保って区間を延伸します。同一端末・同一対象期間の途中で累積額が減少しても、それだけでは起点を変更せず、最初と最新の差分に第1.2節の条件を適用します。

利用枠自体の同一性は [設計書 第5.1節](../../docs/architecture.md#identity) に従い、同一枠を特定した後に対象期間を判定します。

| 条件 | 扱い |
| --- | --- |
| 有効な `resetsAt` が同一 | 比較起点を維持し、最新観測との差分から計算する。 |
| 有効な `resetsAt` が更新 | 新期間へ移行して起点を再設定し、期間をまたぐ差分を使わない。 |
| `resetsAt` が欠落・不正 | 対象期間を特定できないため推定不可とする。 |
| 同一 `resetsAt` で消費率が減少 | 継続性不明として推定不可とし、不明区間をまたがない。 |

`resetsAt` はリセット予定時刻であり、発生通知ではありません。欠測や古い値の再受信後にどこから比較を再開するかは [U3](../../PLAN.md#u3) で決めます。

### 1.4 結果の保存と表示

新たな推定結果は算出日時、比較区間、根拠とともに時系列で追記し、過去結果を改変・遡及再計算しません。同じ内容の再受信を新しい利用実績や推定結果として二重計上しません。

推定条件を満たさない場合は理由を表示し、過去の保存結果があれば算出日時とともに併記します。未実装の機能は推定不可というデータの状態と区別します。比較基準・観測・結果・不可理由の保存範囲と重複防止は [U3](../../PLAN.md#u3)・[U5](../../PLAN.md#u5) に残ります。

<a id="display"></a>
## 2. 取得情報と状態の表示

プロバイダー・プランを限定せず、取得した利用枠・消費率・API 換算額を推定可否にかかわらず表示します。利用額には実際の集計単位（Hub・端末・ツール等）を示し、帰属できない契約へ配分しません。各項目に取得状態と更新日時を示し、未取得値はゼロで埋めません。

Hub 接続、収集設定、保存、推定可否、ブラウザ接続は独立した状態です。同時に成立する状態を示し、過去の保存値を現在取得した値と誤認させません。状態の管理主体と永続性は [設計書 第5.5節](../../docs/architecture.md#state-management) に記載します。

<a id="history"></a>
## 3. 日次・月次実績

履歴は推移閲覧・比較専用です。端末別の保持履歴全体を照合し、停止中の欠落や遅れて報告された実績も再取得値で更新します。応答から消えた保存済み履歴を削除せず、推定結果も変更しません。履歴を同定するキーは [設計書 第5.1節](../../docs/architecture.md#identity) に従います。

| 対象 | 保存・表示規則 |
| --- | --- |
| 日次 | 各端末の現地日付で前日以前を保存する。当日分と SSE 現在値を日次履歴へ転記せず、当日の利用は現在値として表示する。 |
| 月次 | 返却された各月を保存し、当月は「途中集計」と表示する。 |
| 日付と数値 | 端末の現地日付と数値をそのまま保持し、タイムゾーン変換・按分をしない。 |
| 複数端末の合算 | 同じ日付の合計を「現地日付の合計」と明示する。タイムゾーンが混在する場合は、同一時間帯の合計ではない旨を表示する。 |

取得スケジュールの稼働マシン時刻と、保存対象を決める端末現地日付は別です。端末タイムゾーンが欠落・不正な場合の当日除外判定と継続範囲は [U6](../../PLAN.md#u6) に残し、他のタイムゾーンで代用しません。

<a id="scenarios"></a>
## 4. 重要シナリオと検証条件

S1〜S9 を仕様、設計、モック、テストの共通 ID とします。本節は動作と期待結果の正本であり、更新担当・トランザクション等は [設計書 第6節](../../docs/architecture.md#runtime) の同じ ID を参照します。以下は検証条件であり、テスト成功の記録ではありません。モック駆動開発を個別に選択した場合の確認方法・承認記録も該当シナリオへ追記します。既定採用は [U10](../../PLAN.md#u10) で未決です。

<a id="s1"></a>
### S1. 通常の現在値受信と再受信

**動作:** 受信完了した現在値を検証・保存し、第1節に従って推定します。不正入力では保存値を維持して理由を通知し、次の通知の受け付けを続けます。保存成功後に表示を更新し、同じ内容の再受信では二重計上しません。

**検証条件:** 正常な一括保存、同一通知の重複抑止、不正入力後の復帰、保存前に成功通知がないことを確認します。推定では同一 SSE の組を使用し、測定時刻差の許容を取得失敗・鮮度不明の代用にしないことを確認します。

**未決:** 契約帰属・枠識別・比較基準と保存は [U2](../../PLAN.md#u2)〜[U5](../../PLAN.md#u5)。

<a id="s2"></a>
### S2. 補完中の新規受信と定期取得

初回接続・再接続では SSE を直ちに開始し、履歴 GET の完了を待ちません。GET 待機中も現在値の受信・保存・推定を続けます。取得履歴には第3節を適用します。

| 契機・結果 | 動作 |
| --- | --- |
| 初回接続 | Hub の全保持履歴を取得・保存する。 |
| 定期取得 | 稼働マシンの現地時刻で毎日午前1時に Hub ごとに取得する。 |
| 再接続 | 当該 Hub の当日の定期取得が未完了なら取得する。 |
| 通信失敗 | 1時間間隔で再試行し、SSE 受信・推定を継続する。 |
| 取得成功だが前日データなし | 不在を表示し、ゼロ補完や短周期の再試行をせず次回の定期取得を待つ。 |

取得成功はデータの保存完了までを含みます。通信が完了しても保存に失敗した場合は取得成功にせず、通信失敗と同じ再試行に含めません。保存障害は S6 に従います。収集停止中は履歴取得・再試行も止めます。

**検証条件:** GET 遅延・失敗中の SSE 継続、長時間稼働中の定期実行、通信失敗後の再試行と成功後の終了、保存失敗を成功・通信再試行に扱わないこと、成功後の前日データ不在、第3節の非破壊更新・日付・表示、GET が現在値・推定へ混入しないことを確認します。

**未決:** GET の競合・キャンセル、取得完了状態の保存責務・トランザクション、タイムゾーン欠落時の判定は [U6](../../PLAN.md#u6)。

<a id="s3"></a>
### S3. 切断と再接続

**動作:** 収集が有効な Hub に接続できない場合は、上流の停止理由を推測せず「未接続」と表示し、自動再接続を続けます。最後の保存値と時刻、他 Hub の通信と履歴閲覧を維持します。再接続時の現在値は S1、履歴補完は S2 に従い、欠測観測を生成しません。

**検証条件:** 未接続表示、保存値・時刻の保持、再接続時の重複抑止、他 Hub と閲覧の継続を確認します。

**未決・未検証:** 欠測後の推定再開は [U3](../../PLAN.md#u3)、実 Hub の継続受信・再接続は [U1](../../PLAN.md#u1)。

<a id="s4"></a>
### S4. リセット・継続性不明・帰属不明

**動作:** 第1節の対象期間規則に従い、新期間では起点を再設定して過去結果を維持します。帰属・継続性が不明な対象は推定不可として取得値と理由を表示し、識別できる他の対象の推定を続けます。

**検証条件:** 期間横断の計算をしないこと、消費率減少と途中の累積額減少を区別すること、累積額減少だけでは起点を変更しないこと、不明区間をまたがないこと、推定不可時にも過去結果と算出日時を区別して表示することを確認します。

**未決:** 判定対象の同一性と比較再開・保存は [U2](../../PLAN.md#u2)〜[U5](../../PLAN.md#u5)。

<a id="s5"></a>
### S5. Hub 個別の収集停止と再開

**動作:** 停止要求の受付を取り込みの境界とし、当該 Hub の SSE、再接続待ち、履歴 GET、GET 再試行を止めます。一回の SSE データ通知または GET 応答を一件とし、複数端末分を含んでも一件として受信完了を判定します。

受付前に受信完了したデータは、処理待ち・処理中も通常どおり処理・保存します。受信途中の通信は完了を待たず中止し、受付後に遅れて届く応答は破棄します。受信済みデータの処理終了後に「収集停止」と表示します。保存失敗時は危険な書き込みを止め、「収集停止」と「保存失敗」を併記します。

有効・停止の設定は SQLite に保存し、明示的な再開まで通信を再開しません。他 Hub の収集と保存済みデータの閲覧は継続します。

**検証条件:** 停止直前の受信完了、受信途中の中止、キャンセル後の遅着応答の破棄、受信済み処理の終了と停止表示、保存失敗との併記、全通信の停止、他 Hub と閲覧の継続、再開・再起動後の設定維持を確認します。

**未決:** 通信停止・受信済み処理・停止設定保存の順序と担当、設定保存失敗や停止・再開競合時の復元は [U6](../../PLAN.md#u6)・[U7](../../PLAN.md#u7)。

<a id="s6"></a>
### S6. データ保存失敗

**動作:** 保存失敗を成功として通知せず、原因を追跡可能にします。整合性を担保できない書き込みを止め、参照可能な保存値の閲覧と安全な通信・状態通知を維持します。コミット前・後の確定点と復旧は [設計書の S6](../../docs/architecture.md#s6) に従います。

**検証条件:** コミット前の部分保存の不在、後続書き込みの停止、成功通知の不在、原因記録を確認します。コミット後の失敗をロールバック済みとして扱わないことも確認対象です。

**未決:** コミット後の読み出し・通知失敗、DB 参照不能、共有 DB 障害の影響範囲は [U9](../../PLAN.md#u9)。

<a id="s7"></a>
### S7. 再起動とシャットダウン

**動作:** 保存済み現在値と Hub の収集設定を復元し、有効な Hub だけへ接続します。停止した Hub は停止を維持し、接続状態は起動後の通信で判定します。保存値を新規受信値として扱わず、未コミットの観測を取得済みとして生成しません。終了時の処理順序は [設計書の S7](../../docs/architecture.md#s7) に従います。

**検証条件:** 保存値の復元、停止指定 Hub への接続抑止、未コミットデータの不採用、比較基準・推定結果の重複防止を確認します。

**未決:** 比較基準の復元は [U3](../../PLAN.md#u3)・[U5](../../PLAN.md#u5)、収集設定と取得完了状態の復元は [U6](../../PLAN.md#u6)。

<a id="s8"></a>
### S8. 認証と管理操作

**動作:** Web 画面から Hub を登録・一覧表示し、個別に停止・再開できます。Web の全経路を [設計方針 第3.3節](../../docs/design-policy.md#33-認証と信頼境界) の Basic 認証で保護し、認証失敗時は保護対象を返しません。管理操作には入力検証と CSRF 対策を行い、認証情報・共有シークレットを画面・ログ・レスポンスへ出しません。

**検証条件:** 未認証アクセス、CSRF 検証失敗、不正入力の拒否、秘密情報の非露出、正常操作と保存失敗時の結果表示を確認します。

**未決:** 管理 API の契約、秘密情報の保存、CSRF 方式と管理操作の境界は [U7](../../PLAN.md#u7)。方式の採用を本書の記載だけで確定しません。

<a id="s9"></a>
### S9. 手動更新と障害復旧

**動作:** 明示操作で更新し、作業中の停止を許容します。自動更新・自動ロールバック、DB 初期化、履歴改変を行わず、失敗の事実・原因・手動復旧情報を提示します。

**検証条件:** 正常更新と失敗を区別できること、失敗後も既存 DB・履歴を保全し、手動復旧に必要な情報を得られることを確認します。

**未決:** 更新元・適用・再起動・互換性確認・復旧手順は [U8](../../PLAN.md#u8)。
