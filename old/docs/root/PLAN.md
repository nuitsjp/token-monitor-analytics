# 開発計画

合意済みの要件を、設計・実装・検証を繰り返して実現する。旧計画の設計手順 1〜4 は、動作する成果を基準とした段階 A〜D に組み替える。未決事項の ID U1〜U6 は維持する。

進め方は [文書方針](docs/document-policy.md) に従う。全体は概略に留め、直近に実行する範囲だけを具体化する。各段階は初期版を作る途中の到達点であり、合意済み機能の削除や品質要求の緩和を意味しない。

## 現状

- [設計方針](docs/design-policy.md)、[機能要件](docs/requirements.md)、[合意済みの具体仕様](docs/functional-design.md) を設計入力として使う。合意の取り直しや文書全体の再編から始めない。
- 上流ソースの調査根拠と Private Hub の単発取得の範囲は [設計書 第 1〜2 節](docs/architecture.md#1-調査対象と根拠) に記録済み。継続接続や実装の互換性検証が完了したわけではない。
- 段階 A の最小構成（`src/`、`mock/`、`public/`、`tests/`、`package.json`、`mise.toml`）を作成し、旧構成の CI を Windows 上の `mise run check` に置き換えた。
- `npm run check` は Node.js 24.18.0 上で20件すべて成功した。Mock Hub での保存・再受信・再接続・不正入力・保存失敗・Basic 認証・秘密情報非露出を確認し、ローカルの実ブラウザーでも認証済みの現在値表示を確認した。
- 設定済みの Private Hub について、SSE の初回 `snapshot` を同じ入力検証へ通し、端末2台・Hub集約プロバイダー22件を一時SQLiteへ保存できた。実Hubの継続更新・切断再接続、および Linux の対応・検証は未確認であり、U1 の残件とする。
- 未決事項の内容と根拠は [設計書 第 5 節](docs/architecture.md#5-未確認事項と設計への影響) で管理する。契約帰属（U2）や枠識別（U4）を未確認のまま、契約別の推定を成立したものとして扱わない。

## 全体の概略

| 段階 | 到達点 | 主な依存・見直し事項 |
| --- | --- | --- |
| A. 現在値を受信・保存・表示する | Node.js と SQLite の最小構成、必要な Mock Hub、Hub の現在値受信から認証済み画面表示までを動かす。 | 直近の保存・通知・状態管理の境界（U6）。枠の観測間の同一性を必要とする処理は U4 に依存する。 |
| B. 利用許容量を推定・記録する | 帰属を確認できた利用額と消費率から推定し、比較基準・算出時点の結果を保存して履歴を閲覧できる。 | 契約帰属（U2）、比較区間の管理（U3）、枠識別（U4）。成立根拠を確定してから対象処理を実装する。 |
| C. 履歴収集と複数 Hub 管理を揃える | 日次・月次実績の取得・補完・閲覧・比較、複数 Hub の並行収集、登録・一覧・停止・再開と設定復元を実現する。 | 端末の分離（U5）、日付判定・定期取得・通信停止と保存の境界（U6）。 |
| D. 実環境で使える初期版にする | 手動更新・失敗時の復旧、起動・設定・運用手順を揃え、実 Hub と Windows で必要な検証を完了する。 | 実機互換性（U1）と、それまでの実装で残った必須修正。DB・履歴を保全する。Linux 対応・検証は後続の残件とする。 |

これは現在の見通しであり、B と C の順序や各段階の作業範囲は、A の結果と未決事項の依存関係に応じて見直す。推定の判断待ちでも、独立した履歴・管理機能は進められる。実機確認や障害時の検証は各実装に伴って行い、D では残る範囲を確認する。

初期版の全体完了は [機能要件](docs/requirements.md) と [設計方針 第 5 節](docs/design-policy.md) で判断する。端末の手動関連付けなどの [将来要件・初期対象外](docs/design-policy.md#6-事前相談と将来要件) は、この初期版の実装に追加しない。

## 実施済みの作業 — 段階 A

**到達点:** 一つの Hub から受けた現在値を SQLite に保存し、Basic 認証で保護した画面へ、集計単位・状態・更新時刻とともに表示する。最初の確認を一つの Hub で行い、複数 Hub の完成は段階 C で扱う。データは最初から Hub・端末を分離する。

2026-09-12 の利用者指示により、最初の完了基準は Windows のみとする。Linux の対応・検証は後続で行い、今回の完了条件には含めない。

契約別の推定、日次・月次履歴、管理画面の全操作はこの範囲に含めない。取得情報は表示し、推定機能が未実装であることを明示する。帰属・枠識別が不明な値を観測間で結合して比較基準や推定に使わない。

- [x] **今回必要な境界を決める。** 受信・入力検証、共通の直列キュー、SQLite への一括保存、保存成功後の通知、認証と状態管理の責務を [設計書 §6.4](docs/architecture.md#64-段階-a-の実装境界) に反映した。観測間で枠を同一視せず、Hub・観測・端末の単位で保持する。
- [x] **起動・検証できる最小構成を作る。** Node.js 24 と SQLite を使うアプリケーション、SSE 通知を再現する [Mock Hub](mock/hub.js)、実行設定、テスト、Windows 用 CI を追加した。
- [x] **現在値の受信と保存を実装する。** [Hub のSSE接続](src/hub-stream.js)、[入力検証](src/snapshot.js)、[Hub・端末単位のSQLite保存](src/store.js)、切断後の再接続、保存失敗時の通知抑止と参照維持を実装した。
- [x] **認証済みの現在値表示を実装する。** [Web画面・API・ブラウザ向けSSE](src/app.js) にBasic認証を適用し、[保存済み値と状態を表示](public/app.js) する。未取得・未接続・保存失敗・不正データと保存値の時点を区別し、機密情報を出力しない。
- [x] **動作を確認して計画を見直す。** Mock Hub と実ブラウザーで通常表示・再受信・再接続・不正入力・保存失敗・認証拒否を確認し、実Hubでは初回SSE受信・入力検証・一時SQLite保存を確認した。実Hubの継続更新・切断再接続と Linux は未確認として残す。

## 次の作業 — 段階 B の前提整理

**目的:** 現在値の推定を実装する前に、契約帰属と利用枠の同一性を確定できる範囲を定める。確認できない値は推定不可として表示し、仮の比率や名称だけで結合しない。

- [ ] **契約帰属（U2）を確定する。** API換算額を契約・利用枠へ結び付けられる上流項目と、複数契約が混在した場合の推定不可判定を確定する。
- [ ] **利用枠識別（U4）を確定する。** `provider`、アカウント情報、`kind`、`limitId`、`resetsAt` などの組み合わせで同一枠を識別できる範囲と、識別不能時の表示・保存単位を確定する。
- [ ] **成立条件を設計へ反映する。** 決定した条件を [機能要件](docs/requirements.md)、[機能詳細設計](docs/functional-design.md)、[設計書の未確認事項](docs/architecture.md#5-未確認事項と設計への影響) に反映し、推定の実装・テスト範囲を具体化する。

## 次の具体化と進捗の更新

段階 A の作業・検証が一区切りついた時、または前提の変化で進め方を変える必要が生じた時に、全体表の順序・依存関係を見直す。その時点で実行できる次の範囲を選び、「直近の作業」を目的・実装内容・確認方法が分かる項目に更新する。B〜D の詳細をまとめて展開しない。

チェックは実装と必要な確認が済んだ項目に付け、成果物・検証結果への参照を添える。未実施の検証と判断待ちは残し、完成した範囲と混同しない。直近の作業を入れ替える際は、完了結果を「現状」に短く移し、残件を次の範囲へ引き継ぐ。
