# 機能詳細設計

本書は先行して合意した具体仕様を保持する。機能・業務ルールは [機能要件](requirements.md)、責務・保存・並行制御の境界は [アーキテクチャ設計書](architecture.md) を正本とする。追加の記録は [文書方針](document-policy.md) に従い、対応する実装で必要になった時に行う。

## 1. 推定観測と対象期間の対応

| 対応 | 確定している扱い |
| --- | --- |
| 観測の取得経路 | SSE の `snapshot` / `stats` イベントに含まれる現在値を使う。 |
| 観測の組 | 1 回の SSE イベントに含まれる利用額と消費率を 1 組とする。測定時刻のずれは要件で許容した範囲で扱う。 |
| 利用額 | 端末・ツール等に属する累積 API 換算額を使う。採用する具体的な実績項目と契約への対応は U2 として未確定。 |
| 消費率 | 利用枠の `usedPercent` を使い、差分の単位はパーセントポイントとする。 |
| 対象期間 | 同一の利用枠内で `resetsAt` を比較する。利用枠そのものの識別とは分ける。 |

リセット予定時刻 `resetsAt` を基準に対象期間の継続・遷移を判定する。

| 条件 | 扱い |
| --- | --- |
| 有効な `resetsAt` が同一 | 同一期間として扱い、最初と最新の観測から差分計算。 |
| 有効な `resetsAt` が更新された | 新しい対象期間へ遷移したとみなし、起点を再設定（期間を跨ぐ計算は不可）。 |
| `resetsAt` が欠落または不正 | 対象期間を識別できないため推定不可。 |
| 同一 `resetsAt` 内で消費率が減少 | 継続性不明のため推定不可（不明区間を跨ぐ計算は行わない）。 |

上記の値はリセットの発生通知ではない。利用枠の種類だけ、または `resetsAt` だけで異なる契約・利用枠を同一と判定しない。識別の成立条件は設計書の U2・U4 に従う。

## 2. 接続と履歴取得のタイミング

初回接続・再接続時は `GET /api/stats/stream` の SSE 接続を直ちに開始し、現在値の観測・表示を優先する。履歴収集（`GET /api/devices`）は以下の契機で独立して実行する。

| タイミング・状況 | 動作仕様 |
| --- | --- |
| 初回接続時 | Hub が保持する全履歴を取得・保存。 |
| 稼働中の定期実行 | 毎日午前 1 時（稼働マシンの現地時刻）に Hub ごとに保持履歴を取得。 |
| 再接続時 | 当該 Hub の当日の定期取得が未完了である場合に実行。 |
| 通信失敗時 | 1 時間間隔で再試行（SSE の受信・推定は継続）。 |
| 取得成功・前日データなし | データ不在を明示し、次回の定期取得まで待機（短周期での再試行は不要）。 |

※ 定期取得スケジュールは稼働マシンのタイムゾーンを基準とするが、履歴の日付基準（端末の現地日付）および当日除外判定は変更しない。

取得の成功は取得データの保存までを含み、通信失敗と保存失敗を同じ再試行として扱わない。収集を停止した Hub では、上記の全収集通信を明示的な再開まで行わない。

## 3. 受信と停止の判定単位

1 回の GET 応答、または 1 回の SSE データ通知を 1 件として扱う。複数端末分を含む場合も 1 件とする。停止要求の受付時点で、この単位の受信が完了しているかを判定する。

停止時の処理・保存と表示の要件は [要件 第 5.2 節](requirements.md#52-停止時の受信データ)、単一キューと保存順序は [設計書 第 6 節](architecture.md#6-受信データの処理と保存) に従う。具体的なキャンセル API や内部の関数構成は未確定である。

## 4. 未確定事項の扱い

契約・枠の識別、比較基準、日付判定などの未確定事項は [設計書の U1〜U6](architecture.md#5-未確認事項と設計への影響) を参照する。対応する処理の実装時に判断し、必要な決定を該当箇所へ記録する。型・SQL・内部の分岐を含む詳細一覧の完成は求めない。

実装と検証の順序は [開発計画](../PLAN.md) で管理する。構成や保証を変える問題が判明した場合は影響する設計を見直し、合意済み方針から外れる変更は設計方針の事前相談に従う。
