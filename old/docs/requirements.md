# 機能要件

本書は、合意済みの機能、業務ルール、利用者から見た動作の正本とする。システム目標・制約・品質要求・対象外は [設計方針](design-policy.md)、用語は [用語集](../CONTEXT.md) を参照する。実現する責務・境界は [アーキテクチャ設計書](architecture.md)、API 項目の対応や取得時刻等の具体仕様は [機能詳細設計](functional-design.md) に記載する。

2026-09-12 に既存の設計書・README・合意事項から整理した。要件の追加や再合意を目的とせず、成立に必要な未確認事項は設計書の U1〜U6 に残す。

## 1. 機能範囲

| 機能 | 利用者に提供すること |
| --- | --- |
| 現在の利用状況の閲覧 | 複数 Hub が提供する利用枠・消費率・API 換算額を、取得状態と時刻を明示して閲覧できる。 |
| 利用許容量の推定と記録 | 対応する利用額と消費率の増分から推定し、算出時点の結果を履歴として閲覧できる。 |
| 過去実績の収集・閲覧 | 日次・月次の保持履歴を収集・保存し、値の推移の閲覧や比較に利用できる。 |
| Hub 管理 | Web 画面で接続先を登録・一覧表示し、Hub ごとに収集を停止・再開できる。 |
| 手動更新 | 利用者の明示操作で更新し、失敗時は状態と原因を確認して手動復旧できる。 |

端末からの直接収集は行わず、上流 Hub を情報源とする。認証、対応環境、保存期間、Mock Hub、初期対象外の範囲は設計方針に従う。

## 2. 利用許容量の推定

### 2.1 推定に用いる情報

初期版の推定には **SSE で取得した現在値の観測のみ** を使用する。GET で取得した日次・月次実績は推定に使用せず、終了した対象期間の遡及推定も行わない。

### 2.2 計算式

同一の契約・利用枠・対象期間において、API 換算額の増分を $\Delta C$（USD）、消費率の増分を $\Delta p$（パーセントポイント）とした場合、利用許容量は以下の式で算出する。

$$\text{利用許容量} = 100 \times \frac{\Delta C}{\Delta p} \quad (\text{USD})$$

### 2.3 推定可否の判定基準

以下の条件をすべて満たす場合に限り推定を実施し、満たさない場合は「推定不可」とする。

1. API 換算額の増分が対象の契約・利用枠の消費に対応していること（契約の混在がなく帰属が特定できること）。
2. 2 つの観測が同一の対象期間に属し、途中のリセットや欠測により対応関係が不明になっていないこと。
3. $\Delta C > 0$ かつ $\Delta p > 0$ であること（ゼロ・負値・不明値による代用計算は不可）。
4. 定額制の利用枠であり、失効性クレジットや残高メーターではないこと。

契約が複数あっても、実績を契約・利用枠ごとに分離できる範囲では、その単位で判定する。帰属を特定できない利用額を仮の比率で配分したり、未知の利用許容量の比率を設定させたりして推定しない。

### 2.4 比較区間と観測の組み合わせ

1. **観測の組**: 1 回の SSE イベントに含まれる利用額と消費率を 1 組の観測として扱う（測定時刻のずれによる微小誤差は許容）。
2. **最長区間の採用**: 同一対象期間内で比較可能な最初と最新の観測を用い、最も広い区間の差分から計算する。新規観測の到着時は起点を維持して区間を延伸する。
3. **累積額減少の扱い**: 同一端末・同一対象期間で途中に累積額の減少があっても特別扱いせず、最初と最新の観測差分から計算する。
4. **結果の保存**: 新たに算出した推定結果を時系列として追記保存し、過去の推定結果は改変しない。

対象期間の継続・変更・不明を区別し、期間を跨いだ計算や対応関係が不明な区間を跨いだ計算は行わない。リセット予定時刻を用いた具体的な判定は [機能詳細 第 1 節](functional-design.md#1-推定観測と対象期間の対応) に定める。

## 3. 取得情報の表示

プロバイダーやプランによる限定は設けず、取得できた情報は推定可否にかかわらず表示する。

| 項目 | 表示ルール |
| --- | --- |
| 利用枠・消費率等 | 取得できた項目をそのまま表示。 |
| API 換算額 | 取得できた集計単位（Hub・端末・ツール等）を明示して表示（特定契約への配分は行わない）。 |
| 利用許容量 | 計算条件を満たす場合のみ表示。満たさない場合は推定不可と明示し、過去の保存値があれば算出日時とともに併記する。 |

各表示項目には取得状態および更新日時を明記し、未取得の値をゼロ埋めしない。

## 4. 日次・月次実績の保存と利用

履歴収集で取得した保持履歴は、推移の閲覧や比較のために保存する（推定には使用しない）。

| 種別 | 保存・表示ルール |
| --- | --- |
| 日次実績 | **各端末の日付基準で前日以前** を対象とする。当日分は保存せず、SSE 現在値も日次へ転記しない（当日の利用は現在値画面で表示）。 |
| 月次実績 | 返却された各月の実績を保存。当月分は「途中集計」として表示する。 |

- **全履歴の照合**: 端末別の保持履歴全体を照合し、停止中の欠落データや遅れて報告された実績も反映する。
- **非破壊更新**: 同一実績は再取得値で上書き更新し、応答に含まれない過去記録の削除や保存済み推定結果の変更は行わない。
- **日付とタイムゾーン**: 受信した端末ごとの現地日付と数値をそのまま保持し、変換や按分は行わない。当日判定は端末側の日付基準で行う。複数端末の同じ日付を合算する場合は「現地日付の合計」とし、タイムゾーン混在時は同一時間帯の合計ではない旨を明記する。

## 5. Hub 管理と収集の継続

### 5.1 通信切断と収集停止

| 状況 | 利用者から見た動作 |
| --- | --- |
| 収集が有効な Hub へ接続できない | 上流 Hub の停止理由を推測で区別せず「未接続」とし、自動再接続を続ける。 |
| Analytics 上で利用者が収集を停止した | 明示的な再開まで、その Hub の SSE 接続・自動再接続・定期 GET・GET 再試行を止める。 |
| 一部 Hub の収集を停止中 | 保存済みデータを閲覧でき、他 Hub の収集は継続する。 |
| Analytics を再起動した | Hub ごとの収集設定を引き継ぐ。有効な Hub は自動接続し、停止した Hub は停止を維持する。実際の接続状態は起動後の通信で判断する。 |

### 5.2 停止時の受信データ

停止要求の受付時点を取り込みの境界とする。その時点で受信が完了したデータは、処理待ち・処理中を含めて通常どおり処理・保存する。受信途中の通信は完了を待たずに中止し、遅れて届く応答は破棄する。判定単位は [機能詳細 第 3 節](functional-design.md#3-受信と停止の判定単位) に記載する。

受信済みデータの処理終了後に「収集停止」と表示する。保存失敗時は危険な書き込みを止め、「収集停止」と「保存失敗」を併記する。

### 5.3 履歴の定期収集

稼働を続けている間も毎日履歴を取得し、通信失敗時は再試行する。現在値の取得・推定は履歴取得の完了を待たない。取得に成功しても前日分が存在しない場合は不在を表示し、ゼロ補完せず次回の定期取得を待つ。取得の契機・時刻・再試行間隔は [機能詳細 第 2 節](functional-design.md#2-接続と履歴取得のタイミング) を正本とする。

## 6. 分離・重複防止と端末の扱い

- Hub・契約・利用枠ごとに情報を分離する。複数端末に同じ利用枠が現れても、消費率を単純に合算しない。
- 同一内容の再受信を新しい利用実績や推定結果として計上しない。受信時刻や通信経路の違いを新規実績の根拠にしない。
- 同一の利用ログを複数端末へコピー・共有して多重報告する構成はサポートしない。同じアカウントを複数端末で独立利用する構成は対象とする。
- 端末 ID が変わった場合は別端末として扱い、自動で結び付けない。過去データの手動関連付けは [合意済みの将来要件](design-policy.md#合意済みの将来要件) に従い、初期版では実装しない。

## 7. 障害・認証・手動更新の受け入れ条件

これらの品質要求と保証範囲は [設計方針 第 3〜5 節](design-policy.md#3-必要な品質保証と許容する失敗) を正本とする。本書の機能について、少なくとも次を満たすことを受け入れ条件とする。

| 機能・状況 | 受け入れ条件 |
| --- | --- |
| 推定と再受信 | 第 2・6 節の条件と計算区間を守り、対応しない増分の混在や重複計上をしない。 |
| 推定不可・未接続・収集停止 | 取得情報と保存値を閲覧でき、現在の状態と過去値の取得・算出時点を区別できる。 |
| 履歴収集 | 第 4 節の日付基準と更新ルールを守り、現在値・推定結果の更新と混同しない。 |
| 不正データ・保存失敗 | 影響を受ける処理と安全に継続できる処理を分け、保存失敗を成功と表示しない。原因を追跡できる。 |
| 認証・管理操作 | Web 画面・API・ブラウザ向け SSE を保護し、外部入力の検証と重要操作の CSRF 対策を行う。機密情報をログやレスポンスへ出さない。 |
| 手動更新の失敗 | DB・履歴を保全し、失敗の事実・原因と手動復旧に必要な情報を得られる。 |

検証方法と実機で未確認の範囲はアーキテクチャ設計書で管理する。この受け入れ条件の記載は、動作試験の実施・成功を意味しない。
