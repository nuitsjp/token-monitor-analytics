# 設計・文書作成の標準

標準 ID: `project-template-design-and-documentation` / 版: **13**

本書および同階層の標準文書は配布元からの輸入物です。本文は編集せず、プロジェクト固有の差分は [採用記録](../document-policy.md#adoption) に理由とともに記録します（改変は `scripts/doc_check.py` で検知されます）。

<a id="implementation-principles"></a>
## 1. 適用原則

現在の要件を満たす最小限かつ最も単純な構成から着手します。単純さは行数やファイル数だけでなく、理解・実装・変更・検証・運用の総負担の少なさで判断します。既存機能の活用、ライブラリ導入、独自実装を同一基準で比較し、真に必要なコードと文書のみを追加します。

- 依頼範囲外の機能追加、無関係なリファクタリング、汎用化目的の過剰な共通基盤作成は行いません。
- 後方互換性やフォールバックは、明示的な要件がある場合のみ実装します（暗黙の代替値補完は不可）。
- 性能改善は計測結果に基づき、問題箇所に限定して実施します（推測による先行対策は不可）。
- 入力検証はシステム境界（ユーザー入力・外部連携等）で行い、内部での不要な重複検査や過剰防護は避けます。
- テストは合意した振る舞いと実際のリスクを検証します（形式的追認や網羅率目的の作成は不可）。作成・変更の時点は [モック標準の実施手順](mock-driven-development.md#workflow) に従います。

<a id="design-decisions"></a>
## 2. オーバーエンジニアリングの抑止

新しい層、抽象化、依存ライブラリ、外部サービス、運用機構を追加する場合は、以下を説明できることを条件とします。

1. 現在の要件や確認済みリスクの何に対応するか。
2. 導入しない場合、具体的にどのような問題が生じるか。
3. 局所的な修正、より単純な構成、手動運用ではなぜ不十分か。
4. なぜ今必要であり、導入・保守・運用の総負担を受け入れられるか。

将来要件への対応は個別に必要性を判断し、根拠が不十分な場合は実装を見送ります。

<a id="document-roles"></a>
## 3. オーバードキュメンテーションの抑止

決定事項の正本は1箇所に集約し、重複記述を排除します。文書には現在の状態のみを記録し、経緯は git、証跡はテストと CI に委ねます。

- **新設・分割の基準**: 「誰が何を判断するために読むか」「既存正本への追記ではなぜ不十分か」を説明できる場合のみ新設します。コードから自明な内容の逐語説明や他文書の転記は行いません。
- **記入欄の取捨選択**: 判断に必要な項目のみを使用し、該当しない項目は削除できます（非該当の理由が重要な場合のみ記録）。推測による未確定事項の追加は避けます。
- **必要な情報の維持**: 要求、根拠、責務、障害時の動作、検証条件など、実装や受け入れ判断に必要な情報は省略しません。
- **置かないもの**: 自プロジェクトの実行で生じたスクリーンショット、生ログ、ハッシュ一覧、検証成果物ディレクトリはリポジトリに配置しません（ローカル絶対パスも不可）。外部システムの実測応答のみ、取得日時・方法・対象版を添えて `docs/reference/` に1世代保存できます。
- **採用後の上限**: `docs/project.md` 300行、`docs/architecture.md` 200行、`docs/document-policy.md` 100行を超えた場合は、重複削除、確定先への参照置換、または分割を行います。

| 情報の種類 | 記録内容 |
| --- | --- |
| 事実 | 情報源、対象版、確認範囲（仮定と明確に区別する） |
| 合意 | 決定内容、範囲、判断者、日付、利用者の応答原文 |
| 実装 | 対象コードと仕様との対応（コードの存在自体は合意や検証を意味しない） |
| 検証 | 実行条件、対象版、合否（証跡は CI 実行への参照、またはコミット・日付・コマンド・合否の1行） |

判断に必要な未確定事項は追跡用の計画文書を新設せず、停止点で利用者に確認して確定した内容のみを記録します。過去の文書や実装は証跡として扱い、現行仕様へ暗黙的に引き継ぎません。

<a id="architecture-method"></a>
## 4. 全体設計と先行してよい成果物

全体設計は `docs/architecture.md` に集約します。システムコンテキスト（L1）とコンテナ（L2）は必須とし、コンポーネント図（L3）は必要なコンテナのみ作成、コード図（L4）は作成しません。実現パターンには、代表クラスの役割、主成功系列のシーケンス図1本、状態更新の主体、結果確定点、障害時の停止・継続範囲（競合や通信断想定時はトランザクション境界）、モック境界を定義します。

ユースケース着手前に先行作成できるのは以下の2点に限られます。

1. 外部システムから取得した事実（実応答、固定版ソース等）。
2. 後から変更すると複数ユースケースやデータモデル、コンテナ構成の再作業が生じる決定（UC-1 と次ユースケースが扱う論理データモデルの実体と関係を含む）。

未着手の系列・画面・シナリオ図、テーブル定義・カラム型・移行手順、骨組みだけの設計書は先行作成しません。決定事項は `docs/architecture.md` 第4節に出所付きで記録し、全体設計の合意を得てから実処理接続に進みます。

対象系列の動作合意後（UI 確認不要の系列は段階1確認後）、追加・変更するテーブル設計を `docs/architecture.md` 第5節に記述します。ER図とテーブル定義で責務と関係、カラムと型、主キー・外部キー・一意制約・NULL可否を示し、既存設計がある場合は変更点を提示します。系列 ID、対象テーブルと変更範囲、提示コミット、論点と回答、利用者の応答原文を同節に記録し、合意を得てから段階4および設計に依存する実装へ進みます（設計変更がなければ再合意不要）。

<a id="completion"></a>
## 5. 判断の記録と完了基準

設計判断の理由は `docs/architecture.md` 第4節に1行で記録します。ADR（設計判断記録）は「変更負担が大きい」「理由が非自明」「重要なトレードオフがある」のすべてを満たし、1行の記録では不足する場合のみ作成します。

- **設計の完了条件**: 主要系列について、データ整合性、状態更新の主体、結果確定点、障害時の停止・継続範囲、検証方法が明確になった時点で設計完了とします。
- **機能の完了条件**: 合意範囲の実装と段階5の利用者承認、対象系列の段階6で追加・更新した E2E テストおよび実環境検証の合格、必須修正の解消をもって完了とします（モック合意やコードの存在のみでは完了とみなしません）。
- **レビュー指摘の分類**: 指摘は「必須修正（要件充足に必須）」「任意改善（完了を妨げない）」「対象外」に分類します。必須修正が残る場合は未完了とし、合意済みのリスク受容事項を根拠なく再審議しません。

<a id="agreement-changes"></a>
## 6. 合意を保護する変更手続き

1. 着手前に、採用規則、正本の責務、保護する合意、依頼範囲を確認する。
2. 合意済みの要件・制約・仕様を変更・緩和する場合は、変更内容・理由・影響を明示し、合意を得てから適用する（表現改善や承認済み変更への再承認は不要）。
3. 完了前に、着手時の合意との差分、検証結果、正本間のリンク整合性を確認する。
4. 規約・標準・文書方針の文言改訂は実装作業と同一セッションで行わない。必要と判断した場合は利用者に伝え、実装の区切りで独立した変更として扱う。
5. 必須コミットは、系列ごとに段階3のモック提示時点（UI 確認不要の系列は段階1の議論が完了し、利用者が確認した本文を保存した時点）、段階5の完成系監査の提示時点、段階6の完了時点とする。テーブル設計合意が必要な場合は、その提示時点もコミットする（各合意の版はそれぞれの提示コミットで指定し、UI 確認不要の系列では確認後の保存コミットを用いる）。

変更の検討と調査は着手中のユースケースに必要な範囲にとどめます。ユースケース案の検討・保存は [提示と保存の手順](mock-driven-development.md#discussion) に従います。
