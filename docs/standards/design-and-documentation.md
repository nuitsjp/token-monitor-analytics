# 設計・文書作成の共通標準

標準 ID: `design-and-documentation` / 版: **1**

<a id="adoption"></a>
## 1. 適用とプロジェクト固有ルールの分離

本書は、複数のプロジェクトで横断的に再利用する設計および文書作成の標準ルールを定めます。
各プロジェクトの個別ルール（採用バージョン・適用範囲・文書配置）は「文書方針」に、製品固有の要件・制約・品質目標は「設計方針」に記録して分離します。新版の公開や他プロジェクトの個別判断は自動適用されず、プロジェクトごとに明示的に取り込みを判断します。

<a id="design-decisions"></a>
## 2. アーキテクチャ設計・仕組み追加の判断原則

設計の追加や抽象化は、システム全体の理解・変更・検証・運用の負担を総合的に軽減するために行います。形式的な美しさや安易な将来予測に基づく過剰な抽象化・フォールバック・後方互換処理は避け、システム構造や運用に影響を与える仕組みを導入する場合は、以下の4点を説明できる必要があります。

1. **現在の要件・リスクまたは合意済みの将来要件**: なぜその仕組みが必要となる具体的な根拠があるか。
2. **追加しなかった場合の問題**: 導入を見送った場合にどのような課題・障害が生じるか。
3. **単純な代替案が不十分な理由**: 局所的な修正、シンプルな構成、または手動運用では解決できない理由。
4. **今導入すべき理由と負担の比較**: 後回しにせず現時点で導入する合理性と、導入に伴う保守・学習負担の受容。

<a id="document-roles"></a>
## 3. 文書の役割と正本管理

- **正本の一元化**: 同一の決定事項に対する正本は1箇所に限定します。用語集は定義のみ、設計書は振る舞いやデータ構造、計画書は到達点・順序・未決事項を扱います。入口文書（README 等）は概要と参照案内にとどめます。
- **事実・合意・実装・検証の分離**: 調査した事実には情報源と確認範囲、合意には決定内容、実装には対象コード、検証には実行条件と結果を明記します。コードが存在することのみをもって仕様合意や検証完了とみなしてはなりません。
- **未決事項の追跡**: 未確定の課題には一意の ID、前提事実、影響・依存範囲、解消条件を記録して追跡します。未決事項に依存する設計は「未完了」として扱い、独立した作業は並行して進めます。
- **過去資料の位置づけ**: 過去の実装や旧文書は証跡として参照し、現行仕様や指示としては扱いません。確定した現行仕様は最新の正本へ反映します。
- **文書の作成と更新**: 文書は必要性が生じた時点で作成します。文書の新設・分割・統合を行う場合は、正本間の参照リンクや依存関係を整合させます。


<a id="architecture-method"></a>
## 4. アーキテクチャの記述と設計手順

アーキテクチャ記述は arc42 の構成を骨格とし、構造の可視化には C4 モデルを採用します。形式的な全項目記述ではなく、識別規則、エンティティごとの状態管理、および重要シナリオの定義を中心に進めます。

| C4 ビュー | 表現する内容 |
| --- | --- |
| Context 図 | 利用者、対象システム、および外部システム間の関係性と境界 |
| Container 図 | アプリケーションの実行境界、データストアの保存境界、および通信プロトコル（単一プロセス構成でも省略しない） |
| Component 図 | Container 内部の主要コンポーネントの責務と依存関係 |

### 設計の標準手順
1. **外部仕様と事実確認**: API や外部システムのデータ構造・取得可能項目を確認し、具体例を用いて識別規則と重要シナリオを整理する。
2. **境界の定義**: Context 図および Container 図でシステム境界、保存境界、認証境界を定義する。
3. **状態とシナリオの設計**: 正常系および異常系（競合・通信断・障害・復旧）シナリオから、更新担当、結果の確定契機、並行制御、永続化トランザクションを決定し、Component に反映する。
4. **判断理由と検証基準の確立**: 設計判断の理由と検証条件を記録し、品質要求や制約事項と照合する。

<a id="completion"></a>
## 5. 判断の記録・検証・完了判定

重大な設計判断は、設計書内の該当箇所または ADR（Architecture Decision Records）に記録します。ADR は、**変更負担が大きい**、**理由が自明でない**、**実際の選択肢とトレードオフが存在する**のすべてを満たす場合に作成します。

### 初期設計の完了基準
重要シナリオごとに、以下の5項目が具体的に説明できる状態をもって初期設計の完了とみなします。

1. **同一性判定**: 何を同一と判定し、どの情報を対応付けるか。
2. **更新担当**: 誰が、どの対象の状態を更新するか。
3. **結果確定と通知**: いつ保存・計算結果が確定し、利用者や連携先へ何を通知するか。
4. **異常系の振る舞い**: 失敗時に何が残り、何を停止・継続するか。
5. **検証方法**: 期待動作をどのような手段（テスト・実機検証等）で検証するか。

※ 単に文書を作成したことのみをもって完了とせず、検証条件が明確であることを重視します。

<a id="agreement-changes"></a>
## 6. 合意の変更と保護の手続き

プロジェクトで合意された要件、制約、設計手法、完了基準の逸脱を防ぐため、以下の手続きを適用します。

1. **着手前**: 採用バージョン、適用範囲、正本の役割、保護対象の合意、および今回許可された変更範囲を確認する。
2. **変更時**: 要件・制約・必須事項・正本の責務・完了基準を、明示的な合意なく削除・緩和しない。意図の変更を伴う修正を行う場合は、変更前後の内容・理由・影響範囲を提示して承認を得てから適用する（文脈を維持した表現の改善や既承認事項の反映には再承認を求めない）。
3. **完了前**: 着手前の合意内容および今回の指示に照らし、必須事項の欠落や未決事項の誤った完了扱いがないか差分を照合する。

※ 本手続き自体および保護対象の規則も、本変更管理の対象となります。
