# 設計・文書作成の標準

標準 ID: `project-template-design-and-documentation` / 版: **3**

本書と同階層の標準は配布元からの輸入物です。本文を編集せず、プロジェクト固有の差分は [採用記録](../document-policy.md#adoption) の「プロジェクト固有の差分と理由」に理由付きで記録します。`scripts/doc_check.py` が本文の改変を報告します。

<a id="implementation-principles"></a>
## 1. 適用原則

現在の要件を満たす最小限かつ最も単純な構成から着手します。単純さは、コード行数やファイル数だけでなく、理解・実装・変更・検証・運用の総負担の少なさで判断します。既存機能の活用、ライブラリ導入、独自実装を同一基準で比較し、文書もコードも必要なもののみを追加します。

- 依頼範囲外の機能追加、無関係なリファクタリング、汎用化を目的とした過剰な共通基盤は作りません。
- 後方互換性やフォールバックは、明示的な要件がある場合のみ実装します（暗黙的な代替値の補完は行いません）。
- 性能改善は計測結果に基づき、問題箇所に限定して実施します（推測による先行対策は行いません）。
- 入力検証はシステム境界（ユーザー入力・外部連携等）で行い、内部での不要な重複検査や過剰な防護実装は避けます。
- テストは期待される振る舞いと実際のリスクを検証します（実装の形式的追認や網羅率のみを目的とした作成は避けます）。

<a id="design-decisions"></a>
## 2. オーバーエンジニアリングの抑止

新しい層、抽象化、依存ライブラリ、外部サービス、運用機構を追加する場合は、以下を説明できることを条件とします。

1. 現在の要件や確認済みリスクの何に対応するか。
2. 導入しない場合、具体的にどのような問題が生じるか。
3. 局所的な修正、より単純な構成、手動運用ではなぜ不十分か。
4. なぜ今必要であり、導入・保守・運用の総負担を受け入れられるか。

将来の要件であっても、現時点で実装する必要性は個別に判断します。根拠が不十分な場合は計画への記録にとどめ、実装を見送ります。

<a id="document-roles"></a>
## 3. オーバードキュメンテーションの抑止

決定事項ごとの正本は1箇所に集約し、仕様の重複記述を排除します。文書には現在の状態のみを書き、経緯は git、証跡はテストと CI に置きます。

- **新設・分割の基準**: 「誰が何を判断するために読むか」「既存正本への追記ではなぜ不十分か」を説明できる場合のみ新設します。コードから自明な内容の逐語説明や、他文書の転記は行いません。
- **記入欄の取捨選択**: 判断に必要な項目のみを使用し、該当しない項目は削除できます（非該当の理由が重要な場合のみ記録します）。推測による未確定事項の追加は避けます。
- **必要な情報の維持**: 要求、根拠、責務、障害時の動作、検証条件など、実装や受け入れ判断に必要な情報は省略しません。
- **置かないもの**: 自プロジェクトの実行で生じたスクリーンショット、生ログ、ハッシュ一覧、検証成果物のディレクトリはリポジトリに置きません。ローカル絶対パスを書きません。外部システムから取得した実測応答だけは、取得日時・方法・対象版を添えて `docs/reference/` に1世代保存できます。
- **採用後の上限**: `PLAN.md` 100行、`docs/project.md` 300行、`docs/architecture.md` 200行、`docs/document-policy.md` 100行を超えたら、重複の削除、確定先への参照への置換、または分割を行います。

| 情報の種類 | 記録内容 |
| --- | --- |
| 事実 | 情報源、対象版、確認範囲（仮定と明確に区別する） |
| 合意 | 決定内容、範囲、判断者、日付、利用者の応答の原文 |
| 実装 | 対象コードと仕様との対応（コードの存在自体は合意や検証を意味しない） |
| 検証 | 実行条件、対象版、合否。証跡は CI の実行への参照、またはコミット・日付・コマンド・合否の1行 |

未決事項は一意な ID、前提、影響範囲、解消条件で追跡します。過去の文書や実装は証跡として扱い、現行仕様へ暗黙的に引き継ぎません。

<a id="architecture-method"></a>
## 4. 全体設計と先行してよい成果物

全体設計は `docs/architecture.md` に置きます。システムコンテキスト（L1）とコンテナ（L2）の欄は必須で、図は Mermaid の flowchart または C4 専用構文、系列は sequenceDiagram で描きます。コンポーネント図（L3）は必要なコンテナのみ、コード図（L4）は作りません。実現パターンは、代表クラスの役割、主成功系列のシーケンス図1本、状態更新の主体、結果確定点、障害時の停止・継続範囲（競合や通信断が想定される場合はトランザクション境界）、モックに置き換える境界を持ちます。

ユースケースに着手する前に先行して作ってよいのは次の2種類だけです。

1. 外部システムから取得した事実（実応答、上流ソースの固定版）。
2. 後で変えると2つ以上のユースケース、データモデル、コンテナ構成をやり直すことになる決定。UC-1 と次のユースケースが触る論理データモデル（実体と関係のみ）を含みます。

未着手ユースケースの系列・画面・シナリオ図、未着手ユースケースのテーブル定義・カラム型・移行手順、章立てだけの設計書は先行して書きません。決定は `docs/architecture.md` 第4節に出所付きで記録し、実装を捨てても捨てません。全体設計は利用者の合意を得てから実処理接続に進みます。

<a id="completion"></a>
## 5. 判断の記録と完了基準

設計判断の理由は `docs/architecture.md` 第4節に1行で記録します。ADR（設計判断記録）は「変更負担が大きい」「理由が非自明」「重要なトレードオフがある」のすべてを満たし、第4節の1行では足りない場合のみ作成します。

- **設計の完了条件**: 主要な系列について、データの整合性、状態更新の主体、結果確定点、障害時の停止・継続範囲、および検証方法が明確になった時点で設計完了とします。
- **機能の完了条件**: 合意範囲の実装、必要なテストおよび実環境検証の合格、必須修正の解消をもって完了とします。モックでの合意やコードの存在のみでは完了とはみなしません。
- **レビュー指摘の分類**: 指摘は「必須修正（要件充足に必須）」「任意改善（完了を妨げない）」「対象外」に分類します。必須修正が残る場合は未完了とし、合意済みのリスク受容事項を根拠なく再審議しません。

<a id="agreement-changes"></a>
## 6. 合意を保護する変更手続き

1. 着手前に、採用規則、正本の責務、保護する合意、依頼範囲を確認する。
2. 合意済みの要件・制約・仕様を変更・緩和する場合は、変更内容・理由・影響を明示し、合意を得てから適用する（表現の改善や承認済みの変更に対する再承認は不要）。
3. 完了前に、着手時の合意との差分、検証結果、正本間のリンク整合性を確認する。
4. 規約・標準・文書方針の文言改訂は、実装作業と同じセッションで行わない。必要と判断した場合は未決事項として記録し、実装の区切りで独立した変更として扱う。
5. 必須のコミットは、段階3でモックを提示した時点と、段階5の完了時点の2つとする。合意の版は提示時点のコミットで指す。

変更の検討と調査は、着手中のユースケースに必要な範囲で進め、確認が必要な判断事項のみを具体的に提示します。
