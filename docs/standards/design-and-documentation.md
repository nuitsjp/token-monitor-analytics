# 設計・文書作成の共通標準

標準 ID: `design-and-documentation` / 版: **1**

<a id="adoption"></a>
## 1. 適用とプロジェクト固有ルールの分離

本書は再利用する設計・文書作成のルールを定める。各プロジェクトの文書方針に採用版・適用範囲・実際の文書配置を、設計方針に製品の目標・機能・制約・品質要求を記録する。本書は採用版の内容で取り込み、新版の公開や他プロジェクトの判断を自動適用しない。

<a id="design-decisions"></a>
## 2. 設計を追加する判断原則

理解・変更・検証・運用の全体負担を減らす。形式的な品質や部品数・コード量・依存関係の削減を目的にせず、ライブラリ・分割・階層化等は品質を保ちながら負担を減らせる場合に採用する。構造や運用に影響する仕組みを追加するときは、次の4点を説明する。

1. 現在の要件、具体的なリスク、または合意済みの将来要件。
2. 追加しなかった場合に生じる問題。
3. 単純な構成、局所的な修正、手動運用では不十分な理由。
4. 今必要な理由と、見送った場合の負担。

漠然とした将来への備えやベストプラクティスだけを理由に、抽象化・フォールバック・後方互換対応を追加しない。合意済みの制約や受容するリスクを独自の品質目標で置き換えない。

<a id="document-roles"></a>
## 3. 文書の役割と記録の区別

- 同じ決定の正本は一つにする。用語集は意味だけ、設計書は識別・処理・保存等の仕様、計画は到達点・順序・未決・未実装・未検証を扱う。入口の文書は案内と参照手順に絞る。
- 事実には情報源と確認範囲、合意には決定内容、実装には対象コード、検証には条件と結果を残す。調査版と現行版、退避した実装と現行実装を区別し、コードの存在だけで合意・検証済みとしない。
- 未決事項には ID、必要な事実、影響・依存、解消条件を記録する。推測で埋めず、依存する設計は未完とする。独立した作業は継続する。
- 過去資料は証跡として参照し、現行仕様や作業指示として適用しない。確定済み仕様は現行の正本に置く。
- 文書は内容が生じたときに作る。新設・分割・統合では、正本、配置、参照を更新し、決定・ID・確認状況・依存・解消条件を保持する。空の文書を埋めるために書かず、必須内容の不足は未完として追跡する。

<a id="architecture-method"></a>
## 4. アーキテクチャの記述と設計手順

arc42 を必要な内容に絞った骨格とし、構造は C4 で表す。設計の中心は識別・対象ごとの状態・重要シナリオとする。目標・制約、境界、解決方針、構成、実行時動作、配置、横断的概念、判断、品質・リスク、用語を各正本へ割り当てる。全12節を形式的に埋めず、採用する章と記載先を文書方針で定める。

| C4 のビュー | 示す内容 |
| --- | --- |
| Context | 利用者、対象システム、外部システムの関係と範囲。 |
| Container | アプリケーションの実行境界と通信、データストアがある場合は保存境界。単一プロセスを理由に省略しない。 |
| Component | Container 内の主要な責務と依存。部品数や旧実装の分割を先に固定しない。 |

設計は次の順で進める。

1. 外部仕様と取得できる情報を確認し、具体例で用語・同一性・重要シナリオを確かめる。部品分割より先に識別の根拠を決める。
2. Context と Container で境界を確認する。要件に含まれる保存・認証の境界も示す。
3. 状態とシナリオから更新担当、結果の確定点、並行制御、失敗時の停止・継続を決め、Component に反映する。永続化には保存確定点、排他制御、トランザクション範囲を定める。
4. 判断理由と検証条件を記録し、目標・制約・品質要求と照合する。

対象が異なり同時に成立する状態は分け、遷移・相互関係・出力や通知を定義する。正常系と、要件に関係する競合・境界・停止・障害・復旧のシナリオで確かめる。図と本文の範囲を揃え、合意済み・実装済み・未決を区別する。

存在しない保存先や画面を形式のために設けない。合意済み対象の省略は第6節に従う。4+1 は補助の観点として使え、UML や不要なビューを必須にしない。採用済みの arc42・C4 を代替しない。

<a id="completion"></a>
## 5. 判断の記録・検証・完了判定

判断理由は関係する設計箇所に残す。第2節に該当する判断は4点を説明する。ADR は、**変更負担が大きい・理由が自明でない・実際の選択肢とトレードオフがある**の全条件を満たす判断に限り、必要になったときに作る。必要な内容を書き、文章量は固定しない。

初期設計は、重要シナリオごとに次の5項目を説明できることを完了基準とする。

1. 何を同一と判定し、どの情報を対応付けるか。
2. 誰が、どの対象の状態を更新するか。
3. いつ結果が確定し、利用者・連携先へ何を出力・通知するか。
4. 失敗時に何が残り、何を停止・継続するか。
5. 期待動作を何によって検証するか。

未決の登録や文書・図の数だけで設計完了としない。設計、実装、検証の完了を区別し、製品の完了条件は設計方針に定める。

検証は受け入れ条件、重要な境界値、具体的な失敗、再発防止を対象とする。指摘は合意に照らして「必須修正・任意改善・対象外」に分け、未実施の検証と影響を明記する。

<a id="agreement-changes"></a>
## 6. 合意の変更と逸脱を防ぐ手順

1. **着手前**：採用版・範囲、正本、必須事項、完了基準、未決の扱いと、今回変更を認められた範囲を確認する。比較基準は未コミットの合意済み変更も含む着手時点の文書と合意とする。
2. **変更時**：要件・制約・手法・必須事項・正本の責務・完了基準・未決の扱いを、明示指示なく削除・弱化・任意化しない。「整理」「簡素化」「実装を進める」は意味の変更を認める指示ではない。未承認の変更は、変更前後・理由・影響を提示して承認を得てから適用する。意味を保つ編集や承認済み変更に再承認を求めない。矛盾は報告し、影響する判断を独断で確定せず、独立した作業を続ける。
3. **完了前**：変更前の基準と今回の明示指示に照らし、移動・削除した必須内容の行き先、配置・参照・図と本文の整合、未決・未実装・未検証の扱いを確認する。変更後の方針だけで適合を判定しない。意味の変更の有無、確認範囲、残る未決・未検証を報告する。

この手続きは、共通標準の採用範囲・プロジェクトの保護対象・手続き自体にも適用する。保護規則を先に外して必須事項を変更しない。

要求・適用範囲・完了基準・変更手続きの意味を改訂するときは版を進め、内容と理由を記録する。各プロジェクトの採用版更新にも上記手続きを適用する。誤字や意味を保つ参照修正では版を変えない。
