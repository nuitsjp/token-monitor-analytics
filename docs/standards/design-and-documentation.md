# 設計・文書作成の標準

標準 ID: `project-template-design-and-documentation` / 版: **17**

本書および同階層の標準文書は配布元からの輸入物です。本文は編集せず、プロジェクト固有の適用範囲と差分は [文書方針](../document-policy.md#adoption) に記載します（改変は `scripts/doc_check.py` で検知されます）。初回生成後のプロジェクト文書は採用先で管理し、継続更新する共通規則は本標準と [モック標準](mock-driven-development.md) を参照します。

<a id="implementation-principles"></a>
## 1. 適用原則

現在の要件を満たす最小限かつ最も単純な構成から着手します。単純さは行数やファイル数だけでなく、理解・実装・変更・検証・運用の総負担の少なさで判断します。既存機能の活用、ライブラリ導入、独自実装を同一基準で比較し、真に必要なコードと文書のみを追加します。

- 依頼範囲外の機能追加、無関係なリファクタリング、汎用化目的の過剰な共通基盤作成は行いません。
- 後方互換性やフォールバックは、明示的な要件がある場合のみ実装します（暗黙の代替値補完は不可）。
- 性能改善は計測結果に基づき、問題箇所に限定して実施します（推測による先行対策は不可）。
- 入力検証はシステム境界（ユーザー入力・外部連携等）で行い、内部での不要な重複検査や過剰防護は避けます。
- テストは合意した振る舞いと実際のリスクを検証します（形式的追認や網羅率目的の作成は不可）。モック標準の対象作業では、追加・更新の時点は [モック標準の実施手順](mock-driven-development.md#workflow) に従います。対象外の不具合修正や内部変更では、実装と同時に必要なテストを追加・更新し、合格を維持します。

<a id="design-decisions"></a>
## 2. オーバーエンジニアリングの抑止

新しい層、抽象化、依存ライブラリ、外部サービス、運用機構を追加する場合は、以下を説明できることを条件とします。

1. 現在の要件や確認済みリスクの何に対応するか。
2. 導入しない場合、具体的にどのような問題が生じるか。
3. 局所的な修正、より単純な構成、手動運用ではなぜ不十分か。
4. なぜ今必要であり、導入・保守・運用の総負担を受け入れられるか。

将来要件への対応は個別に必要性を判断し、根拠が不十分な場合は実装を見送ります。

<a id="document-roles"></a>
## 3. オーバードキュメンテーションの抑止

情報ごとの正本は [文書方針](../document-policy.md#sources) で定め、本文はその1箇所だけを更新し、他の箇所は参照リンクにします。文書には現在有効な仕様・制約・手順のみを記載します。仕様変更時は既存の記述を置き換え、決定理由、採択・却下の経緯、ADR、合意・監査の記録、応答原文、進捗、過去の検証結果は残しません。

- **新設・分割の基準**: 「誰が何を判断するために読むか」「既存正本への追記ではなぜ不十分か」を説明できる場合のみ新設します。コードから自明な内容の逐語説明や他文書の転記は行いません。
- **記入欄の取捨選択**: 判断に必要な項目のみを使用し、該当しない任意項目は削除できます。以下で必須とする項目は維持します。適用範囲の条件が必要な場合は現在の制約として記載し、推測による未確定事項の追加は避けます。
- **必要な情報の維持**: 要求、確認済みの前提、責務、障害時の動作、検証条件など、実装や受け入れ判断に必要な現在の情報は省略しません。設計の選択理由や検討経緯は含めません。
- **置かないもの**: 自プロジェクトの実行で生じたスクリーンショット、生ログ、ハッシュ一覧、検証成果物ディレクトリはリポジトリに配置しません（ローカル絶対パスも不可）。外部システムの実測応答のみ、取得日時・方法・対象版を添えて `docs/reference/` に1世代保存できます。
- **採用後の上限**: `docs/project.md` 300行、`docs/architecture.md` 200行、`docs/document-policy.md` 100行を超えた場合は、重複削除、確定先への参照置換、または分割を行います。

| 情報の種類 | 記録内容 |
| --- | --- |
| 事実 | 情報源、対象版、確認範囲（仮定と明確に区別する） |
| 仕様・制約 | 現在有効な内容と適用範囲（利用者の確認は会話で行い、文書には結果の仕様のみを反映） |
| 実装 | 対象コードと仕様との対応（コードの存在自体は合意や検証を意味しない） |
| 検証手順 | 実行条件、コマンド、期待結果（実績や合否表は保存せず、最新コードでテストを実行） |

判断に必要な未確定事項は停止点で利用者に確認し、確定した仕様のみを反映します。過去の文書や実装を現行仕様へ暗黙的に引き継ぎません。完了前に今回変更した事実を関連文書から検索し、重複を参照に置き換え、古い説明を更新または削除します。静的検査は記録形式と完全一致する長い本文の重複を検出し、言い換えた重複や実装との不一致はレビューで確認します。

<a id="usecase-documents"></a>
### ユースケースとシナリオの構造

連番IDを設けず名称で識別し、ユースケース名はプロジェクト内、シナリオ名は所属ユースケース内で一意にします。親は `docs/usecases/<名称>/README.md`、子はその直下の `scenarios/<名称>.md` に配置し、それぞれ先頭の `# 名称` をディレクトリ名・ファイル名と一致させます。名称変更時はパスと文書・テストの参照も更新します。

| 文書 | 必須項目 | 任意項目 |
| --- | --- | --- |
| ユースケース | `## 主アクター`、`## 目的`、`## シナリオ`（子への個別リンクのみ）、`## 実現パターン`（設計へのリンク） | `## 前提`、`## 共通の受け入れ条件`など共通事項 |
| シナリオ | `- 種別: 主成功` または `拡張`、`- UI確認: 要` または `不要`、`## 手順`、`## 受け入れ条件`、主成功の `## 開始条件` または拡張の `## 分岐条件` | 必要な補足 |

親の一覧は所属する全シナリオを1回ずつ参照し、主成功は1本とします。拡張の分岐条件には分岐する操作・状態と条件を記載し、変動する手順番号だけで参照しません。固有の条件・手順・期待結果は子、共通事項は親だけで管理します。所属は配置で決まり、別のID・所属項目は置きません。
未着手のユースケースはプロジェクト一覧だけに記載でき、本文とリンクは不要です。作成する実仕様の必須項目は空欄や `{{...}}` のままにしません。配布する作成用雛形は実仕様ではなく、構造検査の対象外です。文書検査は必須項目、選択値、リンクと一覧の対応を確認し、仕様の妥当性・承認は判定しません。

<a id="architecture-method"></a>
## 4. 全体設計と先行してよい成果物

全体構造・共通方針・設計上の制約は `docs/architecture.md` に集約します。システムコンテキスト（L1）とコンテナ（L2）は必須とし、コンポーネント図（L3）は必要なコンテナのみ作成、コード図（L4）は作成しません。実現パターンの名称・適用条件・関与コンテナと設計へのリンクを同書に置き、具体的な設計は `docs/design/UCP-n.md`（先頭見出しは `# UCP-n. 名前`）に分離します。代表クラスの役割・実装パス、主成功系列のシーケンス図1本、状態更新の主体、結果確定点、障害時の停止・継続範囲（競合や通信断想定時はトランザクション境界）、モック境界、UC 固有の逸脱を記録します。既存パターンで説明できないユースケースが生じた場合のみ、[仕組みの追加基準](#design-decisions) を満たして新設します。対象 UC から必要な設計だけを参照し、パターンの本文は UC ごとに複製しません。

ユースケース着手前に先行作成できるのは以下の2点に限られます。

1. 外部システムから取得した事実（実応答、固定版ソース等）。
2. 後から変更すると複数ユースケースやデータモデル、コンテナ構成の再作業が生じる決定（最初と次のユースケースが扱う論理データモデルの実体と関係を含む）。

未着手の系列・画面・シナリオ図、テーブル定義・カラム型・移行手順、骨組みだけの設計書は先行作成しません。現在有効な設計上の制約は `docs/architecture.md` 第4節に集約し、全体設計の合意を会話で得てから実処理接続に進みます。

対象系列の動作合意後（UI 確認不要の系列は段階1確認後）、追加・変更するテーブル設計を `docs/design/data.md`に記述します。ER図とテーブル定義で責務と関係、カラムと型、主キー・外部キー・一意制約・NULL可否を示します。既存設計がある場合は変更範囲と論点を会話で提示し、合意を得てから段階4および設計に依存する実装へ進みます（設計変更がなければ再合意不要）。文書には現在のテーブル設計のみを残します。

DBを使わない場合は `docs/design/data.md` にその旨と実際の保存形式を記し、不要な記入欄を削除します。保存しない場合は同書を作らず、アーキテクチャにその旨を記し、参照も除きます。移行スクリプトは実装として管理し、運用・検証手順は `docs/project.md` から参照します。

<a id="completion"></a>
## 5. 完了基準

設計の理由や選択肢は判断時の会話で説明し、文書には現在有効な設計のみを反映します。既存のADRや決定履歴に現行仕様が含まれる場合は、その内容を対応する正本へ統合して記録を削除します。

- **設計の完了条件**: 主要系列について、データ整合性、状態更新の主体、結果確定点、障害時の停止・継続範囲、検証方法が明確になった時点で設計完了とします。
- **機能の完了条件**: 合意範囲の実装と段階5の利用者承認、対象系列の段階6で追加・更新した E2E テストおよび実環境検証の合格、必須修正の解消をもって完了とします。変更のたびに必要な既存テストを実行して合格を維持し、過去の合格を今回の検証の代わりにしません。結果と未実施の検証は会話または CI で報告します。
- **レビュー指摘の分類**: 指摘は「必須修正（要件充足に必須）」「任意改善（完了を妨げない）」「対象外」に分類します。必須修正が残る場合は未完了とし、合意済みのリスク受容事項を根拠なく再審議しません。

<a id="agreement-changes"></a>
## 6. 合意を保護する変更手続き

1. 着手前に、採用規則、正本の責務、保護する合意、依頼範囲を確認する。
2. 合意済みの要件・制約・仕様を変更・緩和する場合は、変更内容・理由・影響を明示し、合意を得てから適用する（表現改善や承認済み変更への再承認は不要）。
3. 完了前に、着手時の合意との差分、最新コードのテスト結果、正本間のリンク、変更した事実の重複と古い説明を確認する。
4. 規約・標準・文書方針の文言改訂は実装作業と同一セッションで行わない。必要と判断した場合は利用者に伝え、実装の区切りで独立した変更として扱う。
5. 必須コミットは、系列ごとに段階3のモック提示時点（UI 確認不要の系列は段階1の確認済み本文を保存した時点）、段階5の完成系監査の提示時点、段階6の完了時点とする。テーブル設計合意が必要な場合は、その提示時点もコミットする。提示する版は会話で指定し、文書にコミット一覧や承認履歴を作らない。

変更の検討と調査は着手中のユースケースに必要な範囲にとどめます。ユースケース案の検討・保存は [提示と保存の手順](mock-driven-development.md#discussion) に従います。
