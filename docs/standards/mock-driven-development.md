# モック駆動開発の標準

標準 ID: `project-template-mock-driven-development` / 版: **15**

## 1. 目的と適用

最小限の動作するモックで操作・入出力・状態の認識を合わせ、合意した仕様を実現パターンに沿って実処理へ接続します。適用範囲は [文書方針](../document-policy.md#mock-scope) に従います。

仕様合意用モックとテスト用のスタブ・モックは目的が異なり、テスト用モックの存在をもって仕様合意とはみなしません。

<a id="workflow"></a>
## 2. 系列ごとの実施手順

| 段階 | 実施内容（要約） | 次へ進める条件 |
| --- | --- | --- |
| 1. 仕様検討・記録 | 対象系列の案の全文をメッセージで提示して停止し、議論する（初回は主アクター、目的、前提、主成功系列、受け入れ条件、実現パターンの割り当て。初利用のパターン案も含む。2回目以降は拡張1本）。確認後に保存する | 系列 ID、案の全文、UI 確認の要否について議論が完了し、利用者が明示確認した内容だけを保存している |
| 2. モック作成 | 本番の型・契約を共有する合成点1箇所で固定データに差し替え、再現手順を用意する | UI 確認が必要な対象系列を、提示コミットから同一固定データで繰り返し再現できる（失敗分岐・再試行・部分成功は、UI の振る舞いを決める必要がある場合のみ要する） |
| 3. 動作合意 | Playwright CLI でモックの確認手順を事前に実行し、想定結果を確認する。確認目的、簡潔な手順、期待結果、起動手順、URL、提示コミット、対象系列 ID、合成点と再利用する本番型、判断論点（最大3件、各1行、既定案付き）、対象外、返答様式を提示して停止する | Playwright CLI の事前確認が合格し、合意記録の4項目（系列 ID、提示コミットのハッシュ、論点への回答、利用者の応答原文引用）が対象系列について記録されている |
| 4. 実処理接続 | 開始前に必要なテーブル設計の合意を得る。合意した入出力を維持し、画面、業務処理、外部接続、DB 操作・永続化・マイグレーション、必要なエラー処理を含む対象系列の実装をすべて完了し、固定データを外部システム境界側へ移すか削除する | 未実装・未接続の処理がなく、実行経路に仕様合意用モックやフォールバックが残っていない。モック無効構成で入口から結果確定までを手動確認でき、役割表の実装パスが記録されている |
| 5. 完成系監査 | Playwright CLI で実処理の確認手順を事前に実行し、想定結果を確認する。確認目的、簡潔な手順、期待結果、URL、提示コミットを示し、完成した実装の監査を利用者に依頼して停止する。この段階では E2E テストを作成・変更しない | 対象系列の完成した実装について、利用者が必須修正のないことを確認して承認し、系列 ID、提示コミットと応答原文が記録されている |
| 6. E2E 検証完了 | 段階5で利用者が承認した振る舞いを固定する E2E テストを初めて追加・更新する。E2E テストと実環境検証を実施し、合否表を更新してコミットする | 対象系列の E2E テストと実環境検証が合格し、受け入れ条件を満たし、必須修正が解消している |

段階1・3の返答様式は「各論点に『既定でよい』または『変更: …』と1行で回答し、末尾に『合意』または『差し戻し』」とします。段階5は「承認」または「差し戻し」とします（必須の確認点は段階1・3・5と、テーブル追加・変更時の段階4開始前です。差し戻し時は指示された段階へ戻ります）。

<a id="discussion"></a>
### ユースケース案の提示と保存

1. 検討時は、対象範囲で検討した案の全文と未確定の論点をメッセージ本文に提示して停止し、応答を待ちます（要約・差分・リンクのみの提示は不可）。
2. 議論中はファイルに書き込まず、修正案も全文をメッセージで再提示します。最新案への明示的な確認を得て初めて議論完了とし、質問・修正指示・無応答を確認済みと扱いません。
3. 利用者の確認完了後に、その内容のみを `docs/usecases/UC-n.md` と必要な一覧・関連設計へ保存します。確認前の新規作成・更新・下書き保存は禁止し、ユースケース一覧だけの検討や合意済み仕様の変更にも同じ順序を適用します。

- **作業単位と仕掛かり上限**: 1本の系列を段階1から段階6まで通すことを作業単位とし、完了するまで次の系列やユースケースには着手しません。セッションをまたぐ場合も同じ系列を継続し、再開時は既存の合意・完成系監査記録と合否表から現在地を確認します。合意待ちの段階は応答を得るまで進めず、不明点は利用者に確認します。再開用の計画・進捗文書は作りません。段階6ではビルドと E2E テストを1コマンドで再実行できるようにします。CI があれば同じコマンドを CI でも実行し、資格情報や実機 GUI を要する検証は手元で実行して1行の証跡を残します。
- **テストコードの作成時点**: 対象系列の段階1〜5では単体・結合・E2E を含むテストコードを作成・変更せず、手動で確認します。段階5で完成した実装を利用者が承認した後に限り、段階6で合意シナリオと受け入れ条件に基づく E2E テストを追加・更新します（UI 確認不要の系列も同様とし、全ユースケース完了まで延期しません）。段階6で本番実装の変更が必要になった場合は E2E 実装を中断し、段階4に戻って修正後の完成系に段階5の承認を再度得ます。E2E は対象システムの入口から結果までを検証し、具体的なツールは採用プロジェクトで選びます。既存テストの実行は禁止せず、先行して完了した系列の E2E テストは維持します。
- **ユースケースの完了**: 記述済みの全系列が段階6を終え、追加する拡張がないことを段階5の監査で利用者が承認した時点です。
- **合意待ち中の作業**: 段階1の議論中は読み取り調査と案の提示・確認にとどめます。段階3の合意待ち中は、当該系列の UI・系列や未合意のテーブル設計に依存しない部分（外部接続の実装・実測）のみ進められます。未合意のテーブル設計に依存する保存処理やマイグレーションは実装しません。段階は進めず、他系列・ユースケースには着手しません。合意で内容が変わった場合は、影響箇所を修正します。
- **モック対象の絞り込み**: UI 確認は、利用者の操作・入出力・状態の振る舞いを動かして仕様を決定する必要がある系列に限定します。条件とメッセージだけが異なる系列は、条件と対応するメッセージを仕様に定めれば足り、個別の再現は不要です。拡張の本数を理由にしたユースケース分割は行いません。
- **テーブル設計の合意**: 段階3の動作合意後、対象系列で追加・変更するテーブル設計を [設計標準第4節](design-and-documentation.md#architecture-method) に従って提示して停止します。[アーキテクチャ第5節](../architecture.md#tables) に合意を記録するまで段階4には進みません（設計変更がなければ再合意不要）。
- **UI 確認が不要な系列**: 段階2・3を省略します。段階1のメッセージでの確認後、確認済みの本文を保存してコミットし、そのハッシュを提示コミットとして、論点と回答・利用者の応答原文を添えて合意記録を残します。この提示コミットは確認後の保存内容を特定するものであり、確認前には作成しません。必要なテーブル設計合意を経て段階4へ進みます。モックの省略は、必要な仕様合意・実装・検証の省略を意味しません。
- **仕様変更**: 合意済みの内容を変更する場合は、理由と影響を案の全文とともにメッセージで提示し、再合意後にファイルへ反映します。動作合意が必要な系列は段階3、UI 確認不要の系列は確認後の保存時点で提示コミットを更新します。

<a id="boundaries"></a>
## 3. モックを作り込みすぎない

- 置き換え境界は、本番の型・契約を共有でき、反復が最も速い合成点1箇所とします（UI 側でも可。当該境界に実処理があれば利用します）。
- モック専用の型・画面・通信層は作成せず、固定データは算術生成、業務ロジックや永続化の再実装を含まない固定表とし、本番の型で管理します。
- 固定データは段階4完了時に外部システム境界側へ移すか削除し、重複保持しません。
- 本番構成ではモックを無効化し、実処理失敗時のモックへのフォールバックは禁止します（切り替えは合成点1箇所、既定は実処理）。
- モックツールの選定は素朴なモックで不足した時点で行い、事前の比較文書は作成しません（選定時は理由と保守負担を [プロジェクト定義](../project.md#design) に記録）。

## 4. 記録先

モック専用の仕様書は新設せず、既存の正本で管理します。

| 正本 | 記録内容 |
| --- | --- |
| `docs/usecases/UC-n.md`（[一覧](../project.md#usecases) から参照） | ユースケース、系列 ID、系列ごとの UI 確認の要否、動作合意と完成系監査の記録 |
| アーキテクチャ 第3節 | パターンごとのモック境界と合成点、役割と実装パス |
| アーキテクチャ 第5節 | 対象系列で追加・変更するテーブルの設計と合意記録 |
| プロジェクト定義 第5節 | 起動・終了・モック有効/無効の確認・実処理への切り替え手順 |
| プロジェクト定義 第6節 | 系列と構成ごとの合否 |

モックでの合意は実処理の正常動作（保存・認証・性能・耐障害性など）を保証しません。必要な検証は実環境・実処理で実施し、未検証のユースケースを完了扱いにはしません。
