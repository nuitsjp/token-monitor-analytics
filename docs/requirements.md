# Token Monitor Analytics 要件定義

## 1. 文書の位置付け

本書は Token Monitor Analytics の唯一の規範仕様である。用語の意味は [CONTEXT.md](../CONTEXT.md) に従い、README は本書の概要と実装状況だけを示す。`screen-design.md`、`design-system.md`、`architecture.md`、`PLAN.md` は本書を実装へ接続する従属文書であり、本書と矛盾する場合は本書を正とする。

要件に記載していない値の補完、互換処理、推測による関連付けは行わない。対応する外部 API 契約、必要な観測、ユーザーが確定した設定のいずれかが不足する場合は、元観測を保持したうえで当該処理を成立させない。

## 2. 目的と開発段階

Token Monitor Hub が保持する利用実績と利用枠を複数 Hub 横断で蓄積し、根拠を追跡できる形で、論理アカウントごとの API 換算利用上限と利用価値を分析できるようにする。

開発と受入れを次の二段階に分ける。

- **Phase 1** は、ローカル観測正本、識別・関連付け、利用上限推定、履歴、パージ、バックアップと復元を完成させる最初の完了ゲートとする。
- **Phase 2** は、Phase 1 のデータを用いた標準価格との比較、利用実績分析、可視化、エクスポートを追加する後続段階とする。
- クラウド複製は両段階の対象外とし、将来要件として分離する。

## 3. 基本原則

- 各端末のローカルデータベースを、その端末が取得したローカル観測正本とする。
- 原 JSON スナップショット、正規化した元観測、派生計算結果、設定変更監査履歴を区別する。
- 観測されていないアカウント別利用額を、観測値として表示しない。
- 数学的に一意に識別できない値を、均等配分、単純平均、補間、外挿で補わない。
- 同じデータと同じ計算論理版からは、同じ結果と同じ状態分類を再現できるようにする。
- 時刻を持つ内部データは UTC で保持し、有効期間は半開区間 `[開始, 終了)` で表す。
- 元観測と設定変更監査履歴は自動削除しない。物理削除は明示パージだけで行う。
- 資格情報と秘密をローカルデータベース、バックアップ、ログへ保存しない。

## 4. 対応する Hub API 契約

### 4.1 対応範囲

- `[API-01]` 観測データの収集には、認証済みの `GET /api/stats` だけを使用する。公開 API の応答は、アカウント識別情報が除去されるため使用しない。
- `[API-02]` 接続確認と各収集の前に `GET /api/health` の `hubBuild` を取得し、`schemaVersion=1`、`runtime=node-hub`、`coreRevision>=18` を対応条件とする。`coreBuildId` と `runtimeBuildId` は実際に応答したビルドの識別情報として記録するが、互換性判定には使用しない。必須値の欠落、不正、異なる schema または runtime、最低 revision 未満のビルドを推測して解釈しない。
- `[API-03]` 基準とするフィールド構造は、Token Monitor の固定リビジョン [`5ecc60535168f919d8ce5d6d1aaa14c87d11f52b`](https://github.com/Javis603/token-monitor/blob/5ecc60535168f919d8ce5d6d1aaa14c87d11f52b/docs/API.md) とする。ただし、利用上限推定に使用する対応版には 4.2 の利用額専用観測時刻が追加されていなければならない。
- `[API-04]` `GET /api/stats` の応答全体を原 JSON スナップショットとして取得単位のまま保存し、未知のフィールドも失わない。
- `[API-05]` JSON の構文、必須フィールド、型、日時、有限数を検証する。応答全体が不正な場合は正規化せず、取得失敗の事実と理由だけを記録する。
- `[API-06]` 契約ポリシーでは、収集・全体利用実績に対応する schema、runtime、最低 core revision と、利用上限推定にも対応する契約を区別する。利用額専用観測時刻を保証しない契約を、推定対応へ昇格させない。対応中の revision より新しい Hub は同じ契約として受け入れ、互換性が失われた場合は実装を新契約へ対応させたうえで最低 core revision を引き上げる。

### 4.2 利用額の契約

- `[API-COST-01]` 一つの利用額ソースは、`Hub 識別子 × devices[].deviceId × 生利用額サービス識別子` で識別する。
- `[API-COST-02]` 累積 API 換算利用額は、`devices[d].periods.allTime.clientCosts[k]` の USD 値を使用する。Hub 全体の集計値、`today`、`month`、モデル別内訳を利用上限推定の累積利用額へ代用しない。
- `[API-COST-03]` 対応する Hub API は、`devices[d].usageUpdatedAt` に、当該端末の `periods` が最後に実測更新された時刻を RFC 3339 形式で返す。通常の利用実績更新では更新し、利用枠だけを更新して以前の `periods` を引き継ぐ場合は以前の値を維持する。
- `[API-COST-04]` API 換算利用額の観測時刻には `devices[d].usageUpdatedAt` を使用する。`devices[d].updatedAt`、`receivedAt`、Analytics の取得完了時刻を代用しない。
- `[API-COST-05]` `usageUpdatedAt` が欠落、不正、または対応契約で保証されていない利用額は、元観測と全体利用実績には保持できるが、対応観測と利用上限推定には使用しない。
- `[API-COST-06]` 同じ利用額ソースについて、同じ `usageUpdatedAt` に異なる累積値が存在する場合は観測不整合とし、どちらも推定に使用しない。
- `[API-COST-07]` 利用額ソースを含む端末行の `syncUploadIntervalMs` は、`0` または正の有限整数でなければ対応観測に使用しない。

### 4.3 利用枠の契約

- `[API-LIMIT-01]` 一つの利用枠ソースは、`Hub 識別子 × devices[].deviceId × 生利用枠サービス識別子 × accountKey × 観測ウィンドウ照合キー` で識別する。
- `[API-LIMIT-02]` 生利用枠サービス識別子には `devices[d].limits.providers[p].provider` を使用し、生利用額サービス識別子との対応を別に確認する。
- `[API-LIMIT-03]` 利用枠の観測時刻には、そのウィンドウを含む `devices[d].limits.providers[p].updatedAt` を使用する。端末行や limits 全体の `updatedAt`、Analytics の取得完了時刻を代用しない。
- `[API-LIMIT-04]` `accountKey` が欠落または空の provider 行は原 JSON と未同定データとして保持するが、Hub アカウントの自動作成、論理アカウントとの関連付け、利用上限推定には使用しない。
- `[API-LIMIT-05]` プランの報告名には `devices[d].limits.providers[p].planLabel` を使用する。`accountLabel` を暗黙の代替値として使用しない。旧契約を別途対応対象にする場合は、契約ごとの明示的な抽出規則とテストを追加する。
- `[API-LIMIT-06]` `devices[d].limits.refreshMs` は正の有限整数でなければ対応観測に使用しない。端末行の `syncUploadIntervalMs` は、`0` をライブ送信、正の有限整数を固定送信間隔として扱い、欠落または不正な場合は当該端末を対応観測に使用しない。
- `[API-LIMIT-07]` `usedPercent` は有限の数値で `0` 以上 `100` 以下の場合だけ推定入力に使用する。残高、クレジット、従量額、絶対量は元の単位で保持し、利用率へ変換しない。

### 4.4 文字列と日時の正規化

- `[API-NORM-01]` 原 JSON 内の文字列は原形を保持する。サービス・プラン同定候補の集約は原形の完全一致で行い、大文字小文字変換、空白除去、別名推測をしない。
- `[API-NORM-02]` 観測ウィンドウ照合キーでは、`kind` と `metric` を Unicode NFC 正規化し、前後の空白を除いて ASCII 小文字へ変換する。`label` は Unicode NFC 正規化と前後の空白除去だけを行い、大文字小文字と内部空白を保持する。
- `[API-NORM-03]` 同一 provider 行に同じ観測ウィンドウ照合キーが複数ある場合は配列順で区別せず、該当ウィンドウの同一性を確定できないため未算出とする。
- `[API-NORM-04]` RFC 3339 日時は解析後に UTC の瞬時として比較する。不正な日時を取得時刻や現在時刻で置き換えない。

## 5. データモデルと共通規則

### 5.1 識別とカタログ

- `[DM-ID-01]` Hub 登録時に、URL、資格情報、収集担当から独立した不変の Hub 識別子を発行する。同じ URL の再登録だけでは既存 Hub と統合しない。
- `[DM-ID-02]` 生利用額サービス識別子と生利用枠サービス識別子は別々に正式なサービスへ対応付け、有効期間と監査履歴を保持する。
- `[DM-ID-03]` サービス・プラン同定候補は、生利用枠サービス識別子と生報告プラン名の原形が完全一致する観測を全 Hub 横断でまとめる。候補には未確認、確認済み、対象外の状態を持たせる。
- `[DM-ID-04]` 正式なサービスが確認される前に、未同定 provider 行から正式な論理アカウントを自動作成しない。
- `[DM-ID-05]` 正式なサービスの確認後、非空 `accountKey` を持つ Hub アカウントから論理アカウントを自動作成でき、同じ Hub、同じ正式サービス、同じ `accountKey` の後続観測をその論理アカウントへ関連付ける。別 Hub 間では `accountKey` が完全一致しても自動統合せず、ユーザーの確認候補にする。
- `[DM-ID-06]` メールアドレス、表示名、ワークスペース名、端末名の一致は確認材料にできるが、自動統合の根拠にしない。
- `[DM-ID-07]` 論理アカウントは物理削除せず、アーカイブとアーカイブ解除を行う。アーカイブ後の新規観測で自動復帰させず、専用の要確認状態にする。

### 5.2 プランと利用枠定義

- `[DM-PLAN-01]` 一つのサービスに複数のプランを定義でき、各プランを適用期間付きのプラン版として管理する。
- `[DM-PLAN-02]` 同じプランについて、プラン版の有効期間を重複させない。プラン名、標準シート単価、利用上限倍率、公式根拠を変更する場合は既存版を上書きせず、新しい版を作る。
- `[DM-PLAN-03]` 論理アカウントのプラン履歴は、参照するプラン版の有効期間内に収まり、同じ論理アカウントで重複しない半開区間として管理する。
- `[DM-PLAN-04]` Hub の報告プラン名だけでプラン履歴を変更しない。報告名と有効なプラン履歴が不一致の区間はプラン不整合とする。
- `[DM-PLAN-05]` 利用枠定義は、正式なサービス、周期種別、意味、単位を持つ。異なるサービスの利用枠を同じ定義へまとめない。
- `[DM-PLAN-06]` 観測ウィンドウ照合キーが変わった場合、ユーザーが同じ利用枠と確認した前後だけを同じ利用枠定義へ関連付ける。未確認の境界をまたぐ差分は使用しない。
- `[DM-PLAN-07]` プラン利用上限と利用上限倍率は `プラン版 × 利用枠定義` の組ごとに管理する。同じプラン版でも別の利用枠定義の上限や倍率を流用しない。
- `[DM-PLAN-08]` 基準プランと利用上限倍率は、異なるプラン版を同じ方程式系で推定する場合だけ必須とする。単一プラン版だけの方程式系には要求しない。
- `[DM-PLAN-09]` 製品へ固定のサービス、プラン、価格、倍率カタログを同梱しない。標準シート単価、倍率、出典、有効期間はユーザーが登録した情報だけを使用する。
- `[DM-PLAN-10]` 同じ Hub 端末レコード、Hub アカウント、生利用枠サービス識別子、正規化済み `kind` と `metric` について、連続する有効な provider 観測の間で旧 `label` が消え、新 `label` が現れた場合に名称変更候補を作る。候補が一対一でない場合も自動統合せず、関係するすべてのウィンドウを確認材料として示す。

### 5.3 関連付けと完全性

- `[DM-REL-01]` 利用額ソースと論理アカウントは、有効期間付きの n:n 関係として管理する。同じ利用額ソースへ至る複数の関連付けがあっても、その観測値は一度だけ数える。
- `[DM-REL-02]` 利用枠ソースは、同じ時点に一つの論理アカウントと一つの利用枠定義だけへ関連付ける。重なる関連付けを拒否する。
- `[DM-REL-03]` すべての関連付け、候補状態、カタログ、プラン履歴の変更は、変更前後、操作者、UTC 日時を追記型の設定変更監査履歴へ記録する。
- `[DM-REL-04]` 関連付けを分割、統合、修正した場合は、保持した元観測から影響する計算区間を再構成する。
- `[DM-REL-05]` アカウント別推定に使用する利用額ソースについて、各半開区間の活動主体が、推定対象の有効な論理アカウント集合で完全に説明されることをユーザーが確認できるようにする。
- `[DM-REL-06]` 未確認、未関連付け、対象外、またはアーカイブ後に未確認の活動が一つの利用額ソースへ混在する可能性がある場合、その利用額ソースを含む区間全体をアカウント別推定に使用しない。既知分だけを差し引いたり按分したりしない。
- `[DM-REL-07]` `[DM-REL-06]` の利用額も、重複排除後の共有観測利用額として全体利用実績には一度だけ含める。

### 5.4 観測の同一性と重複排除

- `[DM-OBS-01]` 同じ Hub への繰り返し取得で、利用額ソース、`usageUpdatedAt`、生利用額サービス識別子が同一の利用額観測は、正規化後に一つの元観測として扱う。原 JSON スナップショット自体は取得ごとに保持する。
- `[DM-OBS-02]` 利用枠ソース、provider の `updatedAt`、観測ウィンドウ照合キーが同一で、値も同一の利用枠観測は一つとして扱う。同一性キーが同じで値が異なる場合は不整合とする。
- `[DM-OBS-03]` 別 Hub の観測、別の利用額ソース、または Hub 切替前後の累積値を、内容ハッシュや値の一致だけで重複排除しない。
- `[DM-OBS-04]` Hub 切替は、ユーザーが旧 Hub 端末レコード、新 Hub 端末レコード、収集端末、切替日時を確認した場合だけ成立する。端末名や `deviceId` の一致だけでは成立させない。
- `[DM-OBS-05]` 同じアカウント利用枠系列に複数 Hub または複数 Hub 端末レコードの観測を統合する場合、同じ観測時刻で利用率と `resetsAt` が一致する観測は一つとして扱う。いずれかが異なる場合は利用枠観測不整合とし、その時刻の観測を推定に使用しない。

## 6. Phase 1 機能要件

### 6.1 Hub と資格情報の管理

- `[P1-HUB-01]` 複数の Hub を登録、編集、無効化できる。URL を変更しても Hub 識別子を維持する。
- `[P1-HUB-02]` Hub ごとに表示名、URL、対応 API 契約、収集間隔、接続状態、最終取得結果を管理する。
- `[P1-HUB-03]` URL は絶対 URL とする。ホストが `localhost`、ループバック IP アドレス、またはプライベート IP アドレスのリテラルである場合は HTTP または HTTPS を許可し、それ以外は証明書検証を有効にした HTTPS だけを許可する。HTTP は共有秘密を平文で送信するため、利用者が管理する信頼済み LAN に限定する。証明書エラーを無視する設定は提供しない。
- `[P1-HUB-04]` Hub の資格情報は Windows Credential Manager の Generic Credential `TokenMonitorAnalytics/Hub/{Hub 識別子}` に保存する。URL、ローカルデータベース、設定ファイル、バックアップ、ログには保存しない。
- `[P1-HUB-05]` 接続設定または資格情報を無効化・削除しても、Hub 識別子、原 JSON スナップショット、元観測、関連付け、監査履歴を削除しない。
- `[P1-HUB-06]` 接続確認では、到達不能、タイムアウト、TLS エラー、認証失敗、未対応 API 契約、不正 JSON を区別して表示する。応答本文や資格情報をログへ出さない。

### 6.2 収集

- `[P1-COL-01]` Hub ごとに正の収集間隔を設定し、収集を開始、停止、手動実行できる。
- `[P1-COL-02]` 同じ Hub の収集要求を並行実行しない。前回の要求が完了していない場合は重ねて開始せず、スキップした事実を記録する。
- `[P1-COL-03]` 各 HTTP 要求には接続と応答のタイムアウトを設定し、無期限に待機しない。失敗時は暗黙の即時再試行をせず、次の定期実行またはユーザーの手動実行を待つ。
- `[P1-COL-04]` 取得成功時は、Hub 識別子、Analytics の取得開始・完了 UTC 日時、HTTP 状態、対応 API 契約とともに原 JSON スナップショットを一つのトランザクションで保存する。
- `[P1-COL-05]` 保存後に正規化を実行し、すべての元観測から原 JSON スナップショットと JSON パスへ遡れるようにする。正規化または再計算の失敗で、保存済みの原 JSON を失わない。
- `[P1-COL-06]` アプリ再起動後は、収集の有効・無効状態と次回予定を復元する。終了中に経過した回数を遡って連続実行せず、起動後の次回一回から再開する。
- `[P1-COL-07]` 401 または 403 を認証失敗として記録し、資格情報を削除したり別の資格情報へ切り替えたりしない。
- `[P1-COL-08]` `/api/health` が未対応 API 契約を示した場合は、その応答と判定理由を記録し、`/api/stats` を取得しない。対応する schema、runtime、最低 core revision の契約ポリシーを更新するまで正規化と派生計算へ投入しない。

### 6.3 カタログ、アカウント、プランの管理

- `[P1-CAT-01]` 生利用額サービス識別子と生利用枠サービス識別子を一覧し、それぞれ正式なサービスへ関連付けられる。
- `[P1-CAT-02]` サービス・プラン同定候補に、原形の識別子と報告プラン名、取得元 Hub、非秘密の Hub アカウント表示情報、最初・最後の観測時刻を表示する。
- `[P1-CAT-03]` 同定候補を確認済みまたは対象外にでき、後から分割、修正、解除できる。変更後は影響区間を再計算する。
- `[P1-CAT-04]` 正式なサービス、利用枠定義、プラン、プラン版、基準プラン、利用上限倍率とその公式根拠 URL を登録・編集できる。
- `[P1-CAT-05]` 論理アカウントを登録、編集、アーカイブ、アーカイブ解除できる。同じサービスに複数の論理アカウントを登録できる。
- `[P1-CAT-06]` 論理アカウントのプラン履歴を UTC の半開区間で登録し、重複、プラン版の有効期間外、開始と終了の逆転を拒否する。
- `[P1-CAT-07]` Hub 報告プランとプラン履歴の不整合、および正確な変更時刻が不明な区間を表示し、ユーザーが確定するまで該当区間を推定しない。
- `[P1-CAT-08]` アーカイブ済み論理アカウントに一致する新規観測を、通常の現在一覧や推定へ自動復帰させず、確認通知と履歴で参照できる。
- `[P1-CAT-09]` 自動作成した論理アカウントと関連付けを、後から分割、統合、修正できる。変更前後の論理アカウント ID の対応を監査履歴に残し、影響区間を再計算する。

### 6.4 観測ソースの関連付け

- `[P1-REL-01]` 利用額ソースと複数の論理アカウント、ならびに論理アカウントと複数の利用額ソースを、有効期間付きで関連付けられる。
- `[P1-REL-02]` 利用枠ソースを論理アカウントおよび利用枠定義へ、有効期間付きで関連付けられる。
- `[P1-REL-03]` 未関連付けの観測ソースを許容し、元観測として表示するが推定へ使用しない。
- `[P1-REL-04]` 利用枠の照合キー変更を検出した場合、同じ利用枠、別の利用枠、未確認のいずれかを選べる。未確認中も他の収集と分析を継続する。
- `[P1-REL-05]` 利用額ソースの区間ごとに、活動主体の完全性を確認済みまたは未確認として記録できる。完全性の確認には、その区間に有効な全論理アカウントと除外対象がないことを明示する。
- `[P1-REL-06]` 関連付けと完全性の変更前に影響範囲を表示し、変更後は影響する計算区間と派生計算結果だけを再構成する。

### 6.5 周期と計算区間

- `[P1-TIME-01]` 利用周期の境界は、`resetsAt` と実際の利用率リセット観測から決める。UTC の暦週・暦月や Analytics の取得日時を周期境界に代用しない。
- `[P1-TIME-02]` 境界時刻 `B` を特定できる場合、`B` より前を旧区間、`B` 以後を新区間に帰属させる。
- `[P1-TIME-03]` 境界が二つの観測の間にあることだけが分かる場合、旧状態を確認した最後の観測より後、新状態を確認した最初の観測以前を境界不明区間として保持し、その前後を結ぶ差分を作らない。
- `[P1-TIME-04]` 次のいずれかを計算区間の境界とする。
  - 利用周期のリセットまたは周期境界不明区間
  - プラン版の変更、プラン不整合、有効プラン不明区間
  - 利用枠定義、利用額関連付け、利用枠関連付け、活動主体の完全性の変更
  - 生サービス識別子と正式サービスの対応の変更
  - 方程式系に含む利用額ソースまたは論理アカウント集合の変更
  - Hub 切替
  - 累積利用額または利用率の説明できない減少
  - 対応 API 契約または観測時刻契約の変更
- `[P1-TIME-05]` Hub 切替がリセットと一致しない場合、切替を含む利用周期全体を推定不能とし、次の確認済みリセット後から新 Hub の観測だけで再開する。
- `[P1-TIME-06]` 累積利用額または利用率の減少を既知の境界で説明できない場合は観測系列の断絶とし、減少をゼロへ補正せず、境界をまたぐ差分を使用しない。

### 6.6 対応観測と推定観測点

- `[P1-MATCH-01]` 一つの利用額ソースと一つの利用枠ソースの許容時刻差 `T` は、両元観測の取得時に有効だった二つの Analytics 収集間隔、利用額ソース側端末の `syncUploadIntervalMs`、利用枠ソース側端末の `syncUploadIntervalMs`、利用枠ソース側の `devices[d].limits.refreshMs` の最大値とする。ライブ送信を表す `0` は最大値の候補へ加えない。
- `[P1-MATCH-02]` `[P1-MATCH-01]` の五つの値を各元観測の取得メタデータとして記録する。いずれかが欠落、不正、または後から特定不能な場合は、その組を対応観測にしない。
- `[P1-MATCH-03]` 同じ正式サービス、利用枠定義、計算区間、および関連付けで連結された論理アカウントと利用額ソースを、一つの方程式系の対象集合とする。異なる利用枠定義を同じ方程式系へ入れない。
- `[P1-MATCH-04]` 対象集合にある各利用枠観測時刻を基準時刻候補とする。候補ごとに、必要な全アカウント利用枠系列と全利用額ソースから、時刻差がそれぞれの `T` 以下で最小の観測を一つずつ選ぶ。
- `[P1-MATCH-05]` 時刻差が同じ候補が複数ある場合は、基準時刻以前の観測を優先する。同じ側の同一時刻に重複排除後も複数残る場合は観測不整合として推定観測点を作らない。補間、外挿、値の平均は行わない。
- `[P1-MATCH-06]` 必要な利用枠系列または利用額ソースが一つでも許容時刻差内にない場合は、部分和や部分ベクトルを作らず、その基準時刻から推定観測点を作らない。
- `[P1-MATCH-07]` 選択した元観測 ID の組が同一になる複数の基準時刻候補は一つへ重複排除し、最も早い基準時刻を採用する。同じ元観測を別の推定観測点で再利用すること自体は禁止しない。
- `[P1-MATCH-08]` 推定観測点には、基準時刻、選択した全元観測 ID、各時刻差、許容時刻差、対象集合、関連付け、完全性確認、計算論理版を記録する。

### 6.7 利用上限推定

#### 6.7.1 推定対象

- `[P1-EST-01]` 利用上限推定の対象は、パーセント型で利用周期を識別できる `weekly` ウィンドウ、およびユーザーが月次利用枠であると確認した `billing` ウィンドウだけとする。
- `[P1-EST-02]` `session`、5 時間枠、残高、クレジット、従量額、`metric` が `credits` または `spend` のウィンドウ、月次利用枠であることを未確認の `billing` ウィンドウは利用上限推定へ使用しない。
- `[P1-EST-03]` 推定には同じ計算区間の推定観測点だけを使用する。異なるプラン版、利用枠定義、利用周期、関連付け、対象集合をまたいで観測点を混ぜない。

#### 6.7.2 方程式

推定観測点 `t` で、対象集合内の利用額ソースを重複排除して合計した累積 API 換算利用額を `A(t)`、論理アカウント `i` の利用率を `u_i(t) = usedPercent / 100`、そのアカウントに有効な `プラン版 × 利用枠定義` のプラン利用上限を `C_i` とする。

UTC 基準時刻順に並べた推定観測点の**隣接する二点だけ**から、次の差分行を作る。三点以上ある場合も、始点固定や全組合せの差分は作らない。

```text
ΔA_j = A(t_j) - A(t_{j-1})
Δu_ij = u_i(t_j) - u_i(t_{j-1})

ΔA_j = Σ_i C_i × Δu_ij
```

- `[P1-EST-04]` `A(t)` は共有観測利用額であり、一つの利用額ソースへ至る関連付けが複数あっても一度だけ加算する。
- `[P1-EST-05]` `C_i × Δu_ij` は推定アカウント寄与額であり、Hub が観測したアカウント別利用額として表示しない。
- `[P1-EST-06]` 同じプラン版と利用枠定義の組を参照する論理アカウントの `C_i` は同じ未知数とする。
- `[P1-EST-07]` 異なるプラン版が同じ方程式系に含まれる場合は、関係するすべての `プラン版 × 利用枠定義` に有効な利用上限倍率を要求する。基準プランの倍率を `1` とし、倍率で結べないプラン版が一つでもあれば未算出（倍率不足）とする。
- `[P1-EST-08]` 標準シート単価や価格比から利用上限倍率を推測しない。
- `[P1-EST-09]` `ΔA_j < 0` または `Δu_ij < 0` を含む隣接点は、既知の境界で説明できなければ観測系列の断絶とし、差分行を補正して使用しない。
- `[P1-EST-10]` `ΔA_j = 0` かつすべての `Δu_ij = 0` の行は情報を持たないため除外する。それ以外のゼロを含む行は自動除外せず、識別性と残差の評価へ含める。
- `[P1-EST-11]` 自動的な外れ値除外、平滑化、単調化、負値の切り上げを行わない。

#### 6.7.3 数値規則と識別性

- `[P1-EST-12]` JSON の有限数を十進文字列表現のまま保持し、入力の表示丸め値を計算へ使用しない。
- `[P1-EST-13]` 行列計算では各列を L2 ノルムで正規化し、特異値 `σ` が `1e-10 × max(行数, 列数) × σ_max` より大きい列空間の次元を階数とする。ゼロ列は階数へ数えない。
- `[P1-EST-14]` 等値制約と利用上限倍率を適用した後の有効未知数の数を `p`、有効差分行数を `m` とする。係数行列の階数が `p` 未満なら識別不能とする。
- `[P1-EST-15]` 階数が `p` である場合、非負制約付き最小二乗法で解く。すべての報告対象 `C_i` が有限かつ正でなければモデル不適合とし、主要指標へ使用しない。
- `[P1-EST-16]` 計算には少なくとも IEEE 754 binary64 相当の精度を使用し、計算ライブラリ、階数判定、制約解法、丸め規則を計算論理版に固定する。結果比較と品質閾値の判定は表示丸め前の値で行う。
- `[P1-EST-17]` USD は通常画面、詳細画面、Tooltip で小数第 2 位へ四捨五入して表示する。ゲージに併記する割合は通常画面で小数第 1 位、詳細画面・Tooltip・出力で小数第 2 位へ、倍率は通常画面・詳細画面・Tooltip・出力で小数第 2 位へ四捨五入する。保存、再計算入力、品質判定は表示値へ丸めず、CSV・JSON の数値には表示丸めを適用しない。

#### 6.7.4 品質状態

有効差分行 `j` に対する総絶対誤差率 `E` を次で定義する。

```text
E = Σ_j |ΔA_j - Σ_i C_i × Δu_ij| ÷ Σ_j ΔA_j
```

- `[P1-EST-18]` 他の品質条件に先立ち、`Σ_j ΔA_j = 0` の場合は誤差率を `0` と置かず、利用額の信号不足として識別不能にする。
- `[P1-EST-19]` `m < p` または推定観測点が二点未満の場合は観測不足、`m >= p` でも階数が `p` 未満の場合は識別不能とする。
- `[P1-EST-20]` `m = p`、階数が `p`、正の一意解がある場合は暫定推定とする。
- `[P1-EST-21]` `m > p`、階数が `p`、正の一意解があり、総絶対誤差率が `10%` 以下の場合は検証済み推定とする。
- `[P1-EST-22]` `m > p`、階数が `p`、正の一意解があり、総絶対誤差率が `10%` を超える場合はモデル不適合とする。階数は足りていても正の解を得られない場合もモデル不適合とする。
- `[P1-EST-23]` 暫定推定と検証済み推定だけを主要指標へ使用する。モデル不適合で得た候補値は監査用に保持できるが、価値倍率、比較、通常表示へ使用しない。
- `[P1-EST-24]` 状態は、推定対象外、未算出、観測不足、識別不能、暫定推定、検証済み推定、モデル不適合を区別し、状態理由を一つ以上記録する。

### 6.8 推定結果と履歴

- `[P1-RES-01]` 各推定結果に、サービス、利用枠定義、論理アカウント、プラン版、計算区間、状態、推定上限、観測点数、差分行数、階数、総絶対誤差率、最大時刻差、計算論理版を記録する。
- `[P1-RES-02]` 結果から、使用した推定観測点、元観測、原 JSON スナップショット、関連付け、完全性確認、プラン履歴へ遡れるようにする。
- `[P1-RES-03]` 派生計算結果は現在の計算論理で再生成できる非正本データとする。計算区間ごとの結果は保持するが、同じ計算区間の再計算世代を全保存せず現在結果を置き換える。元観測と設定変更監査履歴は保持する。
- `[P1-RES-04]` カレント計算区間に有効な推定がない場合、同じプラン版と利用枠定義の過去の最新有効計算区間を、非カレント、根拠観測時刻、経過時間付きで参照表示できる。プラン版の境界を越えて流用しない。
- `[P1-RES-05]` 最新有効計算区間を年齢だけで自動失効させない。値の古さは利用者が判断できるよう明示する。

### 6.9 保存、容量表示、明示パージ

- `[P1-DATA-01]` 原 JSON スナップショット、元観測、関連付け、カタログ、論理アカウント、プラン履歴、設定変更監査履歴をローカルデータベースへ保存する。
- `[P1-DATA-02]` ローカルデータベースのファイルサイズ、原 JSON スナップショット件数、最古と最新の取得完了日時を表示する。任意閾値の警告や自動削除は行わない。
- `[P1-PURGE-01]` 明示パージの選択条件は Hub 識別子の集合と Analytics 取得完了日時の半開区間 `[開始, 終了)` とする。全 Hub または無期限側の指定を許可する。
- `[P1-PURGE-02]` 実行前に、対象 Hub、選択期間、原 JSON スナップショット件数、最古・最新取得日時、保存済み JSON バイト数に基づく論理削減見込みを表示し、ユーザーの明示確認を要求する。この見込みは SQLite ファイルが直ちに同じバイト数だけ縮小することを保証しない。
- `[P1-PURGE-03]` パージでは選択した原 JSON スナップショット全体、それだけを根拠とする正規化元観測、それらを根拠とする派生計算結果を一つのトランザクションで削除する。原 JSON の一部をサービスまたはアカウント単位で書き換えない。
- `[P1-PURGE-04]` Hub、正式カタログ、論理アカウント、関連付け、プラン履歴、設定変更監査履歴は削除しない。残存元観測から影響区間を再計算する。
- `[P1-PURGE-05]` 削除または再計算に失敗した場合はトランザクションをロールバックし、パージ前のローカル正本を維持する。

### 6.10 ローカルバックアップと復元

#### 6.10.1 成果物

- `[P1-BACKUP-01]` バックアップはユーザーが手動で作成する、一つの ZIP 成果物とする。自動スケジュール、世代管理、外部保存先への転送は Phase 1 に含めない。
- `[P1-BACKUP-02]` ZIP 直下には BOM なし UTF-8 の `manifest.json` と `data.sqlite3` を一つずつ含め、他のエントリ、同名の重複、絶対パス、親ディレクトリ参照を含めない。形式版 1 の `manifest.json` は次のキーだけを持つ。
  - `formatVersion`: 整数 `1`
  - `schemaVersion`: 正の整数で表すデータベーススキーマ版
  - `appVersion`: 空でないアプリケーション版
  - `createdAt`: RFC 3339 UTC 日時
  - `database.path`: 固定文字列 `data.sqlite3`
  - `database.sizeBytes`: `data.sqlite3` の正の非圧縮バイト数
  - `database.sha256`: `data.sqlite3` 全体の SHA-256 を表す 64 桁の小文字 16 進数
- `[P1-BACKUP-03]` `data.sqlite3` は SQLite のオンラインバックアップ機構で同一時点に固定したデータベースファイルとし、元観測、カタログ、関連付け、論理アカウント、プラン、監査履歴、現在の派生計算結果とその根拠、非秘密設定を含む。
- `[P1-BACKUP-04]` Windows Credential Manager の資格情報、アクセストークン、Cookie、その他の秘密を成果物へ含めない。復元後は Hub ごとに資格情報を再登録する。
- `[P1-BACKUP-05]` 成果物はアプリ内暗号化しない。原 JSON、アカウント識別情報、利用履歴を含む機微データであることを作成画面に明示し、端末外の保存先では保存時暗号化を必須の運用条件として案内する。
- `[P1-BACKUP-06]` 作成時は一時ファイルへ完全な成果物を書いてディスクへフラッシュし、読み戻して形式と SHA-256 を検証した後だけ、同じディレクトリ内で保存先へ原子的に置き換える。失敗時に既存成果物を上書きしない。
- `[P1-BACKUP-07]` 同じ端末または同じ媒体にだけ置いた成果物は、媒体故障、端末紛失・盗難、ランサムウェアに対する復旧手段とはみなさない。この残存リスクと、端末外コピーはアプリの自動処理ではないことを案内する。

#### 6.10.2 復元

- `[P1-RESTORE-01]` 復元前に、ZIP 構造、各エントリの CRC、エントリ名と個数、`manifest.json` の JSON 構文と必須フィールド、対応 `formatVersion`、対応 `schemaVersion`、非圧縮バイト数、SHA-256 を全体検証する。
- `[P1-RESTORE-02]` `data.sqlite3` を一時データベースへ展開し、`PRAGMA integrity_check`、`PRAGMA foreign_key_check`、必須テーブルと列、列挙値、日時、参照整合性、区間の非重複、秘密データがないことを検証する。
- `[P1-RESTORE-03]` 一時データベースを開き、正規化データの読取りと派生結果の再計算を実行できることを確認してから適用する。意味検証のために現在のデータベースを先に消去しない。
- `[P1-RESTORE-04]` 適用前にすべてのデータベース接続を閉じ、WAL をチェックポイントし、データベース本体とサイドカーファイルを一組として扱う。耐久化した復元ジャーナルを作成してから、現在の一組を同一ボリュームの退避名へ移動し、検証済み一時データベースを本番名へ原子的に移動して再オープンする。再オープンに失敗した場合は退避した一組を戻す。
- `[P1-RESTORE-05]` 破損、途中切れ、未対応版、チェックサム不一致、意味不正、適用失敗のいずれでも、現在のローカル正本を復元前と同じ状態に保つ。失敗した一時ファイルは本番データベースとして残さない。
- `[P1-RESTORE-06]` 復元成功後も、資格情報が復元されていない Hub を接続不能として明示し、ユーザーが再登録するまで収集しない。
- `[P1-RESTORE-07]` 復旧可能性は正常な作成だけで判断せず、作成した成果物を別の空データベースへ復元して主要件数と代表的な履歴を照合する往復試験で確認する。
- `[P1-RESTORE-08]` RPO は端末外の暗号化保存先へ正常にコピーされ、復元試験に合格した最後の成果物の作成時点とする。固定の RTO は保証しない。
- `[P1-RESTORE-09]` 適用中にプロセスまたは OS が停止した場合は、次回起動時に復元ジャーナルを検出し、検証済みデータベースの適用完了が確認できない限り退避した元の一組へ戻してから起動する。
- `[P1-RESTORE-10]` 復元したデータベースへ、成果物の SHA-256、形式版、スキーマ版、復元 UTC 日時を含む復元成功の監査記録を一件追加する。この記録の追加に失敗した場合は復元失敗として元の一組へ戻す。

### 6.11 Phase 1 の画面

- `[P1-UI-01]` Hub 一覧、接続状態、収集状態、最終成功・失敗、対応 API 契約を表示する。
- `[P1-UI-02]` 未確認のサービス・プラン同定候補、Hub アカウント、利用額ソース、利用枠ソース、利用枠名称変更、プラン不整合、アーカイブ後の新規観測を確認できる作業一覧を提供する。
- `[P1-UI-03]` 論理アカウント、サービス、利用枠定義、プラン版、関連付け、活動主体の完全性を編集し、根拠と影響区間を確認できる。
- `[P1-UI-04]` 論理アカウントと利用枠定義ごとに、カレント計算区間の状態、推定 API 換算利用上限、品質情報、未算出理由を表示する。
- `[P1-UI-05]` 推定結果から、差分行、使用観測、時刻差、利用額ソース、原 JSON、関連付け、計算論理版へドリルダウンできる。
- `[P1-UI-06]` 計算区間ごとの推定履歴と、非カレントの最新有効計算区間を区別して表示する。
- `[P1-UI-07]` データ容量、明示パージのプレビューと確認、バックアップ作成、復元検証と結果を操作できる。

## 7. Phase 2 機能要件

Phase 2 は Phase 1 の受入条件をすべて満たした後に受け入れる。

### 7.1 月間換算と標準価格との比較

- `[P2-VALUE-00]` プラン版ごとに、USD 建て月額標準シート単価、出典 URL、有効期間を登録・編集できる。
- `[P2-VALUE-01]` `weekly` 利用枠の一周期当たり推定 API 換算利用上限 `C` を、次の式で月間換算する。

  ```text
  月間換算推定利用上限 = C × 365.2425 ÷ 12 ÷ 7
  ```

- `[P2-VALUE-02]` ユーザーが月次利用枠であると確認した `billing` 利用枠は、一周期当たり推定 API 換算利用上限をそのまま月間換算推定利用上限とする。
- `[P2-VALUE-03]` 月次利用枠であることを未確認の `billing` 利用枠、`metric` が `credits` または `spend` の利用枠、残高、クレジット、従量額を月間換算と価値倍率へ使用しない。元の単位による利用実績としてだけ表示する。
- `[P2-VALUE-04]` 周期外の手動または自動リセットがあっても、月間換算推定利用上限を増額しない。リセット前後は別の計算区間として扱う。
- `[P2-VALUE-05]` 同時に複数の週次または確認済み月次利用枠がある場合は、それぞれを独立して表示し、独立性が証明されていない利用枠を合算しない。
- `[P2-VALUE-06]` 有効な USD 建て月額標準シート単価 `P` がある場合だけ、次の標準価格推定最大価値倍率を算出する。

  ```text
  標準価格推定最大価値倍率 = 月間換算推定利用上限 ÷ P
  ```

- `[P2-VALUE-07]` 標準シート単価には出典 URL と有効期間を必須とする。年払い価格、割引、税、実請求額、契約固有価格、為替換算値を使用しない。
- `[P2-VALUE-08]` 標準シート単価がない場合も Phase 1 の推定を妨げず、価値倍率だけを未算出にする。
- `[P2-VALUE-09]` カレント計算区間の値と、非カレントの最新有効計算区間を区別し、プラン変更前後の価値を別々に表示する。

### 7.2 利用実績分析

- `[P2-USAGE-01]` 指定期間のトークン数、API 換算利用額、モデル別内訳を、全体、Hub、収集端末、Hub 端末レコード、正式サービス、生利用額サービス識別子、モデルで集計できる。
- `[P2-USAGE-02]` 同じ元観測または利用額ソースが複数の関連付けを経由しても、全体集計へ一度だけ含める。別 Hub の値を内容一致だけで重複排除しない。
- `[P2-USAGE-03]` 単一の論理アカウントだけに完全に関連付く利用額ソースの実績は、そのアカウントへ帰属できる。複数アカウントに関連する実績は共有利用実績として表示し、API 換算利用額は共有観測利用額として区別する。アカウント別トークン数やモデル内訳へ按分しない。
- `[P2-USAGE-04]` 推定アカウント寄与額を表示する場合は「推定」と明示し、共有観測利用額や Hub 観測値と同じ系列名・列名を使用しない。
- `[P2-USAGE-05]` `session` や推定対象外の利用枠に対応する利用も、利用額ソースで観測されたトークン数と API 換算利用額には含める。
- `[P2-USAGE-06]` 残高、クレジット、従量額、通貨を元の単位で表示し、パーセントや USD へ暗黙変換しない。
- `[P2-USAGE-07]` 任意期間の累積値差分を使用する場合は、同じ利用額ソースの隣接する有効観測だけを使い、リセット、Hub 切替、観測系列の断絶をまたがない。
- `[P2-USAGE-08]` 日次または月次として取得元が既に集計した値は、取得元タイムゾーンと期間境界が確認できる場合だけ別の暦期間へ対応付ける。時刻情報がなければ取得元ローカル日付のまま表示する。

### 7.3 可視化とエクスポート

- `[P2-VIS-01]` 期間、Hub、収集端末、サービス、論理アカウント、プラン版、利用枠定義、モデルで絞り込める。
- `[P2-VIS-02]` API 換算利用額、トークン数、推定利用上限、価値倍率の推移を、観測値と推定値が判別できる系列で表示する。
- `[P2-VIS-03]` 集計値から使用した元観測と原 JSON スナップショットへドリルダウンできる。
- `[P2-VIS-04]` 画面上の絞り込み、単位、表示タイムゾーン、集計期間、観測・推定の区別、生成 UTC 日時を含めて CSV と JSON へエクスポートできる。
- `[P2-VIS-05]` CSV は UTF-8 BOM 付き、RFC 4180 準拠とする。JSON は UTF-8、トップレベルに `schemaVersion` と `metadata` と `rows` を持つ。

## 8. 品質、セキュリティ、運用制約

### 8.1 時刻と表示

- `[QL-TIME-01]` 利用者が IANA タイムゾーン識別子から表示タイムゾーンを選べる。保存済み UTC 瞬時と利用周期境界は変更しない。
- `[QL-TIME-02]` 暦日、暦週、暦月の表示は選択したタイムゾーンの現地時刻で区切る。暦週は月曜日開始とし、夏時間の 23 時間日または 25 時間日を実時間へ補正して一律 24 時間とみなさない。
- `[QL-TIME-03]` 取得元の `periodWindows.*.timeZone` が有効な IANA 識別子なら、取得元ローカル日付と組にして保持する。不明な取得元タイムゾーンを表示タイムゾーンで置き換えない。
- `[QL-TIME-04]` 選択中の表示タイムゾーン名を画面上へ常時表示するのは M02 の期間指定箇所だけとする。M11 では設定項目の現在値として表示するが、その他の画面へ常設しない。CSV・JSON には `[P2-VIS-04]` に従って出力条件として含める。

### 8.2 セキュリティと監査

- `[QL-SEC-01]` ログ、エラー表示、エクスポートに資格情報、アクセストークン、Cookie、認証ヘッダーを含めない。
- `[QL-SEC-02]` 原 JSON とバックアップは、アカウント識別情報と利用履歴を含む機微データとして扱う。画面と運用文書で取扱いを明示する。
- `[QL-SEC-03]` 破壊的操作、関連付け、完全性確認、候補状態、プラン履歴、復元の変更を監査履歴から追跡できる。

### 8.3 再現性とテスト

- `[QL-REP-01]` 計算論理版ごとに、API 抽出規則、正規化規則、照合規則、階数判定、解法、品質分類、表示丸めのテストフィクスチャを固定する。
- `[QL-REP-02]` 再計算は元観測を変更せず、同じ入力 ID 集合と計算論理版から同じ推定観測点、差分行、状態、未丸め結果を再現する。
- `[QL-REP-03]` 外部 API の未対応フィールド追加は原 JSON 保存を妨げないが、既存抽出規則の意味を暗黙に変更しない。

### 8.4 UI の共有契約

- `[QL-UI-01]` Go の表示 DTO は、有効な `usedPercent` から計算した未丸めの `remainingPercent` を明示的に返す。UI は `usedPercent` から残り（%）を再計算せず、DTO の `remainingPercent` だけを表示する。
- `[QL-UI-02]` 鮮度状態、状態理由、表示に必要な観測時刻は Go の表示 DTO が返す。UI は経過時間の閾値や鮮度状態を独自判定せず、DTO の状態と理由を表示する。
- `[QL-UI-03]` 状態コードから日本語ラベル、Fluent の intent、アイコン、説明、次操作を得る一元マッパーを Go 側の共有契約として定義する。各画面が状態コードを個別に翻訳したり、次操作を独自に推測したりしない。
- `[QL-UI-04]` プライバシーモードおよび機微データのマスクは、visible text、Tooltip、`title`、`aria-label`、アクセシブル説明、クリップボード、タスクバーのサムネイルで同じ分類規則と同じマスク結果を使う。未加工の値を別の表示経路へ渡さない。
- `[QL-UI-05]` M11 のテーマ設定は `light`、`dark`、`system` の三値を保存できる。`system` は OS のテーマ変更へ追従し、Go の設定状態とイベントを正本として T01 と M00 の表示を同期する。ウィンドウごとの独立したテーマ設定は持たない。
- `[QL-UI-06]` 高コントラストでは、独自 SVG・CSS がシステムの強制色、`currentColor`、システム色を使用し、ハードコードした色だけに依存しない。200% 拡大では独自 SVG・CSS を含む表示と操作を切り取らずリフローし、グラフは表とテキストでも同じ情報を提供する。
- `[QL-UI-07]` ダークテーマのエラーカウンターは、白文字とのコントラスト比 4.5:1 以上を満たす専用の塗り色を使う。

## 9. 対象外

- Phase 1 における標準価格との価値比較、横断的利用実績分析、グラフ、CSV・JSON エクスポート
- 5 時間枠、セッション枠、残高、クレジット、従量額からの API 換算利用上限推定
- 請求書、支払い、税、割引、年払い価格、契約固有価格の管理
- 為替レートの取得・推測、および非 USD 価格からの価値倍率算出
- サービス提供者内部の非公開な料金・利用制限アルゴリズムの再現
- Hub が取得していない利用データのスクレイピング
- 根拠のない比率による共有観測利用額、トークン数、モデル内訳のアカウント別配分
- 推定 API 換算利用上限を正式な契約上限として保証すること
- クラウド複製、クラウドからの復元、複数端末間の設定同期
- バックアップの自動実行、世代管理、外部保存先への転送、アプリ内暗号化、資格情報のバックアップ

## 10. 受入条件

### 10.1 Phase 1 完了ゲート

次の条件をすべて満たしたときだけ Phase 1 を完了とする。

- `[AC-P1-01]` 二つ以上の Hub を異なる Hub 識別子で登録でき、同じ URL の再登録、URL 変更、接続無効化で元観測と識別子が失われない。
- `[AC-P1-02]` ループバックまたはプライベート IP アドレス以外の HTTP URL と証明書検証エラーを拒否し、信頼済み LAN の HTTP Hub を登録・接続でき、資格情報が Windows Credential Manager 以外のデータベース、バックアップ、ログに存在しないことを検査できる。
- `[AC-P1-03]` 定期収集、停止、手動収集、重複実行防止、タイムアウト、再起動後の再開を確認でき、認証失敗・不正 JSON・未対応契約を区別できる。
- `[AC-P1-04]` 原 JSON スナップショットと正規化元観測を分離して保存し、元観測から取得元 Hub、取得日時、JSON パス、原 JSON へ遡れる。
- `[AC-P1-05]` `devices[].updatedAt` だけが更新され `periods` が引き継がれたフィクスチャでは利用額観測時刻が進まず、`usageUpdatedAt` がないフィクスチャから推定観測点を作らない。
- `[AC-P1-06]` 生利用額サービス識別子と生利用枠サービス識別子を別々に正式サービスへ対応付けられ、未確認のサービス・プラン同定候補から正式な論理アカウントを自動作成しない。
- `[AC-P1-07]` 同じ `accountKey` が別 Hub に現れても自動統合せず確認候補にし、空の `accountKey`、メールアドレス、表示名だけでは論理アカウントを作成・統合しない。
- `[AC-P1-08]` サービス、利用枠定義、論理アカウント、プラン版、プラン履歴、二種類の関連付けを作成・修正でき、重複する有効期間を拒否できる。
- `[AC-P1-09]` 確認済みの利用枠名称変更前後を同じアカウント利用枠系列へ統合し、未確認または別枠の境界をまたぐ差分を作らない。
- `[AC-P1-10]` 未確認、未関連付け、対象外、アーカイブ後未確認の活動が混在し得る利用額ソースを含む区間では、既知アカウントだけの推定をせず、共有観測利用額を全体へ一度だけ保持する。
- `[AC-P1-11]` 同じ正規化元観測を繰り返し取得した場合は一度だけ数え、同一キーで値が異なる観測を不整合として推定から除外し、別 Hub の同値を内容だけで重複排除しない。
- `[AC-P1-12]` 許容時刻差内の全利用枠系列と全利用額ソースがそろった場合だけ推定観測点を作り、同距離なら過去側を選び、欠けたソースの部分和、補間、外挿を行わない。
- `[AC-P1-13]` 三つの推定観測点から二つの隣接差分行だけを作り、始点固定差分や三組の全組合せ差分を作らない。
- `[AC-P1-14]` 単一アカウントの点 `(A,u) = (10,0.1), (30,0.3)` から `C = 100` を暫定推定とする。
- `[AC-P1-15]` 単一アカウントの点 `(A,u) = (10,0.1), (30,0.3), (40,0.4)` から `C = 100`、総絶対誤差率 `0%` を得て検証済み推定とする。
- `[AC-P1-16]` 点 `(A,u) = (0,0), (10,0.1), (30,0.2)` では最小二乗候補 `C = 150` の総絶対誤差率が `33.333...%` となり、モデル不適合として主要指標へ使用しない。
- `[AC-P1-17]` 二アカウント二未知数に一つの差分行しかないフィクスチャを観測不足とし、差分行が複数あっても階数不足なら識別不能とする。
- `[AC-P1-18]` 基準プランの上限を `B`、別プランの倍率を `5`、両アカウントの `Δu` をそれぞれ `0.1`、`ΔA` を `60` としたフィクスチャから `B = 100` を暫定推定とする。倍率が欠ける同じフィクスチャは未算出（倍率不足）とする。
- `[AC-P1-19]` `ΣΔA = 0` のフィクスチャで誤差率をゼロとせず識別不能にし、表示丸め前の値で `10%` 閾値を判定する。
- `[AC-P1-20]` リセット、プラン変更、関連付け変更、Hub 切替、説明できない累積値減少の各境界をまたぐ差分を作らず、境界後の観測から別区間を開始できる。
- `[AC-P1-21]` 暫定推定、検証済み推定、モデル不適合、観測不足、識別不能、未算出、推定対象外を区別し、結果から全元観測、時刻差、関連付け、完全性、計算論理版へ遡れる。
- `[AC-P1-22]` 明示パージ前に対象と削減見込みを表示し、確認後に原 JSON 全体と依存する観測・派生結果だけを削除し、失敗時には一件も削除しない。
- `[AC-P1-23]` 正常なバックアップを空のデータベースへ復元し、復元成功の監査記録一件が追加されることを除いて、全テーブル件数、代表的な原 JSON、関連付け、プラン履歴、監査履歴、推定根拠が一致する。
- `[AC-P1-24]` 破損、途中切れ、不正・重複・不足 ZIP エントリ、SHA-256 不一致、未対応形式版、未対応スキーマ版、SQLite 不整合、参照不整合、適用後再オープン失敗、および入替え各段階でのプロセス停止を個別に試験する。失敗または次回起動時の回復後に、現在のデータベースにある全テーブルの主キー順の論理内容と件数が復元前から変わらない。
- `[AC-P1-25]` バックアップに秘密が含まれず、成果物が未暗号化の機微データであること、暗号化された端末外保存が必要であること、資格情報の再登録、RPO、固定 RTO がないことを画面と運用説明で確認できる。
- `[AC-P1-26]` Go の表示 DTO による `remainingPercent` と鮮度状態、状態コードの一元マッパー、全表示経路の同一マスク、M11 の `light`・`dark`・`system` 保存と OS 変更時の T01/M00 同期、ダークエラーカウンターの白文字コントラスト、高コントラストおよび 200% 拡大時の独自 SVG・CSS のリフローを自動試験とパッケージ済み Windows の手動証跡で確認できる。

### 10.2 Phase 2 完了ゲート

次の条件は Phase 1 完了後に評価し、すべて満たしたときだけ Phase 2 を完了とする。

- `[AC-P2-01]` 週次上限 `700` を `700 × 365.2425 ÷ 12 ÷ 7` で月間換算し、確認済み月次 `billing` 上限 `700` はそのまま使用する。
- `[AC-P2-02]` 月次と未確認の `billing`、`credits`、`spend`、残高、従量額を価値倍率へ使用せず、元の単位による利用実績として表示する。
- `[AC-P2-03]` USD 建て月額標準シート単価、出典 URL、有効期間を登録でき、その価格が有効な場合だけ価値倍率を計算し、価格がない場合も Phase 1 の推定値を表示できる。
- `[AC-P2-04]` 複数利用枠を別々に表示し、根拠なく合計した月間上限または価値倍率を表示しない。
- `[AC-P2-05]` 全体、Hub、Hub 端末レコード、サービス、モデルの期間集計で同じ元観測を二重計上せず、別 Hub の観測を内容一致だけで除外しない。
- `[AC-P2-06]` 複数アカウントに関係するトークン数、API 換算利用額、モデル内訳を共有利用実績として一度だけ表示し、アカウント別へ按分しない。API 換算利用額と推定寄与額を明確に区別する。
- `[AC-P2-07]` IANA 表示タイムゾーン、月曜日開始の週、夏時間境界を用いた暦集計を確認でき、取得元タイムゾーン不明の日次値を UTC 日付へ再配分しない。選択中の表示タイムゾーン名は M02 の期間指定箇所だけへ常時表示され、M11 の設定項目と CSV・JSON の出力条件を除く他の画面へ常設されない。
- `[AC-P2-08]` 絞り込み後の表示データを、単位、期間、タイムゾーン、観測・推定区分、スキーマ版付きの CSV と JSON へ出力し、画面の値と一致する。
