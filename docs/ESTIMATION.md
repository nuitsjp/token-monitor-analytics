# 推定の定義と限界

## 金額を再計算しない

Token Monitor Hubが返す`costUsd`/`clientCosts`を観測値として利用する。各AIサービスの請求額を保証する値ではなく、Token MonitorによるAPI換算額である。Analyticsにモデル単価表は置かない。

## 集計スコープを一致させる

上流の金額は主にdevice/client単位、利用率はprovider/account単位。名前がclaudeやcodexというだけで同じ契約だと判断しない。設定でHub、provider、accountKey、deviceIds、clientIds、windowKindを指定し、過不足なく同じ対象を示すと利用者が確認する。

1つの設定は1契約の1制限枠。週間枠と5時間枠は別定義とし、推定結果を合算しない。複数の制限が同時に働く場合、どれが実際の上限になるかはこの単一枠の月換算では分からない。

## 増分の式

同一resetAt、同一SSE streamId内の基準点から、選択した全端末の`allTime.clientCosts[client]`を足した額と、対象枠のusedPercentの差分を取る。

```text
windowCapacityUsd = (currentCost - baselineCost)
                  / ((currentUsedPercent - baselineUsedPercent) / 100)
monthlyCapacityUsd = windowCapacityUsd * (365.2425 / 12 * 24 / windowHours)
```

小さな変化は最初の基準点から蓄積し、既定5ポイント以上で参考推定する。当月金額を週間利用率で割ることはしない。月換算は平均月長の固定係数であり、当月の日数・休業・使用ペースを予測していない。

## 判定

帰属未確認、金額欠落、staleな端末/利用率、時刻差、期限切れの窓、曖昧な窓は推定不可。再接続、窓の変更、カウンター減少、観測間隔超過では基準を作り直す。金額0、未取得nullを混同しない。値の減少を絶対値にしたり負の差を0に丸めたりしない。

上流の`updatedAt`は厳密に同時点で計測されたことの証明ではない。時刻検査は不一致を減らすためであり、統計的な信頼度ではない。契約を共有する別端末、Web上の利用、計測漏れ、対象モデルの違いがあれば推定は偏り得る。

## 日次履歴

設定したtimeZone（既定Asia/Tokyo）を基準に、その日の最新判定と最後の有効推定を別に残す。最新が観測中/推定不可になっても、その日の有効推定値は保持し、その観測時刻を併記する。有効推定なしの日はnull。更新イベントが1度もなかった日は行を作らず、線で補間しない。

設定が変われば推定の基準はリセットする。違う契約/帰属/制限の意味に変える場合は**新しいcontract id**にする。同じidの過去日次値を書き換えたり別の意味に読み替えたりしない。単なる表示名の変更でも初期版は保守的に基準を作り直す。

## まだ行わないこと

履歴の過去単価再計算、複数枠のボトルネック推定、統計的信頼区間、モデル混合補正、リセット時刻の推測、オンライン利用とCLI利用の自動名寄せは対象外。正しく測れていないものを説得的な数値として埋めない。
