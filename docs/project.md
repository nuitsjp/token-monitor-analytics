### UC-1. Hub を登録する

- 主アクターと目的: 利用者。Web 画面から Hub を登録し、その Hub からの収集を開始する。[設計方針 第1節](design-policy.md#1-目標と機能範囲)「複数 Hub の一括管理」の登録と一覧表示に対応する。
- 前提: アプリが起動している。利用者認証はない（[U12](../PLAN.md#u12)）。
- 主成功系列（UC-1-M）:
  1. 利用者は画面の「Hub 管理」で、登録済み Hub の一覧（ID、URL、接続状態、収集状態）を見る。
  2. 利用者は Hub の ID、URL、共有シークレットを入力して「登録」を選ぶ。
  3. システムは入力を検証し、接続設定を保存し、Hub を登録して収集を開始する。
  4. 一覧に新しい Hub が現れ、接続後に現在値が表示される。
  5. 再起動後も登録した Hub が一覧にあり、収集が続く。
- 拡張:
  - UC-1-X1: 2 で入力が不正（ID の重複または形式、URL の形式、シークレットの形式）なら、システムは理由を表示して保存しない。
- 受け入れ条件: 登録から10秒以内に一覧へ反映される。不正入力は保存されない。共有シークレットは画面・ログ・API 応答に出ない。同一オリジン外からの登録要求は拒否される。再起動後に登録が維持される。他の Hub の収集と閲覧に影響しない。
- 実現パターンと逸脱: [P-1](architecture.md#patterns) / 逸脱: なし
- 合意記録:

  - 合意した系列: UC-1-M、UC-1-X1
  - 論点と回答: (1) UC-1-X1 をモックの合意範囲に含める: 既定でよい。(2) 登録直後の表示は 1 行で足りる: 既定でよい。(3) 練習用 Hub のポート 8788 とシークレット表示はモック構成に限る: 既定でよい。

### UC-2. Hub の収集を停止する

- 主アクターと目的: 利用者。Web 画面から登録済み Hub の収集を停止し、その Hub との通信を明示的に再開するまで止める。[設計方針 第1節](design-policy.md#1-目標と機能範囲)「複数 Hub の一括管理」の個別停止に対応する。内部操作の停止処理（[機能仕様 S5](../doc/spec/functional-spec.md#s5)）は実装済みで、本ユースケースの範囲は画面の操作と結果表示、SQLite の `collection_enabled` への保存、再起動後の維持である。
- 前提: アプリが起動している。対象 Hub は一覧にあり収集中である。利用者認証はない（[U12](../PLAN.md#u12)）。
- 主成功系列（UC-2-M）:
  1. 利用者は画面の「Hub 管理」で、登録済み Hub の一覧（ID、URL、接続状態、収集状態、操作）を見る。
  2. 利用者は対象 Hub の行で「停止」を選ぶ。
  3. システムは対象 Hub の通信を中止し、受信済みデータの処理を終えてから収集停止の設定を SQLite に保存する。
  4. 一覧の収集状態が「収集停止」になり、操作結果として停止した旨が表示される。
  5. 再起動後も一覧の収集状態は「収集停止」のままで、その Hub との通信は行われない。
- 拡張:
  - UC-2-X1: 2 で対象 Hub が一覧にない（要求の ID が登録済み Hub と一致しない）なら、システムは理由を表示して状態を変えない。
- 受け入れ条件: 停止から10秒以内に一覧へ反映される。停止後は当該 Hub への SSE 接続、再接続待機、履歴取得を行わない。他の Hub の収集と保存済みデータの閲覧に影響しない。同一オリジン外からの停止要求は拒否される。再起動後に停止が維持される。停止設定の保存に失敗しても通信は停止し、「収集停止」と「保存失敗」を併記する（S5）。共有シークレットは画面・ログ・API 応答に出ない。
- 実現パターンと逸脱: [P-1](architecture.md#patterns) / 逸脱: 入力は Hub の ID だけで、接続設定（設計判断 D-8 の保存先）は変更しない。結果確定点は hubs 表の `collection_enabled` の保存で、外部 Hub との通信は開始ではなく中止する。
- 合意記録:
  - 提示コミット: 0ce3156
  - 合意した系列: UC-2-M、UC-2-X1
  - 論点と回答: (1) 停止 API の契約を D-11 として決定表へ追加する: 既定でよい。(2) 停止設定の保存に失敗しても停止要求は 200 で受け付け、「収集停止」と保存失敗を併記する: 既定でよい。(3) 停止済み Hub への再度の停止要求は 200 で状態を変えず、画面のボタンは停止済みのとき無効にする: 既定でよい。
  - 応答の原文（2026-09-14、リポジトリ所有者）:
    > OKです。

### UC-3. 停止した Hub の収集を再開する

- 主アクターと目的: 利用者。Web 画面から停止中の Hub の収集を再開し、その Hub からの受信と履歴取得を再び始める。[設計方針 第1節](design-policy.md#1-目標と機能範囲)「複数 Hub の一括管理」の再開に対応する。内部操作の再開処理（[機能仕様 S5](../doc/spec/functional-spec.md#s5)）は実装済みで、本ユースケースの範囲は画面の操作と結果表示、SQLite の `collection_enabled` への保存、再起動後の維持である。
- 前提: アプリが起動している。対象 Hub は一覧にあり収集停止中である。利用者認証はない（[U12](../PLAN.md#u12)）。
- 主成功系列（UC-3-M）:
  1. 利用者は画面の「Hub 管理」で、登録済み Hub の一覧（ID、URL、接続状態、収集状態、操作）を見る。
  2. 利用者は収集停止中の Hub の行で「再開」を選ぶ。
  3. システムは収集有効の設定を SQLite に保存し、その Hub への接続と履歴取得を始める。
  4. 一覧の収集状態が「収集中」になり、接続後に接続状態が「Hub 接続正常」になる。
  5. 再起動後も一覧の収集状態は「収集中」のままで、収集が続く。
- 拡張:
  - UC-3-X1: 2 で対象 Hub が一覧にない（要求の ID が登録済み Hub と一致しない）なら、システムは理由を表示して状態を変えない。
- 受け入れ条件: 再開から10秒以内に一覧へ反映される。再開後は当該 Hub の受信と履歴取得が再び行われる。収集中の Hub への再開要求は収集を二重に始めない。他の Hub の収集と保存済みデータの閲覧に影響しない。同一オリジン外からの再開要求は拒否される。再起動後に再開が維持される。保存に失敗した場合は収集を始めず、理由を表示する。共有シークレットは画面・ログ・API 応答に出ない。
- 実現パターンと逸脱: [P-1](architecture.md#patterns) / 逸脱: 入力は Hub の ID だけで、接続設定（設計判断 D-8 の保存先）は変更しない。結果確定点は hubs 表の `collection_enabled` の保存で、その後に収集を始める。
- 合意記録:
  - 提示コミット: cadd7b7
  - 合意した系列: UC-3-M、UC-3-X1
  - 論点と回答: (1) 経路を `POST /api/hubs/{id}/resume` とし、D-11 と同じ検証規則を参照する D-12 を追加する: 既定でよい。(2) 操作列はボタン1つとし、収集中は「停止」、停止中は「再開」に切り替える: 既定でよい。(3) 再開設定の保存に失敗したら収集を始めず、保存できなかった旨を表示する: 既定でよい。
  - 応答の原文（2026-09-14、リポジトリ所有者）:
    > 推奨に従います

### UC-4. アプリを手動で更新し、履歴を保全して復旧する

- 主アクターと目的: 利用者。`git pull` で取得した新しい版のアプリを起動し、既存の DB と履歴を保全したまま更新結果を確認する。更新に失敗したときは手動復旧に必要な情報を得る。[機能仕様 S9](../doc/spec/functional-spec.md#s9) と [設計方針 第5節](design-policy.md#5-データ保全と変更管理の境界) に対応する。更新元は `git pull`、更新の対象はアプリのコードと DB スキーマの移行である。自動更新・自動ロールバック・DB 初期化・履歴の書き換えは行わない。
- 前提: アプリはリポジトリのクローンから `node src/main.js real` で起動している。DB は現在の版のコードで作られたか、それより古い対応範囲の版である。
- 主成功系列（UC-4-M）:
  1. 利用者は起動中のアプリを、起動した端末で Ctrl+C を押して終了する。
  2. 利用者は `git pull` でコードを更新する。
  3. 利用者はアプリを同じモードで起動する。
  4. システムは DB のスキーマ版を確認し、必要な移行を 1 つのトランザクションで行い、起動ログにアプリの版と移行前後のスキーマ版を記録する。
  5. 画面のフッターにアプリの版とスキーマ版が表示され、更新前の登録済み Hub、収集設定、観測と履歴がそのまま残り、収集が続く。
- 拡張:
  - UC-4-X1: 4 で移行に失敗したなら、システムは DB を移行前の版とデータのまま保ち、失敗した段階、原因コード、DB のパス、移行前の版と対応する版、復旧手順を起動ログに記録して起動を中止する。
  - UC-4-X2: 4 で DB の版がアプリの対応範囲外（コードを古い版へ戻した等）なら、システムは DB を書き換えず、DB の版と対応する版、復旧手順を起動ログに記録して起動を中止する。
- 受け入れ条件: 更新後の起動で更新前の観測、履歴、Hub 登録、収集設定が失われない。移行失敗時に `user_version`、テーブル定義、全データが移行前と一致する。起動失敗のログに原因コード、失敗した段階、DB のパス、DB の版と対応する版、復旧手順が含まれる。起動成功のログと画面にアプリの版とスキーマ版が出る。共有シークレットは画面・ログ・API 応答に出ない。
- 実現パターンと逸脱: [P-2](architecture.md#p-2) / 逸脱: なし
- 合意記録:
  - 提示コミット: f3688bb
  - 合意した系列: UC-4-M、UC-4-X1、UC-4-X2
  - 論点と回答: (1) アプリの版は `git rev-parse --short HEAD` の短縮ハッシュとし、git が使えないときは null（画面は「不明」）: 既定でよい。(2) 起動ログの契約を D-13 として決定表へ追加する: 既定でよい。(3) 移行失敗の復旧情報は起動ログにだけ出し、運用手順にログの `recovery` を読む手順を追記する: 既定でよい。
  - 応答の原文（2026-09-14、リポジトリ所有者）:
    > 1: 規定で良い、2: 規定で良い、3: 規定で良い　合意。

合意記録は4項目すべてが揃って初めて合意とみなします。未合意の論点は [PLAN.md](../PLAN.md) の課題 ID を参照します。
