# バックアップ・復元運用手順

## 1. 目的と責任範囲

Token Monitor Analytics のローカル正本を、端末故障、誤操作、アプリ障害、端末盗難から復旧できる状態に保つための手順を定める。

アプリが保証する範囲は、ローカル ZIP の作成、完全性検証、隔離環境での復元試験、ローカル正本への原子的な復元である。端末外への転送、保存先の暗号化、世代保持、暗号化に必要な回復情報の保管は利用者の運用責任とする。

バックアップ ZIP には観測履歴、関連付け、プラン履歴、推計結果と根拠が含まれるため機微情報として扱う。Windows Credential Manager の資格情報、アクセストークン、Cookie は含まれない。復元後はすべての Hub で資格情報の再登録と接続確認が必要になる。

## 2. 平常時のバックアップ

1. アプリの「データ管理」でバックアップを作成する。
2. 作成結果が成功であること、作成 UTC、ZIP 全体の `artifactSha256`、ファイルサイズを記録する。警告がある場合は解消するまで有効な世代として扱わない。
3. アプリの復元試験を実行し、同じ `artifactSha256` に対する試験結果が合格であることを確認する。
4. ZIP を、端末外のアクセス制御された暗号化保存先へコピーする。
5. コピー先 ZIP の SHA-256 を計算し、アプリが表示した `artifactSha256` と一致することを確認する。ファイル名やサイズだけで同一性を判断しない。
6. コピー日時、保存先、SHA-256、復元試験 UTC、確認者を証跡へ記録する。

少なくとも複数時点の世代を端末外に保持する。世代数と作成間隔は、失ってよい観測期間と保存容量から運用責任者が決める。最新世代だけへ上書きしてはならない。

暗号化鍵、回復キー、保存先アカウントの回復手段は、バックアップ ZIP と同じ端末だけに置かない。回復情報から保存先へアクセスし、ZIP を取得して復号できることを四半期演習で確認する。

## 3. 復旧時に必要なもの

- 復元試験に合格した暗号化済みバックアップ ZIP
- 記録済みの `artifactSha256`
- ZIP を復号するための回復情報
- バックアップの `schemaVersion` に対応する Token Monitor Analytics インストーラー
- 各 Hub のアドレスと共有シークレットの原本
- 新しい Windows ユーザープロファイルで資格情報を登録できる権限

アプリは未対応のバックアップ形式版またはスキーマ版を暗黙に変換しない。対応インストーラーがない場合は復元を開始せず、その版を安全な環境へ用意する。

## 4. 復元前の検証

1. ZIP をローカルの作業領域へコピーし、SHA-256 が記録済みの `artifactSha256` と一致することを確認する。不一致なら使用しない。
2. アプリの「復元」で ZIP の検証を実行する。この操作は現在のローカル正本を変更しない。
3. 検証操作 ID、対象 `artifactSha256`、検証結果を確認する。破損、途中切れ、形式不正、SHA-256 不一致、SQLite 整合性不良、秘密の混入、再計算不能のいずれかが報告された ZIP は適用しない。
4. 同じ成果物に対して隔離復元試験を実行し、合格 UTC と `artifactSha256` を記録する。
5. 未保存の画面編集を完了または破棄し、収集中の処理が終了できることを確認する。

検証と適用は別操作である。検証済み操作 ID に束縛された成果物だけを適用し、パスを選び直した場合は再検証する。

## 5. 復元の適用

1. 復元対象の検証操作 ID と `artifactSha256` を確認する。
2. 復元すると現在のローカル正本が置き換わることを確認し、適用を開始する。
3. 展開・検証中は取消しできる。ファイル入替え開始後は取消しやアプリ終了を行わない。
4. アプリが収集停止、データベース接続閉鎖、WAL checkpoint、退避、入替え、再オープン、再検証、復元成功監査の順に完了するまで待つ。
5. 成功後、復元した全 Hub が「復元後再登録待ち」であり、収集が停止していることを確認する。
6. Hub ごとに共有シークレットを明示的に再登録し、接続確認を成功させる。端末に残っていた Credential Manager の資格情報は再利用しない。
7. Hub ごとに収集を明示的に再開する。
8. 手動収集を一回実行し、原 JSON と正規化結果を確認する。
9. 新しいバックアップを一回作成して端末外へコピーし、その成果物の復元試験を合格させる。

手順 5 から 9 までを終えるまで復旧完了とはしない。

## 6. 中断・失敗時の対応

復元適用が失敗した場合は、画面に「現在のローカル正本は変更されていません」と表示され、適用前の収集状態へ戻ったことを確認する。確認できない場合は収集を再開せず、診断情報とアプリ管理領域一式を保全する。

復元中にプロセスまたは OS が停止した場合、次回起動時にアプリはデータベースを開く前に復元ジャーナルを処理する。元の正本へ回復した通知を確認してから通常操作を再開する。

復元ジャーナルが破損している、形式が不明である、候補ファイルとの対応を証明できないなど、状態を判定できない場合、アプリは安全停止する。この場合は次を行う。

1. アプリを繰り返し起動せず、候補ファイルを削除、移動、改名しない。
2. アプリ管理領域を別媒体へバイト単位で退避する。
3. 表示された非秘密の診断情報、アプリ版、発生 UTC、直前に選択した `artifactSha256` を記録する。共有シークレットは記録しない。
4. クリーンな Windows ユーザープロファイルと対応インストーラーを用意し、退避した候補ではなく、既知の正常な端末外バックアップから第 7 節の全損復旧を行う。

## 7. 端末全損・盗難からの復旧

1. 盗難時は、すべての Hub 共有シークレット、端末外保存先の資格情報、同じ端末で利用していた回復資格情報をローテーションする。
2. クリーンな Windows ユーザープロファイルへ、バックアップのスキーマ版に対応するインストーラーを使ってアプリを導入する。
3. 端末とは別に保管した回復情報だけを使い、暗号化保存先へアクセスする。
4. 複数世代から、復元試験に合格した最新の ZIP を取得して復号する。
5. SHA-256 を計算し、保存済みの `artifactSha256` と照合する。
6. 第 4 節と第 5 節に従って検証、隔離復元試験、適用を行う。
7. ローテーション後の共有シークレット原本を使い、全 Hub を再登録して接続確認する。
8. 手動収集、バックアップ作成、端末外コピー、SHA-256 照合、復元試験を完了する。

## 8. RPO と RTO

RPO は固定値ではない。暗号化済みの端末外保存先へ正常にコピーされ、コピー先 SHA-256 が照合され、復元試験に合格した最後の成果物の作成時点まで、という条件付きで説明する。コピーしていないローカル ZIP や、復元試験が未実施または失敗した ZIP は RPO の根拠にしない。

固定 RTO は保証しない。対応版の再インストール、ZIP の取得と復号、検証と適用、全 Hub の資格情報再登録と接続確認、収集再開、手動バックアップ、復元試験合格までの実測時間を演習証跡へ記録する。

## 9. 四半期ごとの復元演習

四半期ごとに、運用 DB と異なるクリーンな環境で次を実施する。

1. 保存先の回復情報だけで暗号化済み ZIP を取得し、復号する。
2. SHA-256 を記録済みの `artifactSha256` と照合する。
3. 対応インストーラーを特定してクリーン環境へ導入する。
4. ZIP 検証と隔離復元試験を合格させる。
5. 復元を適用し、全テーブル件数、代表的な原 JSON、関連付け、プラン履歴、監査履歴、推計根拠を確認する。
6. 試験用 Hub の資格情報原本を使い、再登録、接続確認、手動収集を行う。
7. バックアップを再作成し、その復元試験を合格させる。

証跡には実施 UTC、担当者、アプリ版、バックアップ作成 UTC、`artifactSha256`、保存先区分、検証結果、復元試験結果、資格情報再登録結果、実測復旧時間、発見事項、是正期限を残す。共有シークレット、復号鍵、原 JSON 本文は証跡へ含めない。

演習の完了条件は、端末外にある暗号化成果物からローカル正本を復元し、全 Hub の再登録と収集、次回バックアップと復元試験までを完了できることである。
