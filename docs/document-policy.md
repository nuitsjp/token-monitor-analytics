<a id="mock-development"></a>
### モック駆動開発の統合

標準 `mock-driven-development` **版1の既定採用は提案中**とし、[U10](../PLAN.md#u10) で判断する。個別の開発作業で明示的に選択された場合はその範囲に適用する。文書統合だけでモック作成や承認待ちを必須にせず、製品の採否は [U11](../PLAN.md#u11) で別に扱う。

機能仕様は設計書 第6節の S1〜S9 を使う。実施ルールの記録項目を該当シナリオへ追記し、未決事項の詳細は PLAN.md を参照する。現行の `src/` がないため実施ルールは上記の正本へ置き、別の仕様ひな型は作らない。

モックによる画面の合意は、API の事実確認、識別・保存・障害の設計、実 Hub の検証を代替しない。既存の設計・製品の完了基準を維持する。

## 2. arc42 と C4 の使い方

[共通標準 第4節](standards/design-and-documentation.md#architecture-method)に従い、Markdown と Mermaid で次の3種類を必須とする。

- **Context**：利用者、Analytics、外部 Hub の関係と範囲。
- **Container**：Node.js、ブラウザアプリ、SQLite の実行・保存境界と通信。単一常駐プロセスでも省略しない。
- **Component**：Node.js 内の主要な責務と依存。状態とシナリオから決め、旧実装の部品数に固定しない。

Context と Container に認証境界を示す。初期版の合意と退避した実装を区別し、未決の責務は PLAN.md に対応付ける。旧 Component 図だけで初期版の内部設計を完了としない。

## 3. 設計の進め方

共通標準の手順を、Hub API の識別子・取得値・保持履歴の事実から進める。Hub・端末・契約・利用枠・対象期間と、観測・実績の対応を確認して責務を決める。

接続、収集設定、保存、推定可否は独立した状態として、関係と表示を定める。対象は S1〜S9（通常受信、補完中の受信、再接続、リセット、個別停止、保存失敗、再起動、認証・管理、手動更新）。認証と更新時の履歴保全を設計方針に照らす。作業順序と論点は PLAN.md に置く。

## 4. 判断の記録と初期設計の完了基準

判断理由の4点説明と ADR 条件は [共通標準 第2・5節](standards/design-and-documentation.md#completion)に従う。ADR は第1節の配置に分離し、設計書から参照する。

初期設計は、**共通標準の全5項目を S1〜S9 の各シナリオについて説明できること**で完了とする。同一性の対象には観測・実績・比較基準を含め、第3項では**いつ保存が確定し、画面へ何を通知するか**を説明する。

未決に依存するシナリオは未完とし、文書構成を揃えただけで完了としない。製品の完了は [設計方針 第6節](design-policy.md#6-検証と製品の完了条件)で別に判断する。
