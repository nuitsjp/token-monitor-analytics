# 文書方針

アーキテクチャ文書の骨格には必要な内容に絞った arc42 を使い、構造は C4 で表す。設計の中心を、何を同一と判定するかという識別、対象ごとの状態、重要な実行時シナリオに置く。2026-09-12 の全面リライト指示に基づき、設計手法を参考候補としていた旧方針を置き換える。

## 1. 文書の役割

| 文書 | 正本とする内容 |
| --- | --- |
| [設計方針](design-policy.md) | 目標、機能範囲、制約、品質要求、変更の判断基準、製品の完了条件。 |
| [CONTEXT.md](../CONTEXT.md) | ドメイン用語の意味。API 項目、識別キー、計算条件、状態遷移などの処理仕様は含めない。 |
| [アーキテクチャ設計書](architecture.md) | 外部と内部の境界、識別、状態、保存、実行時シナリオ、設計判断と検証条件。 |
| [TODO.md](../TODO.md) | 未決事項、決定に必要な事実、影響する処理、未検証事項。未実装の確定済み機能とも区別する。 |
| [PLAN.md](../PLAN.md) | 現在の到達点と作業の順序。仕様や未決事項の本文は再掲しない。 |
| [README.md](../README.md) | 利用者向けの紹介、現在使える機能、起動・運用手順、文書への入口。 |
| `docs/adr/` | 変更負担が大きく、理由が自明でなく、実際の選択肢とトレードオフがある判断。必要になったときに作る。 |
| [old/](../old/README.md) | 退避した実装、実行設定、リライト前の文書と調査資料。過去の根拠を確認する資料であり、現在の仕様の正本ではない。 |

同じ決定を複数の文書で定義しない。仕様を理解するために旧文書を往復する必要がないよう、確定済みの内容は現行文書へ記述する。旧文書への参照は調査証跡や変更前の記録を示すために使う。

## 2. arc42 と C4 の使い方

arc42 の目標・制約、コンテキスト、解決方針、構成要素、実行時動作、配置、横断的な概念、判断、品質・リスクを必要な粒度で扱う。目標と制約は設計方針、用語は CONTEXT.md、未決事項は TODO.md を参照する。12節を形式的に埋める必要はない。

C4 は次の区別を保つ。

- Context は、利用者、本システム、外部 Hub の関係とシステムの範囲を示す。
- Container は、Node.js アプリケーション、ブラウザで実行するアプリケーション、SQLite の実行・保存の境界と通信を示す。単一常駐プロセスでも省略しない。
- Component は、Container 内の主要な責務と依存関係を示す。旧実装の部品数やファイル数に固定しない。

図と本文で対象範囲を一致させる。実装済みの構造、合意済みだが未実装の責務、未決事項を区別し、将来の部品分割を既決のように描かない。記法には Markdown と Mermaid を使う。

4+1 の並行処理・シナリオの観点は検討の補助に使う。UML や不要なビューの作成は前提としない。

## 3. 設計の進め方

1. Hub API の事実を確認し、用語、識別ルール、重要シナリオを整理する。具体例を使って、得られる情報と得られない情報を区別する。
2. C4 の Context と Container で、外部との関係、実行と保存、認証の境界を確認する。
3. 独立した状態と重要シナリオから、状態を更新する責務、保存の確定点、停止・継続する処理を決め、Component に反映する。
4. 重要な設計判断と検証条件を記録し、設計方針に照らして確認する。

既存の調査・合意・実装は根拠として利用する。ただし、実装に存在することだけを理由に将来の設計を確定しない。未決事項を推測で埋めず TODO.md に記録し、決定した内容を設計書へ反映する。独立して進められる作業は継続する。

## 4. 判断の記録と初期設計の完了基準

通常の判断理由は関係する設計箇所へ残す。構造や運用に影響する仕組みの追加は、[設計方針 第4節](design-policy.md#4-設計を追加する判断基準)の4点を説明する。ADR の作成は第1節の条件をすべて満たす判断に限り、文章量は固定しない。

初期設計は、重要なシナリオごとに次を説明できることを完了基準とする。

- 何を同一と判定し、どの観測・実績を対応付けるか。
- どの責務が、どの対象の状態を更新するか。
- いつ保存が確定し、画面へ何を通知するか。
- 失敗時に何が残り、どの処理が停止し、どの処理が継続するか。
- その期待動作を何によって検証するか。

未決事項の登録だけで設計済みとしない。依存するシナリオを未完として明示する。一方、文書の網羅性や図の枚数だけで完了を判定しない。実装と検証の完了は設計方針の製品の完了条件で別に判断する。

参考: [arc42](https://arc42.org/overview/)、[C4 model](https://c4model.com/diagrams)。
