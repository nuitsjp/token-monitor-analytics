# 設計方針 (Design Policy)

Token Monitor Analytics は、複数 Hub から AI ツールの利用実績や利用枠を収集し、実測増分に基づいて定額制サービスの利用許容量（米ドル換算の参考値）を推定・保存するセルフホスト型ダッシュボードです。

本書は製品要件の正本です。機能仕様は [機能仕様書](../doc/spec/functional-spec.md)、API 仕様は [連携仕様](../doc/spec/interfaces.md)、アーキテクチャ構造・責務は [アーキテクチャ設計書](architecture.md)、用語定義は [CONTEXT.md](../CONTEXT.md)、未決事項は [PLAN.md](../PLAN.md)、共通標準の採用状況は [文書方針](document-policy.md) を参照してください。

## 1. 目標と機能範囲

| 機能 | 初期版の要件 |
| --- | --- |
| 現在値の閲覧 | プロバイダーやプランを問わず、取得した利用枠・消費率（画面では未使用を100%とする残量率）・API 換算額を取得状態および更新時刻とともに表示する。画面最上段とHubごとの期間別メトリクスでは、Cursorのアカウント全体実績を同じ契約集合ごとに一度だけ数え、他ツールは端末単位で数える |
| 利用許容量の推定 | Hubをまたいで同一と確認できる契約を一つの推定対象として、比較可能な利用額・利用枠の実測増分から利用許容量を算出し、算出時点の結果と根拠を保存する。取得不能・stale・切断等の端末は除外し、残る有効な利用額とその契約集合の利用枠から参考値を算出する。共有利用額は同一プランの共通許容量、または異なるプラン間の基準プラン・倍率を用いて推定する |
| 過去実績の閲覧・比較 | Hub の保持期間に応じた日次・月次実績を定期収集・補完し、推移の保存および比較表示を行う |
| 複数 Hub の一括管理 | 複数 Hub への並行接続・状態監視、Web 画面での登録・一覧表示、Hub 個別の収集停止・再開を提供する |
| 手動更新と復旧 | ユーザーの明示操作によるアップデートを行い、失敗時は原因と手動復旧に必要な情報を提示する |

※ 端末からの直接収集は行わず Hub 経由でのみ取得します。推定不可時でも取得済みの実績・利用枠は表示し、契約に帰属できない利用額は実際の集計単位（Hub や端末等）を明記して表示します。共有利用額を契約別実績へ按分しません。

## 2. 制約と前提事項

| 観点 | 制約・前提 |
| --- | --- |
| 利用者 | 単一利用者（1名） |
| 実行・保存環境 | Node.js 24 LTS の単一常駐プロセスおよび組込 SQLite。外部 DB、Docker、追加の常駐サービスは不要とする |
| 対応環境 | Windows を先行対象とし、初期版の完了判定も Windows のみとする（Linux 対応は後続） |
| ネットワーク・認証 | 初期版は利用者が管理する限定された安全なネットワーク環境を前提とし、利用者認証は設けない。HTTP 接続を許容するが通信の機密性は保証しない。外部 Hub との通信は共有シークレットで認証する |
| 履歴保持 | 履歴データは原則無期限で保持する。日次・月次実績は再取得データで更新し、過去の推定結果は遡及再計算しない |
| 障害と復旧 | 障害時の手動復旧および作業に伴う一時停止を許容する（自動バックアップ・自動更新・自動ロールバックは対象外） |
| 開発環境 | 動作確認用の Mock Hub を同梱するが、実機互換性の確認は実 Hub で行う。実データ用と Mock 用は排他的に起動し、接続先と保存データを分離する。起動は mise の別タスクで提供する（2026-09-13 利用者指示） |
| 性能・規模 | 性能の数値目標は未指定とし、根拠のない上限設定や過剰設計は行わない |

※ 同一アカウントの複数端末利用をサポートします（ログ共有による多重報告構成は考慮外）。

**推定設定の負担（2026-09-13 利用者指示）:** 通常の推定には基準プラン・倍率の設定を要求しません。同じツールで異なるプランの利用額が混在し、まとめて推定する場合に限り、トップレベルの共通設定へ基準プラン（倍率1）と相対的な利用上限倍率を設定します。単一契約、同一プランの複数契約、利用額を契約ごとに分離できる場合は、これらの設定なしで動作させます。共通設定が不正な場合は推定全体を停止しますが、Hubの接続・観測保存は継続します。Hub行の `estimation` は後方互換として扱わず、存在時は `ConfigurationError('hub_estimation_must_be_top_level')` により起動を中止します。具体的な計算条件は [機能仕様 第1.2節](../doc/spec/functional-spec.md#12-計算式と成立条件) に従います。

## 3. 品質要求

### 3.1 識別と履歴の正確性

- Hub、端末、契約、利用枠、対象期間を厳密に区別し、再受信や過去データ補完による二重計上を防止する。
- 観測・端末は Hub と `deviceId` の組で保持する。利用枠に `accountKey` がある全 provider について、`provider` と `accountKey` の組をHubをまたぐ観測上の契約IDとして扱い、公式契約IDとの等価性は保証しない。Grokだけは既合意の `accountEmail` trim・lowercase・SHA-256 キーを継続し、Claudeの組織識別不足は [Issue #34](https://github.com/nuitsjp/token-monitor-analytics/issues/34) として残すが、共通実装をブロックしない。
- プランは全 provider で明示された `planLabel` を属性として使う。既知の Codex wire で `planLabel` がない場合に限り、従来の `accountLabel` をプラン属性として読む。`accountLabel` を一般的なプラン名とはみなさない。
- Grok は正規化後のメールアドレスが異なる場合は別契約とし、メールアドレスが欠落した行は契約を生成せず、端末の取得情報として保持する。トークンの `accountKey` が変わっても契約を分けない。
- `used` と正の `limit` から消費率を導出した場合は、導出に使った `limit` を `percentageLimit` として根拠に保存する。上限の変更は比較境界とし、同じ時刻・同じ率でも `percentageLimit` が異なる報告は競合として扱う。
- 同一契約の複数Hub・端末報告では、利用額ソースを一度ずつ加算し、契約・利用枠の消費率を一度だけ採用する。契約と端末・ツールの関係は多対多で保持する。
- 利用額の収集範囲はCursorをアカウント全体、他ツールを端末単位として扱う。Cursorの同じ契約ID集合を持つ報告は、最新の収集成功日時の一件だけを採用する。契約集合が一部だけ重なる報告や同じ収集日時で値が異なる報告は、推測で統合しない。
- 推定では、最新通知にない端末、staleな端末、利用額・収集成功日時・正常な収集状態を確認できない端末、および欠測境界にある端末を利用額ソースから除外する。残る利用額ソースの契約に必要な利用枠が欠ける場合は推定を停止し、欠落値をゼロで補完しない。除外がある結果は取得できた端末の利用額に基づく参考値であることを明示する。
- Grok は同じ正規化メールアドレスを一契約として表示し、契約と関係デバイスを n:n で保持する。代表表示は正常かつ stale でない報告のうち最新のものを使い、古いトークン行を別カードにしない。同時刻で利用枠の比較対象値が異なる場合は `conflicting_rate` とし、表示メタデータだけの差は比較対象外とする。
- 現在値と過去実績を分離し、利用許容量の推定には SSE 経由の現在値のみを用いる（履歴データから推定値を生成しない）。
- データの対応関係が確認できない場合は「推定不可」とし、推測値やゼロ埋めによる補完を行わない。
- 端末 ID 変更時は別端末として扱い、自動的な名寄せは行わない。
- 日次実績は端末側の現地日付および数値をそのまま保持し、タイムゾーン変換や按分は行わない（当日分を除外した確定値のみ保存）。
- Hub 側で保持期間切れとなった保存済み履歴も保持し続ける。

### 3.2 障害の分離と状態の明示

保全性や正確性を担保できない処理は安全に停止し、正常な機能は継続します。障害や異常を正常終了として隠蔽しません。

| 状況 | 期待する振る舞い |
| --- | --- |
| Hub 接続失敗・切断 | UI に「未接続」を表示し自動再接続を試みる。他 Hub の通信および保存済み履歴の閲覧は維持する |
| Hub 個別の収集停止 | 明示的な再開操作まで該当 Hub の全通信を停止する。他 Hub の収集および既存データの閲覧は維持する |
| 不正な受信データ | 影響を受ける処理を停止して原因と影響を表示する。他 Hub および安全な処理は継続する |
| 保存失敗・整合性異常 | 整合性が損なわれる書き込みを停止し「保存失敗」を表示する。参照可能な保存データの閲覧は維持する |
| 復旧困難な致命的異常 | プロセスの安全な停止を許容し、ログ等で原因を追跡可能にする |

※ Hub 接続状態、収集設定、データ保存状態、推定可否の各状態は独立して管理し、UI 上で同時成立する状態（例: 接続正常だが推定不可）を明示します。

### 3.3 認証と信頼境界

- 初期版は限定された安全な利用環境を前提とし、Web 画面、静的アセット、JSON API、ブラウザ向け SSE は利用者認証なしで提供します。利用者認証は後続実装とし、方式と適用時期は [U12](../PLAN.md#u12) で定めます。
- HTTP 接続を許容しますが、通信の機密性は保証しません。Hub への共有シークレット認証は外部 API の接続要件として維持します。
- 受信データおよび管理操作入力の境界でバリデーションを実施し、不正入力を安全に処理します。
- Hub 管理やシステム更新などの重要操作に CSRF 対策を講じます。
- 認証資格情報や Hub の共有シークレットをログやレスポンスへ出力しません（ログには日時・対象 Hub・処理内容・エラー詳細を記録）。

### 3.4 並行処理と整合性

複数 Hub からの並行受信、実績補完、管理操作が重なった場合でも、データ保存と推定処理の整合性を維持します。推定は同一SSE通知への同時収載を前提にせず、各時点で採用できる論理利用額ソースとその契約の利用枠が前回比較点より新しく正常に観測された時だけ確定します。切断を検知した時点では関係する比較を中断し、次の正常な通知で欠測端末を除外した対象を再構成します。無関係な推定は継続します。通信待機によって他の収集処理をブロックしません。ボトルネックが生じた場合は計測結果に基づいて局所的に対処し、根拠のない早期最適化は行いません。

第1〜3節の要件を根拠とし、[共通標準 第2節の4点](standards/design-and-documentation.md#design-decisions) に基づき新たな仕組みやコンポーネントの追加要否を判断します。判断理由の記録と初期設計の完了基準は [文書方針 第4節](document-policy.md#initial-design-completion) に従います。

## 5. データ保全と変更管理の境界

システムの更新やロジック変更でDBを初期化したり、追記済みの履歴イベントを書き換えたりしません。再計算に必要な入力情報を観測とともに保存し、その履歴から現行規則で比較基準と現在結果を再構築します。過去に保存されていない情報は補完せず、既存結果を保持した上で再構築可能な範囲を扱います。移行は全段階を一つのトランザクションで行い、失敗時は移行前の版とデータへ戻し、原因解消後に再試行します。

以下の変更を行う場合は、事前に影響を説明して利用者の明示的な合意を得る必要があります。

- 履歴データの消失や非互換を伴う変更
- 公開範囲、対象ユーザー数、認証方式の変更
- 単一プロセス・ローカル SQLite 保存構成からの逸脱
- 追加の常駐サービスや外部インフラの必須化
- サポート対象環境の変更

## 6. 検証と製品の完了条件

[共通標準 第5節](standards/design-and-documentation.md#completion) に基づき、以下の受け入れ条件を検証します。

| 検証対象 | 受け入れ条件 |
| --- | --- |
| 通常収集・推定・表示 | 複数 Hub の実測データから同一契約を一件として正しく利用許容量を推定し、結果を永続化・表示できること。各Hub・端末への関連参照とHub別実績を確認できること |
| 再受信・再接続・補完 | データの二重計上、未観測データの推測生成、他 Hub への干渉が発生しないこと。Cursorのアカウント全体実績を重複加算せず、除外後に採用する利用額ソースとその契約の利用枠が新しくなるまで共通推定を確定しないこと |
| リセット・欠測・不正入力 | 期間の異なる増分を混在させず、計算不能な場合に正常値として誤認させないこと |
| データ保存失敗 | 誤った成功通知を出さず、障害原因をログ等で追跡でき、安全な保存データの閲覧を維持できること |
| 管理操作・秘密情報 | 限定された安全な利用範囲で、入力検証と CSRF 対策により意図しない変更を防止し、画面やログへ機密情報を出力しないこと |
| 手動更新失敗 | 既存の DB および履歴データを保全し、手動復旧に必要な情報が得られること |
| 対応環境 | Windows 実機で必要な動作を検証できること（Linux は後続） |

- **レビュー指摘の分類**: 指摘は「必須修正」「任意改善」「対象外」に分類します。データ破損、失敗の隠蔽、機密情報の漏洩、復旧情報の欠落は「必須修正」とし、製品完了前に解消します。合意済みのリスク受容事項（限定された安全な範囲での利用者認証見送り、HTTP 接続の許容、自動バックアップ見送り等）は確定事項として扱います。

※ 上記受け入れ条件を満たし、必要なテスト・検証を通過し、残存する必須修正を解消した時点で初期版の開発完了と判定します。

## 7. 将来要件と初期版の対象外事項

### 後続要件（利用者認証）
ダッシュボード自体の利用者認証は初期版の完了条件から除外し、後続で実装します。認証方式は未決であり、Basic 認証の再採用を前提としません。方式や適用時期は [U12](../PLAN.md#u12) で検討します。

### 将来要件（手動関連付け）
同一 Hub での端末リプレイス時、ユーザーが旧端末と新端末を指定して過去データの参照先を手動で付け替える機能は将来要件とします（初期版では未実装）。この場合も過去の利用額・消費率・推定値自体は変更せず、遡及再計算は行いません。

### 初期版の対象外事項
以下の項目は初期版のスコープ外とし、先行実装は行いません。

- 履歴データの手動・自動削除機能
- 複数ユーザー対応およびロールベースアクセス制御
- 無停止運用および完全自動フェイルオーバー
- 分散アーキテクチャ、マルチプロセス、外部 RDBMS 抽象化
- 過去データの遡及再計算基盤・イベントソーシング
- 自動バックアップおよび自動ロールバック機能
