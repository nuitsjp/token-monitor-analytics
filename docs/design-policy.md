# Token Monitor Analytics — 設計・実装ガードレール

## 1. 設計目標と前提

本プロジェクトは、必要な機能・品質・安全性を満たしたうえで、システムの理解、コード変更、検証、および運用の全体負担を最小化することを基本方針とする。過度な品質追求や、コード行数・ファイル数・依存関係の削減そのものを目的化しない。

本システムは、上流の複数 Token Monitor Hub から利用実績と利用枠を取得し、実測した「API 換算額」と「消費率」の増分から定額制サブスクリプションのドル建て利用許容量を推定・記録するセルフホスト型ダッシュボードである（算出した推定値は参考値であり、公式の利用上限や保証値ではない）。

| 観点 | 合意済みの前提条件 |
| --- | --- |
| 利用者・運用 | 当初は利用者 1 名を想定。障害時やアップデート失敗時の手動復旧を許容する。 |
| 複数 Hub 対応 | **複数の Hub への同時接続および管理を必須要件とする**（並行した集約・管理に対応）。 |
| 基本構成 | Windows および Linux 上で動作する Node.js（24 LTS）の単一常駐アプリケーション。履歴データはローカルの単一 SQLite で管理する。 |
| 外部依存・インフラ | 外部データベース、Docker、追加クラウドインフラは不要（上流 Hub は別途稼働前提）。 |
| 機能要件 | 複数 Hub からの SSE 並行受信・自動再接続、GET リクエストによる端末別利用実績の補完、データ保存・推定、Web UI 閲覧およびブラウザ向け SSE 配信、Web 画面からの Hub 管理（登録・一覧・個別停止）、手動システム更新。端末からの直接トークン収集は含まない。 |
| 接続形態 | LAN、VPN、またはローカルループバック経由。Basic 認証によるアクセス制御を実施し、当面は HTTP 通信を許容する。 |
| 履歴データ・復旧 | 原則無期限で保存し、算出時点の推定結果を保持する。過去データの遡及再計算や、バックアップ機能・定期運用の実装は求めない。 |
| 開発環境 | 動作確認用の模擬 Hub（Mock Hub）を同梱する。外部依存ライブラリの採用は、必要性に応じて個別に判断する。 |

※ 同時接続可能な Hub 数、データ保持量、応答時間などの具体的な数値目標は現時点で未指定であり、根拠のない独自の上限値や要件を設けてはならない。

## 2. アーキテクチャと設計追加の判断基準

外部ライブラリの導入、関数の分割、階層構造やインターフェースの導入は、必要な品質を満たしつつ開発・運用負担を軽減できる場合に限って採用する。「依存の一律禁止」や「レイヤー数・インターフェースの制限」といった極端な制約は設けない。

システムの構造や運用負担に影響を与える仕組みを新たに追加する場合は、事前に以下の 4 点を明確に示す必要がある。

1. 解決すべき現在の要件、具体的なリスク、または合意済みの将来要件
2. その仕組みを追加しなかった場合に生じる具体的な問題
3. よりシンプルな構成、局所的な修正、または手動運用では不十分である理由
4. 今すぐ導入すべき理由と、見送った場合に生じる具体的な負担

単に見た目を整えるだけの全面リファクタリングや、抽象的な理由（ベストプラクティス、堅牢性向上、将来への備え等）による過度な抽象化・不要なフォールバック・後方互換対応は行わない。ただし、日常的な関数の分割や局所的な修正・改善に対してまで、上記の説明や事前承認を求めるものではない。

## 3. 必要な品質保証と許容する失敗

### 3.1 障害時の動作継続と通知

安全に継続できる機能を可能な限り維持し、履歴データの保全や表示の正確性を担保できない処理のみを適切に停止する。異常を隠蔽したり、処理の失敗を正常終了と偽ってはならない。

| 状況 | 求められる振る舞い |
| --- | --- |
| 特定 Hub との一時的な切断 | 該当 Hub への自動再接続を試みつつ、履歴閲覧や他 Hub との通信・処理は継続する。画面上にも未接続状態を明示する。 |
| 一部 Hub の不正データ・非互換 | 不正入力を正常データとして処理せず、影響を受ける処理のみ停止する。他 Hub の通信や履歴閲覧は維持し、原因と影響範囲を明示する。 |
| 保存失敗・書き込み不整合 | 整合性を担保できない書き込み処理を停止する。安全に参照できる範囲で、履歴閲覧やステータス表示は可能な限り維持する。 |
| プロセス全体の継続が困難な異常 | プロセスの完全停止を許容する。コンソールやログ等で原因を追跡可能にする。 |

- **状態表示**: 画面上では、各 Hub の接続状態やデータごとに「正常」「未接続」「保存失敗」「推定不可」を明確に区別し、過去の保存値を現在値と誤認させない表示を行う。
- **ログ記録**: 発生日時、対象 Hub、該当処理、エラー詳細など原因調査に必要な情報を記録する。ただし、認証情報や共有シークレットなどの機密情報は出力してはならない。
- **範囲**: 無停止運用や完全自動復旧、プロセス延命の仕組みは求めない。また、一部機能の維持のためだけに大掛かりな障害隔離機構を導入することも避ける。

### 3.2 履歴・推定・補完の正確性

- **データの分離と整合性**: Hub 単位および契約・利用枠単位でデータを確実に識別・分離し、混同や誤合算を防止する。データの再受信や補完処理における二重計上を防ぎ、リセット前後や対応関係が不明な増分データは無理に補完せず「推定不可」として扱う。
- **実績補完の範囲**: 停止中や再接続時の過去実績は、各 Hub から取得できた範囲内に限って補完する。未観測の利用枠や推定値を推測で生成してはならない（Hub 側に残っていないデータの完全復元は保証外）。
- **履歴の保全**: 過去の各時点で算出して表示した推定結果はそのまま保持し、ロジック変更に伴う過去データの改変は行わない（再計算を目的としたイベント再生機構等は不要）。
- **保存期間と改変の禁止**: 履歴データは原則無期限で保持し、自動削除・集計置換や手動削除機能の先行実装は行わない。バックアップ機能は必須としないが、エラー処理や更新失敗を理由としたデータベースの初期化、履歴の削除・改変は禁止する。

### 3.3 認証・外部入力・機密情報の保護

- **アクセス制御**: Web 画面、API、ブラウザ向け SSE エンドポイントには Basic 認証を適用する。認証情報や共有シークレットをログやレスポンスに出力してはならない。
- **通信経路**: 当面は HTTP 通信を許容するが、通信経路の暗号化（TLS/VPN 等）がない環境では認証情報の機密性が保たれない前提とする。説明資料等でも「アクセス制御」と「通信経路の暗号化」を明確に区別して記載すること。[1]
- **入力検証と CSRF 対策**: 外部との信頼境界（Hub 受信データや管理操作）で必要なバリデーションを実施する（内部モジュール間の過剰な重複検証は不要）。Hub 管理やシステム更新などの重要操作には、CSRF 等を防ぐ保護対策を講じること。[2]
- **ユーザー管理**: 単一ユーザー想定のため、複数ユーザーの権限管理やデータ分離は初期対象外とする。

### 3.4 同時実行・性能・対応環境

- **並行処理の整合性**: 複数 Hub からの並行受信、過去実績補完、管理操作が重なった場合でも、排他制御によりデータ保存および推定計算の整合性を維持する（将来のマルチプロセス化や分散配置を想定した過剰な制御基盤は不要）。
- **性能とリソース**: 性能改善やリソース最適化は、実環境で具体的な問題が発生した段階でボトルネックを特定・計測し、局所的な改善から対処する（無期限保存方針は、無制限のストレージや特定応答時間の保証を意味しない）。
- **対応環境**: 対象プラットフォームは Windows および Linux（Node.js 24 LTS）。OS 間の動作差異を検証し、未指定のバージョンや環境への互換対応を独断で追加しないこと。

## 4. アップデートと手動復旧

- **実行方式**: システムのアップデートはユーザーの明示的な操作に基づいて実行する。自動更新、自動ロールバック、無停止更新などの高度な仕組みは求めない。
- **手動復旧の原則**: アップデート失敗時は手動復旧を基本とし、作業に伴うシステム停止を許容する。失敗時はその事実と原因を追跡可能なログ・エラー情報として記録し、誤った成功通知を行わないこと（事前自動バックアップや完全な原状復元機能は必須としない）。
- **データ保全と承認**: アップデート処理に伴うデータベースの初期化や履歴の改変・削除は禁止する。**既存データの消失リスクや互換性を損なう破壊的変更を行う場合は、事前に影響範囲と手動復旧の制約を説明し、ユーザーから明確な承認を得ること。**

## 5. テスト・レビュー・完了条件

テストは、受け入れ条件の達成、重要な境界値の検証、具体的な失敗ケースの確認、および不具合の再発防止を目的に実施する（テストコード行数やカバレッジ数値自体の目的化は避ける）。

| 確認対象 | 主な確認内容 |
| --- | --- |
| 通常の収集・推定・保存・閲覧 | 複数 Hub それぞれの対象契約・利用枠の実測値から正しく推定を行い、算出時点の結果を確実に保存・表示できること。 |
| 再接続・利用実績の補完 | データの再受信や過去履歴の補完において二重計上を行わず、他 Hub のデータに影響を与えないこと。未観測の利用枠や推定値を推測で独自生成しないこと。 |
| リセット・欠測・不正入力 | 対応関係のない増分データを混在させず、計算が成り立たない推定結果を正常値として表示しないこと。 |
| 保存失敗・障害時の表示 | 保存失敗時に誤った成功通知を行わず、原因を追跡できること。一部 Hub の障害時も安全に稼働できる機能は継続すること。 |
| 認証・管理操作 | 保護対象への不正アクセスや意図しない設定変更・更新を防止し、機密情報を不要に出力しないこと。 |
| アップデート失敗 | 履歴データを破壊せず、失敗の事実を明示して手動対応に必要な情報を記録・提示できること。 |
| OS 間の差異 | Windows と Linux の双方で動作を確認すること。 |

- **検証の基準**: 模擬 Hub（Mock Hub）での検証のみをもって「実機との互換性が確認できた」と判断しない。未実施の検証項目がある場合は、事実と影響範囲を明確に報告すること。
- **レビュー指摘の分類**: 指摘は「必須修正」「任意改善」「対象外」の 3 つに分類する。データ破損、失敗の隠蔽、機密情報漏洩、検証・復旧情報の欠落等は「必須修正」とする。合意済みのリスク受容事項（HTTP 許容、バックアップ見送り、手動復旧方針等）を単なる懸念で蒸し返して修正を求めない。
- **完了条件**: **受け入れ条件を満たし、必要な検証を通過し、残存する必須修正が解消された時点でタスク完了とみなす。** 独断によるさらなる構造改善やアイデア提案で作業を引き延ばさないこと。

## 6. 事前相談と将来要件

事前に相談すべき事項は、合意済みの前提や方針から外れ、システムの保証範囲、基本構造、または運用負担に影響を与える変更に限定する。

- 履歴データの消失や過去バージョンとのデータ非互換を伴う変更
- 公開範囲、対象ユーザー、認証方式の変更
- 単一プロセス構成やローカル保存の原則から外れる構成
- 追加の常駐サービスや運用インフラの必須化
- サポート対象環境の変更

本方針の範囲内に収まる日常的な実装判断は担当者の裁量で進めてよい。外部ライブラリの採用も必要性と保守負担を総合的に判断して行い、上記基準を超える場合にのみ相談する。

手動履歴削除、複数ユーザー権限管理、無停止運用、分散処理、マルチ DB 抽象化、過去データ再計算基盤、自動バックアップ・ロールバック等は初期対象外とする。「将来のため」だけの先行実装は避け、責務の適切な分離を意識したうえで現時点で真に必要な仕様のみを実装すること。

## 7. 未決事項・適用時の確認・根拠

現時点で品質水準やリスク受容に関する重大な未決事項はないが、以下の項目は作業時に確認すること。

| 確認項目 | 扱いと留意点 |
| --- | --- |
| 現行の設計方針や指示事項（`AGENTS.md` 等） | 作業前に関連ファイルを確認し、矛盾点があれば報告する。既存の指示事項を無断で削除・上書きしないこと。 |
| 実装詳細（ソースコード、Hub API 仕様、DB 構造、ビルド・テスト手順等） | 既存リポジトリ等から事実を確認し、推測で補わないこと。不明点は着手前に解消する。 |
| 接続数・データ保持量・性能の具体値 | 複数 Hub 対応は必須だが、数値目標は現時点で未指定。過剰設計や独自の上限値追加は避け、必要に応じて利用条件を確認する。 |

本方針の採択後は、Git リポジトリで管理される本書（`docs/design-policy.md`）を正本として扱う。見直し時は最新の本書と改定指示を参照し、変更理由をコミット履歴等に記録すること。リスク受容の範囲に関わる重要な変更は、事前にユーザーとの合意を得ること。
