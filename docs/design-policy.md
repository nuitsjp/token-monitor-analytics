# Token Monitor Analytics — 設計・実装ガードレール

## 1. 設計目標と前提

システムの理解、変更、検証、運用の全体負担を最小化することを基本方針とする。過度な品質追求や、コード量・依存関係の削減そのものの目的化は避ける。

本システムは、上流の複数 Token Monitor Hub から利用実績と利用枠を取得・表示し、実測増分から定額制サービスの利用許容量（米ドル換算）を推定・記録するセルフホスト型ダッシュボードである（推定値は実測に基づく参考値であり、公式上限や保証値ではない）。

| 観点 | 方針・前提 |
| --- | --- |
| 想定利用者 | 1 名（障害時や更新失敗時の手動復旧を許容）。 |
| 構成・環境 | Windows / Linux（Node.js 24 LTS）の単一常駐プロセス。組込 SQLite を使用し、外部 DB や Docker は不要。 |
| 機能範囲 | 複数 Hub からの並行受信（SSE による現在値の表示・推定）、GET による実績の定期収集・補完、Web 配信（ブラウザ向け SSE、Basic 認証）。端末からの直接収集は行わない。 |
| 複数 Hub 管理 | 複数 Hub への並行接続・状態監視、および Hub 個別の収集停止・再開。 |
| 表示対象 | プロバイダーやプランを限定せず、取得できた利用枠・消費率・API 換算額を表示（推定不可の場合も取得情報は表示）。 |
| 接続・認証 | LAN、VPN、またはローカル環境。Basic 認証によるアクセス制御を実施（当面は HTTP 通信を許容）。 |
| 履歴方針 | 履歴は原則無期限で保存し、算出時点の推定結果を保持。日次・月次実績は再取得値で更新するが、推定結果の遡及再計算や自動バックアップは行わない。 |
| 開発環境 | 動作確認用の模擬 Hub（Mock Hub）を同梱。 |
| 性能・規模 | 数値目標は未指定とし、根拠のない独自の上限設定や過剰設計は設けない。 |

## 2. アーキテクチャと設計追加の判断基準

文書作業の判断基準と、設計・実装を段階的に進める方法は [文書方針](document-policy.md) に従う。具体的な作業範囲は [開発計画](../PLAN.md) で管理する。

ライブラリ導入や構造化（関数分割、階層化等）は、品質を維持しつつ開発・運用負担を軽減できる場合に限り採用する。システムの構造や運用負担に影響を与える仕組みを追加する場合は、事前に以下 4 点を明確にする。

1. 解決すべき現在の要件、具体的なリスク、または合意済みの将来要件
2. 追加しなかった場合に生じる具体的な問題
3. よりシンプルな構成、局所的な修正、または手動運用では不十分である理由
4. 今すぐ導入すべき理由と、見送った場合に生じる具体的な負担

抽象的な理由（ベストプラクティス、将来への備え等）による過度な抽象化、不要なフォールバック、後方互換対応は行わない（日常的な関数分割や局所的な改善は対象外）。

## 3. 必要な品質保証と許容する失敗

### 3.1 障害時の動作継続と通知

安全に継続できる機能を維持し、データの保全や表示の正確性を担保できない処理のみを適切に停止する。異常の隠蔽や、失敗を正常終了と偽る処理は行わない。

| 状況 | 求められる振る舞い |
| --- | --- |
| Hub への接続失敗・切断 | 原因を問わず自動再接続を継続。履歴閲覧や他 Hub との通信を維持し、画面に「未接続」を表示する。 |
| 一部 Hub の不正データ | 当該データの影響を受ける処理のみ停止。他 Hub の通信や履歴閲覧を維持し、原因と影響を表示する。 |
| 保存失敗・整合性異常 | 整合性を担保できない書き込みを停止。安全に参照できる範囲で閲覧や状態表示を維持し、「保存失敗」を表示する。 |
| 復旧困難な異常 | プロセスの完全停止を許容。ログ等で原因を追跡可能にする。 |

- **状態の明示**: 接続状態やデータごとに「正常」「未接続」「収集停止」「保存失敗」「推定不可」を画面上で明確に区別し、過去の保存値を現在値と誤認させない。
- **収集停止の扱い**: 利用者が特定 Hub の収集停止を操作した場合、再開操作まで該当 Hub の全通信を停止する（他 Hub の収集や保存済みデータの閲覧は維持）。
- **表示と推定の分離**: 推定不可の場合も、取得できた利用枠や実績を更新時刻・取得状態とともに表示する。契約への帰属が不明な API 換算額は、集計単位（Hub・端末・ツール等）を明示して表示する。
- **ログ記録**: 発生日時、対象 Hub、処理内容、エラー詳細を記録する（認証情報や共有シークレットは出力しない）。
- **許容事項**: 単一利用者環境のため、無停止運用、完全自動復旧、大規模な障害隔離機構の実装は求めない。

### 3.2 履歴・推定・補完の正確性

- **データ分離と二重計上防止**: Hub 単位および契約・利用枠単位でデータを識別・分離し、再受信や補完時の二重計上を防止する。同一ログの多重報告（端末間のファイル複製構成）はサポート対象外とする。
- **現在値と過去実績の役割分離**: 推定には SSE で取得した現在値の観測のみを使用する。GET で取得した日次・月次実績は推移の閲覧や比較のみに用い、過去の利用許容量の遡及推定や現在値の更新には使用しない。
- **端末 ID 変更の扱い**: 端末再設定等で ID が変更された場合は別端末として扱い、自動での名寄せは行わない（手動関連付けは将来要件。第 6 節参照）。
- **推定条件と計算区間**: 契約・利用枠・対象期間が特定でき、同一期間内で正の増分が得られる場合に限り、最初と最新の観測差分から算出する（計算式・業務ルールは [機能要件](requirements.md#2-利用許容量の推定)、API 項目との対応は [機能詳細設計](functional-design.md#1-推定観測と対象期間の対応) 参照）。
- **実績補完の範囲**: 停止中や再接続時の過去実績は Hub の保持範囲内に限り補完し、未観測の利用枠や推定値を推測で独自生成しない。
- **日次履歴の日付基準**: 端末ごとの現地日付と数値をそのまま保持し、タイムゾーン変換や按分は行わない。当日分は端末側の日付基準で除外する。
- **履歴の保全**: 履歴は原則無期限で保存し、算出時点の推定結果を保持する。ロジック変更に伴う遡及再計算や、データベース初期化・履歴改変は禁止する。

### 3.3 認証・外部入力・機密情報の保護

- **アクセス制御**: Web 画面、API、ブラウザ向け SSE に Basic 認証を適用する。認証情報や共有シークレットをログやレスポンスに出力しない。
- **通信経路**: 当面は HTTP 通信を許容するが、暗号化のない環境では機密性が担保されない前提とする（「アクセス制御」と「通信経路の暗号化」を区別する [1]）。
- **入力検証と CSRF 対策**: Hub 受信データや管理操作などの信頼境界で入力検証を実施する。Hub 管理やシステム更新などの重要操作には CSRF 対策を講じる [2]。
- **ユーザー管理**: 単一利用者想定のため、複数ユーザーの権限管理やデータ分離は実装しない。

### 3.4 同時実行・性能・対応環境

- **並行処理の整合性**: 複数 Hub からの並行受信、実績補完、管理操作が重複した場合でも、排他制御によりデータ保存および推定計算の整合性を維持する。
- **性能とリソース**: 実環境でのボトルネック計測に基づいて局所的に対処し、早期最適化は行わない。
- **対応環境**: Windows および Linux（Node.js 24 LTS）。OS 間の動作差異を検証し、未指定環境への互換対応は独断で追加しない。

## 4. アップデートと手動復旧

- **実行方式**: 利用者の明示的な操作により実行する（自動更新や自動ロールバックは実装しない）。
- **手動復旧の原則**: 失敗時は手動復旧を基本とし、作業に伴うシステム停止を許容する。失敗の事実と原因をログ等に記録する。
- **データ保全と承認**: アップデート処理に伴うデータベース初期化や履歴改変は禁止する。既存データの消失リスクや互換性を損なう変更は、事前に影響範囲を説明し、利用者の明示的な承認を得ること。

## 5. テスト・レビュー・完了条件

テストは、受け入れ条件の達成、重要な境界値の検証、具体的な失敗ケースの確認、不具合の再発防止を目的に実施する（カバレッジ数値自体の追求を目的化しない）。

| 確認対象 | 主な確認内容 |
| --- | --- |
| 通常の収集・推定・表示 | 複数 Hub の実測値から正しく推定を行い、算出結果を確実に保存・表示できること。 |
| 再接続・実績補完 | 二重計上や推測値の独自生成がなく、他 Hub のデータに影響を与えないこと。 |
| リセット・欠測・不正入力 | 対応関係のない増分データを混同せず、計算不能な推定結果を正常値として表示しないこと。 |
| 保存失敗・障害時の表示 | 保存失敗時に誤った成功通知を行わず原因を追跡できること。一部障害時も継続可能な処理を維持すること。 |
| 認証・管理操作 | 保護対象への不正アクセスや意図しない変更を防止し、機密情報を出力しないこと。 |
| アップデート失敗 | 履歴データを破壊せず、失敗を明示して手動対応に必要な情報を提示できること。 |
| OS 間の差異 | Windows と Linux の双方で期待通り動作すること。 |

- **検証基準**: 模擬 Hub（Mock Hub）での検証のみをもって実機互換と判断しない。未実施の検証項目がある場合は、事実と影響範囲を明確に報告する。
- **レビュー指摘の分類**: 指摘は「必須修正」「任意改善」「対象外」に分類する。データ破損、失敗の隠蔽、機密情報漏洩、復旧情報の欠落等は「必須修正」とする。合意済みのリスク受容事項（HTTP 許容、自動バックアップ見送り等）を再審議しない。
- **完了条件**: 受け入れ条件を満たし、必要な検証を通過し、残存する必須修正が解消された時点でタスク完了とする。

## 6. 事前相談と将来要件

### 事前相談が必要な事項

合意済みの前提や方針から外れ、システムの保証範囲、基本構造、または運用負担に影響を与える変更は、着手前に必ず相談すること。

- 履歴データの消失やデータ非互換を伴う変更
- 公開範囲、対象ユーザー、認証方式の変更
- 単一プロセス構成やローカル保存の原則から外れる構成
- 追加の常駐サービスや運用インフラの必須化
- サポート対象環境の変更

### 合意済みの将来要件

同一 Hub 内において、利用者が旧端末と新端末を指定し、過去データの `deviceId` を新しい `deviceId` に書き換えて手動で関連付ける機能を将来実装する。変更対象は端末への帰属参照に限定し、保存済みの利用額・消費率・推定値・算出時点の変更や遡及再計算は行わない（初期版では実装しない）。

### 初期対象外（先行実装の禁止）

以下の機能・基盤は初期対象外とし、先行実装は行わない。

- 手動・自動の履歴削除機能
- 複数ユーザー対応・権限管理
- 無停止運用・完全自動復旧機構
- 分散処理・マルチプロセス・マルチ DB 抽象化
- 過去データの遡及再計算・イベント再生基盤
- 自動バックアップ・自動ロールバック
