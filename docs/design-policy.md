# 設計方針

Token Monitor Analytics は、複数の Hub の実績・利用枠を閲覧し、実測増分から定額制サービスの利用許容量を米ドル換算の参考値として推定・保存する、セルフホスト型ダッシュボードである。

本書は製品要件の正本とする。具体的な仕様は [設計書](architecture.md)、用語は [CONTEXT.md](../CONTEXT.md)、未決・未検証事項は [PLAN.md](../PLAN.md)、共通原則の採用版と文書構造は [文書方針](document-policy.md) に置く。

## 1. 目標と機能範囲

| 機能 | 初期版の要件 |
| --- | --- |
| 現在値の閲覧 | プロバイダー・プランを限定せず、取得した利用枠・消費率・API 換算額を、取得状態・更新時刻とともに表示する。 |
| 利用許容量の推定 | 同一の契約・利用枠・対象期間の利用額と消費率の実測増分から算出し、算出時点の結果と根拠を保存する。 |
| 過去実績の閲覧と比較 | Hub の保持範囲から日次・月次実績を定期収集・補完し、推移を保存・表示する。 |
| 複数 Hub 管理 | 並行接続・状態監視、Web での登録・一覧、Hub 個別の収集停止・再開を提供する。 |
| 手動更新と復旧 | 明示操作で更新し、失敗の原因と手動復旧に必要な情報を提示する。 |

端末から直接収集しない。推定できなくても取得できた実績・利用枠を表示し、契約に帰属できない利用額には Hub・端末・ツール等の実際の集計単位を示す。

## 2. 制約と受容するリスク

| 観点 | 制約 |
| --- | --- |
| 利用者 | 1 名。 |
| 実行と保存 | Node.js 24 LTS の単一常駐プロセスと組込 SQLite。外部 DB・Docker・追加常駐サービスを必須にしない。 |
| 対応環境 | Windows を先行し、初期の完了判定も Windows のみ。Linux 対応と OS 間の差異の検証は後続とする。 |
| 接続と認証 | LAN・VPN・ローカル環境で、Web に Basic 認証を適用する。HTTP を許容し、アクセス制御は行うが通信の機密性は保証しない。 |
| 履歴 | 原則無期限。日次・月次実績は再取得値で更新し、保存済み推定結果は改変・遡及再計算しない。 |
| 障害と更新 | 手動復旧と作業中の停止を許容する。自動バックアップ・自動更新・自動ロールバックは行わない。 |
| 規模と性能 | 数値目標は未指定。根拠のない上限や早期最適化を導入しない。 |
| 開発 | 動作確認用 Mock Hub を同梱するが、それだけで実機互換性を保証しない。 |

同一アカウントを複数端末で独立に利用する構成を対象に含む。同一ログを端末間でコピー・共有して多重報告する構成は対象外とする。

## 3. 品質要求

### 3.1 識別と履歴の正確性

- Hub・端末・契約・利用枠・対象期間を区別し、再受信や補完で二重計上しない。
- 現在値と過去実績を分離し、推定には SSE の現在値のみを使う。履歴 GET から現在値や過去の推定値を生成しない。
- 対応関係が成立しない値は「推定不可」とし、比率配分・ゼロ埋め・代用で算出可能にしない。未観測の利用枠や推定値も補わない。
- 端末 ID の変更は別端末として扱い、自動で名寄せしない。
- 日次履歴は端末の現地日付・数値を保持する。タイムゾーン変換・按分をせず、端末側の日付で当日分を除外する。
- Hub から再取得できなくなった保存済み履歴も保持する。

### 3.2 障害の分離と状態の明示

保全・正確性を担保できない処理を止め、安全な機能は継続する。失敗を正常終了として扱わない。

| 状況 | 振る舞い |
| --- | --- |
| Hub 接続失敗・切断 | 「未接続」を表示して自動再接続を続け、他 Hub の通信と履歴閲覧を維持する。 |
| Hub 個別の収集停止 | 明示的な再開まで全収集通信を止め、他 Hub の収集と保存済みデータの閲覧を維持する。 |
| 不正な受信データ | 影響する処理を止めて原因・影響を表示し、他 Hub と安全な処理を維持する。 |
| 保存失敗・整合性異常 | 整合性を担保できない書き込みを止め、「保存失敗」を表示し、参照可能な保存値の閲覧を維持する。 |
| 復旧困難な異常 | プロセス停止を許容し、原因をログ等で追跡可能にする。 |

接続・収集設定・保存・推定可否は独立して管理する。画面では各対象の「正常」「未接続」「収集停止」「保存失敗」「推定不可」と同時成立する状態の関係を示し、過去の保存値を現在取得した値と誤認させない。

### 3.3 認証と信頼境界

- 画面・静的ファイル・API・ブラウザ向け SSE のすべてに Basic 認証を適用する。
- Hub 受信データ・管理操作等の信頼境界で入力を検証し、外部の文字列を HTML として解釈しない。
- Hub 管理・システム更新等の重要操作に CSRF 対策を適用する。
- 認証情報・Hub の共有シークレットをログやレスポンスへ出さない。ログには発生日時・対象 Hub・処理内容・エラー詳細を残す。

根拠: [RFC 7617](https://www.rfc-editor.org/rfc/rfc7617.html)、[OWASP CSRF 対策](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。

### 3.4 並行処理と性能

複数 Hub の受信・実績補完・管理操作が重複しても、保存と推定の整合性を維持する。通信待ちで他の収集を止めない。性能の問題は実環境で計測し、局所的に対処する。

## 4. 設計を追加する判断基準

第1〜3節を根拠に [共通標準 第2節の4点](standards/design-and-documentation.md#design-decisions)で判断し、第5節の変更の境界を適用する。判断の記録と初期設計の完了基準は [文書方針 第4節](document-policy.md#4-判断の記録と初期設計の完了基準)に従う。

## 5. データ保全と変更の境界

更新・ロジック変更で DB 初期化、履歴改変、推定結果の遡及再計算を行わない。更新失敗の事実・原因を記録し、手動復旧を基本とする。

次の変更は着手前に影響を説明して利用者へ相談する。データ消失リスクや互換性を損なう変更には明示的な承認を得る。

- 履歴消失・データ非互換を伴う変更。
- 公開範囲・対象ユーザー・認証方式の変更。
- 単一プロセス・ローカル保存の原則から外れる構成。
- 常駐サービス・運用インフラの必須化。
- サポート対象環境の変更。

## 6. 検証と製品の完了条件

[共通標準 第5節](standards/design-and-documentation.md#completion)に従い、次を検証する。

| 対象 | 受け入れ条件 |
| --- | --- |
| 通常収集・推定・表示 | 複数 Hub の対応する実測値から推定し、結果を保存・表示できる。 |
| 再受信・再接続・補完 | 二重計上、未観測値の独自生成、他 Hub へのデータ影響がない。 |
| リセット・欠測・不正入力 | 対応しない増分を混ぜず、計算不能な結果を正常値として表示しない。 |
| 保存失敗 | 成功通知を出さず、原因を追跡でき、安全に参照できる保存値を維持する。 |
| 認証・管理操作 | 不正アクセス・意図しない変更を防ぎ、機密情報を出力しない。 |
| 手動更新失敗 | DB・履歴を保全し、原因と手動復旧の情報を得られる。 |
| 対応環境 | Windows で必要な動作を確認し、Linux 対応時は OS 間の差異を検証する。 |

データ破損、失敗の隠蔽、機密情報漏洩、復旧情報の欠落は必須修正とする。HTTP 許容・自動バックアップ見送り等の受容済み条件は再審議しない。受け入れ条件を満たし、必要な検証を通過し、必須修正を解消した時点で初期版を完了とする。

## 7. 将来要件と初期対象外

将来、利用者が同一 Hub の旧端末・新端末を指定し、過去データの `deviceId` を新端末へ変更して手動で関連付ける。変更は帰属参照に限り、利用額・消費率・推定値・算出時点を変えず、遡及再計算しない。初期版では実装しない。

次も初期対象外とし、先行実装しない。

- 手動・自動の履歴削除。
- 複数ユーザー対応・権限管理。
- 無停止運用・完全自動復旧。
- 分散処理・マルチプロセス・マルチ DB 抽象化。
- 遡及再計算・イベント再生基盤。
- 自動バックアップ・自動ロールバック。
