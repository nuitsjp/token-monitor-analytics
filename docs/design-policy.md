# 設計方針 (Design Policy)

Token Monitor Analytics は、複数の Hub から AI ツールの利用実績および利用枠を収集し、実測増分に基づいて定額制サービスの利用許容量を米ドル換算の参考値として推定・保存するセルフホスト型ダッシュボードです。

本書は製品要件の正本です。詳細な技術仕様は [アーキテクチャ設計書](architecture.md)、用語定義は [CONTEXT.md](../CONTEXT.md)、未決・未検証事項は [PLAN.md](../PLAN.md)、共通原則の採用状況は [文書方針](document-policy.md) に定めます。

## 1. 目標と機能範囲

| 機能 | 初期版の要件 |
| --- | --- |
| 現在値の閲覧 | プロバイダーやプランを問わず、取得した利用枠・消費率・API 換算額を、取得状態および更新時刻とともに表示する |
| 利用許容量の推定 | 同一の契約・利用枠・対象期間に属する利用額と消費率の実測増分から利用許容量を算出し、算出時点の結果と根拠を保存する |
| 過去実績の閲覧・比較 | 各 Hub の保持期間に応じた日次・月次実績を定期収集・補完し、推移の保存および比較表示を行う |
| 複数 Hub の一括管理 | 複数 Hub への並行接続・状態監視、Web 画面での登録・一覧表示、Hub 個別の収集停止・再開を提供する |
| 手動更新と復旧 | ユーザーの明示操作によるアップデートを行い、失敗時は原因と手動復旧に必要な情報を提示する |

※ 端末からの直接収集は行わず、Hub 経由でのみデータを取得します。推定が成立しない場合でも取得できた実績・利用枠は表示し、契約に帰属できない利用額は Hub や端末などの実際の集計単位を明記して表示します。

## 2. 制約と前提事項

| 観点 | 制約・前提 |
| --- | --- |
| 利用者 | 単一利用者（1名） |
| 実行・保存環境 | Node.js 24 LTS の単一常駐プロセスおよび組込 SQLite。外部 DB、Docker、追加の常駐サービスは必須としない |
| 対応環境 | Windows を先行対象とし、初期版の完了判定も Windows のみとする（Linux 対応および OS 間差異の検証は後続） |
| ネットワーク・認証 | LAN・VPN・ローカル環境を想定し、Web 画面および全通信経路に Basic 認証を適用する（HTTP 接続を許容） |
| 履歴保持 | 履歴データは原則無期限で保持する。日次・月次実績は再取得データで更新し、過去の推定結果は遡及再計算しない |
| 障害と復旧 | 障害時の手動復旧および作業に伴う一時停止を許容する（自動バックアップ・自動更新・自動ロールバックは対象外） |
| 開発環境 | 動作確認用の Mock Hub を同梱するが、実機互換性の確認は実 Hub で行う |

※ 同一アカウントを複数端末で独立して利用する構成をサポートします（ログの共有による多重報告構成は考慮しません）。

## 3. 品質要求

### 3.1 識別と履歴の正確性

- Hub、端末、契約、利用枠、対象期間を厳密に区別し、再受信や過去データ補完による二重計上を防止する。
- 現在値と過去実績を分離し、利用許容量の推定には SSE 経由の現在値のみを用いる（履歴データから推定値を生成しない）。
- データの対応関係が確認できない場合は「推定不可」とし、推測値やゼロ埋めによる補完を行わない。
- 端末 ID が変更された場合は別端末として扱い、自動的な名寄せは行わない。
- 日次実績は端末側の現地日付および数値をそのまま保持し、タイムゾーン変換や按分は行わない（端末側の日付基準で当日分を除外して確定値を保存）。
- Hub 側で保持期間切れ等により再取得できなくなった保存済み履歴も保持し続ける。

### 3.2 障害の分離と状態の明示

保全性や正確性を担保できない処理は安全に停止し、正常な機能は継続して提供します。障害や異常を正常終了として隠蔽しません。

| 状況 | 期待する振る舞い |
| --- | --- |
| Hub 接続失敗・切断 | UI に「未接続」を表示し自動再接続を試みる。他 Hub の通信および保存済み履歴の閲覧は維持する |
| Hub 個別の収集停止 | 明示的な再開操作まで該当 Hub の全通信を停止する。他 Hub の収集および既存データの閲覧は維持する |
| 不正な受信データ | 影響を受ける処理を停止して原因と影響を表示する。他 Hub および安全な処理は継続する |
| 保存失敗・整合性異常 | 整合性が損なわれる書き込みを停止し「保存失敗」を表示する。参照可能な保存データの閲覧は維持する |
| 復旧困難な致命的異常 | プロセスの安全な停止を許容し、ログ等で原因を追跡可能にする |

※ Hub 接続、収集設定、データ保存、推定可否の各状態は独立して管理し、UI 上で同時成立する状態（例: 接続正常だが推定不可、など）を明示します。

### 3.3 認証と信頼境界

- Web 画面、静的アセット、JSON API、ブラウザ向け SSE の全通信経路に Basic 認証を適用する。
- Hub からの受信データおよび管理操作入力の境界でバリデーションを実施し、外部入力文字列を安全に取り扱う。
- Hub 管理やシステム更新などの重要操作に CSRF 対策を講じる。
- 認証資格情報や Hub の共有シークレットをログやレスポンスへ出力しない（ログには発生日時・対象 Hub・処理内容・エラー詳細を記録）。

### 3.4 並行処理と整合性

複数 Hub からの並行受信、実績補完、管理操作が重なった場合でも、データ保存と推定処理の整合性を維持します。通信待機によって他の収集処理をブロックしません。


## 4. 設計を追加する判断基準

第1〜3節の要件を根拠とし、[共通標準 第2節の4点](standards/design-and-documentation.md#design-decisions) に基づいて新たな仕組みやコンポーネントの追加要否を判断します。判断理由の記録および初期設計の完了基準は [文書方針 第4節](document-policy.md#initial-design-completion) に従います。

## 5. データ保全と変更管理の境界

システムの更新やロジック変更に伴う DB の初期化、履歴の改変、過去の推定結果の遡及再計算は行いません。更新失敗時は原因を記録し、手動復旧を原則とします。

以下の変更は、事前に影響を説明して利用者の明示的な合意を得る必要があります。

- 履歴データの消失や非互換を伴う変更
- 公開範囲、対象ユーザー数、認証方式の変更
- 単一プロセス・ローカル SQLite 保存のアーキテクチャから外れる構成
- 追加の常駐サービスや外部インフラの必須化
- サポート対象環境の変更

## 6. 検証と製品の完了条件

[共通標準 第5節](standards/design-and-documentation.md#completion) に基づき、以下の受け入れ条件を検証します。

| 検証対象 | 受け入れ条件 |
| --- | --- |
| 通常収集・推定・表示 | 複数 Hub の対応する実測データから正しく利用許容量を推定し、結果を永続化・表示できること |
| 再受信・再接続・補完 | データの二重計上、未観測データの推測生成、他 Hub への干渉が発生しないこと |
| リセット・欠測・不正入力 | 期間の異なる増分を混在させず、計算不能な場合は正常値として誤認させないこと |
| データ保存失敗 | 誤った成功通知を出さず、障害原因をログ等で追跡でき、安全な既読データの閲覧を維持できること |
| 認証・管理操作 | 不正アクセスや意図しない変更を防止し、画面やログへ機密情報を出力しないこと |
| 手動更新失敗 | 既存の DB および履歴データを保全し、手動復旧に必要な情報が得られること |
| 対応環境 | Windows 実機で必要な動作を検証できること（Linux は後続対応） |

※ 上記の受け入れ条件を満たし、必要なテスト・検証を通過した時点で初期版の開発完了と判定します。

## 7. 将来要件と初期版の対象外事項

### 将来要件（手動関連付け）
同一 Hub における端末リプレイス時、ユーザーが旧端末と新端末を指定して過去データの参照先を手動で付け替える機能は将来要件とします（初期版では未実装）。この場合も過去の利用額・消費率・推定値自体は変更せず、遡及再計算は行いません。

### 初期版の対象外事項
以下の項目は初期版のスコープ外とし、先行実装は行いません。

- 履歴データの手動・自動削除機能
- 複数ユーザー対応およびロールベースアクセス制御
- 無停止運用および完全自動フェイルオーバー
- 分散アーキテクチャ、マルチプロセス、外部 RDBMS 抽象化
- 過去データの遡及再計算基盤・イベントソーシング
- 自動バックアップおよび自動ロールバック機能
