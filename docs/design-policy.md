# Token Monitor Analytics — 設計・実装ガードレール

## 1. 設計目標と前提

本プロジェクトでは、必要な機能・品質・安全性を十分に満たしたうえで、システムの理解、コードの変更、動作検証、および運用にかかる全体の負担を抑えることを基本方針とする。過度な品質の追求や、コード行数・ファイル数・依存関係の削減そのものを目的化してはならない。

本システムは、上流の Token Monitor Hub から利用実績と利用枠を取得し、実測した API 換算額と消費率の増分に基づいて、定額制サブスクリプションにおけるドル建ての利用許容量を推定・記録し続けるセルフホスト型ダッシュボードである。なお、算出した推定値はあくまで参考値であり、公式の利用上限や保証値として扱ってはならない。

| 観点 | 合意済みの前提条件 |
| --- | --- |
| 利用者・運用 | 当初は利用者1名のみを想定する。障害対応やアップデート失敗時における手動での復旧作業を許容する。 |
| 基本構成 | Windows および Linux 上で動作する Node.js の単一常駐アプリケーションとする。履歴データの正本はローカルの単一 SQLite データベースで管理する。実行環境は Node.js 24 LTS を基準とする。 |
| 外部依存・インフラ | 本システム（Analytics）の運用にあたり、外部データベース、Docker、追加のクラウドインフラを必須としない（上流の Hub は別途稼働している前提とする）。 |
| 入力・機能要件 | Hub からの SSE 受信および自動再接続、GET リクエストによる端末別利用実績の補完、データの保存・推定、Web UI での閲覧およびブラウザ向け SSE 配信、Web 画面からの Hub 登録・停止、ユーザー操作によるシステム更新。なお、端末から直接トークンを収集することはない。 |
| 接続形態 | ローカルループバック、LAN、または VPN 経由での接続を想定する。Basic 認証によるアクセス制御を実施し、当面の間は HTTP 通信を許容する。 |
| 履歴データ・復旧 | データは原則として無期限で保存し、算出時点に表示した推定結果をそのまま保持する。過去データの遡及再計算や、バックアップ機能の実装、定期バックアップの運用は求めない。 |
| 開発環境 | 動作確認用として模擬 Hub（Mock Hub）を同梱する。標準機能（ビルトイン機能）のみに限定せず、実行時・ブラウザ側・開発用の各外部依存ライブラリの採用は、その必要性に応じて個別に判断する。 |

利用者が1人であることだけを根拠に、接続先 Hub も1つだけであると決めつけてはならない。Hub の接続数、履歴データの保持量、応答時間などの数値上限や目標値は現時点で未指定であり、根拠なく独自の数値を要件化してはならない。

システムの構造や運用負担に影響を与える仕組みを新たに追加する場合は、事前に以下の4点を明確に示すこと。

1. 解決すべき現在の要件、具体的なリスク、またはすでに承認されている将来要件
2. その仕組みを追加しなかった場合に生じる具体的な問題
3. よりシンプルな構成、局所的な修正、または手動運用では不十分である理由
4. 今すぐ導入すべき理由と、導入を見送った場合に生じる具体的な負担

「ベストプラクティスだから」「堅牢性の向上」「将来のため」といった抽象的な理由だけで設計を追加してはならない。要件上の根拠がない過度な抽象化（一般化）、不要なフォールバック処理、後方互換対応、設定項目の追加は避けること。ただし、日常的な関数分割や局所的な修正・改善に対してまで、上記の説明や事前承認を一律に求めるものではない。

## 3. 必要な品質保証と許容する失敗

### 3.1 障害時の動作継続と通知

本システムの基本方針は、**安全に継続できる機能を可能な限り維持し、履歴データの保全や表示の正確性を担保できない処理のみを適切に停止させること**である。システムの稼働を無理に継続させるために異常を隠蔽したり、処理が失敗しているにもかかわらず正常に完了したかのように通知してはならない。

| 状況 | 求められる振る舞い |
| --- | --- |
| Hub との一時的な切断 | 保存済み履歴の閲覧機能を維持しつつ、自動再接続を試みる。現在未接続である旨を画面上で明確に示す。 |
| 一部の Hub における不正データや非互換 | 不正な入力を正常なデータとして処理せず、影響を受ける処理のみを停止する。正常な Hub との通信や履歴閲覧まで一律に停止させることは避け、影響範囲とその原因を明示する。 |
| 保存の失敗・書き込み整合性が保てない異常 | 保存が成功したかのように装わず、影響を受ける書き込み処理を停止する。安全に参照できる範囲で、履歴の閲覧やステータス表示は可能な限り維持する。 |
| プロセス全体の安全な継続が判断できない異常 | プロセスの完全停止を許容する。Web 画面を提供できない場合は、起動元（コンソール出力）へのエラー出力やログによって原因を追跡できるようにする。 |

画面上では、「正常」「未接続」「保存失敗」「推定不可」の状態を明確に区別して表示する。過去に保存した古い値を表示する際は、現在の正常な観測結果であると誤認されないよう配慮すること。また、原因調査に必要な情報（発生日時、対象 Hub、該当処理、エラー詳細など）を確実にログ等に残すものとし、認証情報や共有シークレットなどの機密情報は決して含めてはならない。

無停止運用や障害からの完全自動復旧、プロセスを無理に延命させる仕組みの実装は求めない。また、正常な機能を維持するためだけに、大掛かりな障害隔離機構を新たに導入することも避ける。

### 3.2 履歴・推定・補完の正確性

データの再受信や履歴の補完処理において、同一の利用実績を二重に計上してはならない。異なる契約や利用枠、あるいはリセット前後の数値を誤って組み合わせて計算しないこと。増分の対応関係や計算の成立条件が確認できない場合は、無理に数値を埋めず「推定不可」として扱う。

システム停止中や再接続時における過去の利用実績は、Hub から取得できた範囲内に限って補完する。観測できていない過去の制限枠や推定値を勝手に生成してはならない。なお、Hub 側に残っていない実績や、取得できなかった観測データの完全な復元までは保証しない。

過去の各時点で算出して表示した推定結果は履歴としてそのまま保持し、将来の推定ロジック変更に伴って過去データを暗黙的に書き換えてはならない。過去データの再計算を目的とした全イベントの保存やイベント再生機構の実装は求めないが、現在の推定処理の継続、二重計上の防止、および不具合調査に必要となる最小限の情報は確実に保持すること。

履歴データは当初、無期限で保持するものとし、自動削除、保存期間の上限設定、集計データへの自動置換といった仕組みは導入しない。将来的な手動削除機能の要否も未確定であるため、先行して実装しないこと。

**「バックアップの仕組みを求めないこと」と「アプリケーションの不備によって履歴が破壊されることを許容すること」は別問題である。** バックアップを取得していない状態でデータが失われた場合、その復元までは保証対象外とする。しかし、保存や更新の処理に失敗したことを理由に、既存のデータベースを独断で初期化したり、過去の履歴を勝手に削除・改変したりすることは固く禁止する。

### 3.3 認証・外部入力・機密情報の保護

保護対象となる Web 画面、API、ブラウザ向け SSE エンドポイントには Basic 認証によるアクセス制御を適用し、フロントエンド側の制御のみに依存しないようにする。また、認証情報や Hub の共有シークレットは、ログや不要な HTTP レスポンスに出力してはならない。

当面 HTTP 通信を許容する方針は、通信の暗号化を必須要件としないという判断に過ぎず、Basic 認証によって通信経路まで保護されるわけではない。TLS や VPN などの保護がない通信経路では、認証情報や通信内容の秘匿性は保証されない。ドキュメントや説明においても、「アクセス制御」と「通信の暗号化」を明確に区別して記載すること。[1]

Hub からの入力データや管理操作など、システムの信頼境界（外部との接点）において必要なバリデーションを確実に実施する。ただし、同一の検証を信頼境界の内側（内部モジュール間など）で目的もなく重複して行う必要はない。また、Hub の設定変更やシステム更新といった重要な操作には、外部サイトから意図しないリクエストを実行させられる事態（CSRF 等）を防ぐ保護対策を講じること。これは、HTTP 通信を許容していることとは別の安全要件である。[2]

複数ユーザー間での権限管理やユーザーごとのデータ分離は、初期フェーズのスコープ外とする。将来的に公開範囲や利用者を拡大する場合には、影響を受けるセキュリティ要件を改めて検討する。

### 3.4 同時実行・性能・対応環境

Hub からのデータ受信、過去実績の補完、ユーザーによる管理操作などの処理が同時に発生した場合でも、データの保存および推定計算の整合性を維持すること。単一プロセスで稼働する構成だからといって、実際に並行して実行されうる処理の排他制御や整合性検証を怠ってはならない。一方で、将来のマルチプロセス化や分散配置を前提とした複雑な制御基盤を先行して実装する必要はない。

パフォーマンス改善やリソース消費の最適化は、実際の利用環境で発生した具体的な問題に基づいて対処する。履歴データの蓄積によって性能上の支障が出た場合は、ボトルネックとなっている処理を特定・計測し、まずは局所的な改善から検討すること。「無期限保存」の方針を理由に、無制限のストレージ容量や特定の応答時間を常に保証するものではない。

対応プラットフォームは Windows および Linux とし、動作に影響を及ぼす可能性のある OS 間の差異を検証する。明示されていない過去バージョンの Node.js や旧バージョンの Hub、他の OS に対する互換性対応を勝手に追加しないこと。現在のサポート対象範囲を変更する必要が生じた場合は、事前に相談を行うこと。

## 4. アップデートと手動復旧

システムのアップデートは、ユーザーによる明示的な操作に基づいて実行する。バックグラウンドでの無人自動適用、自動ロールバック、無停止アップデートといった高度な仕組みは求めない。

アップデートが失敗した場合は手動での復旧を基本とし、その間システムが停止することも許容する。正常に完了していない更新を成功と誤認させる表示を行わず、どの処理がどのような原因で失敗したのかを追跡できるログやエラー情報を残すこと。アップデート実行前の自動バックアップや、「いかなる場合も必ず以前の状態に復元できること」を一律の必須条件とはしない。

ただし、アップデート処理の都合でデータベースを無断で初期化したり、過去の履歴を削除したり、保存済みの推定結果を書き換えたりすることは固く禁止する。**既存の履歴データが消失するリスクがある変更や、以前のバージョンでデータを読み込めなくなるような破壊的変更を行う場合は、事前にその影響範囲と手動復旧における制約を説明し、ユーザーの明確な承認を得ること。**「手動復旧を基本とする」という方針は、失われたデータを後から復元できることを意味するものではない。

## 5. テスト・レビュー・完了条件

テストは、受け入れ条件の達成、重要な境界値の検証、想定される具体的な失敗ケースの確認、および不具合の再発防止を目的として実施する。テストコードの行数やカバレッジ率の数値そのものを目的化しないこと。変更の影響範囲に応じて、以下の観点を優先して検証する。

| 確認対象 | 主な確認内容 |
| --- | --- |
| 通常の収集・推定・保存・閲覧 | 対象の契約および利用枠に対応する実測値から正しく推定を行い、算出時点の結果を確実に保存・表示できること。 |
| 再接続・利用実績の補完 | データの再受信や過去履歴の補完において二重計上を行わず、未観測の利用枠や推定値を勝手に生成しないこと。 |
| リセット・欠測・不正入力 | 対応関係のない増分データを混在させず、計算が成り立たない推定結果を正常な数値として表示しないこと。 |
| 保存失敗・障害時の表示 | 保存失敗時に誤って成功通知を行わず、原因を追跡できること。また、安全に稼働できる機能は可能な限り継続させること。 |
| 認証・管理操作 | 保護対象リソースへの不正アクセスや、意図しない設定変更・アップデートを防止し、機密情報を不要に出力しないこと。 |
| アップデート失敗 | 独断で履歴データを破壊せず、失敗の事実を明示して、手動対応に必要な情報を記録・提示すること。 |
| OS 間の差異 | Windows と Linux で挙動が異なる可能性のある変更については、影響を受ける双方の環境で動作を確認すること。 |

モック（模擬）Hub を用いた検証と、本物の Hub 実機との接続確認は明確に区別し、モック Hub での確認のみをもって「実 Hub との互換性が確認できた」とみなしてはならない。未実施の検証項目がある場合は、その事実と影響範囲を明確に報告すること。

コードレビューや設計レビューにおける指摘は、「必須修正」「任意改善」「対象外」の3つに明確に分類する。合意事項に反するデータの破損、処理失敗時の誤った成功通知、機密情報の漏洩、必要な検証や手動復旧に不可欠な情報の欠落などは、「必須修正」として対応する。一方で、すでにリスク受容として合意されている事項（HTTP 通信の許容、自動バックアップの未実装、手動復旧方針など）を、単体で問題視して修正を求めるような再提案は行わない。前提条件に変化が生じた場合や、新たな重大リスクが判明した場合に限り、具体的な根拠を示して再検討を提案すること。

**受け入れ条件を満たし、必要な検証を通過し、残存する必須修正がなくなった時点でタスク完了とみなす。** 独断によるさらなる構造改善や追加のアイデア提案を理由に、実装作業を漫然と引き延ばしてはならない。また、必要な検証が未実施のまま残っている場合は、完了条件を満たしたとはみなさない。

## 6. 事前相談と将来要件

事前相談が必要な事項は、合意済みの前提や方針を超えて、システムの保証範囲、基本構造、または運用負担を変更する場合に限定する。具体的には、履歴データの消失や過去バージョンとのデータ非互換を伴う変更、公開範囲・対象ユーザー・認証方式の変更、単一プロセス構成やローカル完結の保存から逸脱する構成、追加の常駐サービスや運用インフラの必須化、サポート対象環境の変更などが該当する。

本方針の範囲内に収まる日常的な実装判断については、開発者の裁量で進めて構わない。外部ライブラリの追加に関しても、一律にユーザーの事前承認を待つのではなく、その必要性と全体の保守負担を総合的に判断したうえで採用し、上記の方針境界を超える場合にのみ相談すること。

手動による履歴削除機能は、将来的な検討事項にとどめる。また、複数ユーザーの権限管理、無停止運用、分散処理、マルチデータベース対応の抽象化レイヤー、過去データの再計算基盤、自動バックアップ、自動ロールバックなどは、いずれも初期リリースの実装対象外とする。「将来必要になるかもしれない」という理由だけで先行実装することは避け、将来要件が具体化した際に拡張しやすい設計（後付け可能な境界の整理）を意識しつつ、現時点で真に必要な仕様のみを実装すること。
