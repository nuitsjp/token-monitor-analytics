# 設計方針

Token Monitor Analytics は、複数の Token Monitor Hub が提供する利用実績と利用枠を閲覧し、実測増分から定額制サービスの利用許容量を米ドル換算の参考値として推定・保存する、セルフホスト型ダッシュボードである。

本書を目標・機能範囲・制約・品質要求の正本とする。識別、計算、保存、状態、実行時動作は [アーキテクチャ設計書](architecture.md)、用語は [CONTEXT.md](../CONTEXT.md)、未決事項と未検証事項は [TODO.md](../TODO.md) に置く。

## 1. 目標と機能範囲

システムの理解、変更、検証、運用の全体負担を最小化する。形式的な品質、部品数、コード量、依存関係の削減を自己目的にしない。

| 機能 | 初期版で実現すること |
| --- | --- |
| 現在値の閲覧 | プロバイダーやプランを限定せず、取得した利用枠、消費率、API 換算額を、取得状態と更新時刻とともに表示する。 |
| 利用許容量の推定 | 同一の契約・利用枠・対象期間に属する利用額と消費率の実測増分から算出し、算出時点の結果と根拠を保存する。 |
| 過去実績の閲覧と比較 | Hub の保持範囲から日次・月次実績を定期収集・補完し、推移を保存・表示する。 |
| 複数 Hub 管理 | 並行接続と状態監視、Web 画面での登録・一覧表示、Hub 個別の収集停止・再開を提供する。 |
| 手動更新と復旧 | 利用者の明示操作で更新し、失敗時に原因と手動復旧に必要な情報を提示する。 |

端末からの直接収集は行わない。推定が成立しない場合も、取得できた実績と利用枠を表示する。契約に帰属できない利用額は、Hub・端末・ツール等の実際の集計単位を明示する。

## 2. 制約と受容するリスク

| 観点 | 決定済みの制約 |
| --- | --- |
| 利用者 | 1 名。複数ユーザー管理と権限管理は不要。 |
| 実行と保存 | Node.js 24 LTS の単一常駐プロセスと組込 SQLite。外部 DB、Docker、追加の常駐サービスを必須にしない。 |
| 対応環境 | Windows を先行し、最初の完了判定は Windows のみとする。Linux の対応・OS 間の差異の検証は後続で行う。 |
| 接続範囲 | LAN、VPN、ローカル環境。Web のアクセス制御は Basic 認証とする。 |
| 通信 | 当面は HTTP を許容する。アクセス制御と通信の暗号化を区別し、HTTP での機密性は保証しない。 |
| 履歴 | 原則無期限に保存する。日次・月次実績は再取得値で更新する。保存済み推定結果の遡及再計算や改変はしない。 |
| 障害と更新 | 手動復旧と作業中の停止を許容する。自動バックアップ、自動更新、自動ロールバックは行わない。 |
| 規模と性能 | 数値目標は未指定。根拠のない独自上限や早期最適化を導入しない。 |
| 開発 | 動作確認用の Mock Hub を同梱する。Mock Hub だけで実機互換性を保証しない。 |

同一ログを複数端末へコピー・共有して多重報告する構成はサポート対象外とする。同じアカウントを複数端末で独立に利用する構成は対象に含む。

## 3. 品質要求

### 3.1 識別と履歴の正確性

- Hub・端末・契約・利用枠・対象期間を混同しない。同じ情報の再受信や補完を追加の利用実績として計上しない。
- 現在値観測と過去実績を分離する。推定には SSE の現在値のみを使い、履歴 GET で現在値や過去の推定値を生成しない。
- 推定の対応関係が成立しない値は「推定不可」とし、比率配分、ゼロ埋め、別の情報による代用で成立したことにしない。
- 端末 ID が変わった場合は別端末とし、自動で名寄せしない。
- 日次履歴は端末の現地日付と数値を保持する。タイムゾーン変換や按分はせず、当日分は端末側の日付基準で除外する。
- 未観測の利用枠や推定値を独自に補わない。Hub から再取得できなくなった保存済み履歴も保持する。

計算式、比較区間、日次・月次の更新規則は [識別・推定・保存の設計](architecture.md#crosscutting) に定める。

### 3.2 障害の分離と状態の明示

安全に継続できる機能を維持し、データの保全や表示の正確性を担保できない処理を停止する。失敗を正常終了として扱わない。

| 状況 | 必要な振る舞い |
| --- | --- |
| Hub の接続失敗・切断 | 自動再接続を続け、他 Hub の通信と履歴閲覧を維持する。「未接続」を表示する。 |
| Hub 個別の収集停止 | 明示的な再開まで当該 Hub の全収集通信を停止する。他 Hub の収集と保存済みデータの閲覧は維持する。 |
| 不正な受信データ | 影響を受ける処理を止め、原因と影響を表示する。他 Hub と安全に継続できる処理を維持する。 |
| 保存失敗・整合性異常 | 整合性を担保できない書き込みを止め、「保存失敗」を表示する。参照可能な保存値の閲覧を維持する。 |
| 復旧困難な異常 | プロセス停止を許容する。原因をログ等で追跡できるようにする。 |

接続、収集設定、保存、推定可否は対象の異なる状態として管理し、画面では各対象の「正常」「未接続」「収集停止」「保存失敗」「推定不可」を区別する。異なる対象の状態が同時に成立する場合、その関係を表示で隠さない。過去の保存値を現在取得した値と誤認させない。

### 3.3 認証と信頼境界

- Web 画面、静的ファイル、API、ブラウザ向け SSE に Basic 認証を適用する。
- Hub 受信データと管理操作などの信頼境界で入力を検証する。外部由来の表示文字列を HTML として解釈しない。
- Hub 管理とシステム更新などの重要操作に CSRF 対策を適用する。
- 認証情報と Hub の共有シークレットをログやレスポンスへ出さない。ログには発生日時、対象 Hub、処理内容、エラー詳細を残す。

根拠: [RFC 7617](https://www.rfc-editor.org/rfc/rfc7617.html)、[OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)。

### 3.4 並行処理と性能

複数 Hub の受信、実績補完、管理操作が重複しても、保存と推定の整合性を維持する。通信待ちが他の収集を止めないようにする。性能上の問題には実環境での計測を根拠に局所的に対処する。

## 4. 設計を追加する判断基準

ライブラリ導入、モジュール分割、階層化等は、品質を維持しながら開発・運用の負担を軽減できる場合に採用する。システムの構造や運用に影響する仕組みを加えるときは、次の4点を説明する。

1. 解決すべき現在の要件、具体的なリスク、または合意済みの将来要件。
2. 追加しなかった場合に生じる具体的な問題。
3. より単純な構成、局所的な修正、手動運用では不十分な理由。
4. 今すぐ必要な理由と、見送った場合の具体的な負担。

漠然とした将来への備えやベストプラクティスだけを理由とする抽象化、フォールバック、後方互換対応は追加しない。記録方法と初期設計の完了基準は [文書方針](document-policy.md) に従う。

## 5. データ保全と変更の境界

更新やロジック変更に伴う DB 初期化、履歴改変、推定結果の遡及再計算を行わない。更新失敗時は事実と原因を記録し、手動復旧を基本とする。

次の変更は着手前に影響範囲を説明し、利用者へ相談する。既存データの消失リスクや互換性を損なう変更は明示的な承認を得る。

- 履歴データの消失やデータ非互換を伴う変更。
- 公開範囲、対象ユーザー、認証方式の変更。
- 単一プロセス、ローカル保存の原則から外れる構成。
- 追加の常駐サービスや運用インフラの必須化。
- サポート対象環境の変更。

## 6. 検証と製品の完了条件

テストは受け入れ条件、重要な境界値、具体的な失敗、再発防止を確認するために行う。

| 確認対象 | 受け入れ条件 |
| --- | --- |
| 通常収集・推定・表示 | 複数 Hub の対応する実測値から推定し、結果を保存・表示できる。 |
| 再受信・再接続・補完 | 二重計上、未観測値の独自生成、他 Hub のデータへの影響がない。 |
| リセット・欠測・不正入力 | 対応しない増分を混ぜず、計算不能な結果を正常値として表示しない。 |
| 保存失敗 | 成功通知を出さず、原因を追跡でき、安全に参照できる保存値を維持する。 |
| 認証・管理操作 | 不正アクセスと意図しない変更を防ぎ、機密情報を出力しない。 |
| 手動更新失敗 | DB・履歴を保全し、失敗の原因と手動復旧の情報を得られる。 |
| 対応環境 | Windows で必要な動作を確認する。Linux 対応時は OS 間の差異を検証する。 |

指摘は「必須修正」「任意改善」「対象外」に分類する。データ破損、失敗の隠蔽、機密情報漏洩、復旧情報の欠落は必須修正とする。HTTP 許容や自動バックアップ見送りなど、受容済みの条件を再審議しない。

受け入れ条件を満たし、必要な検証を通過し、必須修正が解消した時点で製品の初期版を完了とする。文書の完成と製品の完成を区別し、未実施の検証は事実と影響を明記する。

## 7. 将来要件と初期対象外

将来、同一 Hub の旧端末と新端末を利用者が指定し、過去データの `deviceId` を新端末へ書き換えて手動で関連付ける。変更は端末への帰属参照に限定し、利用額、消費率、推定値、算出時点を変更せず、遡及再計算もしない。初期版では実装しない。

以下は初期対象外であり、先行実装しない。

- 手動・自動の履歴削除。
- 複数ユーザー対応・権限管理。
- 無停止運用・完全自動復旧。
- 分散処理、マルチプロセス、マルチ DB 抽象化。
- 過去データの遡及再計算・イベント再生基盤。
- 自動バックアップ・自動ロールバック。
