# Token Monitor Analytics — 設計・実装ガードレール

## 1. 設計目標と前提

必要な機能・品質・安全性を満たしたうえで、理解・変更・検証・運用の総負担を小さくする。品質の最大化、コード行数・ファイル数・依存数の最小化を目的にしない。

本システムは、上流の Token Monitor Hub から利用実績と利用枠を受け取り、実測した API 換算額と消費率の増分から、定額サブスクリプションのドル建て利用許容量を推定・継続記録するセルフホスト型ダッシュボードである。推定値を公式の利用上限や保証値として扱わない。

| 観点 | 承認済みの前提 |
| --- | --- |
| 利用者・運用 | 当初は利用者本人一人。障害対応や更新失敗時の手動復旧を許容する。 |
| 基本構成 | Windows / Linux 上の Node.js 単一常駐アプリ。履歴の正本はローカル SQLite データベース一つ。実行環境の基準は提供概要の Node.js 24 LTS。 |
| 運用依存 | Analytics の運用に外部 DB、Docker、追加のクラウド基盤を必須化しない。上流 Hub は別途稼働している前提。 |
| 入力・機能 | Hub の SSE 受信・自動再接続、GET による端末別利用実績の補完、保存・推定、Web 閲覧・SSE 配信、Web からの Hub 登録・停止、利用者操作によるシステム更新。端末から直接トークンを収集しない。 |
| 接続 | loopback、LAN、VPN 経由。Basic 認証によるアクセス制御を行い、当面は HTTP を許容する。 |
| 履歴・復旧 | 当初は無期限保存。当時表示した推定結果を保存する。過去データの再計算、バックアップ機能、定期バックアップ運用は要求しない。 |
| 開発 | 提供概要では模擬 Hub を同梱する。組込み機能だけに限定せず、実行時・ブラウザー側・開発用の依存を必要性で判断する。 |

利用者が一人であることから、Hub 数も一つと推測してはならない。Hub 数・履歴量・応答時間などの数値上限や目標は未指定であり、任意の数値を要件化しない。

## 2. 構成と設計追加の判断

依存ライブラリ、関数分割、レイヤー、インターフェースは、必要な保証を満たし、総負担が小さくなる場合に採用できる。一律の依存禁止・レイヤー数制限・インターフェース禁止は設けない。既存の構成を整えることだけを目的に全面改修しない。

構造や運用負担を変える仕組みの追加には、次の四点を短く示す。

1. 対応する現在の要求、具体的なリスク、または承認済みの将来要件。
2. 追加しない場合に起きる具体的な問題。
3. より単純な構成・局所的な対処・手動運用では不足する理由。
4. 今必要な理由と、延期した場合の具体的な負担。

「ベストプラクティス」「堅牢性」「将来のため」だけでは採用理由にしない。要求に根拠のない一般化、フォールバック、互換対応、設定項目を追加しない。通常の関数分割や局所修正に、上記の説明や事前承認を一律に要求しない。

## 3. 必要な保証と許容する失敗

### 3.1 障害時の継続・通知

中心方針は、**安全に継続できる機能を残し、履歴の保全や表示の正しさを守れない処理だけを止めること**である。継続のために異常を隠したり、誤った成功を通知したりしない。

| 状況 | 必要な振る舞い |
| --- | --- |
| Hub の一時的な切断 | 保存済み履歴の閲覧を継続し、自動再接続を行う。未接続であることを画面で示す。 |
| 一部 Hub の不正データ・非互換 | 不正な入力を正常な観測として扱わず、影響する処理を止める。正常な Hub や閲覧まで一律に止めず、影響範囲と原因を示す。 |
| 保存失敗・書込みの整合性を守れない異常 | 保存成功として扱わず、影響する書込みを止める。安全に読める履歴の閲覧と状態表示は可能な範囲で残す。 |
| プロセス全体の安全な継続を判断できない異常 | 全体停止を許容する。画面を提供できない場合は、起動元へのエラー出力やログで原因を追えるようにする。 |

画面では、正常、未接続、保存失敗、推定不可を区別する。保存済みの古い値を表示する場合は、現在の正常な観測と誤認させない。原因調査に必要な発生時刻、対象 Hub、処理、エラーなどを残し、認証情報や共有シークレットを含めない。

無停止運用、障害の完全自動復旧、プロセスを無理に生存させるための仕組みは要求しない。正常な機能を残すためだけに、大掛かりな障害隔離基盤を追加しない。

### 3.2 履歴・推定・補完の正しさ

再受信や履歴補完で同じ利用実績を二重計上しない。異なる契約・利用枠・リセット前後の値を誤って組み合わせない。増分の対応関係や計算の成立条件を確認できない場合は、数値を埋めず推定不可とする。

停止中や再接続時の利用実績は、Hub から取得できた範囲だけ補完する。観測していない過去の制限枠や推定値は生成しない。Hub に残っていない実績や、取得できなかった観測の完全な復元は保証しない。

当時表示した推定結果を履歴として保持し、推定方法の修正に伴って暗黙に書き換えない。過去の再計算のための全イベント保存・再実行基盤は要求しない。ただし、現在の推定処理の継続、二重計上の防止、必要な不具合調査に使う最小限の情報は保持する。

履歴は当初無期限で保存し、自動削除・保存期限・集計結果への自動置換を追加しない。将来の手動削除機能は未確定であり、先行実装しない。

**バックアップ不要と、アプリによる履歴の破壊を許容することは別である。** バックアップのない履歴が失われた場合、その復元は保証対象外とする。一方、保存・更新の失敗を理由に既存 DB を無断で初期化したり、履歴を削除・改変したりしてはならない。

### 3.3 認証・外部入力・秘密情報

Basic 認証によるアクセス制御を保護対象の画面・API・ブラウザー SSE に適用し、画面側の制御だけに依存しない。認証情報と Hub の共有シークレットは、ログや不要な応答に出さない。

HTTP の許容は通信暗号化を要求しないという判断であり、Basic 認証で通信まで保護されるという意味ではない。TLS や VPN など別の保護がない経路では、認証情報や通信内容の秘匿を保証しない。説明文でもアクセス制御と通信暗号化を区別する。[1]

Hub 入力や管理操作など、信頼境界で必要な検証は行う。同じ検証を境界の内側で無目的に重複させない。Hub 設定変更やシステム更新には、別サイトから利用者の意図しない操作を誘発されることを防ぐ保護を設ける。これは HTTP の許容とは別の条件である。[2]

複数利用者の権限分離や利用者別データ分離は当初の対象外とする。公開範囲や利用者を拡大する場合は、影響する保護条件を再検討する。

### 3.4 同時実行・性能・対応環境

通常の Hub 受信・補完・管理操作が重なっても、保存と推定の整合性を守る。単一プロセス構成を理由に、実際に重なる処理の検証を省かない。一方、複数プロセス・分散構成を前提とした制御基盤は先行実装しない。

性能や資源消費の対策は、実際の利用条件と問題に対応させる。履歴の増加で支障が出た場合は、その処理を確認・計測し、局所的な改善を先に検討する。無期限保存を理由に、無制限の容量や一定の応答時間を保証しない。

Windows / Linux を対象とし、影響する OS 差を検証する。未指定の旧 Node.js、旧 Hub、他 OS との互換対応は自動的に追加しない。既存の対応範囲を変更する場合は事前相談の対象とする。

## 4. 更新と手動復旧

更新適用は利用者の明示的な操作で行う。無人の自動適用、自動ロールバック、無停止更新は要求しない。

更新失敗時は手動復旧を基本とし、停止を許容する。成功していない更新を成功と表示せず、失敗した処理と原因を確認できる情報を残す。更新前バックアップや「必ず旧状態へ戻せること」を一律の実行条件にしない。

それでも、更新処理による無断の DB 初期化・履歴削除・保存済み推定結果の書換えは禁止する。**既存履歴の消失を伴う変更、または旧版で既存データを扱えなくなる変更は、実施前に影響と手動復旧の制約を説明し、利用者に確認する。** 手動復旧という方針から、失われたデータを復元できると推測してはならない。

## 5. テスト・レビュー・完了条件

テストは受け入れ条件、重要な境界条件、具体的な失敗、不具合の再発防止に対応させる。本数や網羅率の数値自体を目標にしない。変更の影響範囲に応じ、次を優先して確認する。

| 確認対象 | 主な確認内容 |
| --- | --- |
| 通常の収集・推定・保存・閲覧 | 対象契約と利用枠に対応する実測値から推定し、当時の結果を保存・表示できる。 |
| 再接続・利用実績補完 | 再受信や補完で二重計上せず、観測していない制限枠・推定値を生成しない。 |
| リセット・欠測・不正入力 | 対応しない増分を混ぜず、成立しない推定を数値として表示しない。 |
| 保存失敗・障害表示 | 誤った成功通知をせず、原因を追える。安全な機能を可能な範囲で継続する。 |
| 認証・管理操作 | 保護対象への未認証アクセスと意図しない設定変更・更新を防ぎ、秘密情報を不要に出力しない。 |
| 更新失敗 | 無断で履歴を破壊せず、失敗を明示し、手動対応に必要な情報を残す。 |
| OS 差 | Windows / Linux で挙動が変わる変更は、影響する環境で確認する。 |

模擬 Hub を用いた検証と実 Hub との接続確認を区別し、模擬 Hub だけの確認を実 Hub との互換確認済みと扱わない。未実施の検証と、その影響を明示する。

レビューは「必須修正」「任意改善」「対象外」に分ける。合意した保証に反するデータ破損、誤った成功通知、情報漏洩、必要な検証・復旧情報の欠落は必須修正として扱う。受容済みの HTTP 利用、バックアップなし、手動復旧などを、それ自体で欠陥として再提案しない。前提の変化や新たな重大リスクがある場合だけ、根拠を示して再検討を求める。

**受け入れ条件を満たし、必要な検証に合格し、必須修正が残っていなければ完了とする。** 任意の構造改善や改善案の追加を理由に実装を継続しない。必要な検証が未実施の場合は、完了条件を満たしたと扱わない。

## 6. 事前相談と将来要件

事前相談は、合意した範囲を越えて保証・構造・運用負担を変える変更に絞る。対象は、履歴消失や旧版とのデータ非互換、公開範囲・利用者・認証方式の変更、単一プロセスやローカル保存を外れる構成、追加の常駐サービスや運用基盤の必須化、対応環境の変更などである。

本方針内で完結する通常の実装判断は進めてよい。依存の追加も、一律に利用者承認を待つのではなく、必要性と総負担で判断し、上記の境界を越える場合に相談する。

手動の履歴削除は将来の可能性にとどまる。複数利用者管理、無停止運用、分散処理、汎用 DB 切替基盤、履歴再計算基盤、バックアップ、自動ロールバックは当初の実装対象に含めない。将来の必要性だけで先行実装せず、要求が確定した場合にも後付け可能性を考慮し、今必要な境界だけを検討する。
