# Token Monitor Analytics — 設計・実装ガードレール

## 1. 設計目標と前提

本プロジェクトでは、必要な機能・品質・安全性を十分に満たしたうえで、システムの理解、コードの変更、動作検証、および運用の全体にかかる負担を抑えることを基本方針とする。過度な品質の追求や、コード行数・ファイル数・依存ライブラリの削減自体を自己目的化してはならない。

本システムは、上流の Token Monitor Hub から利用実績と利用枠を取得し、実測した「API 換算額」と「消費率」の増分に基づいて、定額制サブスクリプションにおけるドル建ての利用許容量を推定・記録するセルフホスト型ダッシュボードである。なお、算出した推定値はあくまで参考値であり、公式の利用上限や保証値として扱ってはならない。

| 観点 | 合意済みの前提条件 |
| --- | --- |
| 利用者・運用 | 当初は利用者 1 名のみを想定する。障害対応やアップデート失敗時における手動での復旧作業を許容する。 |
| 基本構成 | Windows および Linux 上で動作する Node.js の単一常駐アプリケーションとする。履歴データの正本はローカルの単一 SQLite データベースで管理する。実行環境は Node.js 24 LTS を基準とする。 |
| 外部依存・インフラ | 本システム（Analytics）の運用にあたり、外部データベース、Docker、追加のクラウドインフラは必須としない（上流の Hub は別途稼働している前提とする）。 |
| 入力・機能要件 | Hub からの SSE 受信と自動再接続、GET リクエストによる端末別利用実績の補完、データの保存・推定、Web UI での閲覧およびブラウザ向け SSE 配信、Web 画面からの Hub 登録・停止、ユーザー操作によるシステム更新。なお、端末から直接トークン利用量を収集する機能は含まない。 |
| 接続形態 | ローカルループバック、LAN、または VPN 経由での接続を想定する。Basic 認証によるアクセス制御を実施し、当面は HTTP 通信を許容する。 |
| 履歴データ・復旧 | データは原則として無期限で保存し、算出時点で表示した推定結果をそのまま保持する。過去データの遡及再計算や、バックアップ機能の実装、定期バックアップの運用は求めない。 |
| 開発環境 | 動作確認用として模擬 Hub（Mock Hub）を同梱する。標準機能（組み込み機能）のみに限定せず、実行時・ブラウザ側・開発用の各外部依存ライブラリの採用は、必要性に応じて個別に判断する。 |

利用者が 1 名であることだけを理由に、接続先 Hub も 1 つだけと独断で限定してはならない。Hub の接続数、履歴データの保持量、応答時間などの具体的な上限値や目標値は現時点で未指定であり、根拠なく独自の数値を要件化してはならない。

## 2. アーキテクチャと設計追加の判断基準

外部ライブラリの導入、関数の分割、階層構造（アーキテクチャレイヤー）やインターフェースの導入は、必要な品質を満たしつつ、全体の開発・運用負担を軽減できる場合に限って採用する。「依存ライブラリの一律禁止」「レイヤー数の制限」「インターフェースの全面禁止」といった極端な制約は設けない。また、単に既存コードの見た目を整えることだけを目的とした全面的なリファクタリングは行わない。

システムの構造や運用負担に影響を与える仕組みを新たに追加する場合は、事前に以下の 4 点を明確に示す必要がある。

1. 解決すべき現在の要件、具体的なリスク、または合意済みの将来要件
2. その仕組みを追加しなかった場合に生じる具体的な問題
3. よりシンプルな構成、局所的な修正、または手動運用では不十分である理由
4. 今すぐ導入すべき理由と、導入を見送った場合に生じる具体的な負担

「ベストプラクティスだから」「堅牢性の向上」「将来のため」といった抽象的な理由だけで設計を追加してはならない。要件上の根拠がない過度な抽象化（汎用化）、不要なフォールバック処理、後方互換対応、安易な設定項目の追加は避けること。ただし、日常的な関数の分割や局所的な修正・改善に対してまで、上記の説明や事前承認を一律に求めるものではない。

## 3. 必要な品質保証と許容する失敗

### 3.1 障害時の動作継続と通知

本システムの基本方針は、**安全に継続できる機能を可能な限り維持し、履歴データの保全や表示の正確性を担保できない処理のみを適切に停止させること**である。システムの稼働を無理に継続させるために異常を隠蔽したり、処理が失敗しているにもかかわらず正常終了したかのように装ってはならない。

| 状況 | 求められる振る舞い |
| --- | --- |
| Hub との一時的な切断 | 保存済み履歴の閲覧機能を維持しつつ、自動再接続を試みる。画面上でも現在未接続である旨を明確に示す。 |
| 一部の Hub における不正データや非互換 | 不正な入力を正常データとして処理せず、影響を受ける処理のみを停止する。正常な Hub との通信や履歴閲覧まで停止させることは避け、影響範囲とその原因を明示する。 |
| 保存の失敗・書き込み整合性が保てない異常 | 失敗を隠蔽せず、整合性を担保できない書き込み処理を停止する。安全に参照できる範囲で、履歴の閲覧やステータス表示は可能な限り維持する。 |
| プロセス全体の安全な継続が判断できない異常 | プロセスの完全停止を許容する。Web 画面を提供できない場合は、起動元（コンソール出力）へのエラー出力やログによって原因を追跡できるようにする。 |

画面上では、「正常」「未接続」「保存失敗」「推定不可」の各状態を明確に区別して表示する。過去に保存した古い値を表示する際は、現在の観測結果であると誤認されないよう配慮すること。また、原因調査に必要な情報（発生日時、対象 Hub、該当処理、エラー詳細など）を確実にログ等へ記録する。ただし、認証情報や共有シークレットなどの機密情報は決して記録してはならない。

無停止運用や完全自動復旧、プロセスを無理に延命させる仕組みの実装は求めない。また、一部の正常な機能を維持するためだけに、大掛かりな障害隔離機構を新たに導入することも避けること。

### 3.2 履歴・推定・補完の正確性

データの再受信時や履歴の補完処理において、同一の利用実績を二重計上してはならない。異なる契約や利用枠、あるいはリセット前後の数値を誤って組み合わせて計算しないよう注意すること。増分の対応関係や計算の成立条件が確認できない場合は、無理に値を補完せず「推定不可」として扱う。

システム停止中や再接続時における過去の利用実績は、Hub から取得できた範囲内に限って補完する。観測できていない過去の利用枠や推定値を推測で独自に生成してはならない。なお、Hub 側に残っていない実績や、取得できなかった観測データの完全な復元までは保証しない。

過去の各時点で算出して表示した推定結果は履歴としてそのまま保持し、将来の推定ロジック変更に伴って過去データを暗黙的に書き換えてはならない。過去データの再計算を目的とした全イベントの保存やイベント再生機構の実装は求めないが、推定処理の継続、二重計上の防止、および不具合調査に必要となる最小限の情報は確実に保持すること。

履歴データは当初、無期限で保持するものとし、自動削除、保存期間の上限設定、集計データへの自動置換といった仕組みは導入しない。手動削除機能についても、将来的な要否が未確定であるため先行実装は行わない。

**「バックアップの仕組みを求めないこと」と「アプリケーションの不具合によるデータ破損を許容すること」は全く別の問題である。** バックアップが存在しない状態でデータが失われた場合、その復元までは保証しない。しかし、保存や更新の処理に失敗したことを理由に、既存のデータベースを独断で初期化したり、過去の履歴を勝手に削除・改変したりすることは固く禁止する。

### 3.3 認証・外部入力・機密情報の保護

保護対象となる Web 画面、API、ブラウザ向け SSE エンドポイントには Basic 認証によるアクセス制御を適用し、フロントエンド側の制御だけに依存しない構成とする。また、認証情報や Hub の共有シークレットをログや不要な HTTP レスポンスに出力してはならない。

当面 HTTP 通信を許容する方針は「通信の暗号化を必須要件としない」という判断に過ぎず、Basic 認証によって通信経路まで保護されるわけではない。TLS や VPN などの保護がない通信経路では、認証情報や通信内容の機密性は保証されない。ドキュメントや説明においても、「アクセス制御」と「通信経路の暗号化」を明確に区別して記載すること。[1]

Hub からの受信データや管理操作など、システムの信頼境界（外部との接点）において必要なバリデーションを確実に実施する。ただし、同一の検証を信頼境界の内側（内部モジュール間など）で無意味に重複して行う必要はない。また、Hub の設定変更やシステム更新といった重要な操作には、外部サイトを経由した意図しないリクエストの実行（CSRF 等）を防止する保護対策を講じること。これは、HTTP 通信を許容していることとは別の安全要件である。[2]

複数ユーザー間での権限管理やユーザーごとのデータ分離は、初期フェーズの対象外とする。将来的に公開範囲や利用者を拡大する場合は、影響を受けるセキュリティ要件を改めて検討する。

### 3.4 同時実行・性能・対応環境

Hub からのデータ受信、過去実績の補完、ユーザーによる管理操作が同時に発生した場合でも、データ保存および推定計算の整合性を維持すること。単一プロセス構成であっても、並行して実行される処理の排他制御や整合性チェックを怠ってはならない。一方で、将来のマルチプロセス化や分散配置を前提とした複雑な制御基盤を先行実装する必要はない。

パフォーマンス改善やリソース消費の最適化は、実際の利用環境で具体的な問題が発生した際に対処する。履歴データの蓄積によって性能上の支障が出た場合は、ボトルネックとなっている処理を特定・計測し、まずは局所的な改善から検討すること。「無期限保存」の方針は、無制限のストレージ容量や特定の応答時間を常に保証することを意味しない。

対応プラットフォームは Windows および Linux とし、動作に影響を及ぼす可能性のある OS 間の差異を検証する。指定されていない過去バージョンの Node.js や旧バージョンの Hub、他の OS に対する互換性対応を独断で追加してはならない。現在のサポート対象範囲を変更する必要が生じた場合は、事前に相談すること。

## 4. アップデートと手動復旧

システムのアップデートは、ユーザーによる明示的な操作に基づいて実行する。バックグラウンドでの自動更新、自動ロールバック、無停止アップデートといった高度な仕組みは求めない。

アップデートが失敗した場合は手動での復旧を基本とし、復旧作業に伴うシステム停止も許容する。正常に完了していない更新を成功と誤認させる表示は行わず、どの処理がどういった原因で失敗したかを追跡できるログやエラー情報を確実に残すこと。アップデート実行前の自動バックアップや、いかなる場合でも必ず元の状態に復元できる仕組みは必須条件としない。

ただし、アップデート処理の都合でデータベースを独断で初期化したり、過去の履歴を削除したり、保存済みの推定結果を改変したりすることは固く禁止する。**既存の履歴データが消失するリスクがある変更や、旧バージョンとのデータ互換性を失うような破壊的変更を行う場合は、事前に影響範囲と手動復旧における制約を説明し、ユーザーから明確な承認を得ること。**「手動復旧を基本とする」という方針は、失われたデータを後から復元できることを意味するものではない。

## 5. テスト・レビュー・完了条件

テストは、受け入れ条件の達成、重要な境界値の検証、想定される具体的な失敗ケースの確認、および不具合の再発防止を目的として実施する。テストコードの行数やカバレッジ率の数値自体を目的化してはならない。変更の影響範囲に応じて、以下の観点を優先して検証する。

| 確認対象 | 主な確認内容 |
| --- | --- |
| 通常の収集・推定・保存・閲覧 | 対象の契約および利用枠に対応する実測値から正しく推定を行い、算出時点の結果を確実に保存・表示できること。 |
| 再接続・利用実績の補完 | データの再受信や過去履歴の補完において二重計上を行わず、未観測の利用枠や推定値を推測で独自に生成しないこと。 |
| リセット・欠測・不正入力 | 対応関係のない増分データを混在させず、計算が成り立たない推定結果を正常な数値として表示しないこと。 |
| 保存失敗・障害時の表示 | 保存失敗時に誤って成功通知を行わず、原因を追跡できること。また、安全に稼働できる機能は可能な限り継続させること。 |
| 認証・管理操作 | 保護対象リソースへの不正アクセスや、意図しない設定変更・アップデートを防止し、機密情報を不要に出力しないこと。 |
| アップデート失敗 | 独断で履歴データを破壊せず、失敗の事実を明示して、手動対応に必要な情報を記録・提示すること。 |
| OS 間の差異 | Windows と Linux で挙動が異なる可能性のある変更については、影響を受ける双方の環境で動作を確認すること。 |

模擬 Hub（Mock Hub）を用いた検証と実機 Hub との接続確認は明確に区別し、模擬 Hub での確認のみをもって「実機との互換性が確認できた」と判断してはならない。未実施の検証項目がある場合は、その事実と影響範囲を明確に報告すること。

コードレビューや設計レビューでの指摘は、「必須修正」「任意改善」「対象外」の 3 つに明確に分類する。合意事項に反するデータ破損、処理失敗時の誤った成功通知、機密情報の漏洩、必要な検証や手動復旧に不可欠な情報の欠落などは「必須修正」とする。一方で、合意済みのリスク受容事項（HTTP 通信の許容、自動バックアップの見送り、手動復旧方針など）を、単に懸念されるという理由だけで蒸し返して修正を求めてはならない。前提条件に変化が生じた場合や、新たな重大リスクが判明した場合に限り、具体的な根拠を示して再検討を提案すること。

**受け入れ条件を満たし、必要な検証を通過し、残存する必須修正が解消された時点でタスク完了とみなす。** 独断によるさらなる構造改善や追加のアイデア提案を理由に、実装作業を漫然と引き延ばしてはならない。また、必要な検証が未実施のまま残っている場合は、完了条件を満たしたとはみなさない。

## 6. 事前相談と将来要件

事前に相談すべき事項は、合意済みの前提や方針から外れ、システムの保証範囲、基本構造、または運用負担に影響を与える変更に限定する。具体的には、履歴データの消失や過去バージョンとのデータ非互換を伴う変更、公開範囲・対象ユーザー・認証方式の変更、単一プロセス構成やローカル保存の原則から外れる構成、追加の常駐サービスや運用インフラの必須化、サポート対象環境の変更などが該当する。

本方針の範囲内に収まる日常的な実装判断は、担当者の裁量で進めてよい。外部ライブラリの追加についても、一律にユーザーの事前承認を待つのではなく、必要性と全体の保守負担を総合的に判断して採用し、上記の判断基準を超える場合にのみ相談すること。

手動による履歴削除機能は、将来の検討事項にとどめる。また、複数ユーザーの権限管理、無停止運用、分散処理、複数データベース対応のための抽象化レイヤー、過去データの再計算基盤、自動バックアップ、自動ロールバックなどは、いずれも初期リリースの実装対象外とする。「将来必要になるかもしれない」という理由だけの先行実装は避け、将来の拡張性を損なわない境界設計（責務の適切な分離）を意識したうえで、現時点で真に必要な仕様のみを実装すること。
