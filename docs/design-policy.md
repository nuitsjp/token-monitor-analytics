# Token Monitor Analytics — 設計・実装ガードレール

## 1. 設計目標と前提

本プロジェクトは、機能・品質・安全性の要件を満たしたうえで、システムの理解、コード変更、検証、および運用の全体負担を最小化することを基本方針とする。過度な品質追求や、コード量・ファイル数・依存関係の削減そのものを目的化しない。

本システムは、上流の複数 Token Monitor Hub から利用実績と利用枠を取得し、実測増分から定額制サブスクリプションの利用許容量（ドル換算）を推定・記録するセルフホスト型ダッシュボードである（推定値は参考値であり、公式上限や保証値ではない）。

| 観点 | 前提条件 |
| --- | --- |
| 想定利用者 | 1 名（障害時やアップデート失敗時の手動復旧を許容）。 |
| 複数 Hub 対応 | 複数 Hub への同時接続・並行集約・管理を必須要件とする。 |
| 構成・環境 | Windows / Linux（Node.js 24 LTS）の単一常駐プロセス。ローカル SQLite で履歴管理し、外部 DB や Docker は不要。 |
| 機能範囲 | 複数 Hub からの SSE 並行受信・自動再接続、実績補完（GET）、データ保存・推定、Web UI 閲覧およびブラウザ向け SSE 配信、Hub 管理（登録・一覧・個別停止）、手動更新。端末からの直接収集は行わない。 |
| 接続・認証 | LAN、VPN、またはローカルループバック経由。Basic 認証によるアクセス制御を実施（当面は HTTP 通信を許容）。 |
| 履歴データ方針 | 原則無期限で保存し、算出時点の推定結果を保持する（遡及再計算やバックアップ機能は実装しない）。 |
| 開発環境 | 動作確認用の模擬 Hub（Mock Hub）を同梱する。 |

※ 接続 Hub 数、データ保持量、応答時間などの数値目標は現時点で未指定であり、根拠のない独自の上限値や要件を設けない。

## 2. アーキテクチャと設計追加の判断基準

アーキテクチャ設計の進め方、文書の役割分担、初期設計の完了基準は [アーキテクチャ設計の進め方](architecture-process.md) に従う。目標・制約・品質要求・リスク受容の正本は本書とする。

外部ライブラリの導入やコードの構造化（関数の分割、階層構造、インターフェース等）は、品質を維持しつつ開発・運用負担を軽減できる場合に限って採用する。「依存の一律禁止」や「構造の制限」といった極端な制約は設けない。

システムの構造や運用負担に影響を与える仕組みを新たに追加する場合は、事前に以下の 4 点を明確に示す必要がある。

1. 解決すべき現在の要件、具体的なリスク、または合意済みの将来要件
2. その仕組みを追加しなかった場合に生じる具体的な問題
3. よりシンプルな構成、局所的な修正、または手動運用では不十分である理由
4. 今すぐ導入すべき理由と、見送った場合に生じる具体的な負担

抽象的な理由（ベストプラクティス、将来への備え等）による過度な抽象化、不要なフォールバック、後方互換対応は行わない。ただし、日常的な関数分割や局所的な改善にまで上記 4 点の説明や事前承認を求めるものではない。

## 3. 必要な品質保証と許容する失敗

### 3.1 障害時の動作継続と通知

安全に継続できる機能を可能な限り維持し、履歴データの保全や表示の正確性を担保できない処理のみを適切に停止する。異常の隠蔽や、失敗を正常終了と偽る処理は行わない。

| 状況 | 求められる振る舞い |
| --- | --- |
| 特定 Hub との一時的な切断 | 該当 Hub への自動再接続を試みつつ、履歴閲覧や他 Hub との通信・処理を継続する。画面上にも未接続状態を明示する。 |
| 一部 Hub の不正データ・非互換 | 不正入力を正常データとして扱わず、影響を受ける処理のみ停止する。他 Hub の通信や履歴閲覧は維持し、原因と影響範囲を明示する。 |
| 保存失敗・書き込み不整合 | 整合性を担保できない書き込み処理を停止する。安全に参照できる範囲で、履歴閲覧やステータス表示は可能な限り維持する。 |
| プロセス継続が困難な異常 | プロセスの完全停止を許容する。コンソールやログで原因を追跡可能にする。 |

- **状態表示**: 各 Hub の接続状態やデータごとに「正常」「未接続」「保存失敗」「推定不可」を画面上で明確に区別し、過去の保存値を現在値と誤認させない。
- **ログ記録**: 発生日時、対象 Hub、該当処理、エラー詳細など原因調査に必要な情報を記録する。認証情報や共有シークレットなどの機密情報は出力しない。
- **許容事項**: 無停止運用や完全自動復旧、大掛かりな障害隔離機構の実装は求めない。

### 3.2 履歴・推定・補完の正確性

- **データ分離と二重計上防止**: Hub 単位および契約・利用枠単位でデータを識別・分離し、混同や誤合算を防止する。再受信や補完時の二重計上を防ぎ、リセット前後や対応関係が不明な増分データは無理に補完せず「推定不可」として扱う。
- **複製ログを報告する構成の扱い**: 同じ利用ログファイルを複数端末にコピー・同期し、それぞれの Token Monitor から Hub に報告する構成はサポート対象外とする。端末間の複製ログを自動検出・除外する仕組みは実装しない。SSE の再受信や GET 補完による二重計上は引き続き防止する。
- **端末 ID の変更**: 端末 ID が変わった場合は別端末として扱い、以前の端末と自動で結び付けない。過去の記録を保持し、新しい端末の観測を起点に推定する。手動による関連付けは第 6 節の将来要件とする。
- **初期版の推定精度**: 同じ Hub 応答に含まれる利用額と消費率の測定時刻のずれによる誤差は、参考値として許容する。取得周期の調整や時刻の補正は行わない。契約・利用枠・対象期間の対応が不明な場合は、引き続き推定不可とする。
- **実績補完の範囲**: 停止中や再接続時の過去実績は Hub から取得できた範囲内に限り補完し、未観測の利用枠や推定値を推測で独自生成しない（Hub 未保持データの完全復元は保証外）。
- **履歴の保全**: 算出時点の推定結果をそのまま保持し、ロジック変更に伴う過去データの遡及改変や再計算機構は行わない。
- **データ保持と破壊操作の禁止**: 履歴は原則無期限で保持する（自動・手動削除機能は作らない）。エラー処理や更新失敗を理由とした DB 初期化や履歴の削除・改変は禁止する。

### 3.3 認証・外部入力・機密情報の保護

- **アクセス制御**: Web 画面、API、ブラウザ向け SSE エンドポイントに Basic 認証を適用する。認証情報や共有シークレットをログやレスポンスに出力しない。
- **通信経路**: 当面は HTTP 通信を許容するが、通信経路の暗号化（TLS/VPN 等）がない環境では機密性が保たれない前提とする。説明資料等でも「アクセス制御」と「通信経路の暗号化」を明確に区別して記載する。[1]
- **入力検証と CSRF 対策**: 外部との信頼境界（Hub 受信データや管理操作）で必要なバリデーションを実施する（モジュール間の重複検証は不要）。Hub 管理やシステム更新などの重要操作には CSRF 対策を講じる。[2]
- **ユーザー管理**: 単一ユーザー想定のため、複数ユーザーの権限管理やデータ分離は実装しない。

### 3.4 同時実行・性能・対応環境

- **並行処理の整合性**: 複数 Hub からの並行受信、実績補完、管理操作が重なった場合でも、排他制御によりデータ保存および推定計算の整合性を維持する（分散配置等を想定した過剰な制御基盤は不要）。
- **性能とリソース**: 性能改善や最適化は実環境でボトルネックを特定・計測した上で局所的に対処する。数値目標のない早期最適化は行わない。
- **対応環境**: Windows および Linux（Node.js 24 LTS）。OS 間の動作差異を検証し、未指定環境への互換対応は独断で追加しない。

## 4. アップデートと手動復旧

- **実行方式**: システムのアップデートはユーザーの明示的な操作により実行する（自動更新、自動ロールバック、無停止更新は求めない）。
- **手動復旧の原則**: 失敗時は手動復旧を基本とし、作業に伴うシステム停止を許容する。失敗の事実と原因をログ等に記録し、誤った成功通知を行わない（自動バックアップや原状復元機能は実装しない）。
- **データ保全と承認**: アップデート処理に伴う DB 初期化や履歴改変は禁止する。**既存データの消失リスクや互換性を損なう破壊的変更を行う場合は、事前に影響範囲と復旧制約を説明し、ユーザーから明確な承認を得ること。**

## 5. テスト・レビュー・完了条件

テストは、受け入れ条件の達成、重要な境界値の検証、具体的な失敗ケースの確認、および不具合の再発防止を目的に実施する（テストコード行数やカバレッジ数値の追求を目的化しない）。

| 確認対象 | 主な確認内容 |
| --- | --- |
| 通常の収集・推定・表示 | 複数 Hub の実測値から正しく推定を行い、算出結果を確実に保存・表示できること。 |
| 再接続・利用実績の補完 | 二重計上や推測値の独自生成がなく、他 Hub のデータに影響を与えないこと。 |
| リセット・欠測・不正入力 | 対応関係のない増分データを混在させず、計算不能な推定結果を正常値として表示しないこと。 |
| 保存失敗・障害時の表示 | 保存失敗時に誤った成功通知を行わず原因を追跡できること。一部障害時も継続可能な処理を維持すること。 |
| 認証・管理操作 | 保護対象への不正アクセスや意図しない変更を防止し、機密情報を不要に出力しないこと。 |
| アップデート失敗 | 履歴データを破壊せず、失敗の事実を明示して手動対応に必要な情報を記録・提示できること。 |
| OS 間の差異 | Windows と Linux の双方で動作すること。 |

- **検証の基準**: 模擬 Hub（Mock Hub）での検証のみをもって実機互換と判断しない。未実施の検証項目がある場合は、事実と影響範囲を明確に報告する。
- **レビュー指摘の分類**: 指摘は「必須修正」「任意改善」「対象外」の 3 つに分類する。データ破損、失敗の隠蔽、機密情報漏洩、検証・復旧情報の欠落等は「必須修正」とする。合意済みのリスク受容事項（HTTP 許容、バックアップ見送り、手動復旧方針等）を単なる懸念で蒸し返さない。
- **完了条件**: **受け入れ条件を満たし、必要な検証を通過し、残存する必須修正が解消された時点でタスク完了とみなす。** 独断による追加の構造改善やアイデア提案で作業を引き延ばさないこと。

## 6. 事前相談と将来要件

### 事前相談が必要な事項
合意済みの前提や方針から外れ、システムの保証範囲、基本構造、または運用負担に影響を与える変更は、着手前に必ず相談すること。

- 履歴データの消失やデータ非互換を伴う変更
- 公開範囲、対象ユーザー、認証方式の変更
- 単一プロセス構成やローカル保存の原則から外れる構成
- 追加の常駐サービスや運用インフラの必須化
- サポート対象環境の変更

※ 本方針の範囲内に収まる日常的な実装判断（ライブラリ採用の要否や局所的な改善等）は担当者の裁量で進めてよい。

### 合意済みの将来要件

同じ Hub 内で、利用者が旧端末と新端末を指定し、Analytics に保存した過去データの `deviceId` を新しい `deviceId` に書き換えて手動で関連付ける機能を将来実装する。変更対象は端末への帰属とその関連参照に限定し、保存済みの利用額・消費率・推定値・算出時点を変更したり、推定結果を遡及再計算したりしない。

本機能は初期版では実装しない。具体的な更新対象、変更先の既存データとの衝突、旧 ID の再受信・補完による二重計上、関連参照を含む一括更新の整合性は将来の実装時に設計・検証する。初期設計はこの要件を記録する範囲とし、専用の基盤を先行導入しない。

### 初期対象外（先行実装の禁止）
「将来のため」を理由とした以下の機能・基盤の先行実装は行わない。現時点で真に必要な仕様のみを実装すること。

- 手動・自動の履歴削除機能
- 複数ユーザー対応・権限管理
- 無停止運用・完全自動復旧
- 分散処理・マルチプロセス・マルチ DB 抽象化
- 過去データの遡及再計算・イベント再生基盤
- 自動バックアップ・自動ロールバック

## 7. 未決事項・適用時の確認・根拠

現時点で重大な未決事項はないが、以下の項目は作業時に確認すること。

| 確認項目 | 扱いと留意点 |
| --- | --- |
| 既存の設計方針・指示事項 | 作業前に `AGENTS.md` 等を確認し、矛盾点があれば報告する。既存の指示事項を無断で変更しない。 |
| 実装詳細 | ソースコード、Hub API 仕様、DB 構造等の事実を確認し、推測で補完しない。不明点は着手前に解消する。 |
| 性能・保持量の具体値 | 複数 Hub 対応は必須だが数値目標は未指定。独自の上限設定や過剰設計を避け、必要に応じて確認する。 |

本書（`docs/design-policy.md`）は Git リポジトリで管理される正本とする。見直し時は最新の本書と改定指示を参照し、変更理由をコミット履歴等に記録すること。リスク受容の範囲に関わる重要な変更は、事前にユーザーとの合意を得る。
