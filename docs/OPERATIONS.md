# 運用・無料枠・障害時の扱い

## 無料枠は実際の利用量で確認する

1 Hub = 1 Cloudflare Account、Analyticsは別アカウントという配置。HubのDurable Objectは、SSE接続とハートビートが続く間、無通信に近い状況でもDurationを消費する。[S5][S6] 公式の128 MB計量では24時間起動が約11,059 GB-s/日で、13,000 GB-s/日のFree枠内だが、同アカウント内の他のObject等の消費は別途加算される。

複数アカウントに分ければ無条件に無料を保証できる、とはしない。Cloudflareのアカウント運用条件と、各サービスの実測メーターを確認する。上限回避を目的にアカウントを自動作成する機能はない。

Analyticsは最大1 LiveRoomを短いPOST/閲覧のために使い、無通信時にWebSocketを保持したままhibernateできる。ただし更新が頻繁なら起きている時間は増える。常時無料や休止時間を未計測のまま断定しない。[S1]

D1 Freeは読取り500万行/日、書込み10万行/日、1DB500MB、アカウント合計5GBが確認基準。[S3][S4] **バッチ送信にしても書込み行数は減らない。** 1イベントあたり観測、索引、latestに加え、対象契約ごとのstateとdailyの書込みが発生する。契約数/イベント頻度で10万行へ近づく可能性がある。テストは課金メーターを再現しない。

## 保存量

詳細小型snapshotは既定7日。毎時17分のCronで最大500行を削除し、最新snapshotは期限にかかわらず保護する。日次推定は長期保持する。期限を過ぎていても削除が追い付くまで残るため、**7日がディスク容量の上限保証ではない**。イベントが1日12,000件を大幅に超える場合は保持量と削除処理を見直す。削除自体もD1の書込みを消費する。

例として1イベント2 KiB×7,200件/日×7日ならJSON本体だけで約98 MiB。索引・ページ・契約データは追加。実際のイベントサイズを測り、500MBに余裕を持たせる。Rawの無制限保存、古いセッションの全複製はしない。

## Collector

outbox既定256 MiB、JSONファイル1件/イベント。1つのプロセスだけが使う。容量上限に達すると未送信を消すのではなく受信処理を待機し、アップローダーが排出する。ディスク故障や破損時は停止して管理者へ委ねる。ログ監視はjournalctlとpending_bytesから始める。独立したメッセージブローカーや二重化プロセスを入れない。

## 障害の意味

- Analytics停止: 受信済みのデータをoutboxに残し再送。
- Collector停止/SSE断: 上流イベント履歴は回復できない。最新snapshotから観測再開。
- D1成功後の応答喪失: 同じIDで再送し、保持中データは二重登録しない。
- Web通知だけ失敗: D1には残る。画面の再接続/再読込みで回復。通知の完全配信は保証しない。
- Access期限切れ: APIは401、次の通知時には期限切れWebSocketを閉じる。再ログインする。

## 最初の受入試験

模擬Hubで接続/利用額/推定を確認し、Hub停止→再起動とAnalytics停止→再起動を試す。次に実Hubで各項目の意味を確認する。Ubuntuへ移してから24時間程度のログとCloudflare使用量を**利用者の環境で**観測する。このZIP作成中に24時間稼働試験を実施したという意味ではない。
