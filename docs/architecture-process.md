# アーキテクチャ設計の進め方

本書は、アーキテクチャ設計の手順、各文書の役割、および初期設計の完了基準を定める。システムの目標・制約・品質要求の正本は [設計・実装ガードレール](design-policy.md) とする。

## 1. 採用手法と目的

本システムは単一プロセスの常駐アプリケーションであり、アーキテクチャ設計では「内部の責務分担」と「並行処理・障害時の整合性」に重点を置く。これらを整理・伝達するため、以下の手法を組み合わせて採用する。

| 手法 | 適用方針 |
| --- | --- |
| arc42 | 文書全体の骨格。構造、実行時動作、設計判断を中心に記録する（要件・制約はガードレールを参照）。 |
| C4 model | Context、Container、Component の各図により、外部連携、システム境界、内部責務と依存関係を可視化する。 |
| 4+1 ビュー | Process と Scenarios の観点を取り入れ、並行処理や相互作用から構造の妥当性を検証する（独立文書は作成しない）。 |

記述には Markdown と Mermaid を用い、形式の網羅ではなく設計意図の伝達を重視する。

## 2. 文書の役割分担

各文書は、記録すべき具体的内容が生じた時点で作成する。

| 文書 | 役割 |
| --- | --- |
| `docs/design-policy.md` | 目標、制約、品質要求、設計判断基準の正本。 |
| `docs/architecture-process.md`（本書） | 設計手順、文書の役割分担、初期設計の完了基準。 |
| `CONTEXT.md` | 業務概念を定義する用語集（実装詳細は含めない）。 |
| `docs/architecture.md` | 構造、データ識別・保存、状態遷移、排他制御などの設計仕様・実装詳細。 |
| `docs/adr/NNNN-*.md` | 重大なアーキテクチャ判断の記録（ADR）。 |

### ADR の記録基準

日常的な技術選定は設計書に記載し、以下のすべてを満たす重大な判断のみを ADR として記録する（[設計・実装ガードレール](design-policy.md) の仕組み追加基準に準拠）。

- 後からの変更負担が大きい
- 採用理由が直感的に自明でない
- 複数の選択肢とトレードオフを比較検討した

## 3. 設計で定義する事項

設計書（`docs/architecture.md`）において、以下の仕様を具体化する。

### 3.1 データ識別と保存ルール

Hub API 仕様と実データに基づき、以下を定義する。

- 識別情報の定義（Hub、契約、利用枠、対象期間、観測・実績）
- 同一実績の判定条件（再受信時・実績補完時）
- 観測データの対応付け条件と、推定不可の判定基準
- SQLite の保存設計（主キー・一意性制約、永続化対象と再取得可能データの切り分け）

### 3.2 構造・責務・並行制御

C4 図を用いてコンポーネントの責務と関係性を明示し、以下を決定する。

- 各コンポーネント（受信、補完、推定、保存、画面配信）の責務と状態の保持・更新処理
- 並行実行する処理と直列化が必要な処理の区別
- 排他制御の適用範囲と SQLite トランザクション境界
- データ保存完了と画面通知の連携（過去の保存値と最新状態を誤認させない表示仕様を含む）

Hub の接続状態、保存処理の状態、推定対象の算出可否を分けて定義し、それぞれの関係と表示方法を明記する。これらは同時に成立し得るため、「正常」「未接続」「保存失敗」「推定不可」を単一の排他的な状態にまとめない。

### 3.3 主要シナリオと障害時の振る舞い

[設計・実装ガードレール](design-policy.md) の品質要求（認証、CSRF 対策、手動復旧、OS 対応等）に基づき、以下の主要シナリオにおける期待動作（処理の継続・停止、データ保存、画面表示、ログ記録）を定義する。

- 複数 Hub からの通常受信、推定、保存、および画面配信
- 切断後の再接続と実績補完（新規・重複データの受信を含む）
- 利用枠のリセット、欠測、対応関係が不明な観測データの受信
- Hub の個別停止と実行中処理の競合
- 一部 Hub における不正データ受信や非互換の発生
- 保存失敗、書き込み不整合、およびプロセスの停止・再起動

## 4. 設計手順

1. **Hub API の確認と識別ルールの整理**: 実データを調査し、データ識別ルールと前提シナリオを具体化する。
2. **システム境界の定義（C4 Context / Container）**: 外部連携、プロセス、永続化、認証の各境界を明確にする。
3. **内部責務と処理フローの設計（C4 Component / Process）**: コンポーネント間の責務、処理順序、排他制御、トランザクション境界を定義する。
4. **設計判断の記録と要件照合**: 重要な判断を ADR に記録し、[設計・実装ガードレール](design-policy.md) との整合性を確認する。

## 5. 初期設計の完了基準

以下の事項が明確化され、[設計・実装ガードレール](design-policy.md) との整合性が確認できた段階をもって初期設計の完了とする。

- **設計内容の確定**: データ識別・保存ルール、コンポーネント責務と状態管理、並行性・排他制御、および主要シナリオ（障害時含む）の挙動が定義されていること。
- **検証方針の明確化**: 各シナリオの期待動作を確認するテスト方法が定まっていること。
- **未決事項の解消**: 設計判断を左右する未確認事項が解消されているか、既知のリスクとして明記されていること。
