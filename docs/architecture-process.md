# アーキテクチャ設計の進め方

本書は、システムアーキテクチャ設計の進め方、記録先、および初期設計の完了基準を定める。
なお、システムの目標、制約、品質要求、リスク受容の正本は [設計・実装ガードレール](design-policy.md) とする。

## 1. 採用する方法と理由

本システムは単一プロセスの常駐アプリであり、設計の重点は「内部の責務分担」と「並行処理・障害時の整合性」にある。これらを的確に整理・伝達するため、以下の手法を組み合わせて採用する。

| 手法 | 適用方針 |
| --- | --- |
| arc42 | 文書全体の骨格。要件は [設計・実装ガードレール](design-policy.md) の参照にとどめ、構造、実行時動作、設計判断、用語に絞って記録する。 |
| C4 model | Context、Container、Component の各図により、外部連携、システム境界、内部責務と依存方向を可視化する。 |
| 4+1 ビュー | Process ビューと Scenarios の観点を取り入れ、並行処理や相互作用から構造の妥当性を検証する（独立文書は作成しない）。 |

形式を埋めることではなく設計判断の伝達を優先し、記述には Markdown（文章・表）と Mermaid（図）を用いる。

## 2. 文書の役割分担

| 文書 | 役割 |
| --- | --- |
| `docs/design-policy.md` | 目標、制約、品質要求、リスク受容、判断基準の正本。 |
| `docs/architecture-process.md`（本書） | 設計の進め方、記録先、初期設計の完了基準。 |
| `CONTEXT.md` | プロジェクト固有の業務概念を定義する用語集。 |
| `docs/architecture.md` | 構造、識別・保存ルール、状態、排他制御などの具体的な設計仕様。 |
| `docs/adr/NNNN-*.md` | 重大なアーキテクチャ判断の記録（ADR）。 |

各文書は記録すべき具体的内容が生じた時点で作成し、事前に空の文書を作成しない。

### 用語集と設計書の境界

- **用語集（`CONTEXT.md`）**: 「利用枠」など業務概念の意味を定義する。API 項目名、DB カラム、アルゴリズム、遷移条件などの実装詳細は含めない。
- **設計書（`docs/architecture.md`）**: 「どの項目で識別するか」「どの条件で推定不可とするか」など、具体的な仕様や実装詳細を記録する。

### ADR の記録基準

以下のすべてを満たす設計判断のみを ADR として記録する。

- 後からの変更負担が大きい
- 背景を知らない第三者には採用理由が判断しにくい
- 複数の選択肢とトレードオフを比較検討した

日常的な技術選択やライブラリ選定は設計書に記載し、[設計・実装ガードレール](design-policy.md) の「仕組み追加時の 4 点説明」に該当する重大な判断のみ ADR に集約して設計書から参照する。

## 3. 具体的な設計で明らかにすること

### 3.1 識別と保存のルール

Hub API の仕様と実際の取得データに基づき、以下を定義する（未確認の識別子や履歴の存在を仮定しない）。

- 識別情報の定義（Hub、契約、利用枠、対象期間、観測・実績）
- 同一実績の判定条件（再受信時・実績補完時）
- 観測データの対応付けと、対応付けられない場合の扱い（推定不可の判定基準）
- SQLite の保存設計（主キー・一意性制約、観測と推定結果の関係）
- 永続化が必要なデータと、Hub から再取得可能なデータの切り分け

### 3.2 構造と処理の責任

C4 図を用いてコンポーネントの責務と関係性を明示する。受信、補完、推定、保存、画面配信の各責務を整理し、状態の保持場所と更新処理を定義する。

また、並行処理や競合を考慮し、以下を決定する。

- 並行実行を許可する処理と、順序制御（直列化）が必要な処理の区別
- 排他制御の適用範囲と SQLite トランザクション境界
- 保存完了と画面通知のタイミング関係

### 3.3 状態と画面表示

「正常」「未接続」「保存失敗」「推定不可」は対象が異なり併発し得るため、単一フラグではなく対象ごとに独立して定義する。

| 対象 | 設計内容 |
| --- | --- |
| Hub 接続 | 接続、切断、再接続、個別停止の遷移条件と、通信中処理の扱い |
| 保存処理 | 書き込みの継続・停止条件と、安全に読み取り可能な範囲 |
| 推定処理 | 観測データの対応付け条件と、推定不可の判定基準 |
| 画面表示 | 過去の保存値と最新状態を明確に区別する表示仕様 |

設計時は対象ごとの状態遷移（表や状態遷移図）と、それらの相互作用（シーケンス図）を整理する。

### 3.4 主要シナリオと方針の充足

以下の主要シナリオについて、期待動作（処理の継続・停止、データ保存、画面表示、ログ記録）を定義する。

- 複数 Hub からの通常受信、推定、保存、および画面配信
- 切断後の再接続と実績補完（新規・重複データの受信を含む）
- 利用枠のリセット、欠測、対応関係が不明な観測データの受信
- Hub の個別停止と、実行中処理の競合
- 一部 Hub における不正データ受信や非互換の発生
- 保存失敗、書き込み不整合、およびプロセスの停止・再起動

あわせて、[設計・実装ガードレール](design-policy.md) の品質要求（認証、CSRF 対策、手動復旧、OS 対応など）をどの設計で満たすかを明記する。

## 4. 着手順序

1. **Hub API の確認と識別ルールの整理**: 取得データを調査し、識別ルールと前提シナリオを具体化する。
2. **システム境界の整理（C4 Context / Container）**: 外部連携、実行・保存の境界、認証境界を明確にする。
3. **内部責務と処理フローの具体化（C4 Component / Process）**: コンポーネント間の責務、処理順序、排他制御、トランザクション境界を定義する。
4. **設計判断の記録と要件照合**: 重要な判断を ADR に記録し、[設計・実装ガードレール](design-policy.md) の要求事項との整合性を確認する。

## 5. 初期設計の完了基準

主要シナリオにおいて、以下の事項が具体的に説明できる状態をもって初期設計の完了とする。

- **同一性の判定**: 何をもって同一データ・同一実績とみなすか
- **責務と状態管理**: どのコンポーネントが状態を保持し、更新するか
- **並行性と順序制御**: どの処理を並行させ、どの処理を直列化するか
- **永続化と通知**: いつ保存が確定し、どのタイミングで画面へ通知するか
- **障害時の挙動**: 異常発生時に何を停止・継続し、復旧に必要な情報が残るか
- **検証方法**: 期待動作をどのようなテストで確認するか

[設計・実装ガードレール](design-policy.md) の各要求との整合性が確認され、設計判断を左右する未確認事項が解消（またはリスクとして明記）されていることを確認する。
