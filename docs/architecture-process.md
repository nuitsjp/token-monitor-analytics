# アーキテクチャ設計の進め方

本書は、アーキテクチャ設計の手順、各文書の役割、および初期設計の完了基準を定める。システムの目標・制約・品質要求の正本は [設計・実装ガードレール](design-policy.md) とする。

## 1. 採用する方法と理由

本システムは単一プロセスの常駐アプリであり、設計の重点は「内部の責務分担」と「並行処理・障害時の整合性」にある。これらを整理・伝達するため、以下の手法を組み合わせて採用する。

| 手法 | 適用方針 |
| --- | --- |
| arc42 | 文書全体の骨格。構造、実行時動作、設計判断に絞って記録する（要件はガードレールを参照）。 |
| C4 model | Context、Container、Component の各図により、外部連携、システム境界、内部責務と依存関係を可視化する。 |
| 4+1 ビュー | Process と Scenarios の観点を取り入れ、並行処理や相互作用から構造の妥当性を検証する（独立文書は作成しない）。 |

形式の網羅ではなく設計判断の伝達を重視し、記述には Markdown と Mermaid を用いる。

## 2. 文書の役割分担
各文書は記録すべき具体的内容が生じた時点で作成し、事前に空のファイルを作成しない。

| 文書 | 役割 |
| --- | --- |
| `docs/design-policy.md` | 目標、制約、品質要求、設計判断基準の正本。 |
| `docs/architecture-process.md`（本書） | 設計の進め方、記録先、初期設計の完了基準。 |
| `CONTEXT.md` | プロジェクト固有の業務概念を定義する用語集。 |
| `docs/architecture.md` | 構造、識別・保存ルール、状態、排他制御などの具体的な設計仕様。 |
| `docs/adr/NNNN-*.md` | 重大なアーキテクチャ判断の記録（ADR）。 |

### 用語集と設計書の境界

- **用語集（`CONTEXT.md`）**: 「利用枠」など業務概念を定義する。API 項目名、DB カラム、アルゴリズム等の実装詳細は含めない。
- **設計書（`docs/architecture.md`）**: 識別ルールや推定不可の判定条件など、具体的な仕様・実装詳細を記録する。

### ADR の記録基準

日常的な技術選定は設計書に記載し、以下のすべてを満たす重大な判断のみを ADR として記録する（[設計・実装ガードレール](design-policy.md) の仕組み追加基準に準拠）。

- 後からの変更負担が大きい
- 採用理由が直感的に判断しにくい
- 複数の選択肢とトレードオフを比較検討した

## 3. 具体的な設計で明らかにすること

### 3.1 識別と保存のルール

Hub API の仕様と実データに基づき、以下を定義する。

- 識別情報の定義（Hub、契約、利用枠、対象期間、観測・実績）
- 同一実績の判定条件（再受信時・実績補完時）
- 観測データの対応付けと、対応付けられない場合の扱い（推定不可の判定基準）
- SQLite の保存設計（主キー・一意性制約、観測と推定結果の関係）
- 永続化が必要なデータと、Hub から再取得可能なデータの切り分け

### 3.2 構造と処理の責任

C4 図を用いてコンポーネントの責務と関係性を明示する。受信、補完、推定、保存、画面配信の各責務を整理し、状態の保持場所と更新処理を定義する。

また、並行処理や競合を考慮し、以下を決定する。

- 並行実行する処理と直列化が必要な処理の区別
- 排他制御の適用範囲と SQLite トランザクション境界
- 保存完了と画面通知のタイミング関係

### 3.3 状態と画面表示

状態は対象ごとに独立して定義し、状態遷移図やシーケンス図を用いて相互作用を整理する。

| 対象 | 設計内容 |
| --- | --- |
| Hub 接続 | 接続・切断・再接続・個別停止の遷移条件と、通信中処理の扱い |
| 保存処理 | 書き込みの継続・停止条件と、安全に参照可能な範囲 |
| 推定処理 | 観測データの対応付け条件と、推定不可の判定基準 |
| 画面表示 | 過去の保存値と最新状態を明確に区別する表示仕様 |

### 3.4 主要シナリオと方針の充足

以下の主要シナリオについて、期待動作（処理の継続・停止、データ保存、画面表示、ログ記録）を定義する。

- 複数 Hub からの通常受信、推定、保存、および画面配信
- 切断後の再接続と実績補完（新規・重複データの受信を含む）
- 利用枠のリセット、欠測、対応関係が不明な観測データの受信
- Hub の個別停止と、実行中処理の競合
- 一部 Hub における不正データ受信や非互換の発生
- 保存失敗、書き込み不整合、およびプロセスの停止・再起動

あわせて、[設計・実装ガードレール](design-policy.md) の品質要求（認証、CSRF 対策、手動復旧、OS 対応など）を満たす設計を明記する。

## 4. 着手順序

1. **Hub API の確認と識別ルールの整理**: 実データを調査し、識別ルールと前提シナリオを具体化する。
2. **システム境界の整理（C4 Context / Container）**: 外部連携、実行・保存、認証の各境界を明確にする。
3. **内部責務と処理フローの具体化（C4 Component / Process）**: コンポーネント間の責務、処理順序、排他制御、トランザクション境界を定義する。
4. **設計判断の記録と要件照合**: 重要な判断を ADR に記録し、[設計・実装ガードレール](design-policy.md) の要求事項との整合性を確認する。

## 5. 初期設計の完了基準

主要シナリオにおいて以下が明確化され、[設計・実装ガードレール](design-policy.md) との整合性が確認できた段階をもって初期設計の完了とする。

- **データ識別**: 同一データ・同一実績の判定条件
- **責務と状態管理**: コンポーネントごとの責務と状態保持・更新処理
- **並行性と順序制御**: 並行処理と直列化の区別、排他制御の範囲
- **永続化と通知**: データ保存の確定契機と画面通知のタイミング
- **障害時の挙動**: 異常発生時の停止・継続範囲とログ記録内容
- **検証方針**: 各シナリオの期待動作を確認するテスト方法

※ 設計判断を左右する未確認事項が解消されている（またはリスクとして明記されている）こと。
