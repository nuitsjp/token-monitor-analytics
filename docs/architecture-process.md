# アーキテクチャ設計の進め方

本書は、システムアーキテクチャ設計の進め方、記録先、および初期設計の完了基準を定める。
システムの目標、制約、品質要求、およびリスク受容の正本は [設計・実装ガードレール](design-policy.md) とし、具体的な設計内容は本書の方針に従って別途記録する。

## 1. 採用する方法と理由

本システムは、単一の Node.js 常駐プロセス、ローカル SQLite、複数 Hub との接続を基本構成とする。設計の重点は「内部の責務分担」と「並行処理・障害時の整合性」にある。これらを過不足なく整理・伝達するため、以下の手法を組み合わせて採用する。

| 方法 | 本プロジェクトでの適用方針 |
| --- | --- |
| arc42 | 文書全体の骨格として採用する。[設計・実装ガードレール](design-policy.md) で定義済みの要件は参照にとどめ、必要な項目（構造、実行時動作、設計判断、用語）に絞って記録する。 |
| C4 model | Context、Container、Component の各図により、外部との関係、実行・保存の境界（Node.js と SQLite）、内部の責務と依存方向を可視化する。 |
| 4+1 ビュー | Process view と Scenarios の観点を取り入れ、並行処理や主要な相互作用から構造の妥当性を検討・検証する（独立した文書は作成しない）。 |

図面やテンプレートの形式を埋めること自体を目的とせず、設計判断を的確に伝えることを優先する。記述には Markdown（文章・表）と Mermaid（図）を用いる。

## 2. 文書の役割分担

| 文書 | 役割 |
| --- | --- |
| `docs/design-policy.md` | 目標、制約、品質要求、リスク受容、実装・検証の判断基準の正本。 |
| `docs/architecture-process.md`（本書） | アーキテクチャ設計の進め方、記録先、初期設計の完了基準。 |
| `CONTEXT.md` | Hub、契約、利用枠、観測、推定、補完など、プロジェクト固有の用語を定義する用語集。 |
| `docs/architecture.md` | 構造、識別・保存ルール、状態とシナリオ、排他制御、障害時の動作など、具体的な設計仕様。 |
| `docs/adr/NNNN-*.md` | 後からの変更負担が大きく、採用理由を明文化する価値がある重要な設計判断。 |

用語集、設計書、ADR は、記録すべき具体的な内容が生じた時点で作成する（事前に空の文書を作成しない）。

### 用語集と設計書の区別

- **用語集（`CONTEXT.md`）**: 「利用枠とは何か」など、業務概念の意味を定義する。API 項目、SQLite のカラム、アルゴリズム、遷移条件などの実装詳細や処理仕様は含めない。
- **設計書（`docs/architecture.md`）**: 「どの API 項目で識別するか」「どの条件で推定不可とするか」など、具体的な処理仕様や実装詳細を記録する。

### ADR の対象

次のすべてを満たす設計判断を ADR として記録する。

- 後からの変更負担が大きい。
- 背景を知らない第三者には、採用理由が判断しにくい。
- 複数の選択肢とトレードオフを比較検討して決定した。

ライブラリの選定や個別方式の決定など、日常的な技術選択ごとに機械的に作成する必要はない。通常の説明は設計書に記載し、[設計・実装ガードレール](design-policy.md) 第 2 節の「仕組み追加時の 4 点説明」を要する重大な判断については、ADR に集約して設計書から参照する。

## 3. 具体的な設計で明らかにすること

### 3.1 識別と保存のルール

Hub API の仕様と実際の取得データに基づき、以下を定義する（未確認の識別子や履歴の存在を仮定しない）。

- Hub、契約、利用枠、対象期間、観測・実績の識別情報
- 再受信時および実績補完時における、同一実績の判定条件
- リセットや欠測をまたぐ観測の対応付け条件と、対応付けられない場合の扱い（推定不可の判定基準）
- SQLite に保存するデータ、主キー・一意性制約、および保存済み推定結果と観測との関係
- プロセス再起動時に永続化すべき情報と、Hub から再取得可能な情報の切り分け

### 3.2 構造と処理の責任

C4 図を用いて、各コンポーネントの責務と関係性を明示する。旧実装の構成にとらわれず、受信、補完、推定、保存、画面配信の各責務を整理し、状態の保持場所と更新処理を定義する。

また、並行受信、実績補完、管理操作が重複した場合を考慮し、以下を決定する。

- 並行実行を許可する処理と、順序制御（直列化）が必要な処理の区別
- 排他制御の適用範囲と、SQLite トランザクションに含める処理境界
- 保存完了と画面・ブラウザ通知のタイミング関係

### 3.3 状態と画面表示

「正常」「未接続」「保存失敗」「推定不可」は対象が異なり同時に発生し得るため、単一の排他的な状態フラグとして扱わず、対象ごとに独立して定義する。

| 対象 | 設計内容 |
| --- | --- |
| Hub 接続 | 接続、切断、再接続、個別停止の遷移条件と、通信中の処理の扱い。 |
| 保存処理・保存先 | 書き込みを継続・停止する条件と、安全に読み取り可能な範囲。 |
| 推定処理 | 観測データを対応付けて算出できる条件、および推定不可となる条件。 |
| 表示データ | 算出時点と最新状態を区別し、過去の保存値を現在値と誤認させない表示仕様。 |

設計時は対象ごとの状態遷移（表や状態遷移図）と、それらの相互作用（シーケンス図）を整理する。

### 3.4 主要シナリオと方針の充足

少なくとも以下の主要シナリオを具体化し、期待動作（保存結果、表示状態、停止・継続する処理、ログ記録内容）を定義する。

- 複数 Hub からの通常受信、推定、保存、および画面配信
- 切断後の再接続と実績補完（補完中の新規・重複データ受信を含む）
- 利用枠のリセット、欠測、対応関係が不明な観測データの受信
- Hub の個別停止と、実行中の受信・補完の競合
- 一部 Hub における不正データ受信や非互換の発生
- 保存失敗、整合性を維持できない書き込み、およびプロセスの停止・再起動

あわせて、認証、入力検証、CSRF 対策、手動復旧時の履歴保全、OS 対応（Windows / Linux）など、[設計・実装ガードレール](design-policy.md) の各要求をどの設計で満たすかを明記する。

## 4. 着手順序

1. **Hub API の確認と識別ルールの整理**: 取得可能なデータを調査し、用語、識別ルール、重要シナリオを具体化する。
2. **システム境界の整理（C4 Context / Container）**: 外部接続、実行・保存境界（Node.js と SQLite）、および認証境界を明確にする。
3. **内部責務とシナリオの具体化（C4 Component / Process / Scenarios）**: 処理順序、排他制御、トランザクション境界を検討し、各シナリオの動作を整理する。
4. **設計判断の記録と要件照合**: 重要なアーキテクチャ判断を ADR に記録し、[設計・実装ガードレール](design-policy.md) の品質要求との適合性を確認する。

## 5. 初期設計の完了基準

主要シナリオにおいて、以下の事項が具体的に説明できる状態をもって初期設計の完了とする。

- **同一性の判定**: 何をもって同一データ・同一実績とみなすか。
- **責務と状態管理**: どのコンポーネントが状態を保持し、更新するか。
- **並行性と順序制御**: どの処理を並行させ、どの処理を直列化するか。
- **永続化と通知**: いつ保存が確定し、どのタイミングで画面へ通知するか。
- **障害時の挙動**: 異常発生時に何を停止し、何を継続するか。復旧に必要な情報が残るか。
- **検証方法**: 期待動作をどのようなテストで確認するか。

設計方針の各要求との整合性が確認され、判断を左右する未確認事項が解消（または明記）されていることを確認する。
