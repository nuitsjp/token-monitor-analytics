# アーキテクチャ設計の進め方

本プロジェクトでは、arc42 を必要な内容に絞って文書の骨格にし、静的構造は C4 で表し、識別・状態・実行時シナリオを中心にアーキテクチャを設計する。

本書は設計の進め方と記録先を定める。目標・制約・品質要求・リスク受容の正本は [設計・実装ガードレール](design-policy.md) とし、具体的なアーキテクチャは設計を進めながら別途記録する。

## 1. 採用する方法と理由

本システムでは、単一の Node.js 常駐プロセス、ローカル SQLite、複数 Hub との接続という基本構成が決まっている。設計の重点は、内部の責務分担と、並行処理・障害時の整合性にある。

二重計上を防ぐには同じ実績を識別できる必要があり、増分を正しく計算するには同じ契約・利用枠・リセット期間に属する観測を対応付ける必要がある。この定義が曖昧なままでは、部品の分割や排他制御だけを整えても正しさを保証できない。識別ルールと具体的なシナリオから、必要な状態と責務を明らかにする。

| 方法 | 本プロジェクトでの使い方 |
| --- | --- |
| arc42 | 構造、実行時動作、設計判断、用語などを整理する文書の骨格として使う。全 12 節を埋めず、既存の設計方針で定義済みの内容は参照する。 |
| C4 | Context、簡潔な Container、主要な Component の図で、外部との関係、実行・保存の境界、内部の責務と依存方向を表す。 |
| 4+1 | Process view と Scenarios の観点を使い、並行処理と重要な相互作用から構造を検討・検証する。ビューごとの独立した文書は必須としない。 |

C4 の Container はアプリケーションやデータストアの境界を表すため、単一プロセスでも意味がある。Context と Container を同じ図として扱わず、Node.js アプリと SQLite の関係を明示する。ブラウザ側の実行部分は、採用する Web UI の構成に応じて境界を定める。

4+1 は UML を必須とせず、不要なビューの省略も認めている。方法論の形式や図の数を満たすことではなく、必要な設計判断を説明できることを優先する。Markdown の文章・表と Mermaid の図を基本とし、内容に適した表現を選ぶ。

## 2. 文書の役割分担

| 文書 | 役割 |
| --- | --- |
| `docs/design-policy.md` | 目標、制約、品質要求、リスク受容、実装・検証の判断基準の正本。 |
| `docs/architecture-process.md`（本書） | アーキテクチャ設計の進め方、記録先、初期設計の完了基準。 |
| `CONTEXT.md` | Hub、契約、利用枠、観測、推定、補完など、このプロジェクト固有の用語の意味を定義する用語集。 |
| `docs/architecture.md` | 構造、識別・保存ルール、状態とシナリオ、排他制御、障害時の動作など、具体的な設計。 |
| `docs/adr/NNNN-*.md` | 後から変更する負担が大きく、採用理由を残す価値がある設計判断。 |

用語集、具体的な設計書、ADR は、記録する内容ができた時点で作成する。空の文書や ADR を先に揃えない。

### 用語集と設計書の区別

「利用枠とは何か」は `CONTEXT.md` に記録する。「どの API 項目で識別するか」「どの条件で推定不可になるか」は `docs/architecture.md` に記録する。用語集には API 項目、SQLite のキー、アルゴリズム、遷移条件などの実装詳細や処理仕様を入れない。

### ADR の対象

次のすべてを満たす判断を ADR に記録する。

- 後から変更する負担が大きい。
- 背景を知らない読み手には、採用理由が分かりにくい。
- 実際の選択肢とトレードオフを比較して決定した。

SQLite ライブラリやブラウザ向け SSE の方式など、技術選択ごとに機械的に ADR を作らない。通常の説明は設計書に記録する。設計方針の第 2 節が求める「仕組み追加時の 4 点説明」が必要な判断では、その説明を残す。ADR の対象なら ADR にまとめ、設計書から参照する。文章量は一段落に固定せず、判断を理解するために必要な内容を記す。

## 3. 具体的な設計で明らかにすること

### 3.1 識別と保存のルール

Hub API の仕様と実際に取得できるデータを確認し、次を明らかにする。未確認の識別子や履歴情報が取得できると仮定して設計しない。

- Hub、契約、利用枠、対象期間、観測・実績をどの情報で識別するか。
- 再受信や実績補完で、何を同一の実績と判定するか。
- リセットや欠測をまたぐ観測を、どの条件で対応付けられるか。対応付けられない場合をどう扱うか。
- SQLite に保存するデータ、その識別キーと一意性の制約、保存済みの推定結果と観測との関係。
- プロセスの再起動をまたいで、どの情報を保持し、どの情報を Hub から再取得できるか。

### 3.2 構造と処理の責任

C4 の図では、部品名に加えて責務と関係を説明する。受信、補完、推定、保存、画面配信などの責務を整理し、状態を保持する場所と更新する処理を明らかにする。

部品数は先に固定しない。旧実装の分割は参考資料として扱い、現在の要件に対する妥当性を再確認する。旧実装に存在したことだけを理由に構造や機能を引き継がない。

並行受信、補完、管理操作について、同時に進めてよい処理と順序を制御する処理を区別する。排他制御の範囲、SQLite のトランザクションに含める更新、保存完了と通知の関係を定める。具体的な直列化方式は、これらの条件を確認してから選ぶ。

### 3.3 状態と画面表示

「正常」「未接続」「保存失敗」「推定不可」を、一つの対象に属する排他的な状態としてまとめない。対象が異なり、同時に成立し得るため、それぞれの状態と関係を定義する。

| 状態の対象 | 設計する内容 |
| --- | --- |
| Hub の接続 | 接続、切断、再接続、個別停止の条件と、進行中の通信の扱い。 |
| 保存処理・保存先 | 書き込みを継続・停止する条件と、安全に読み取りを続けられる範囲。 |
| 推定対象 | 観測を対応付けて算出できる条件と、推定不可になる条件・理由。 |
| 表示するデータ | 観測・算出時点と現在の状態を区別し、過去の保存値を現在値と誤認させない表示。 |

例えば、Hub に接続できていても、必要な観測の対応関係が不明なら推定できない。状態遷移図や表で対象ごとの状態を表し、シーケンス図で対象間の相互作用を説明する。全状態を組み合わせた巨大な状態機械は作らない。

### 3.4 重要シナリオと既存方針との対応

少なくとも次のシナリオを具体化し、関連する設計方針と対応付ける。図で説明する価値のある相互作用にはシーケンス図を使い、単純な条件や期待結果は文章・表で記録する。

- 複数 Hub からの通常受信、推定、保存、画面配信。
- 切断後の再接続と実績補完。補完中に新規データや重複データが届く場合も含む。
- 利用枠のリセット、欠測、対応関係が不明な観測。
- Hub の個別停止と、進行中の受信・補完が重なる場合。
- 一部 Hub の不正データや非互換が発生した場合。
- 保存失敗、整合性を維持できない書き込み、プロセスの停止・再起動。

各シナリオでは、保存結果、表示状態、停止する処理、継続する処理、原因を追跡する情報を明らかにする。補完と購読の開始順序は、Hub API が提供する情報と欠落・重複の扱いを確認して決める。

認証・入力検証・CSRF 対策を適用する境界、手動更新失敗時の履歴保全と復旧、Windows と Linux の対応についても、既存方針をどの設計で満たすかを記録する。識別と状態の検討だけで品質要求の確認を完了したとみなさない。

## 4. 着手順序

1. **Hub API の事実を確認し、用語・識別ルール・重要シナリオを整理する。** 実際に取得できる識別子や履歴情報を根拠にする。用語集を先に完成させようとせず、具体例で定義を確かめながら進める。
2. **C4 で外部との境界と実行・保存の境界を確認する。** Context と Container を簡潔に記述し、認証を適用する境界も示す。
3. **状態とシナリオを使って、内部の責務を決める。** 処理順序、排他制御、保存の確定範囲を検討し、必要な責務を Component 図へ反映する。シナリオと構造を往復し、必要なら用語や識別ルールを見直す。
4. **重要な判断と検証条件を残す。** 各シナリオの期待結果を具体化し、必要な判断を ADR に記録する。認証、手動更新時の履歴保全、対応 OS も既存方針と照合する。

## 5. 初期設計の完了基準

重要なシナリオごとに、次を説明できることを初期設計の完了基準とする。

- 何を同一と判定するか。
- 誰がどの状態を保持し、更新するか。
- どの処理を並行させ、どの処理の順序を制御するか。
- いつ保存が確定し、何を画面やブラウザへ通知するか。
- 失敗時に何が残り、何を停止し、何を継続できるか。
- 期待結果をどの検証で確認するか。

設計方針の各要求と設計の対応を確認し、設計判断を左右する未確認事項が残っていれば明記する。図やテンプレートを埋めたことだけを完了の根拠にしない。初期設計の完了と実装の動作検証は区別し、未実施の検証を成功として扱わない。
