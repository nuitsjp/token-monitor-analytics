# アーキテクチャ設計の進め方

本書は、アーキテクチャ設計の手順、各文書の役割、および初期設計の完了基準を定める。システムの目標・制約・品質要求の正本は [設計・実装ガードレール](design-policy.md) とする。

## 1. 採用手法と目的

単一プロセス常駐型である本システムの特性を踏まえ、「内部の責務分担」と「並行処理・障害時のデータ整合性」に重点を置く。記述には Markdown と Mermaid を用い、以下の手法を組み合わせて設計意図を明確に伝達する。

| 手法 | 適用方針 |
| --- | --- |
| arc42 | 文書全体の基本構成。構造、実行時動作、設計判断の記録。 |
| C4 model | Context、Container、Component 図による境界・責務・依存関係の可視化。 |
| 4+1 ビュー | Process（並行性）と Scenarios（主要ユースケース）による妥当性検証。 |

## 2. 文書の役割分担

記録すべき具体的内容が生じた段階で各文書を作成・更新する。

| 文書 | 役割 |
| --- | --- |
| `docs/design-policy.md` | 目標、制約、品質要求、設計判断基準の正本。 |
| `docs/architecture-process.md`（本書） | 設計手順、文書の役割分担、初期設計の完了基準。 |
| `CONTEXT.md` | ドメイン用語の定義（実装詳細を含まない用語集）。 |
| `docs/architecture.md` | 構造、データ識別・保存、状態遷移、排他制御などの設計仕様。 |
| `docs/adr/NNNN-*.md` | 重大なアーキテクチャ判断の記録（ADR）。 |

### ADR の記録基準

日常的な技術選定は設計書（`docs/architecture.md`）に記載し、以下のすべてを満たす判断のみを ADR として記録する。

- 後からの変更負担が大きい
- 採用理由が直感的に自明でない
- 複数の選択肢とトレードオフを比較検討した

## 3. 設計書で定義する事項

設計書（`docs/architecture.md`）では以下の仕様を具体化する。

- **データ識別と保存ルール**:
  Hub、契約、利用枠、対象期間、観測・実績の識別キーと一意性制約。同一性の判定と二重計上防止。推定可否の判定基準。
- **構造・責務・並行制御**:
  受信、補完、推定、保存、画面配信のコンポーネント責務。並行処理と直列化の境界、SQLite トランザクション境界。保存成功と画面通知の連携。
- **主要シナリオと障害時の振る舞い**:
  通常受信・表示、再接続と実績補完、リセット・欠測時の対応、Hub 個別停止、不正データ受信、保存失敗時の動作（処理継続・停止、画面表示、ログ記録）。

## 4. 設計手順

1. **Hub API 仕様の確認**: 実機・コードを調査し、データ識別ルールと前提シナリオを整理する。
2. **システム境界の定義（C4 Context / Container）**: 外部連携、プロセス、永続化、認証の各境界を確立する。
3. **内部責務と処理フローの設計（C4 Component / Process）**: コンポーネント責務、処理順序、排他制御、トランザクション境界を策定する。
4. **設計判断の記録と整合性確認**: 重要事項を ADR に記録し、[設計・実装ガードレール](design-policy.md) と照合する。

## 5. 初期設計の完了基準

以下の 3 点が満たされ、[設計・実装ガードレール](design-policy.md) との整合性が確認できた段階で初期設計を完了とする。

1. **設計仕様の確定**: 第 3 節の各事項（データ識別、責務、並行制御、主要シナリオ）が具体化されている。
2. **検証方針の確立**: 各シナリオの期待動作を検証するテスト方法が定まっている。
3. **未決事項の整理**: 設計判断を左右する未確認事項が解消されているか、既知のリスクとして管理されている。
