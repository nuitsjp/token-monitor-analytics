# アーキテクチャ設計の進め方

本書は、アーキテクチャ設計の手順、各文書の役割、および設計の完了基準を定める。システムの目標・制約・品質要求の正本は [設計・実装ガードレール](design-policy.md) とする。

## 1. 採用手法と目的

単一プロセス常駐型である本システムの特性を踏まえ、「内部の責務分担」と「並行処理・障害時のデータ整合性」に重点を置く。記述には Markdown と Mermaid を用い、以下の手法を組み合わせて設計意図を可視化する。

| 手法 | 適用方針 |
| --- | --- |
| arc42 | 文書全体の基本構成。構造、実行時動作、設計判断の記録。 |
| C4 model | Context、Container、Component 図による境界・責務・依存関係の可視化。 |
| 4+1 ビュー | Process（並行性）と Scenarios（主要ユースケース）による妥当性検証。 |

### ADR の記録基準

日常的な技術選定は設計書（`docs/architecture.md`）に記載し、以下のすべてを満たす判断のみを ADR として記録する。

- 後からの変更負担が大きい
- 採用理由が自明でない
- 複数の選択肢とトレードオフを比較検討した

## 3. 設計手順と定義事項

設計は以下の手順で進め、仕様を `docs/architecture.md` にまとめる。

1. **Hub API 仕様の確認**: 実機・コードを調査し、前提シナリオとデータ識別ルール（Hub・契約・利用枠・対象期間・実績のキー定義、同一性判定、推定可否基準）を整理する。
2. **システム境界の定義（C4 Context / Container）**: 外部連携、プロセス、永続化、認証の境界を確立する。
3. **内部責務と処理フローの設計（C4 Component / Process）**: コンポーネント責務（受信・推定・保存・配信）、並行制御（直列化キュー）、SQLite トランザクション境界を策定する。
4. **主要シナリオと障害時の振る舞いの策定（Scenarios）**: 通常受信、再接続と実績補完、リセット・欠測対応、Hub ごとの収集停止・再開、不正データや保存失敗時の動作を定義する。
5. **設計判断の記録と整合性確認**: 重要事項を ADR に記録し、[設計・実装ガードレール](design-policy.md) との整合性を確認する。

## 4. 初期設計の完了基準

以下の 3 点を満たした段階で初期設計を完了とする。

1. **設計仕様の確定**: 第 3 節の各事項（データ識別、内部責務、並行制御、主要シナリオ）が具体化されていること。
2. **検証方針の確立**: 各シナリオの期待動作を検証するテスト方法が定まっていること。
3. **未決事項の整理**: 設計判断を左右する未確認事項が解消されているか、既知のリスクとして管理されていること。
