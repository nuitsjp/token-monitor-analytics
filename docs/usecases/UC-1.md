# UC-1. 設定されたHubの最新情報をローカルに保存し、通知する

- 主アクター: 利用者。起動後の受信・保存・通知は自動で行います。
- 目的: Hubの最新情報をローカルで利用可能にし、閲覧側へ更新を通知します。
- 前提: 2つのHubについて、安定したID・表示名・URL・認証トークンを含む接続設定ファイルが用意されています。
- 起動条件: 利用者がアプリケーションを起動します。
- 保存対象: HubのID・表示名、Hubが配信する利用量、上限、端末状態等の最新状態と受信時刻。URL、認証トークン、受信イベントの履歴は保存しません。

## 主成功系列

UC-1-M / UI確認: 不要。通知の配信までを対象とし、画面への反映はUC-2で扱います。段階2・3を省略します。

| 手順 | アクター | 操作・処理 |
| --- | --- | --- |
| 1 | アプリケーション | `.env` から接続設定ファイルの場所を取得する |
| 2 | アプリケーション | 設定ファイルを読み、2つのHubの必須項目・ID重複・URL形式を検証する |
| 3 | アプリケーション | 各HubのIDと表示名をDBへ同期し、Hubごとに独立したSSE接続を開始する |
| 4 | アプリケーション | 各Hubの初回全体状態を検証し、受信元に紐づけて最新状態と受信時刻を一括保存する |
| 5 | アプリケーション | 保存確定後、閲覧用の最新状態を生成し、接続中の閲覧側へ通知する |
| 6 | アプリケーション | 以後の通知もHubごとの受信順で検証・保存し、保存確定後に閲覧側へ通知する |
| 7 | アプリケーション | 終了時は両Hubの受信と閲覧側への配信を終了し、DBを閉じる |

## 拡張系列

### UC-1-X1. Hub切断時に再接続する

- 主アクター: 利用者。起動後の再接続は自動で行います。
- 目的: 通信切断後も、アプリケーション再起動なしで当該Hubの最新状態の受信・保存・通知を再開します。
- 前提: UC-1-MによりHubへの受信が開始されている、または起動後の初回接続がまだ成功していない。
- 分岐点: UC-1-Mの手順3の接続失敗、または手順6の途中で当該HubのSSEが通信断で終了したとき。
- UI確認: 不要。受信・保存・通知の再開を対象とし、画面表示はUC-2で扱います。段階2・3を省略します。

| 手順 | アクター | 操作・処理 |
| --- | --- | --- |
| 1 | アプリケーション | 当該Hubの接続失敗、または受信接続の通信断を検知する |
| 2 | アプリケーション | 最後に保存できた状態を維持し、もう一方の受信とWebサーバーは継続する |
| 3 | アプリケーション | 同じ接続設定で、当該Hubへ切断中は同時に1本だけ、3秒間隔で再接続する |
| 4 | アプリケーション | 再接続後の初回全体状態（snapshot）を検証し、最新状態と受信時刻を一括保存する |
| 5 | アプリケーション | 保存確定後、閲覧用の最新状態を生成し、接続中の閲覧側へ通知する |
| 6 | アプリケーション | 以後の通知をUC-1-Mの手順6と同じく検証・保存・通知する |
| 7 | アプリケーション | 終了時は再接続待ちを含め、当該Hubの受信を終了する |

受け入れ条件:

- 通信断（接続そのものの失敗、またはストリーム終了）では、当該Hubを停止したままにせず、同じ接続設定で再接続します。
- 再接続はHubごとに独立し、切断中の接続は同時に1本だけです。もう一方の受信とWebサーバーは継続します。
- 再接続の間隔は3秒です。アプリケーション稼働中は上限なく繰り返します。
- 再接続後の初回はsnapshotを検証して保存し、その接続では初回全体状態の前の差分通知を受け付けません。
- 切断中および再接続成功前は、最後に保存できた有効な状態を維持します。保存済みデータの取り消しや未保存値による代替は行いません。
- 再接続後の保存成功後に、保存済み状態と一致する閲覧用データを通知します。切断中は閲覧側へ切断専用の通知を送りません。
- HTTP応答が不正な場合（認証失敗を含む）、不正通知、保存失敗では再接続せず、当該Hubの受信を停止します。もう一方の受信とWebサーバーは継続します。
- 通常終了では再接続待ちと受信を止めます。
- 通信断の原因と再接続後の保存成功をログに残し、URLと認証トークンは含めません。
- テーブル変更はありません。

## 受け入れ条件

- 2つのHubから独立して受信し、初回および更新後の最新状態を、保存処理とは別のDB接続からHubごとに読み取れます。
- 初回状態・全体更新・鮮度更新の保存成功後に、保存済み状態と一致する閲覧用データが通知されます。
- 保存確定前、不正通知、保存失敗、heartbeatでは、データ更新を通知しません。
- 閲覧側の接続時には、その時点の最新保存値を通知し、以後の更新へ取りこぼしなく接続します。
- 複数の閲覧側へ同じ最新状態を提供できます。通知は最新状態の共有を目的とし、途中の全イベントの再送は保証しません。
- 閲覧側が未接続または切断されても、Hubからの受信・保存は継続します。通知失敗によって保存済みデータを取り消しません。
- 一方の認証失敗・通信断・不正通知・保存失敗でも、もう一方の受信とWebサーバーは継続します。通信断からの当該Hubの再接続はUC-1-X1で扱います。
- 設定ファイルが存在しない、JSONが不正、必須項目が欠ける、またはHub IDが重複する場合は起動に失敗します。
- 未受信でもHubを識別できます。同じHub IDでの再起動、表示名やURLの変更でも保存状態を維持し、別の提供元には別のIDを使います。
- 同じ情報を再受信しても利用量が二重加算されません。
- 不正な通知や保存失敗では、最後に保存できた有効な状態を維持します。
- アプリケーションを終了・再起動しても保存済みの状態が残ります。
- URLと認証トークンをDB、受信データの保存内容、ログ、閲覧側への通知に含めません。設定ファイルはアプリケーションから更新しません。
