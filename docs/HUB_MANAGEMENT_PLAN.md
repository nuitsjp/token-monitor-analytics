# Hub管理UIの実装計画

状態: 設計・計画のみ（2026-09-06）。以下の機能は未実装。現在のCLI設定手順は引き続き有効。

## 目的と合意事項

Analyticsの画面からHubの追加・更新・停止・削除とSecretの差し替えを行えるようにする。Go CollectorとNode.js Analyticsは同居する別プロセスとして維持する。

- Collectorは共有設定ファイルを定期確認する。Analytics→Collectorの内部SSEやCollectorのHTTP待受は追加しない。
- Hub→CollectorのSSE、Collector→Analyticsのloopback HTTP POST、Analytics→ブラウザーのSSEは維持する。定期確認するのはローカル設定ファイルだけ。
- 通常設定とSecretを別ファイルに保存する。今回は暗号化しない。秘密情報ファイルは平文であり、OSのアクセス権で保護する。
- 通常運用の設定更新はAnalyticsに集約する。Collectorは読み取り専用。1 Analytics、1 Collector、1 outbox writerを維持する。
- 履歴の正本は既存SQLiteだけ。設定用DB、外部キュー、クラウドサービス、OS別の常駐管理ヘルパーは追加しない。

## 初期実装の範囲

既存画面にHub管理を追加し、一覧・追加・表示名/URLの更新・Secret差し替え・有効化/停止・削除を提供する。保存状態、Collectorへの反映状態、Hubの接続状態を区別して表示する。0件でも両プロセスが起動し、UIから最初のHubを登録できるようにする。

Hub IDは登録後に変更・再利用しない。URL変更は同じHubの移転として扱い、別Hubへの切替は新規登録する。未削除の登録は停止中を含め最大8件とし、削除済みIDの記録はこの枠に数えない。重複ID・重複URLを検証する。

契約設定のUI化、複数管理者の権限モデル、Secretの暗号化・鍵管理、Hub自体の作成/削除、履歴の消去、外部公開は対象外。画面でいうHub削除は、このCollectorによる収集対象から外す操作である。

## 保存モデル

ファイル名は以下を予定する。Ubuntuは既存の私的設定ディレクトリー、Windowsはユーザーの保護されたローカルディレクトリーに置く。デモ用は別の保存先とする。

| ファイル | 内容・責務 |
| --- | --- |
| `analytics.json` / `collector.json` | 待受、DB/outbox、認証の環境変数名、共有Hub設定へのパスなどの起動設定 |
| `hubs.json` | schema version、単調増加するrevision、Hub ID・表示名・URL・状態・secretRef。秘密情報ファイルへの相対パスもここで固定する |
| `hub-secrets.json` | 不透明なsecretRefからSecretへの対応。Hub Secretだけを保存する |

管理モードでは両プロセスが同じ`hubs.json`を参照する。既存の各設定内のHub配列と共通設定を同時に有効にしない。相対パスはそれぞれの設定ファイルの場所を基準に解決し、ブラウザーからパスを指定させない。

Hub Secretをingest/viewer資格情報と兼用しない。既存Hubの環境変数参照は初回移行時に解決し、移行後のSecret変更は環境変数の再読込やプロセス再起動に依存しない。

## 保存と部分失敗

2ファイルを同時に置換できるとは扱わない。Secretの参照を不変にして、次の順序で安全に切り替える。

1. Analyticsが管理操作を直列化し、要求のrevisionが現在値と一致することを確認する。不一致は競合として返し、上書きしない。入力・契約参照・URL・秘密値の検証を先に完了する。
2. Secret変更時は新しいsecretRefを発行し、旧参照を保持したまま秘密情報ファイルへ追記する。一時ファイルの書込み・同期・close・置換を行う。既存参照の値は書き換えない。
3. 新しい参照とrevisionを持つ通常設定を同じ手順で置換する。この置換を設定保存の確定点とする。Collectorは秘密情報ファイルだけの変更では再接続しない。
4. Analytics内の取込み処理と設定切替を直列化し、新しいHub IDの許可を反映してから保存成功を返す。取込みはこの直列化の中で現在の登録を検証し、SQLite COMMIT後だけ観測ACK・通知を返す原則を維持する。
5. 保存確定後に既存のブラウザー向けSSEで管理状態の更新を通知する。Collectorへの反映完了やHub接続成功を保存成功と同一視しない。

手順2の後で失敗しても旧設定が旧Secretを参照できるようにする。通常設定の置換後に応答が失われた場合は再取得で保存済みrevisionを確認できるようにする。同じ内容の保存ではrevision更新・再接続を行わない。

Collectorは通常設定→参照先の秘密情報→通常設定のrevision再確認の順で読み、整合する全体を検証してから採用する。欠損・不正JSON・参照不足・競合中は部分適用せず、稼働中の直前の有効設定を維持して再試行する。起動時に有効な設定を読めなければ安全なエラーで停止する。

初期版では未参照Secretを稼働中に自動削除しない。整理は両プロセス停止中の明示的な保守操作とし、古い読取りとの競合を避ける。Secret差し替え・Hub削除で過去の秘密値が自動消去されるとは案内しない。

Windowsのファイルロック・置換失敗は有限回の再試行後に保存失敗として返し、既存ファイルを先に削除しない。Linuxの同期・Windowsの置換を含め実OSで検証し、電源断への完全な耐久性は未検証のまま保証しない。

## Collectorの設定反映

既定2秒間隔でサイズ上限付きの通常設定を読み、revisionを比較する。起動時にも読み込む。OS固有のファイル監視やmtimeだけの検知に依存しない。Analyticsが停止していてもファイルが有効なら収集を継続する。

Hubごとに購読のcontextと終了待ちを管理する。追加は開始、停止・削除は終了待ち、URL/secretRef変更は旧購読の終了後に新購読を開始する。表示名だけの変更では再接続しない。新購読では新streamIdを使用し、履歴を通じて異なるストリームを連続観測と推測しない。

購読変更中も既存outboxとアップローダーを1つずつ維持する。Hubの認証等の恒常エラーは対象Hubに閉じ込め、設定変更によって再試行できるようにする。一時的な切断のバックオフ再接続は維持する。outboxの破損・保存不能やingestの恒常的な拒否は別の全体障害として扱い、未送信データを保持する。

## 停止・削除・履歴

停止は再有効化可能。削除は収集停止とアーカイブであり、IDと表示名等の最小記録を保持する。通常一覧から除外しても、停止・削除前にoutboxへ入った観測は受け付ける。削除済みHubの履歴や他Hubと混在する未送信バッチを消去・拒否しない。未知のIDは引き続き拒否する。

契約が参照しているHubは削除を拒否し、停止を案内する。過去観測と推定の帰属・金額・欠測の意味は変更しない。削除済みHubに新しい契約を作成することは許可しない。

## 状態表示とHTTP境界

CollectorからAnalyticsへの小さな状態報告POSTを追加する。これは既存ingestとは別エンドポイントとし、loopback側だけで既存Collector用Bearer認証を検証する。状態変化時と既定15秒のheartbeatで、適用revision・Hub ID別接続状態・安全なエラーコードを報告する。観測がないHubや停止中も反映状況を確認できるようにする。

状態報告は一時的な情報としてAnalyticsのメモリーに保持し、履歴DBやoutboxへ保存しない。失敗しても収集を止めず、次回に最新状態を送る。既定45秒を超えて届かなければ接続中と断定せず「Collector状態不明」とする。Analytics再起動後も次の報告までは不明とする。

ブラウザーは既存SSEによる通知で状態を再取得する。要求したrevisionとCollectorの適用revisionを比較し「反映待ち」を表示する。「保存済み」「設定反映済み」「Hub接続中」「最終観測」は別の意味として表示する。

## 秘密情報と編集権限

現在の「Hub SecretはCollectorだけが保持しAnalyticsへ転送しない」という仕様を、管理モードでは「Analyticsの管理処理とCollectorが扱う」に改める。AnalyticsはUIから受け取ったSecretを秘密情報ファイルへ保存し、Collectorは同じファイルを読む。Hub SecretをSQLite・outbox・状態報告に含めない。

Ubuntuの現行発行構成では同じ発行ユーザーのディレクトリー0700・ファイル0600を利用する。Windowsでは実行ユーザーのACLで保護する。別ユーザーの手動配置では両プロセスの必要最小限のアクセスを明示して準備し、広い権限へ自動緩和しない。設定・秘密情報・一時ファイル・バックアップをGit/配布物/静的配信から除外する。

UIには管理用の許可した項目だけを返す。Secretは登録・差し替え専用で、取得API・入力欄の再表示・localStorage・ログ・例外に出さない。「変更なし」と「差し替え」を明示し、空欄による意図しない消去を避ける。参照ID、内部パス、env名、設定ファイル全体は配信しない。

編集は起動設定の明示的な管理有効化で許可する。初期版は単一所有者向けとして、管理有効時は既存の閲覧境界を通過できる利用者に編集を許す。既存配置を自動的に編集可能へ変更しない。Tailscaleモードで有効化する場合、その待受に到達できる利用者が管理者となることを設定手順に明記し、到達範囲を所有者の端末に制限する。複数の閲覧専用利用者が必要なら初期版の管理を有効にせず、権限分離を別途設計する。

変更APIはJSONのみを受け付け、許可Originを必須検証し、CSRF対策とHost検査を行う。通常のBasic/SSH転送、loopback、Tailscale専用待受の境界は維持する。ingestトークンをブラウザーの編集資格情報に使わず、Tailscale側からingest/Collector状態報告を受け付けない。URLはHTTPS origin（ローカル開発だけloopback HTTP）に限定し、認証付きURL・パス・クエリー・フラグメント・リダイレクトを許可しない。

## 移行・CLI・発行

初回移行は両プロセスを停止し、既存の発行ロック内で実施する。AnalyticsのHub ID/表示名とCollectorのHub ID/URL/Secretを突き合わせ、不一致、秘密値不足、契約参照の不整合があれば書換え前に停止する。保護されたバックアップを取り、秘密情報→通常設定→両起動設定の順に作成・切替する。途中失敗時は再実行で完了できるようにし、不完全な移行では起動しない。旧版コードへの自動ロールバックは行わない。

移行完了後は旧Hub配列・Hub用envへの依存を除去する。バックアップ内の旧Secretは保護したまま保守対象として記録する。ingest/viewer認証、契約、SQLite、outboxは引き継ぐ。従来形式は移行前の起動互換として維持するが、管理UIを有効化するには共通設定へ移行する。

`configure:ubuntu`は起動設定・空の共通設定・秘密情報ファイルの初期化と停止中の初回移行を担当する。管理モード移行後のHub変更引数は明確なエラーにし、稼働中の別writerにしない。既存の管理ファイルがある場合はHub設定を再生成しない。初回はHub 0件でも構成完了とする。

`publish:ubuntu`は管理ファイルとSecretを保持し、通常更新で移行やHub再設定を暗黙に実行しない。公開検証では「起動成功」と「Hub観測あり」を区別し、意図した0件・全停止を発行失敗にしない。`status:ubuntu`も未登録・停止・認証エラー・状態不明を区別する。権限準備は`provision:ubuntu`、通常設定は`configure:ubuntu`、sudo不要の発行は`publish:ubuntu`という責務を維持する。

## 実装順序

各段階の検証を通してから次に進む。以下はすべて未着手。

2. **Collectorの動的反映** — ファイル定期確認、Hub単位の終了待ちと差分反映、障害分離、状態報告を実装する。アップローダーとoutboxは維持する。

4. **管理画面** — 0件の初期案内、CRUD、停止、Secret差し替え、競合/保存失敗/反映待ち/接続状態を実装する。削除時は収集停止と履歴保持の意味を確認画面に示す。
5. **移行と運用統合** — Windows/Ubuntuの設定移行、configure/publish/status、権限、配布物除外を整え、README・構成・セキュリティ・運用手順を実装済み仕様へ更新する。

## 受入条件

- 0件からUIで登録し、プロセス再起動なしで受信開始できる。設定が正常なら通常2秒程度で確認されるが、終了待ち・接続時間を含む即時反映は保証しない。
- 表示名だけの変更は接続を維持する。URL/Secret変更は対象Hubだけを再接続し、同じHubの購読を重ねない。1 Hubの認証失敗中も他Hubの収集・outbox送信が続く。
- 停止・削除前の未送信バッチが他Hub分と混在しても排出できる。契約参照中の削除は拒否され、ID再利用や履歴消去は起きない。
- 2ファイル間の書込み失敗、ディスク不足、不正設定、同時編集、保存後の応答喪失、Collector/Analytics再起動を試験する。部分適用・意図しないSecret消失・二重writerが起きない。
- Analytics停止中もCollectorは保存済み設定で動作する。状態報告の失敗は収集を止めず、停止したCollectorを接続中と表示し続けない。
- 管理無効時の拒否、Basic/loopback/Tailscale境界、Origin/CSRF、外部ingest/状態報告遮断、Secret非露出をネイティブHTTPで検証する。
- 移行を途中で止めても再実行で復旧し、同一設定のconfigure/publish再実行でHub・Secret・DB・outboxが変更されない。デモと本番は混在しない。
- Go: gofmt、go test ./...、go vet ./...、Linuxのgo test -race ./...。Analytics: npm test、npm run typecheck。結合: node --experimental-strip-types tools/integration.mjs。既存の観測HTTP/SSE/SQLite検証も維持する。
- Windowsでパス・ACL・ファイル置換/ロック・終了処理、Ubuntuで権限・ユーザーsystemd再起動を実機確認する。OS再起動と未実施OSの結果は別に記録し、未実施を成功としない。
