# Token Monitor Analytics

Token Monitor Analyticsは、[Token Monitor](https://github.com/Javis603/token-monitor)が収集したAIツールの利用量・API換算額・アカウント別プラン利用率を継続的に蓄積し、分析・可視化するための非公式コンパニオンアプリケーションです。

Windows向けのネイティブデスクトップアプリケーションとして、Wails v3、Goバックエンド、Webフロントエンドを使用して実装します。

## 背景

Claude Code、Codex、Cursor、GitHub CopilotなどのAIサービスの有料プランでは、一定期間内の利用枠が提供されています。

しかし、多くのサービスでは利用枠が金額ではなく、利用率、トークン、リクエスト数、クレジット、一定期間の制限などとして表示されます。そのため、契約によって実質的にどの程度のAPI利用価値が提供されているのかを、サービス間で直接比較することは困難です。

Token Monitorは、複数のAIツールについて以下の情報を取得できます。

* 実際に使用したトークン数
* モデル別のAPI換算利用額
* アカウントに適用されたプランの利用率
* 利用枠のリセット日時
* ツール、モデル、デバイスごとの利用状況

ただし、API換算利用額と利用率は同じ識別粒度ではありません。API換算利用額、トークン数、モデル内訳はHub端末とサービス単位の「利用額ソース」として扱い、利用率、リセット日時、報告プランはHub、サービス、Hubアカウント、利用枠種別単位の「利用枠ソース」として扱います。両者はそれぞれ論理アカウントへ関連付け、論理アカウントと時間区間を介して結合します。

利用額ソースと論理アカウントはn:nで関連付けます。一方、1つの利用枠ソースを同じ時点に関連付けられる論理アカウントは1つまでです。同じ論理アカウントを複数Hubの利用枠ソースへ関連付けることはできます。未関連付けの利用枠ソースは元観測として保持しますが、アカウント単位の推定には使用しません。

Hub登録時には、URL、資格情報、収集担当から独立した不変のHub識別子を発行します。URL変更や収集担当の引継ぎ後も識別子を維持しますが、同じURLの再登録だけでは既存Hubへ自動統合せず、既存Hubの継続はユーザーが明示します。

元観測と履歴には自動的な期限削除を設けません。Hubを削除または無効化する操作では、接続設定と資格情報だけを除去または無効化し、履歴上のHub識別情報と元観測は残します。論理アカウントは物理削除せずアーカイブし、過去の関連付けと分析結果を維持します。アーカイブは後から解除できます。元観測の物理削除は、ユーザーが明示的に指定したパージだけで行います。

明示パージでは、Hubと取得期間を指定して原JSONスナップショット全体を選択します。全Hubまたは全期間も指定でき、実行前に対象件数と対象期間をプレビューします。対象スナップショットに紐づく派生結果も併せて削除しますが、原JSONをサービス単位またはアカウント単位に改変する部分削除は行いません。将来クラウド複製を提供する場合のパージ連携は、その機能の要件として別途定義します。

同じサービスと`accountKey`が完全一致するHubアカウントは、同じ論理アカウントへ自動的に関連付けます。初めて取得したキーには論理アカウントを自動作成します。メールアドレス、プロファイル名、ワークスペース名の一致は候補提示にだけ使い、異なるキーを自動統合しません。ユーザーが後から関連付けを分割・統合・修正した場合は、保持した元観測から影響区間を再計算します。

アーカイブした論理アカウントと一致する`accountKey`の新規観測は自動復帰させず、「アーカイブ済みアカウントの新規観測」として扱います。通常一覧、現在比較、通常の候補通知からは隠しますが、履歴では参照できます。ユーザーがアーカイブ解除した場合だけ、同じ論理アカウントIDで復帰させます。

未確認候補は、完全一致する生のサービス名と生の報告プラン名を全Hub横断で1候補にまとめたものです。候補には未確認・確認済み・対象外の状態を持たせ、取得元Hub、`accountKey`、観測期間を根拠として表示します。確認時には正式なサービスとプランへ関連付け、後から候補を分割または修正できます。各観測時点のプラン版は、論理アカウントのプラン履歴と版の適用期間で決定し、Hubの報告名だけで新版へ自動変更しません。

対象外候補の元観測は保持し、重複排除後の全体トークン数とAPI換算利用額には一度だけ含めます。一方、論理アカウント別の利用上限推定、価値倍率、プラン比較からは除外し、「未分類／対象外」として扱います。対象外を解除した場合は、保持した元観測から影響期間を再計算します。

一方、Token Monitorは、API換算利用額と利用率を組み合わせてアカウント別の推定上限額を算出し、その推移を長期的に保存することを主目的としていません。

Token Monitor Analyticsは、この不足部分を補完します。

## 最重要ゴール

本プロジェクトの最重要ゴールは、各サービスの論理アカウントについて、適用プランで利用できたと推測されるAPI換算上限額を継続的に算出し、その推移をトレースできるようにすることです。

以下は目標仕様です。現行実装の対応範囲と未実装項目は、後段の「現行実装」節に分けて記載します。

推定上限額は、同じ計算区間に関連付けた利用額ソースの累積API換算利用額差分と、対象となる論理アカウントの利用率差分から算出します。基本となる関係は次のとおりです。

```text
ΔA = Σ_i C_i × Δu_i
```

ここで、Aは関連付けられた利用額ソースを重複排除して合計した累積API換算利用額、C_iは論理アカウントiの対象利用枠上限、u_iは`usedPercent / 100`です。同じ計算区間内で、リセット・プラン変更・系列断絶などの境界をまたがない対応観測を2点以上構成し、同一プランの等値関係と公式な利用上限倍率を制約として加えます。解が数学的に一意に定まる場合だけ推定し、定まらない場合は算出不能とします。

単一論理アカウントの例では、同じ計算区間の2点が t1: A=800 USD, u=0.40、t2: A=1,200 USD, u=0.60 なら、差分から次のように求めます。

```text
ΔA = 1,200 - 800 = 400 USD
Δu = 0.60 - 0.40 = 0.20
C = ΔA ÷ Δu = 400 ÷ 0.20 = 2,000 USD
```

周期の途中から起動した場合でも、周期開始時点との一致は要求せず、同じ計算区間内の対応観測を2点以上構成できれば推定できます。1つの利用額系列に複数の論理アカウントが含まれる場合も、同一プランの等値関係や公式倍率によって解が一意になるなら推定できます。

固定のサービス、プラン、価格、倍率カタログは製品に同梱しません。Hubで観測したサービス名と報告プラン名は未確認候補として提示し、ユーザーが確認した後に正式な定義として登録します。標準価格、公式な利用上限倍率、出典、適用期間は自動補完せず、ユーザーが登録した情報だけを使用します。異なるプランが同じHub内に混在する場合だけ、サービスごとの基準プランと、基準プランに対する各プランの公式な利用上限倍率を制約に使用します。利用上限倍率はプラン版の属性であり、論理アカウントや利用枠へ個別設定しません。例えばPremiumプランの利用上限が基準となるStandardプランの5倍と公式に示されている場合、Premiumの有効なプラン版の倍率を5として扱います。論理アカウントのプラン履歴から観測日時に適用されるプラン版を選び、その版の倍率を同時期の利用上限推定対象へ適用します。異なるプランが混在しない通常のHubでは、基準プランや倍率の設定を要求しません。

異なるプランが混在しているかどうかは、観測日時に有効な論理アカウントのプラン履歴から判定します。Hubが報告するプラン名は照合に使用しますが、プラン履歴を自動的には変更しません。旧プランの最終観測と新プランの初回観測の間で変更時刻を特定できない場合は、その間を有効プラン不明区間として保持し、区間をまたぐ計算だけを除外します。新プランの初回観測以後は、新しい計算区間として分析を再開できます。

Token Monitorの標準UIでは、1台の端末が同時に接続できるHubは1つです。ただし、利用周期の途中で接続先Hubを切り替えると、新しいHubにも当該期間の累積利用額が送られるため、切替前後のデータが重複し得ます。切替が利用枠のリセットと一致しない場合、その利用周期は推定不能とし、元データを保持したまま次のリセット後から推定を再開します。

Hub切替を行った場合だけ、ユーザーが旧Hubの端末レコード、新Hubの端末レコード、同じ物理端末であること、切替日時を登録します。`deviceId`やホスト名の一致は候補提示に使用できますが、自動統合は行いません。通常運用ではこの設定は不要です。

同じ論理アカウントの利用率を複数Hubが報告する場合、それらは別々の容量ではなく、同じ利用枠に対する複数の観測として扱います。Token Monitorが報告する`limits.providers[].updatedAt`を観測時刻として1つの時系列へ統合し、利用率の加算や平均は行いません。同一時刻の値が一致しない観測や`updatedAt`がない観測は、元データを保持したまま推定から除外します。

API換算利用額と利用率は独立した時刻に更新されるため、同じHub応答内の値も同時刻とはみなしません。利用率には`limits.providers[].updatedAt`、利用額には収集端末の`updatedAt`を使い、関連する端末ごとに許容時刻差以内の最近傍観測だけを対応付けます。許容時刻差は、Analyticsの取得間隔、端末のHub送信間隔、利用制限の更新間隔のうち最も長い間隔です。補間・外挿は行わず、採用した実際の時刻差を推定品質として保存します。

複数時点の観測とこれらの制約によって値が数学的に一意に定まる場合だけ推定します。一意に定まらない場合は、均等配分や利用率の単純平均を行わず、観測不足または識別不能として表示します。

一意解に必要な最小数の観測だけで求めた値は「暫定推定」として表示します。余分な観測によって同じ上限を検証できた値は「検証済み推定」とします。観測数が足りていても差分を共通の上限で説明できない場合は「モデル不適合」とし、候補値と残差を分析詳細に残しますが、ダッシュボードや標準価格推定最大価値倍率などの主要指標には使用しません。

上限は、同一プランと公式な利用上限倍率を制約とした非負の最小二乗法で推定します。余分な観測がある場合は、観測されたAPI換算利用額差分に対する推定誤差の合計割合を「総絶対誤差率」として計算し、10%以下を検証済み推定、10%超をモデル不適合とします。サービスごとの閾値変更や、品質判定に都合の悪い観測だけを除く自動外れ値処理は行いません。

利用率または累積API換算利用額が減少し、既知のリセット、プラン変更、期間更新で説明できない場合は「観測系列の断絶」として記録します。減少値を補正して差分計算には使わず、断絶後の新しい基準値から別の計算区間を開始します。断絶理由は後から分類できますが、断絶をまたぐ差分は推定へ戻しません。

これは、その計算区間で観測された利用額の増分と利用率の増分が同じ関係で続く場合に、その論理アカウントのプランでどの程度のAPI利用が可能だったかを推測するものです。

この値はベンダーが保証する正式な契約金額ではなく、実際の利用実績に基づくAPI換算上の推定値です。同一プランの上限は共通値として推定しますが、使用するモデルやトークン構成、観測誤差によって、各時点から得られる推定値には変動が生じます。この変動と推定品質を含めて継続的に記録・観測することを、本プロジェクトの重要な価値とします。

## 目的

Token Monitor Analyticsでは、以下を実現します。

* Token Monitorの認証付きHub APIへ接続する
* 異なる端末または異なる時点の複数Hubを横断して扱う
* API換算利用額、利用率、利用枠、リセット日時を定期的に取得する
* サービス、論理アカウント、Hubアカウント、利用枠ごとに観測データを保存する
* 同一計算区間内でAPI換算利用額と利用率の対応観測を構成する
* 論理アカウントの推定API換算上限額を算出する
* 推定上限額の時間的な変化をグラフで確認する
* 実際の利用額、推定上限額、推定品質を比較する
* 公式の標準シート単価を任意登録した場合、標準価格推定最大価値倍率を確認する
* 複数の論理アカウントとプランを横断的に分析する
* Token Monitorが収集する各種データを、分析用ダッシュボードとして閲覧する

## 分析対象

サービス上のアカウントには、複数の独立した利用枠が存在する場合があります。

例えば、Claude Codeには5時間枠と週次枠があり、他のサービスにも日次、週次、月次、請求期間、クレジットなどの異なる制限があります。

Token Monitor Analyticsでは、これらを元データとして個別に保持します。利用上限推定には、週次または月次相当で、`usedPercent`と利用周期を持ち、残高・クレジット・従量額ではないパーセント型利用枠だけを使用します。

```text
サービス
  └─ 論理アカウント
      ├─ セッション／5時間枠
      ├─ 日次枠
      ├─ 週次枠
      ├─ 月次枠
      └─ 請求期間枠
```

推定上限額は、利用上限推定対象の利用枠ごとに独立して計算します。週次利用率を月間API換算利用額の絶対値で除すなど、基準期間が異なる単一点の値は組み合わせません。累積API換算利用額は、同じ計算区間内の対応観測間の差分だけを使用します。5時間枠・セッション枠の利用率は分析しませんが、そのセッションで使用されたトークンとAPI換算利用額は全体の利用実績へ含めます。

同じ`weekly`または`billing`でも、Token Monitorの`metric`や`label`が異なる利用枠は別の利用枠として扱います。明示的な利用枠IDは提供されないため、同じHub、サービス、Hubアカウント内では、正規化した`kind`、`metric`、`label`の組を観測の照合に使用します。この組は永続IDとはみなさず、組まで同じ利用枠が同一観測内に複数ある場合は、配列順で推測せず識別不能とします。`resetsAt`は周期境界、`source`は取得経路として保持します。

週次・月次の利用周期の境界はUTCの暦週・暦月で決めません。Hubが報告する`resetsAt`と実際のリセット観測から特定します。画面上の残時間は、`resetsAt - 現在時刻`から派生表示します。境界時刻`B`を特定できた場合、観測時刻が`B`より前の観測は旧計算区間、`B`以後の観測は新計算区間へ帰属させ、計算区間は半開区間`[開始, 終了)`として扱います。正確な境界時刻が不明で2観測間に発生したことだけが分かる場合は時刻を推測せず、その境界をまたぐ差分を除外し、リセット後最初の観測から新しい計算区間を開始します。UTCは時刻を保存・比較する表現に限り、周期境界を決めません。

同じアカウントで`label`だけが変わった場合は、名称変更候補としてユーザーへ非ブロッキングで提示します。ユーザーは同じ利用枠、別の利用枠、不明のいずれかを選べます。未解決中も同期と他区間の分析は継続し、変更境界をまたぐ差分だけを除外します。同じ利用枠と確認された場合は元観測から再計算しますが、プラン変更境界をまたぐ計算は行いません。

## 主な表示・分析機能

### 推定上限額の推移

サービス、論理アカウント、利用枠ごとに、以下の推移を表示します。

* API換算利用額
* ベンダー報告の利用率
* 推定API換算上限額
* 利用枠のリセット日時
* 観測日時
* 推定値の変動幅

### プラン標準価格に対する価値評価

サービス提供者が公表するプラン1シート当たりの標準価格を任意登録した場合、次の参考指標を表示します。実際の請求額、税、割引、支払い、請求書は管理しません。

通常画面では、現在有効なプラン版に属する各利用枠ウィンドウを別々に扱います。各ウィンドウのカレント計算区間に有効な推定があれば、その区間を使用します。カレント計算区間に必要な観測が不足している場合、その区間自体は推定不能として扱い、同じプラン版のカレント計算区間より前にある最新有効計算区間を、カレントではないこと、根拠となる観測時刻、経過期間（鮮度）付きで表示できます。最新有効計算区間は年齢によって自動失効させず、該当する過去区間がなければ未算出とします。プラン変更境界を越えて引き継ぎません。カレンダー月や契約更新日を待って集計するものではありません。

同時に複数の週次または月次利用枠ウィンドウがある場合は、それぞれを独立して月間換算し、標準価格推定最大価値倍率を表示します。ウィンドウ間の独立性や重複が不明なため合算せず、総計も表示しません。

```text
週次枠の月間換算推定利用上限
= 1週当たり推定API換算利用上限 × 365.2425 ÷ 12 ÷ 7

月次枠の月間換算推定利用上限
= 1月当たり推定API換算利用上限

標準価格推定最大価値倍率
= 月間換算推定利用上限 ÷ USD建て月額標準シート単価
```

プラン変更前後にそれぞれ必要な観測があれば、変更境界をまたがず、各プラン版の値を直ちに別々に算出します。履歴では計算区間ごとに、適用プラン版、1周期当たりの推定上限、月間換算推定利用上限、標準価格推定最大価値倍率、推定品質と算出根拠の推移を確認できます。ここでいう計算区間の履歴は指標の推移を指し、派生計算結果の全世代保存を必須としません。

標準シート単価は、HubのAPI換算利用額と同じUSD建て月額価格に限定し、公式情報の出典と有効期間を持たせます。為替換算、年払い価格の月額換算、割引、契約固有価格の管理は行いません。未登録でも利用上限の推定には影響しません。標準価格推定最大価値倍率は、月間換算推定利用上限だけを標準シート単価と比較して算出します。実際の利用量とAPI換算利用額は、下記の利用実績分析として独立して扱います。

カレント計算区間について、利用率と累積API換算利用額の差分を構成できる異なる実観測時刻の有効な対応観測が少なくとも2点必要です。2点以上は必要条件であって十分条件ではありません。利用率差分などが未知の上限を識別する独立した情報を持たなければ、2点あっても識別不能とします。複数論理アカウントや異種プラン混在で未知数が増える場合は、さらに独立した観測が必要です。

### 期間内の利用実績

副次機能として、任意期間のトークン使用量とAPI換算利用額を全Hub横断で集計します。全体、Hub、収集端末、サービス、モデル、日、週、月、任意期間で絞り込み、入力、出力、キャッシュ読み取り、キャッシュ書き込みなど、Hubが提供する内訳を表示します。

時刻を持つデータはUTCで保存し、画面表示と日・週・月のカレンダー集計時にユーザーが指定したタイムゾーンを適用します。これはリミットの利用周期境界をUTCの暦週・暦月で決めることを意味しません。Token Monitorが端末ローカル日付で既に日次集計したデータは、取得元の日付とタイムゾーンを保持します。別のタイムゾーンの日次データへ推測で再配分せず、必要に応じて取得元タイムゾーン基準の別系列として表示します。

利用額ソースが1つの論理アカウントだけに関連付く期間は、トークン数とモデル内訳をそのアカウントへ帰属できます。複数の論理アカウントへ関連付く場合は「共有・帰属不能」として全体集計に一度だけ含め、アカウント別には按分しません。利用率から推定したAPI換算利用額の比率も、トークン数やモデル内訳の按分には流用しません。

`billing`利用枠が残高、クレジット、従量額、絶対値だけを報告する場合も、元の値、単位、通貨、観測時刻、期間境界を履歴として表示します。`metric: credits`と`metric: spend`は利用実績分析の対象ですが、API換算利用上限の推定式には使用しません。

### 初期スコープ外の将来候補

初期スコープの分析に加えて、将来的に次の分析を検討します。

* 利用枠の消費速度
* リセット時点までの利用率予測
* 未使用のまま失効した推定API換算額
* モデル構成による推定上限額の変化

## データ保存

初期バージョンでは、すべてのデータをローカルデータベースへ保存します。

保存対象には、少なくとも以下を含めます。

* Token Monitorから取得した観測時点のスナップショット
* サービス、論理アカウント、Hubアカウントの識別情報
* 利用枠の種類
* 利用枠の開始日時とリセット日時
* API換算利用額
* 利用率
* 推定API換算上限額
* 任意の標準シート単価
* 算出条件とデータ品質
* 取得日時と計算日時

取得した元データと算出後の分析データを分離して保存し、計算方法を変更した場合に再計算できる構造とします。ユーザーによる設定変更は、変更日時、対象、変更内容を含む追記型の監査履歴として記録します。派生計算結果は基本的に全世代を保存せず、再計算時に現在の結果へ更新します。現在の結果には計算ロジック版、使用した元観測、適用した関連付けを記録します。性能評価により派生結果をキャッシュまたは保持することは許容しますが、再生成可能な非正本データとして扱い、全世代の履歴保存は必須としません。

元観測・履歴は自動的に期限削除しません。Hub接続設定や認証情報の削除・無効化、論理アカウントのアーカイブだけでは元観測を削除せず、履歴上の識別情報と過去の関連付けを維持します。元観測の物理削除は、Hubと取得期間で指定する明示パージだけで行います。パージでは原JSONスナップショット全体と紐づく派生結果を対象にし、サービス・アカウント単位の部分削除は行いません。実行前に対象件数と対象期間を表示します。将来クラウド複製を提供する場合のパージ連携は、その機能の要件として別途定義します。

容量確認では、ローカルデータベースのサイズ、原JSONスナップショット件数、最古の取得日時、最新の取得日時を表示します。自動削除や任意の閾値による警告は行いません。

ローカルデータベースは、その端末が収集した元観測の正本です。複数端末データを統合表示するクラウド複製、クラウドからの復元・取り込み、クラウド上の設定編集、双方向の設定同期は、初期スコープ外の将来拡張です。

## クラウド対応（将来拡張・初期スコープ外）

以下は将来のクラウド複製に関する方針であり、初期版の要件・受入条件には含めません。

クラウドは複数端末のローカル正本からデータを受け取り、統合表示する一方向の複製とします。クラウドを正本としてローカルへ復元・取り込みしたり、クラウド上で設定を編集したり、設定を双方向同期したりする機能は提供しません。復旧にはバックアップを使用します。

クラウド複製を利用する場合は、各Hubにアクティブな収集担当端末を1台だけ割り当てます。担当変更はHub識別子を維持した明示的な引継ぎとし、引継ぎ時刻以後は新担当の観測だけを正規観測として扱います。同じHubで同時収集を検出した場合は収集担当競合として扱い、ユーザーが一方を選ぶまで重複分を集計・推定から除外します。競合中も元観測は保持します。

```text
Token Monitor
      ↓
Token Monitor Analytics
      ↓
ローカルデータベース（正本）
      ↓ 任意・一方向複製
クラウドストレージ／分析サービス
      ↓
Webブラウザ・別端末
```

クラウド接続は初期版の必須要件ではなく、将来の提供可否と範囲を別途決定します。

## 対象外

初期段階では、以下を対象外とします。

* ベンダー内部の料金計算方法を完全に再現すること
* 非公開の割引、優遇、補正係数を追跡すること
* 推定上限額を正式な契約上限として保証すること
* Token Monitor自体の利用量収集機能を置き換えること
* クラウドサービスの利用を必須とすること
* Token Monitorが取得できない利用量を独自にスクレイピングすること

ベンダー固有の詳細な割引を再現するのではなく、Token Monitorが算出したAPI換算額と、ベンダーが報告した利用率を共通の評価材料として使用します。

## プロジェクト方針

Token Monitor Analyticsは、以下の方針を重視します。

1. 推定API換算上限額の推移を最優先で記録する
2. ローカルファーストで動作する
3. 元データと計算結果を分離して保持する
4. 計算根拠を確認できるようにする
5. プロバイダーごとの差異を吸収しつつ、無理な共通化はしない
6. クラウド連携は初期スコープ外とし、将来拡張として扱う
7. Token Monitorを収集基盤として活用し、既存機能を重複実装しない

## 位置付け

Token MonitorがAIツールの利用状況を収集・表示するモニターであるのに対し、Token Monitor Analyticsは、そのデータを長期保存し、論理アカウントのプラン価値と推定利用上限を分析するアプリケーションです。

```text
Token Monitor
= 利用状況と利用枠を収集する

Token Monitor Analytics
= 収集されたデータを蓄積し、推定・比較・分析する
```

本プロジェクトはToken Monitorの非公式な関連プロジェクトであり、Token Monitor本体およびその開発者による公式製品ではありません。

## 現行実装：ローカル収集

現行コードは Windows ネイティブの Wails v3 アプリとして、単一Hubの設定、Hub APIの取得、SQLite保存、Credential Managerからのシークレット取得、取得時刻の記録、定期取得を実装しています。保存するデータは、Token Monitorが返した原JSONスナップショットと、そこから計算した観測結果を別テーブルに分けています。既定のデータベースは `%APPDATA%\Token Monitor Analytics\data.db` です。テストや開発では `TOKEN_MONITOR_ANALYTICS_DB` で保存先を上書きできます。

複数Hub、不変Hub ID、論理アカウント、利用額ソースと利用枠ソースの関連付け、2点差分による推定、非負最小二乗法、リセット半開区間、利用枠ごとの`updatedAt`対応は現行コードに未実装です。

Hub の共有シークレットは SQLite へ保存せず、Windows Credential Manager の Generic Credential `TokenMonitorAnalytics/Hub/default` に保存します。資格情報を登録した Windows ユーザーと、アプリを実行するユーザーは同じである必要があります。旧バージョンの SQLite に平文シークレットが残っている場合は、Credential Manager への保存に成功した後で SQLite から削除します。

### 起動手順（Windows）

必要なものは Go 1.25 以降、Node.js/npm、WebView2、Wails v3 CLI です。Wails v3 CLI は公式手順に従ってインストールしてください。

```powershell
go install github.com/wailsapp/wails/v3/cmd/wails3@latest
wails3 doctor
git clone <repository>
cd token-monitor-analytics
npm --prefix frontend install
wails3 dev
```

配布用の Windows バイナリは次で作成します。

```powershell
wails3 build
```

アプリ画面で Token Monitor Hub の URL と共有シークレットを入力して「設定を保存」し、「今すぐ取得」または「定期取得を開始」を押します。共有シークレットは Windows Credential Manager から読み出し、Hub API の `Authorization: Bearer <secret>` にだけ使用します。取得間隔の既定値は 300 秒です。

## 現行実装：簡易分析

現行の簡易分析は、Token Monitor Hubの`GET /api/stats`から取得した`periods.today`、`periods.month`、`periods.allTime`、`limits.providers[].windows[]`を使います。provider別の費用は`clientCosts`の同名キーを使い、対応する期間がある場合は、同一スナップショットのAPI換算利用額を利用率で除す旧単一点式で推定します。週次・セッション専用の費用期間がない場合は、`today`の参考費用と利用率を`partial_period`として保存し、期間が一致しないため推定値を算出しません。`clientCosts`がない場合や同じproviderに複数アカウントがある場合も、費用を推測・重複帰属せず、推定値を作りません。対応期間がない`billing`枠などは`missing_period`となります。この方式は上記の目標仕様ではなく、2点以上の差分推定へ置き換える対象です。

現行コードでは、providerとaccountKeyに対するプラン名と月額USDを`subscriptions(provider, accountKey, planName, monthlyPriceUsd)`として管理します。最新月次利用額と月額USDから実利用倍率を、最新の`ok`観測と月額USDから推定倍率を表示します。実利用倍率は旧仕様の指標であり、目標仕様の標準価格推定最大価値倍率には使用しません。保存済み観測の利用額・利用率・推定上限額をSVGグラフで表示し、最新スナップショットの月次Tool・Model・Device内訳を確認できます。エクスポートはJSONとUTF-8 BOM付きCSVに対応します。

未確認候補、正式なサービス・プラン・プラン版、論理アカウントのプラン適用期間、アーカイブ、カレント／最新有効計算区間、利用枠ごとの月間換算は現行コードに未実装です。これらは上記の目標仕様に含まれます。

## 現行試作の説明：クラウド連携（初期スコープ外）

現行リポジトリにはクラウド連携の試作実装が含まれますが、これは初期スコープ外です。初期版はローカルだけで動作し、クラウド試作の利用を前提にしません。試作は特定クラウドへ固定せず、SQLiteを使う自己ホスト型同期サーバーを提供します。

### クラウド同期サーバー

同期サーバーは、デバイスIDとローカルスナップショットIDの組で増分データを重複排除します。この重複排除は試作用であり、将来要件の不変Hub ID、収集担当、競合管理を実装したものではありません。各端末のローカル正本から一方向に受信し、Bearer認証された`POST /api/v1/sync`で保存します。`GET /api/v1/dashboard`とブラウザー画面では複数端末のデータを統合表示できますが、クラウドからローカルへの復元・取り込み、クラウド上の設定編集、双方向の設定同期は行いません。ブラウザーに入力したシークレットは`sessionStorage`にだけ保持します。

```powershell
$env:TOKEN_MONITOR_ANALYTICS_CLOUD_SECRET_FILE = 'D:\secure\token-monitor-analytics-cloud-secret.txt'
$env:TOKEN_MONITOR_ANALYTICS_CLOUD_DB = 'D:\data\token-monitor-analytics-cloud.db'
$env:TOKEN_MONITOR_ANALYTICS_CLOUD_ADDR = ':8080'
go run ./cmd/cloudserver
```

コンテナでは`deploy/cloudserver/Dockerfile`を使用できます。公開環境ではリバースプロキシでHTTPSを終端し、`/data`を永続ボリュームへ割り当ててください。デスクトップアプリではCloud URLと共有シークレットを設定し、手動同期または定期収集後の自動同期を使用します。クラウド用シークレットはGeneric Credential `TokenMonitorAnalytics/Cloud/default`に保存します。

### バックアップと復元

「バックアップ作成」は、原JSONスナップショット、算出結果、現行の`subscriptions`へ登録したプラン名と月額USD、非秘密設定を1つのJSONへ出力します。Windows Credential Managerのシークレットは含みません。バックアップにはSHA-256チェックサムが付き、外部に保存したバックアップJSONからの復元では全体を検証してから単一SQLiteトランザクションでローカル正本を置換します。検証失敗時は既存データを維持します。復元後のクラウド同期カーソルは0へ戻り、ローカル正本の全スナップショットを重複排除付きで再送します。クラウドを復元元または取り込み元にはしません。

手動バックアップのRPOは最後に作成した時点、通常の復元RTOは数分です。自動世代管理は実装していないため、運用ではバックアップJSONとクラウドサーバーの`cloud.db`を、バージョニングまたはオブジェクトロックのある外部保管先へ日次保存してください。Credential Manager喪失時は、機外で管理するHub／Cloudシークレットを同じWindowsユーザーで再登録する必要があります。四半期ごとに別のテスト環境へ復元し、スナップショット件数、登録した月額USD、ダッシュボード表示を確認してください。

API 形式の根拠は Token Monitor 本体の [Hub API ドキュメント](https://github.com/Javis603/token-monitor/blob/main/docs/API.md)です。
